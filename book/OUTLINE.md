# 全书骨架

> 这一份是全书的骨架，不是书的正文。学生 2026-10-12 认了（DECISIONS-R1 R1-291），照它写章。
> 依据：DECISIONS-R1 的 R1-289 到 R1-291。课程全景照 KNOWLEDGE_BASE 第七节。补课链照 PROJECT_STRUCTURE「补课链进度」。项目事实照 CLAUDE.md 第二层。

## 一、这本书是什么

一本离开 Claude Code 也能读的课本。读者跟着它，从零做出一个能上线的全栈应用，同时学会给 AI 搭一套可靠的工作环境。

它同时教两样东西：

- 一个真实项目怎么一步步做出来：想法，需求，设计，选型，写代码，测试，上线，演进。
- 怎么让 AI 在每一步里可靠地干活：规矩写在哪，它能碰什么，谁来验证，出了错怎么修。

学这两样，为的是第三样：攒出一套换个项目还能用的框架。框架中间有一个中枢，带着没有开发背景的人把项目一步步做到上线。这是目标，现在还没做成。它的规格在 `docs/HARNESS.md`，每章第九节收的是它的原料。

## 二、写法约定

1. 用课本的口吻。不出现「老师说」「你当时」这类课堂话术。课上发生过、值得留的事，写成中性的案例。
2. 网页版讲过的知识点一条不丢。文字重写。再补漏、纠错、按现状更新。相对网页版改了什么，写在章末（问 249 A）。
3. 全书按现在的做法写。步骤和 prompt 都是在 Claude Code 里直接能照做的。早先三方上课的做法，只在附录记一页（问 250 A）。
4. 每章既讲为什么，也讲怎么做。prompt 给原文，命令给原文，写明应该看到什么。
5. 重复贴过的文件不逐章重贴。每样产物在它被建出或改动的那一章收一次原文。
6. 不设自测。篇幅用在讲深讲细上。
7. 正文里不留过程性的话。「等裁决」「没核实」这类话不进书。没定的事先问清再写。
8. Claude Code 的产品事实，写章时对官方文档核，章末记核对日期。
9. 书里每个事实性的说法都要核过，章末写出处。核不了的不写成事实。说不通的地方不找补。

## 四、导读一章的提纲

1. 这本书教什么，为了什么。两样东西，为什么要一起学。学这两样为的是第三样：一套换个项目还能用的框架，中间有个中枢。第三样写成目标，不写成已经做到。
2. 这本书写给谁。主要是没有任何开发背景的人，有技术背景的人也能读。
3. 最后做成什么。一个团队任务协作工具：谁用（负责人、执行者），能做什么，长什么样（十个页面），跑在哪（四个容器）。
4. 全流程地图。六个阶段。每个阶段进来什么、出去什么、过关点验什么。
5. 现在走到哪。一张进度表，随课更新。
6. 读之前要准备什么。电脑，软件，账号。只列清单，安装指向官方页。
7. 这本书怎么读。每章的固定结构，附录怎么查，记号约定。
8. 本章依据。出处与核对日期。

## 五、每章的固定结构

1. **本章位置。** 在地图上第几步。上一章交来什么。这一章产出什么。下一章拿它做什么。
2. **学完能做到什么。** 三到五条，都是能检验的。
3. **原理。** 为什么要有这一步，不做会怎样。核心概念一个一个讲，每个配例子。
4. **动手。** 一步一步来。每步四样：目的，要敲的命令或要发的 prompt 原文，应该看到什么，出了错怎么办。
5. **产出物。** 这一章留下的文件，关键内容的原文，它现在的样子。
6. **Claude Code 知识点。** 这一章第一次用到的功能：是什么，原理，怎么用，什么时候不用。
7. **常见的坑。** 对应反模式库里的条目，中性写法。
8. **小结与速查。**
9. **换个项目还用得上的。** 这一章里换个项目还用得上的协议、模板、标准，是沉淀进框架的原料。只属于本项目的不列。判断标准照课程规则 59（问 255 A）。
10. **本章依据。** 出处，核对日期，相对网页版改了什么。

## 六、一章是怎么写出来的

1. 列这一章的知识点清单，三栏：网页版讲过的，要补的，要纠的。同时查这一章涉及的行业标准与主流做法，对 `docs/arch/STANDARDS.md`，没登的同批补登。给学生过目。
2. 开口的问题先问完。
3. 写。
4. 核。Claude Code 的事实对官方文档。命令实际跑过，没跑的不写「应该看到」。
5. 推到 GitHub，学生在手机的 GitHub 上读，提意见（问 302 A）。
6. 送独立审查。复课前送一次，把那时写好的章一起送；以后一篇写完送一次（问 288 C）。
