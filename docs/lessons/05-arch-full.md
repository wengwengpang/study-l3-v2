## 一、这节课学到的三件事

### 1. 模块按业务域切，不按技术层切
一个功能的代码集中在一个模块内。若按技术层分目录（所有 controller 一处、所有 service 一处），改一个功能要在三个目录之间跳，永远不知道改全了没有。
配套铁律：一张表有且只有一个拥有者。拥有 = 唯一写入者。读不算拥有。

### 2. 分层是「谁接活、谁干活、谁碰数据库」
餐厅比方：服务员（Controller）接单不做菜；厨师（Service）做菜不接客；仓库管理员（Repository）取原料不懂菜谱；菜单（shared types）两边看同一份。
不分层的三个后果：改不动（业务规则和 HTTP 处理混在一起）、测不了（测业务规则要先造请求和数据库）、重复（同一条规则在多个接口各写一遍）。
NestJS 真实层序：Guard → Pipe → Controller → Service → Repository → Prisma。守卫在 Controller 之前，被拒的请求 Controller 方法根本不会被调用。

### 3. 两级权限落两层
不查业务表就能判的归 Guard（角色级）。必须先拿到记录才能判的归 Service（数据级）。
这一句是本节最可复用的产出，遇到任何新的权限判断都能直接定落点。

# 第三节 · 数据流（下半场窗口）

## 这一节在做什么
第一节模块划分、第二节分层架构，画的都是不动的东西，是一张平面图。
第三节是让真实请求走进这张图，看哪扇门推得开、哪扇是墙。
判据：覆盖每一种检查点，不是覆盖每一个接口。它不是测试，真跑是 Lec 14 tester 的活。

两条路径：
R2 读路径 = 执行者查看一条任务的详情，踩数据级权限。
W1 写路径 = 负责人创建任务并分配给执行者，踩角色级权限 + 形状校验 + 跨模块调用。

## 走查撞出来的核心问题
AuthzGuard 要判「是不是本项目成员」，需要项目 id。
但第二节规定 Guard 不查业务表、不解析请求体。
而 R2 的请求里可能只有任务 id，「任务属于哪个项目」写在 tasks 表里。
规矩与需求直接顶上。这个矛盾在静态分层图上看不出来，只有走一遍才会自己撞出来。

## 十二条裁决
T1 服务端校验用项目自写的 Zod 管道（实现 PipeTransform 调共享 schema）。不用内置 ValidationPipe（它底层是 class-validator，与 Zod 选型冲突），不引第三方库。
T2 任务类接口路由嵌套项目 id。必付代价：Service 取到记录后必须比对 projectId 与路径项目 id。
T3 路径参数不做格式校验，非法值落入鉴权失败；查询参数走 Zod 管道。两类分开。
T4 会话固定 30 天，不滑动续期，纯读不写 sessions。让 R2 保持纯读，且可逆（将来加续期只是读会话那步多一个分支）。
T5 assignee 必须是本项目成员，不只是系统用户。允许分给负责人自己。
T6 两级权限界线修订为：只用「会话 + 路径参数 + project_memberships」能判的归 Guard；需读业务表记录或读请求体内容才能判的归 Service。
T7 决策 6 已裁决本版延后（PRD.md:295-299），不是待定。
决策 A 角色经请求上下文由 Guard 传给 Service，Service 不重复查。
决策 B 路径 id 查库前先转数字，转不动视为查不到。这是容错，不是格式校验。
决策 C R2-8 保留，取数方式留给 05-API。
决策 D projectId 只从路径取，禁止从请求体取。
决策 E W1-5 退回「参数不合法」。

## 两个越权漏洞，以及它们是同一个防御的两面
R2 方向：路径填自己有权限的项目 id，任务 id 填别人项目的 → R2-6 比对 task.projectId 挡住。
W1 方向：路径填自己有权限的项目 id，请求体里写别的 projectId → 决策 D「只从路径取」挡住。
一句话：鉴权用哪个 id 判，读写就必须用哪个 id。不一致就是漏洞。

## 拆穿的两条假理由
C3：第二节说「Guard 里做 IO 会让管道变重」，用它否决查库 Guard。但 AuthGuard 读 sessions、AuthzGuard 读 project_memberships，两个 Guard 本来就在做 IO。
反模式 40：老师推荐 T3 时说「非法 id 自然落入鉴权失败」，只在格式合法值不存在时成立；格式非法会让 Prisma 抛异常，走内部错误那条路。
共同形状：结论成立，论据不成立。理由比决策传得更远，决策只管这一处，理由会被下游拿去推别的地方。

# 第四节 · 部署拓扑（第三个窗口）

## 这一节在讲什么

第二节画的是一间屋子里家具怎么摆，请求进了后端之后先过 Guard 再过 Pipe。
第四节画的是整个小区的平面图：有几栋房子、大门传达室在哪、外面的人怎么进来、房子之间走哪条内部路。

四个词对应四样东西。
容器 = 一栋自带水电家具的独立房子，换台服务器原样搬走还能住。
Docker Compose = 小区的规划图加物业，一份文件说明有几栋、谁能走到谁家门口。
Nginx = 大门传达室，外面所有人只能从这进，它看你找谁再带你过去。
端口映射 = 在围墙上开一个对外的窗口，开了外面能直接够到那栋房子。

关键区分：第四节是图纸，不是生效。真正跑起来在 Lec 9（反模式 35 的形状）。

## 本节 16 条裁决（T8-T23）

拓扑骨干四条：
- T8 四个容器：Nginx / 前端 Next.js 服务进程 / 后端 NestJS / PostgreSQL。前端单起是为保住 SSR 与服务端重定向，依据 TECH_STACK 选 Next.js 时写的三条理由之一。
- T9 Nginx 只做反向代理 + TLS 终止，不托管静态资源。静态由前端服务自己发。原定三职责，本节收窄为两项。
- T14 同域名按路径前缀分流：根路径到前端，API 前缀到后端。一张证书，Cookie 同源，不配跨域。
- T15 SSR 取数走容器内网直连后端，不绕公网。代价：前端配两套后端地址，服务端渲染时须手工转发会话凭据。

环境与端口四条：
- T10 数据库端口开发暴露、生产不暴露。
- T16 生产只开 Nginx 的 80/443，开发额外开前后端端口。
- T17 本地日常只有数据库进容器，前后端在宿主机跑；另留完整四容器配置，上线前验一次。
- T23 TECH_STACK「环境一致」读作镜像与运行时一致，配置按环境不同。

边界与留白五条：
- T11 主拓扑按生产画一套，另附差异清单，不画两套完整图。
- T18 第四节只写拓扑差异，环境变量与密钥归 ENV_DESIGN。
- T19 图上不画将来组件（Redis / WebSocket / 定时任务），只在文字注明接入点并标「非本版已定选型」。
- T20 只写「证书由宿主机挂载进 Nginx」，签发续期留 Lec 15。引入签发组件属 D4 技术选型。
- T22 画数据卷，备份方案进 BACKLOG 留 Lec 15。

模块边界三条：
- T12 Guard 按归属拆两句：AuthGuard 属 auth 读 sessions，AuthzGuard 属 authz 读 project_memberships。
- T13 依赖图只记业务依赖（Service 调 Service），Guard 等横切件挂在路由上不计入。authz 不再依赖 auth，当前用户 id 经请求上下文取得。
- T24 据 T13 删掉 tasks→authz 这条边。

另加 T21 数据库迁移人工触发，不随容器启动自动跑。理由不是偏好是宪法：迁移不可逆，D5 要求喊主人加双确认，藏进容器启动就绕过了 D5。

## 本窗口真正学到的三件事

### 一、产出短不等于决策少（反模式 41）

桥梁写「第四节最短」，老师照收，排了 4-5 段。实际走了 7 段。
正文确实只有约 130 行，但每一笔都压在一个未定的取舍上。画一根从 Nginx 到后端的箭头，背后是「同域名还是子域名」这个没人定过的问题。
估一节的重量，要数它依赖多少未决项，不看正文预计多长。

### 二、拆两轮买的是选择权

第一轮只核对不写正文，报出 4 处冲突、9 项未暴露取舍。
如果一个 prompt 跑完，这 9 项不会出现在面前。architect 会自己挑答案填进正文，写得顺顺当当，读的时候看不出这里原本有个选择。
那就是反模式 33：把属于主人的取舍包装成理所当然的技术结论。
拆两轮花的时间，买的就是这 9 个选择权。

### 三、立口径要回扫自己的过去（规则 69 追加段）

老师立了 T13「Guard 不计入依赖图」，只拿它判 architect 新报的两个问题，没回头扫依赖图里已有的边。
结果 tasks→authz 按新口径不该存在却留着，而 projects 同样挂 AuthzGuard 却没记。同一种挂载关系，一个记一个不记，口径不自洽。
由 architect 抓出，抓它的机制是 prompt 里那句「发现冲突先指出再继续」。这句话在 05-ARCH 已连续四轮报出真问题。
教训：定义类裁决的传播面，包含它自己的过去。
