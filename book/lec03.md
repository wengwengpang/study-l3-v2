# 第 3 课　界面设计

## 一、本章位置

这一章属于第一篇「立项准备」。业务代码仍然不写。上一章定产品做什么，这一章定用户看到什么、怎么走、出了状况时看到什么。

**上一章交来什么。** 需求文档 `docs/design/PRD.md`：十七条用户故事，权限矩阵，错误与边界规则，审定决策 D1 到 D9。规则书第二层 A、B。

**这一章产出什么。**

- designer 角色 `.claude/agents/designer.md`。
- 界面设计 `docs/design/UI_DESIGN.md`：页面结构、主流程、异常流程、三态、视觉方向。
- 需求文档末尾的澄清注记和待验证盲区。
- 规则书第二层 C：写代码时必须守住的几条硬结论。
- 界面样稿 `docs/design/mockups/`：能看的样子，文字仍是准绳。
- 反模式库第 31 号。

**下一章拿它做什么。** 第 4 课选技术时，这里定的组件方向是已有的约束。第 5 课和两节补课的表、接口，要接得住这里的页面和权限。第 11 课的前端照它写代码，三态一个不能少。

**这一章最要紧的一件事。** 把判断写成文件，不留到写代码时临时拍。写的过程中，设计会撞出需求文档自己的矛盾。这时候要让 AI 停下来，由人定口径。

## 二、学完能做到什么

1. 能分清页面结构、主流程、异常流程、三态、视觉方向各管什么。
2. 能给角色写分段的 prompt：先读定义文件，路径写死，矛盾先指出，做完就停。
3. 能处理需求文档内部的矛盾：定一个口径，加澄清注记，已确认的原文不动。
4. 能给每个要取数据的界面定三态，空态分角色，不懂的标「设计提案，待确认」。
5. 能判断一条新信息该放哪一层，并把文字设计变成一份看得见的样稿。

## 三、原理

**为什么要有这一步。** 上一章说过，需求文档是要求清单：三室两厅，几个消防出口。这一章画的是平面图和动线：门朝哪开，进门先到哪，灯坏了怎么办。

**不做会怎样。** 写接口、写前端的时候，会发现页面之间怎么跳没人定过，只能临时拍。临时拍就容易漏权限、漏跳转。新用户第一次进来，看到一片空白，以为东西坏了。

### 先认几个词

**UI。** User Interface，用户界面。

**页面结构、主流程、异常流程、三态、视觉方向。** 这一章的五样东西，下面一个一个讲。

**骨架屏。** Skeleton。数据还没回来时，先画一些灰色占位块，形状贴近最后的内容。

**线框图、效果图、原型。** 线框图用方块示意布局，不管颜色。效果图是带精确颜色和尺寸的视觉稿。原型是能看、有时还能点的样子。NN/g 这样说它们的差别：「The fidelity of the prototype refers to how closely it matches the look-and-feel of the final system.」保真度，就是它有多像最后的成品。

**Tailwind CSS 和 shadcn/ui。** 本项目前端写样式用的两样东西。Tailwind 带一套默认调色板。shadcn/ui 自己说「This is not a component library. It is how you build your component library.」它不是装上就用的包，而是把组件的源代码交到你手里，代码能改，默认样式已经选好。为了好懂，本章把这类现成组件统称「组件」。

### 五样东西，从一栋楼讲起

把产品想成一栋楼：

| 东西 | 回答什么 | 比方 |
|---|---|---|
| 页面结构 | 有哪些页面，每页有什么 | 有哪些房间，房间里放什么 |
| 主流程 | 一切顺利时，人怎么走 | 访客进门的路线 |
| 异常流程 | 走不通时，人往哪拐 | 门锁着，从哪绕过去 |
| 三态 | 同一页在三种状况下的样子 | 灯没亮、房间空着、房间着火 |
| 视觉方向 | 整体什么调性 | 北欧极简，不是墙漆色号 |

为什么要分开做，不一口气画完？因为一次只解决一个问题。房间数清楚了，走动和状态才有地方挂。这也是 designer 的信念：好设计是减法，一个界面只为一个核心任务服务。

### 主流程只画正常路径

「主」的意思是只画顺利的那条路。失败、没权限、没数据，都留给下一段。混在一起画，主干会被一堆「如果失败了」打断，看不清。先把主干立直，再挂分支。

这个产品有两类用户，核心任务不一样，所以主流程至少两条：

- 负责人：登录，建项目，邀成员，派任务。
- 执行者：登录，进项目，看我的任务，更新状态。

每一步都要对得上前面定的页面，还要标它服务哪条用户故事。这是第 0 课证据契约的延续：设计不是凭空来的，要指得回需求。

### 异常流程和三态是两件事

这两样最容易混。

**异常流程是动线。** 执行者点了一个不属于自己的任务，系统把他挡回去，告诉他往哪走。这是一条岔路的走法。

**三态是同一页的三张脸。** 任何要从后端取数据的界面，都有三种样子：

- **加载态。** 数据还在路上。
- **空态。** 请求成功了，但是没有数据，比如新项目一个任务都没有。
- **错误态。** 请求失败了，比如断网。

**空态最常被漏。** 可新用户第一次进来，看到的正是空态。NN/g 的建议第一句就是「Do not default to totally empty states.」不要默认留一片空白。它接着说要告诉用户这里本来会显示什么，并给一条路开始：「Provide direct pathways (i.e., links) to getting started with key tasks related to populating the empty state.」

**同一个空列表，两张脸。** 这是最容易做成一刀切的地方。负责人看到「项目还没有任务」和创建入口。执行者只看到「当前没有分配给你的任务」，不给创建入口，因为他没这个权限。不点明，往往只做出一种。

**有的空态根本不该存在。** 执行者看不到项目主页，那就不用给执行者编一个主页空态，他进项目直接落到任务页。任务详情只有一条数据，要么有要么没有，没有「空列表」这回事，标「不适用」，比占一个格子解释半天干净。

**错误态不要猜。** 需求文档的错误与边界规则，就是给这一步准备的。比如密码规则直接决定注册页怎么提示。designer 要去查，不能编一句听起来专业的话。规则里没写的，比如「数据加载失败」，就只定结构：局部错误块，一句说明，一个重试。文案标「设计提案，待确认」。不确定就明说不确定，这才可信。

**没权限不算错误。** 重试也没用，所以不给重试，只显示「权限不足」，不露被访问的数据。

**骨架屏的来历。** 骨架贴近最后的结构，加载完页面不会跳。本项目定的是所有数据界面统一用骨架屏。NN/g 的说法窄一些：骨架屏「used to indicate progress only when the process that the system is performing is a full-page load」，只有整页加载时才用，单个模块用转圈往往更合适。那是一篇主流文章，不是标准。这个出入本项目记进了待办，到写前端之前再定。

### 视觉只定方向

请设计师定装修风格，这个阶段要的是「北欧极简、原木加白」，不是「墙漆色号多少、踢脚线多高」。色号和尺寸等真正施工时再定，现在定了多半要推翻。

方向会约束后面所有具体的决定，它自己不陷进细节。这就是这一步的分寸：**判断要前置，但别前置过头。** 所以这一段只定四样：整体调性，调色板取向，组件选型方向，三态的视觉原则。不给色值，不给像素。

### 真人设计师怎么交接，这里为什么不一样

真实团队里，UI 设计师确实出效果图，每个按钮的颜色、圆角、内边距都标死。设计师把链接交给前端，前端在 Figma 的 Dev Mode 里点元素，读出尺寸和属性。官方的说法是：「Help developers quickly visualize spacing and sizing.」切到代码视图，「the inspect panel displays autogenerated code snippets for the layer」。

本项目走另一条路。传统做法像设计师亲手画一把独一无二的椅子，标好每个尺寸，木工照着做。这里更像从宜家目录里选现成的家具：shadcn/ui 的组件「have carefully chosen default styles」，按钮的内边距、圆角出厂就定好了，不用人一个个标。

所以真正要设计的，只剩三件：

1. 哪些页面，每页什么结构。
2. 用户怎么走，各种状态长什么样。
3. 整体调性，选哪几种组件。

这三件正是 designer 做的。

**但这个选择有两个缺口，不粉饰。**

- **元素之间的节奏。** 文字设计够你把家具摆进去，就像一份平面图加家具清单。可这块和那块之间空多少，整体松紧如何，文字没说。补得好是干净，补不好是挤。
- **独特的外观。** 想要品牌感和精心的视觉层次，默认样式不够，那才真要效果图。本项目选的是功能优先。

**一个先后要照实说。** Tailwind 和 shadcn/ui 是这一课就定的方向，写在 designer 的职责里，比下一章的技术选型还早。下一章选型时，它们已经是约束。这不是最规范的顺序，只是当时就这样走的，下一章还会讲到。

### 文字之外，还要一份看得见的样稿

只有文字，有一个大问题：没有开发背景的人，读完十个页面的描述，想不出它们长什么样。

做不做原型，有现成的说法。GOV.UK 的服务手册说原型「allows your team to explore design ideas much faster and at lower risk than using your production code」，比直接写正式代码快，风险也低。它是英国政府公共服务的手册，约束不到本项目，这里只当参考。NN/g 补了一句为什么不用一上来就做得很精致：「Low-fidelity prototypes put less pressure on users.」

所以本书把出图放进正式步骤，三条边界要记住：

- **文字是准绳，样稿只是看样子。** 两边对不上，以 `UI_DESIGN.md` 为准，再决定要不要改文字。
- **出图不归 designer。** designer 是只读的文字角色，出图由主对话做。设计类角色该不该有写文件的权限，这件事关系到整套框架，留到全书走完再定，已经记进待办。
- **样稿不是代码。** GOV.UK 也说「Do not just copy prototype code into production.」原型的代码不要直接搬进正式产品。

画出来真的有用。本项目第一次画样稿，文字里看不出来的事当场就露了，第 8 步会讲。

### 需求文档自己打架时

designer 读需求时可能发现，文档自己跟自己对不上。本项目就撞上了：

- US-03 写「所有任务集中展示」「用户创建新任务」，没限定角色。
- US-06 写「任何成员打开」都能看到负责人。
- 权限矩阵和决策 D6 写的是：执行者只看自己的任务，不能建任务。

**这不是 designer 的错，也不是谁写错了字。** 需求文档是两批拼出来的。前一批故事写在权限概念出现之前，措辞宽。后一批权限矩阵专门把权限收紧。两批之间没人回头对齐，老措辞和新决策就顶上了。

**这时 AI 该做什么。** 列出冲突，停下来，等人定。不能自己挑一边硬做。这正是 prompt 里「发现矛盾先指出」在起作用，也是反模式 16 号（一味附和）的反面。它说「这里对不上」，比它闷头画完更值钱。

**人怎么定。** 当年摆了三个选项：

- A，以权限矩阵和决策为准，老故事加注记。
- B，保留「人人都看所有任务」，回头改权限矩阵。代价大，还要推翻刚审定的决策。
- C，第三种切法，比如能看到任务存在但看不了详情。

选的是 A。理由是权限矩阵是后补的、集中的、人专门审定过的，代表更成熟的意图。老故事的宽措辞本身才是漏洞，该被澄清，不该反过来推翻新决策。

**怎么改。** 已确认的原文一字不动，加一段澄清注记。上一章讲过这个做法，原文收在本章第五节。注记有固定的格式：

```text
本条措辞早于权限概念引入，实际口径以权限矩阵 + D6 为准——<一句话说清正确口径>。原 US 文字不改。
```

三样要素：这条写在什么之前，现在以谁为准，原文不改。

**怎么防下次。** 补需求不只是加新的，还要校老的。分批补写之后，做一遍新旧一致性扫描，把老故事里和新决策冲突的措辞找出来。这就是反模式 31 号。

**一个小技巧。** 定了口径之后，别把所有答案都喂给它，留一两个判断让它自己给方案。比如 D6 只说了谁看什么，任务入口做一张页还是两张，让 designer 选，再说一句理由。它给出来再对，比直接告诉它更能验出它读懂了没有。

### 角色和产出是两个东西

`designer.md` 是一位设计师的职责说明，`UI_DESIGN.md` 是这位设计师交的图纸。一个管「谁来做、怎么做」，一个是「做出来的东西」。

这两样要分开想，因为寿命和改法都不一样。本项目的 designer 角色文件在第 2 课补需求时就建了，也出过一版界面草案。可草案只在对话里，窗口一关就没了，第 3 课只好重做。角色文件留下来了，产出却丢了。

### 一条新信息，产生时就定它住哪

这一课真实发生过一件小事。口径是人在对话里定的，然后写进给 AI 的 prompt，再写进 `UI_DESIGN.md` 的文件头。同一条信息存了三份：人的脑子，prompt，文件。哪天开一个新窗口，除了文件，那两份都不在了。

这里其实有两种对齐，别混：

- **内容对齐。** 文档里的话互相矛盾。上一节讲的就是，用注记解决。
- **上下文传递对齐。** 一个临时定下的口径，怎么才能不丢，下游怎么自动知道。

第二种的根在于：一条信息产生的时候，没人当场决定它住在哪一层、能活多久，于是散落在对话里，靠人记。解法是一张表，按寿命和适用范围分三层：

| 信息类型 | 住哪 | 为什么 |
|---|---|---|
| 换个项目还用得上的做法 | 全局的 `~/.claude/` | 跨项目 |
| 本项目的事实裁决 | 项目内的文件：需求文档、规则书第二层 | 只属于这个项目，但要长期有效 |
| 只用一次的交接状态 | 交接说明 | 下次用完就扔 |

「权限口径」属于第二层，它有两个家，各管一头：需求文档里的澄清注记，让读文档的人和 AI 不糊涂；规则书第二层 C，让每次进项目的 AI 都知道。

**什么时候落盘，看重新生成要多贵。** 页面结构跑一次要一分多钟，还要人审，丢了很贵，审完当场存。一句短注记丢了也不心疼，可以和别的一起存。拿不准就当场存。

**想以后再做的事，也要落下来。** 想搁置一件事没问题，但要记进一个长期的待办清单，不能只留在对话里。本项目有个真实的教训，第七节讲。

**改之前看一眼它是叶子还是根。** `UI_DESIGN.md` 这种文件，别的文件不依赖它的内部结构，改起来自由，叫叶子产物。角色标准、规则书这种，后面都照着它们来，改一处要看下游，叫根产物。
