# 附录 H　问题与解法

这一份收课上提出的课程做法类问题，一个问题写一个案例。你遇到同样的问题时，翻到对应的案例，照着做。

每个案例十一节，顺序固定：问题是什么，症状与实据，为什么会这样，行业怎么解决，考虑过哪几种，最后怎么做的，具体怎么用，有没有用，换个项目照着做，还没解决的，出处。

这个结构借自两样现成的做法。一样是事后复盘。Google 的 SRE 一书这样定义它：「A postmortem is a written record of an incident, its impact, the actions taken to mitigate or resolve it,」「the root cause(s), and the follow-up actions to prevent the incident from recurring.」出了什么事、影响多大、怎么处置、根因是什么、后续还要做什么，十一节里都有。另一样是文档写作框架 Diátaxis 里的「操作指南」：「How-to guides are about goals, projects and problems, not about tools.」它按读者要解决的问题排，不按知识的分类排。两句原文都在 2026-10-19 取回核过。

接口、数据库这类知识，写在各章正文里，不在这里。

## 案例一　开课读得太多，中途会漂

### 一、问题是什么

2026-10-17，补课 05-API 第七窗口开课。项目主人提出：

> 我们现在新窗口开篇前加上必读的7个文件和自检要读的内容太多，导致你跑偏或忘记……你认真查下目前行业或有什么专业方法可以解决这问题？或者有没有印象图加深你印象，或关系图来组织？

这里的「你」指 Claude Code。每开一个新窗口，它先读三份开课资料和七个必读文件，再逐条过一遍开课自检，然后才开始上课。规矩都写在文件里，也都读过了，做到一半还是会忘。

### 二、症状与实据

先看要读多少。第七窗口开课时数过：开课读的文件共 2666 行，自动记忆另有 509 行。课程规则 81 条，反模式 46 条，开课自检编到第 20 项。规则文件的 547 个非空行里，有 127 行以「背景」「关系」「判定」这类词开头，讲的是来历和关系，不是要做的动作。反模式库 279 个非空行里，这类行有 96 行。

再看漏了什么。上一个窗口（第六窗口）收尾回顾时，记下了这些错：
- 报进度凭印象，漏了契约的一整节（见案例二）。
- 课程规则 77 要求拍板时当场判定的事，两次被推到了结课。
- 开课没有先带着重温上一个窗口。
- 数错的数七处。其中五处被提交前的计数闸门拦下，没有落进文件；两处是事后自查出来的。
- 用量过半以后，错误明显变多。

前三种，规矩明明写着，到时候没想起来，都在「只靠读」那一层。拦下来的五处，靠的都是命令。

第八窗口开课时又量了一次读量，用 wc -m 数字符，合计约 16.5 万字符。七个必读文件约占 45%。最大的单份不是必读文件，是 Claude Code 自动记忆里的一份会话流水账，约占 17.5%。

### 三、为什么会这样

**一句话：开头读一遍，撑不住一个长会话。读进来的规矩会被越来越长的对话挤到中间，到用的时候想不起来。**

打个比方。早上把一整本员工手册读完，下午遇到一件事，手册里明明写了怎么办，却想不起来。不是没读，是读得太早、读得太多，中间又塞进了一整天的事。

Claude Code 官方的最佳实践页，把这件事放在全页最前面：「Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills.」又说：「When the context window is getting full, Claude may start "forgetting" earlier instructions or making more mistakes.」

几篇研究说的是同一件事：
- Liu 等人的《Lost in the Middle》发现，相关信息放在长输入的开头或结尾时，表现最好：「performance is often highest when relevant information occurs at the beginning or end of the input context」。开课读的规矩，会随着对话变长被挤到中间。这篇测的是从长文里找答案，搬到「守规矩」上，是推断。
- Chroma 的《Context Rot》（2025）：「model performance consistently degrades with increasing input length」。输入越长，表现越差。
- IFScale（2025）一次给出最多 500 条指令：「even the best frontier models only achieve 68% accuracy at the max density of 500 instructions.」要守的规矩越多，守得越差。

Anthropic 讲上下文管理的文章（2025-09-29）把它归成一句：上下文「must be treated as a finite resource with diminishing marginal returns」，越多越不值钱。

还有一层：规矩只增不减。每踩一个坑，就多一条规则或一条反模式，很少有删的时候。于是读量一窗比一窗大。

### 四、行业怎么解决

**一句话：不靠记性。规矩按时刻分成短检查单，到了那一刻再看；能交给机器的，交给机器。**

飞行员不会在起飞前把整本手册背下来。检查单按时刻分开：启动前一张，起飞前一张，降落前一张。美国联邦航空条例第 121.315 条要求：「The procedures must be designed so that a flight crewmember will not need to rely upon his memory for items to be checked.」

Anthropic 那篇文章推荐的也是这个方向，叫「just in time」：「agents built with the “just in time” approach maintain lightweight identifiers」。手边只留轻量的索引，用到的时候再取细节。

安全工程里有个瑞士奶酪模型。James Reason 2000 年在《英国医学杂志》上写，每一层防护都「more like slices of Swiss cheese, having many holes」。安全不靠哪一片没有洞，靠叠几片，让洞对不齐。他还说：「We cannot change the human condition, but we can change the conditions under which humans work」。改不了人会忘，能改的是让人不必记。

Claude Code 官方也把两类东西分开：写在 CLAUDE.md 里的话是建议，钩子是确定会执行的。最佳实践页原话：「Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens.」钩子指南页说，钩子让「certain actions always happen rather than relying on the LLM to choose to run them」。记忆页还给了篇幅上限：「target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence.」

### 五、考虑过哪几种

**印象图、关系图。** 项目主人提过用图来加深印象。对 Claude Code 不管用：官方记忆页写明「Each Claude Code session begins with a fresh context window.」每个窗口从空白开始，图留不下「印象」，起作用的只有这一刻读进来的字。对人有用：所以检查单末尾附了一张关系图，GitHub 上能直接显示，给项目主人看各个时刻的先后。

**现在就把开课资料全面重组。** 没选。整节课结课时出开课那一套的精简方案，早就定了（问 325 A）；中途大改，等于推翻它。

**并进结课时的精简方案再做。** 没选。离结课还有几个窗口，这期间照样会漂。

**选的：先试点一份时刻检查单（问 501 A）。** 开课照旧读七个必读文件，规则一条不改。另建一份短文件，按时刻排卡，到点先读那一张。先试一个窗口，收尾回顾时看错数；后来延长到两个窗口（问 510 A）。

试点里又定了几处：
- 自动记忆里原有一份「发前自查」，本身就是按时刻记的清单。新文件建了，两份并存迟早打架。定的是把它搬进检查单，成为第 12 张卡，自动记忆里只留一行指针（问 503 A）。没选两份并存，也没选只扩自动记忆那一份。
- 每一条标出靠什么守住（问 505 A）。没选不标。
- 钩子先不加（问 511 A）。没选第八窗口开头就加一个「每条消息自动附一行提醒」的钩子。理由：权限与钩子的配置要项目主人亲手写（课程规则 66），课程原把钩子排在第 8 课，试点的数据也还不够。
- 项目主人同时要一份能回溯的记录，像书前面的目录。定的是用脚本从决策记录的标题行现场打印目录，不另存一份（问 502 A）。没选生成一份目录文件，也没选手写目录：两种都要另存，迟早和正文对不上。

### 六、最后怎么做的

**方向，四样：** 能删的删；剩下的到点再读；读也不保险的，交给命令、交给钩子；关键处由人把关。

防护按靠不靠得住排，由弱到强是：开头读一遍，到点读卡，命令判对错，钩子自动跑，人把关；结课另有送审。越往后，越不靠记性。钩子这一层，现在还一条都没有。

**先收拢已有的。** 这个办法一提出，项目主人就问：是不是项目里本来就有，只是没留意。一搜，确实大半本来就有，只是散在各处：
- 自动记忆里的发前自查，按「什么时刻做」记。
- 每一步开头三行锚点，第三行写「这一步我最可能犯什么错」。
- 框架规格 docs/HARNESS.md 的原则 17，早已认出长会话这个问题。
- 待办清单第 7 条，早排了第 8 课用钩子在压缩后提醒重读。
- 每条课程规则末尾的「进自检」判定行，早写了它在哪一刻起作用。
- 课程知识库里的强化 4「条件触发」（满足条件才触发的重要指令）、补丁 13「动手前后检查」，讲的也是到了那一刻再查。

新的只有一样：把这些散着的时刻收成一份按时刻排的索引，每张卡指回正本。教训也落了地：**提新办法之前，先在自己项目里搜已有的做法。** 这一条补进了 HARNESS 原则 1。

**检查单 docs/CHECKPOINTS.md。** 十三张卡，从「开课」到「整节课结课」，中间依次是：派子代理前、报告回来、出推荐前、拍板之后、改已有文件前、提交前、删文件前、报进度时、定新做法时、窗口收尾、发每条消息前。每张 1 到 9 条，共 69 条。每条只写要做的动作和正本在哪，不抄正文；正本改了，卡上只改指针。

两种用法，每张卡的标题后写明用哪种：
- 先读再做：动手前读完这一张。
- 做完对一遍：做完逐条核，在消息末尾写出来。

每条标了靠什么守住：
- 【命令】有现成命令判对错，但要记得跑。17 条。
- 【读】只能靠读卡照做。48 条。
- 【你】由项目主人把关。4 条。

由钩子守的，0 条。洞在哪，一眼看得见。

**决策记录目录 scripts/decision-index.sh。** 从决策记录的标题行现场打印「编号 | 日期 | 提交号 | 标题」，日期与提交号取自 git blame。行业里也这么做：管架构决策记录的工具 adr-tools，源码里就有生成目录与关系图的命令。Keep a Changelog 则提醒：「Using commit log diffs as changelogs is a bad idea: they're full of noise.」直接拿 git log 当目录，太吵。

用法：跑 `bash scripts/decision-index.sh R1 开课`，列出标题里带「开课」的每一条，各带日期与提交号；再拿某一条的提交号跑 `git show --stat`，看那一次改了哪些文件。

**框架规格。** HARNESS 原则 17 补了一层：到点读卡，交给机器，关键处由人把关。

### 七、具体怎么用（走一个例子）

第八窗口开课，要改交付物清单文件头的一句话，把「本窗口目标」换成第八窗口的。这是「改已有文件前」那一刻，先读第 6 张卡，照着做。

第 1、2 条：原文用命令导出，不手打；改前数原文，恰好 1 次才动手。

```
sed -n '8p' docs/lessons/05-api-wbs.md
grep -cxF "$(sed -n '8p' docs/lessons/05-api-wbs.md)" docs/lessons/05-api-wbs.md
```

应该看到：第一条打出那一行原文，第二条打出 1。是 0，说明原文抄错了；大于 1，说明不止一处，替换会改错地方。原文要是以「- 」开头，grep 会把它当成选项，要在 -cxF 后面加 -e。

第 6 条：预期数先算，不估。新句先存进临时文件，用 wc -l 数，是 1 行；一行换一行，文件应仍是 125 行。

第 5、7 条：改的是 docs/ 下的文件，事先说会弹一次确认窗。只用 Edit 改，改的字和同意的对照一字不差。

接着是「提交前」那一刻，读第 7 张卡：先看 git status，只提交这一份文件；再数次数，和预期比。

```
git status --short
wc -l < docs/lessons/05-api-wbs.md
```

应该看到：git status 只列出这一份文件；行数 125。再用上面那样的 grep -cxF 数新句、旧句，应是 1 次、0 次。几个数都对上才提交；有一个不等，就停下，不提交。

最后是「发每条消息前」那一刻：消息末尾写一行「发前自查」，写这条消息碰到了哪几张卡、各项过没过。

### 八、有没有用

**一句话：拦得住的是命令那一层；只靠读的那一层，照样会漏。整体有没有用，还没有能比的数据。**

错数：第七窗口收尾回顾记下 3 处错。第六窗口那份清单（见第二节）口径不一样，数错的数单算了七处，不能直接拿来比。何况第七窗口同时把推理强度（effort）从 high 换成了 xhigh，两样一起换，分不清是谁起的作用。

两个实例，正好一层一个：
- 漏的。第七窗口收尾时拍了一条裁决，改掉了更早一条裁决的一半。检查单第 5 张卡有一条要求：改了一条裁决，回扫指着它的卡。这一条标的是【读】，当时没扫，于是有一张卡还指着旧口径。到第八窗口开课对账时，才查出来。
- 拦下的。第八窗口数原文次数时，原文以「- 」开头，grep 把它当成了选项，报「invalid option」，没有给出数。加 -e 重数，得 1。命令那一层，错了会出声。

机器能查多少：第八窗口跑了一次只读的体检脚本 scripts/doc-check.sh。检查单里它认得的编号有 75 处（规则、反模式、原则、决策记录），引了不存在编号的 0 处。它查不了三样：「问 N」这类问题编号、交付物清单的编号、卡与卡之间的互指。编号还在、意思已经过时的，它也查不出，上面那个「漏的」就是这一种。

token：不省，还略多。检查单约占开课读量的 3%，每条消息末尾还多一行自查。它想换的是少返工，这一点还没有数据证明。量读量时，倒是查出了真正能省的一块：那份自动记忆流水账，定在第八窗口收尾精简（问 520 A）。

### 九、换个项目照着做

1. 先量。开课要读几份、多少字，规矩有多少条。找出最大的那一份。
2. 能删的先删。流水账、讲来历的长段，不放在每次必读的地方。
3. 先在自己项目里搜。已有的、按时刻起作用的提醒，先收拢。
4. 列出一件长事里会停下来的时刻：开工、派人、收结果、出建议、拍板后、改文件前、提交前、删东西前、报进度、定新做法、收尾、每条消息发出前、整件事结束。
5. 每个时刻一张卡，不超过九条。只写动作和正本在哪，不抄正文。
6. 每条标靠什么守住：命令、读、人。
7. 到点先读那一张；做完逐条对一遍，写出来。
8. 标「读」的，挑能写成命令的改成命令；能交给钩子的，交给钩子。
9. 记录的目录从正文现场生成，不另存一份。
10. 先试点，回顾时看错数，再定留不留。

### 十、还没解决的

截至 2026-10-19：
- 检查单在第八窗口收尾回顾时定为长期留下，第九窗口删并专场里和其余规矩一起精简。
- 钩子一条都还没有；挑哪几条交给钩子，放在第九窗口删并专场里定。
- 卡与卡之间有没有重复、正本改了卡上跟没跟上，没有机器查。
- 开课仍然读全七个必读文件；能不能少读，整节课结课时定（问 325 A、521 A）。
- 那份自动记忆流水账，第八窗口收尾精简。

## 案例二　答进度时漏了一整块

### 一、问题是什么

2026-10-17，补课 05-API 第六窗口。项目主人问：

> 本节课还有多少内容没做/做到哪

Claude Code 答了全图，说接口契约「分三块」：第零节、第一节、第二节。项目主人回了一句：

> 第三节呢

契约其实有四节。第三节「本节裁决汇总」，登记着这节课所有拍板的结论，当时已经登到 API-53。漏掉的，恰恰是最要紧的那一节。项目主人接着说：

> 上回的……这么重要的主要内容怎么能忘记？想办法解决，参考行业怎么做专业做法怎么做，是否需要待办清单等。

### 二、症状与实据

契约文件有四个二级标题：零、一、二、三。答进度时没有打开文件一节一节数，是凭对话里的印象说的。

漏掉的那一节有个特点：它是一路随拍随登的。每拍板一条，就顺手登一条，它从来不在「还没做」的那一堆里。于是在印象里，它不算一项要交的东西。

同一个窗口里，同一个形状还出现了两次：
- 课程规则 77 要求拍板时当场判定进不进框架。这个窗口定了一种新做法，判定两次被推到了结课。
- 开课流程本来就要求列「本课产物清单」。开课时只随手列了几样，没有拆成全集。

还有一样连带的。课上说「放到结课再做」的事，记在每个窗口的交接文件（桥梁）里，到这时攒了 35 条。桥梁一窗一份，每次重抄；哪一次漏抄一条，那一条就丢了。

### 三、为什么会这样

**一句话：凭印象报进度，印象里只装得下「还没做」的那几样。一直在顺手做的那一样，从印象里掉了。**

打个比方。搬家时有人问「还剩几箱」，你凭印象说「三箱」，车上其实是四箱。少的那一箱，恰好是你一直顺手在装、从来没当成「待办」的那一箱。

再往下拆，是三个缺口：
- 没有一张盖住全部产物的清单。没有全集，就只能凭印象。
- 规矩按字眼触发。课程规则 77 只在出现「拍板」「入库」这类字眼时才被想起来；这次定的是一种做法，不是一条项目裁决，没触发。
- 说推的事放在了一次性的载体里。这是反模式 24 号（重要的东西只记进一次性载体）的形状。

规矩读过还会忘，更一般的原因见案例一第三节。

### 四、行业怎么解决

**一句话：先列一张盖住全部工作的清单，每项写清做到什么样算完，再用机器核这张清单有没有漏。**

项目管理里有一种做法，叫工作分解结构（WBS），把一件大事要交的东西一层一层拆到最小。它最要紧的一条规矩叫「100% 规则」。项目管理协会（PMI）的《Practice Standard for Work Breakdown Structures》第二版这样写，经维基百科「Work breakdown structure」条目转引：「The 100% rule states that the WBS includes 100% of the work defined by the project scope」。表必须盖住全部工作，一项不少。

表上每一项，要事先写清做到什么样才算完。Scrum 指南管这个叫「完成的定义」：「The Definition of Done is a formal description of the state of the Increment」。

长期的待办和这一轮的待办，要分开放。Scrum 指南说，产品待办是「an emergent, ordered list of what is needed to improve the product」；这一轮的待办是「a highly visible, real-time picture of the work that the Developers plan to accomplish during the Sprint」。

说了「以后再做」的事，管理上叫行动项。维基百科的定义是「an action item is a documented event, task, activity, or action that needs to take place」，每一项要有负责人和计划完成的时间。Scrum 每一轮结束时开回顾会，指南原话：「The most impactful improvements are addressed as soon as possible.」「They may even be added to the Sprint Backlog for the next Sprint.」改进项要进下一轮的待办，和正事一起排。

Scrum 整套做法的根，是三根支柱：「transparency, inspection, and adaptation」，看得见、常检查、随时调。每一轮开头先定一个目标，指南叫它「the single objective for the Sprint」。

最后一层，交给机器。Claude Code 官方最佳实践页说：「Claude stops when the work looks done. Without a check it can run, "looks done" is the only signal available」。给它一个能跑的检查，「做完了」才有硬标准。

### 五、考虑过哪几种

**清单放哪。** 三种（问 489）：
- 放进桥梁的状态表。没选：桥梁一窗一份，放进去还是一次性载体。
- 只靠每条消息末尾的自查。没选：缺的不是提醒，是一份按产物拆到底、每项写清完成标准的清单。
- 本节课单建一份交付物清单文件，报进度从它导出。选了这一种。

长期待办清单（BACKLOG）也考虑过，不合适：它装的是跨课、这节课不做的事，不装这节课要交的全部东西。

**什么时候推到整个项目。** 三种（问 490）：只改框架规格；全都等结课；这个窗口就落三处（课程规则、开课自检、框架规格）。选了最后一种。等结课，正好重犯「推到结课就忘」的错。

**说推的事放哪。** 三种（问 492）：留在桥梁；只另建一张表；搬进交付物清单新开的一节，说推就当场登。选了最后一种。

**从 Scrum 再借什么。** 三种（问 494）：不采纳；全登成待议；每个窗口开头写一句本窗口目标，收尾做一次回顾，现在就进清单。选了最后一种。回顾，Scrum 指南说是为了「plan ways to increase quality and effectiveness」；这里每个窗口收尾答三问：哪里顺、哪里出错、改进项是什么。产品目标（「describes a future state of the product」）本项目早有，导读和框架规格第一节写着最终要做成什么。窗口末检视、待办定期梳理两样，登进清单，结课时再定。

**要不要加进开课自检。** 项目主人提出，把这件事加进每个窗口开头的自检。加了：开课自检第 19 项问「交付物清单建了吗」，第 20 项问「定下新做法时，会当场过三问吗」（用到整个项目吗、进框架吗、进教科书吗）。同时说明：开课提醒一次挡不住这一类，这个窗口开课时读过课程规则 77，照样推到了结课。要和每条消息的自查、能跑的命令一起，三样才稳。

### 六、最后怎么做的

**交付物清单 docs/lessons/05-api-wbs.md。** 一节课一份，换窗口沿用；结课时没做完的转进 BACKLOG，然后删掉。分五节：
- 接口契约本身，拆到每个小节。
- 契约以外的本节交付，比如书章、检查单、脚本。
- 每个窗口收尾要做的：笔记、目录树、桥梁、删减、回顾、本窗口目标。
- 整节课结课要做的。
- 推到结课的事。

每一项三栏：交付件、完成的定义、状态。状态只用五种：已完、进行中、待做、随做、移出。

拆到这么细，契约第三节就不可能再被漏掉：它就写在表上。完成的定义举一例：契约第一节的每个小节，要这个小节涉及的裁决都写进正文，没有一处还写着「待……定」，项目主人读过、认了，才算完。

**覆盖核对命令。** 放在清单开头：

```
grep -E "^#{2,3} " docs/arch/API_CONTRACT.md | sed -E 's/^#+ //' | while IFS= read -r h; do grep -qF -- "$h" docs/lessons/05-api-wbs.md || echo "清单里缺：$h"; done
```

逐段看：第一段把契约里所有二级、三级标题挑出来；第二段去掉开头的井号；第三段一个一个拿出来，到清单里按原文找；找不到，就打印「清单里缺」。**没有输出，才说明契约的每个标题都在清单里。** 这条命令建的时候正反各跑过一次：正着跑，契约 12 个标题全在，没有输出；反着跑，喂一个不存在的标题「四、不存在的一节」，它报了出来。

**推到结课的事。** 清单第五节。说「放到结课再做」，当场登一行：一句话、出处、状态。不登，就不许说推。结课时逐条清：做完了写提交号，移进 BACKLOG 写编号，项目主人定了不做写那道题的编号。三样之一，才算清完。原在桥梁里的 35 条当窗就搬了进来，加上另一处没裁的几项，登成 36 条。

**规矩跟着改。** 课程规则 87 管每节课都建清单、报进度从它导出、说推就登；开课自检加了第 19、20 项；每条消息的自查加了两项（报进度前先导出产物大纲；定新做法时当场过三问），后来搬进了检查单第 12 张卡。框架规格 HARNESS 的原则 18（先给全图）和原则 5（交接）各补了一层。

**三层摆放，各管一个时刻。** 开课自检，开场提醒一次；每条消息的自查，每发一条过一遍；能跑的命令，不靠任何人记得。

### 七、具体怎么用（走一个例子）

第八窗口开课，项目主人问：「上一个窗口的东西你做完啦？」这是检查单第 9 张卡「报进度时」那一刻。照着做。

第一步，跑覆盖核对命令，就是上面那一条。应该看到：没有输出。有输出，先补清单，再开口。

第二步，从清单导出每一项的状态，不凭印象：

```
grep -E "^\| [CDW][0-9]" docs/lessons/05-api-wbs.md | awk -F'|' '{gsub(/^ +| +$/,"",$2); gsub(/^ +| +$/,"",$5); print $2 " | " $5}'
```

应该看到：每一项一行，「编号 | 状态」，比如「C1-4 | 待起草……」「D5 | 已完（2bc0aed）」。

第三步，打开产物本身，数还没填的占位：

```
grep -n "待第 3 组定" docs/arch/API_CONTRACT.md
```

那一次数出 9 处，而交接文件写的是「六处」。没有顺着说，先看这 9 处各在哪：6 处在第一节正文里，另 3 处在第三节汇总的「落点」行里，是指着正文那 6 处的。两边对得上。

第四步，才开口，按清单分开说：做完的、没做的、挪进本窗口的；每一样后面带提交号或文件位置。那一次的答案是：上一个窗口没做完，没做的都已登在清单里，状态写着本窗口。

### 八、有没有用

**一句话：漏掉整块的事没再出；但清单只核标题，状态写得对不对，还是靠读。**

第七窗口开课、第八窗口开课与答进度时，都先跑了覆盖核对。第八窗口那一次，还对出了「九处对六处」，当场打开文件核清。

局限有三处：
- 覆盖核对只拿契约的标题去对。契约以外的交付件，比如书章、笔记、删减，没有机器核，靠清单本身写全。
- 状态靠人改，会过时。第七窗口有一份对照，落盘时里面写的状态已经过时，只好另出一份改；之后检查单第 6 张卡加了一条：对照里的状态，按整批落完之后的样子写。第八窗口写完案例一时，清单里这一项还写着「待做」，要另出一份对照去改；不改，下一次报进度就会照着它报错。
- 推到结课的事越攒越多：搬进来时 36 条，到第八窗口是 47 条。结课时要一条一条清。

### 九、换个项目照着做

1. 开工就建一张交付物清单，把这件事要交的东西拆到最小，一项不漏。
2. 每一项写「做到什么样算完」。
3. 状态只用固定的几种。
4. 清单开头放一条能跑的覆盖核对命令：把主产物的全部标题，逐个回清单里找。
5. 报进度前先跑它，没输出才开口；进度从清单导出，不凭印象。
6. 说「以后再做」的事，当场登进清单的一节，写出处和状态。不登，不许说推。
7. 每一轮开头写一句本轮目标，结尾做一次回顾。
8. 收尾时逐条清：做完、移进长期待办，或明确不做。
9. 长期待办和这一轮的清单分开放，两边只经「移出」相通。

### 十、还没解决的

截至 2026-10-19：
- 覆盖核对只核契约的标题，其余交付件没有机器核。
- 清单里的状态过没过时，没有机器查。
- 推到结课的事已有 47 条，整节课结课时逐条清。
- 「报进度凭印象」要不要单列成一条反模式或规则，整节课结课时定。
- 规矩只增不减：长期待办清单从没定期梳理过；结课时要问一句「这节有哪些能删」。这两样都已登进清单，结课时定要不要变成规矩。

## 案例三　规矩只增不减

### 一、问题是什么

2026-10-19，补课 05-API 第八窗口。项目主人问了一句：

> 我发现自资料重构以来整个项目都是不断变大，但没有对不必要的进行删减合拼，怎么搞？

这不是第一次提。更早的第六窗口，项目主人顺手补过一句：

> 注意处理一些废旧文件，不要只知道增加而忘记删减

当时 Claude Code 认了：那个窗口落了二十多份对照，一份文件都没删。认完接着往下做，还是没删。

### 二、症状与实据

Claude Code 量了一遍。起点是资料重构那个标签，2026-09-28：

| 量什么 | 起点 | 2026-10-19 |
|---|---|---|
| docs/ 下的课程资料（不含样本、决策记录） | 5256 行 | 8407 行 |
| 决策记录 | 326 行 | 11643 行 |
| 课程规则文件 | 601 行 | 641 行 |
| 开课手册 | 101 行 | 156 行 |
| 框架规格 | 220 行 | 385 行 |
| 目录树 | 116 行 | 152 行 |
| 规则条数 | 83 条 | 81 条 |
| 反模式条数 | 46 条 | 46 条 |

这段时间提交了 1359 次。课程资料新增文件 16 份，删除 0 份。自动记忆另有 26 份，52536 字符。

看表的最后两行：条数没涨，字在涨。规则没有变多，每一条越写越长。

有意思的是，删的机制早就有。资料管理员的体检报告，必须填删并候选。课程规则 54 写着结课前先删并。开课手册的试行标准写着：「规则总数没涨；涨了，要有对应的删并」。可这些都排在结课或开课体检。这节课八个窗口没结过课，体检闸门五次没走。一次也没触发。

后来又查出两个同样形状的例子：
- 检查单第 12 张卡写着「过两三个窗口，照命中数挑删除候选」，第九窗口定的。到第十七窗口，一次也没挑过。
- 框架规格要求，每新开三条原则，整体读一遍。原则 20、21、22 新开时，都没对那一行，该做的整体读漏了。

定了要定期做的事，却没挂在一个会被读到的时刻上。

### 三、为什么会这样

**一句话：加有固定的时刻，删没有。**

打个比方。东西进家门有固定的时刻：买回来，就进门了。扔东西没有这样的时刻，总说大扫除时一起扔。大扫除一直不来，屋子只会越来越满。

这里也一样。每踩一次坑，当场加一条规矩，这个时刻天天有。删排在结课，结课八个窗口没到。两边的频率不对等，结果只能是只增不减。

再往下拆，有三层：
- 不是所有增长都有害。决策记录是日志，按需查最后几条。书和契约是产物。有害的是每次开课都要读的那部分：必读文件、开课资料、桥梁、自动记忆、检查单。它们占上下文，为什么要紧见案例一第三节。
- 规矩越多，只靠读的那一层洞越多。当时检查单 69 条，48 条只靠读。
- 光喊删也不行。框架规格原则 4 有一句：删除是唯一一种做错了不会报错的改动。要删，得有证据。

### 四、行业怎么解决

**一句话：定期修剪；删之前先弄清它为什么在那儿；写的时候就知道会过时的，定个到期日。**

Claude Code 官方最佳实践页讲 CLAUDE.md 时，说了三句。第一句管多久做一次：「Treat CLAUDE.md like code: review it when things go wrong, prune it regularly」。第二句管怎么判：「For each line, ask: "Would removing this cause Claude to make mistakes?" If not, cut it.」第三句管判完怎么办：「Ruthlessly prune. If Claude already does something correctly without the instruction, delete it or convert it to a hook.」不一定是删，也可以改成钩子，交给机器。

删之前要弄清楚为什么。这个道理有个名字，叫切斯特顿的篱笆。维基百科的说法是：「"Chesterton's Fence" is the principle that reforms should not be made until the reasoning behind the existing state of affairs is understood.」路上有一道篱笆，你看不出它有什么用，想拆。切斯特顿在 1929 年的《The Thing: Why I Am a Catholic》里说：「Go away and think.」「Then, when you can come back and tell me that you do see the use of it, I may allow you to destroy it.」规矩也一样。每一条都是撞过坑才加的，看不出用处，不等于没有用处。

立法上有一种办法，叫日落条款。维基百科的定义是：「In public policy, a sunset provision or sunset clause is a measure within a statute, regulation, or other law」「that provides for the law to cease to be effective after a specified date,」「unless further legislative action is taken to extend it.」到了日子自动失效，要留，得有人出来主张。默认的方向从留变成了删。本项目每份文件开头写一行「去留」，写明长期还是一次性、什么时候删，是同一个思路的小号版本。

### 五、考虑过哪几种

**什么时候删。** 三种（问 527）：
- 照旧放结课，每个窗口量一下行数。没选：放在结课，正是一次也没触发的原因。
- 现在停下手里的契约，全做删并。没选。
- 下个窗口开头专做一次，不开新内容。选了这一种。

**删多大范围。** 三种（问 557）：到此为止；七个必读、自动记忆等全做；只再做检查单一份，其余退回结课。选了最后一种。检查单当时 70 条，分三批过。

**凭什么判删留。** 三种（问 558）：往后记命中，每条防线拦下东西时当场记一笔，再照命中数挑候选；不记；别的办法。选了第一种。框架规格原则 4 补了这样一句：「只凭『看着没用』就删，和只凭『看着有用』就留，是同一个毛病。」

- 都不立。没选。

**大活怎么办。** 七个必读逐条过、自动记忆逐份过，这节课放不下。开了一条待办「精简专场」，排在补课链上完、下一节正课开课之前（问 667）。

**先做两件减法（第八窗口）。** 删了四份旧桥梁和一份旧报告（提交 0a20909），这是重构以来第一次真删文件。书章草稿里的两块挪进了这份附录。

## 案例四　人工闸门要算总账

### 一、问题是什么

2026-10-20，补课 05-API 第十窗口开课。开课和体检的闸门刚走完，项目主人打断：

> 先停下补充个问题：上面所做的存档的报告和管理员自测和指纹检测对比等开课和体检闸门，也就是刚做的以上动作能做成自动吗？非必要不要我手动选择。这样太浪费我时间。整体解析集中到一处

### 二、症状与实据

Claude Code 数了这个窗口从开课到闸门走完，项目主人被叫停的次数：看状态栏，答精力，第 563 问，亲手跑两次指纹，回「测」，弹窗选 No，说「发」，三道检验题，第 567 问，第 568 问，同意两份对照。一共十五次，另有五次改文件的弹窗。

真正需要动脑的，两三次。

其中还有一道是白造出来的。第 568 问，起因是核对脚本的一个旧问题没修，每个窗口都会再造一次。

人被问多了，问题就不起作用了。更早有一次重温检验，项目主人回了一句「按你推荐」，那道检验就等于没做。

### 三、为什么会这样

**一句话：每道闸门都是撞了坑才加的，单看都有理；可是都加在人身上，没人算过加起来有多少。**

打个比方。一条路每出一次事故，就加一个检查岗。每个岗单看都有理。可没人从头开到尾算一算，要停多少次车。

再往下拆，有两层：
- 当初的理由是对的。第 121 问定下核查命令由项目主人亲手跑，不经 Claude Code 的手，理由是不让被查方自己查自己。
- 能替人站岗的机器排得太后。钩子排在第 8 课，中间这段时间，只能人来站。

### 四、行业怎么解决

**一句话：先问这件事要不要人的判断。不要的，交给机器；要的，才留给人。**

Google 的《Site Reliability Engineering》管这类活叫苦活（toil）：「Toil is the kind of work tied to running a production service that tends to be manual, repetitive,」「automatable, tactical, devoid of enduring value, and that scales linearly as a service grows.」

它给的判据，正好能拿来分闸门：「If a machine could accomplish the task just as well as a human, or the need for the task could be designed away,」「that task is toil.」「If human judgment is essential for the task, there's a good chance it's not toil.」

它还有一句容易漏：人亲手跑脚本，也算。「the hands-on time a human spends running that script (not the elapsed time) is still toil time.」让项目主人亲手跑指纹命令，就是这一条。

在 Claude Code 里，这台机器就是钩子。案例一第四节引过官方的话：写在 CLAUDE.md 里的话是建议，钩子是确定会执行的。

### 五、考虑过哪几种

先把所有闸门分成三类：
- 甲类，不用钩子就能去掉人的，五件：核对脚本按编号去重；桥梁文件不问送审；固定派单直接派；指纹改由 Claude Code 跑；取消改 .gitignore 测弹窗，只看状态栏。
- 乙类，要钩子才能去掉的，四件：开会话时查权限模式；子代理前后跑指纹；开会话时跑 fetch 报差几条；记账文件放宽护栏。
- 丙类，留给人的：精力，真取舍，改说明书时说的「帮我改」，检验题。

**甲类什么时候做。** 三种（问 569）：只做前三件；全放结课；五件现在都做。选了最后一种。

**乙类什么时候做。** 三种（问 570）：这个窗口用量够就上；照原计划放第 8 课；结课时一起定。选了最后一种。到结课定的时候，并回了第 8 课，和别的钩子一起做（问 667）。

**这里有个真取舍。** 指纹改由 Claude Code 跑，等于推翻第 121 问：站岗的成了被查方。当时把这个代价写明了，等钩子上了再交给机器。

### 六、最后怎么做的

甲类五件一批做完，项目主人只说一次「帮我改」。

**脚本。** 核对脚本 scripts/report-check.sh 改成按编号去重，只比代码框里的行。试跑四例：真报告通过；另外三份故意改坏的，都拦下。

**开课手册。** 第 2 件改写。现在闸门这一段，项目主人只在回话里写一句状态栏是不是 manual mode。指纹、派资料管理员、存报告、跑核对脚本，都由 Claude Code 做。脚本两项一致，就提交，再报要点。

**规则。** 课程规则 4 加了例外：资料管理员的固定派单，直接派。其余派单照旧先给项目主人看。

### 七、具体怎么用（走一个例子）

你的项目里也有一串要人确认的事。照这样算一次总账。

第一步，列。把一次开工从头到尾，人被叫停的每一次写下来，弹窗也算。照对话数，不凭印象。

第二步，分。每一次问三句：机器做得和人一样好吗？这件事能不能设计掉？要不要人的判断？

本项目的三个例子：

| 闸门 | 判 | 去向 |
|---|---|---|
| 亲手跑指纹命令 | 机器做得一样好 | 甲类，改由 Claude Code 跑 |
| 改 .gitignore 测弹窗 | 能设计掉：防护本体是 settings.json 里写明的默认模式 | 甲类，取消 |
| 改说明书时说「帮我改」 | 要人的判断 | 丙类，留下 |

第三步，算代价。每去掉一道，问两句：它原来防什么？现在谁防？指纹这一道，原来防被查方自己查自己；现在暂时没人防，等钩子。写下来，别当没这回事。

第四步，把这笔账记下来。下次再加闸门时，先翻出来，看加了之后一共叫停几次。

### 八、有没有用

**一句话：闸门这一段，人只剩一句话；可是机器那一半还没上，现在站岗的是被查方。**

第二十窗口开课，体检一次过。闸门这一段，项目主人只写了一句状态栏。

局限有三处：
- 钩子还是 0 条。项目的 .claude/settings.json 里没有 hooks。乙类四件排在第 8 课。
- 指纹由 Claude Code 跑，是被查方自己查。第 121 问当初要防的，现在没防住。
- 这笔账只算了开课这一段。改文件的弹窗，还在。

### 九、换个项目照着做

1. 每加一道要人做的事，写清它防什么。
2. 定期算总账：一次开工，人被叫停几次，其中几次要动脑。
3. 每一道问三句：机器做得一样好吗？能不能设计掉？要不要人的判断？
4. 不用新工具就能去掉的，先去掉。
5. 要新工具的，排进计划，写明什么时候上。
6. 真要人判断的，留下，别怕。少了杂事，这几次才会被认真对待。
7. 去掉一道，写明原来防什么、现在谁防。

### 十、还没解决的

截至 2026-11-03：
- 乙类四件等第 8 课。
- 这笔总账只算过一次，后来加的闸门没重算过，也没有定期算的时刻。
- 中断后开新会话走不走闸门，没定，登在待办 83。

## 案例五　做到一半断了，接着做之前先复查

### 一、问题是什么

2026-10-29，补课 05-API 第十八窗口。Claude Code 一轮做到一半就停了，没发消息。项目主人回「继续」。过一会儿又停了：

> 怎么又停了？

第四次停下时，项目主人说：

> 怎么又来了；补充每次突然中断必须重新检查相关部分，避免出错

接着又补了一句，这件事不能只管这一个窗口：

> 补充每次突然中断必须重新检查相关部分，避免出错，并记得全局通用不只在本窗口

2026-11-03，第二十一窗口，又碰上一次更重的。项目主人出门一会儿，WSL 整个断了：

> 上个窗口由于我出去了一会，wsl突然中断，所以上次的记录全没和不知道做到哪了。记得不就和检测核实。

### 二、症状与实据

第十八窗口停了五次，都停在一次工具调用之后、写给项目主人的消息之前：
- 一次提交之后。
- 八次 Edit 之后。
- 导出十一格状态之后。
- 又一次提交之后。
- 待办清单十一处落了八处之后。

五次复查，都没查出改坏东西。第五次查出待办清单和副本正好差三行，就是没落的那三处。

第二十一窗口那一次，查出来是这样：
- 会话记录还在，最后一条是 11:54:22。项目主人以为全没了，其实没有。
- 丢的是 /tmp 下的会话临时目录。预拼的副本和扫描脚本都没了。
- 最后三个调用（预拼、Edit、提交）只有发出，没有结果。书章里没有那两节，git 里也没有那次提交。
- 那两节的全文，还在会话记录里，就在写临时文件的那次调用里。

### 三、为什么会这样

**一句话：断点前做到哪，自己记得的不一定对。危险不在断，在接着做的时候凭记得。**

打个比方。炒菜炒到一半去接电话，回来不记得放没放盐。凭记得再放一勺，菜就咸了。该做的是先尝一口。

再往下拆，有三层：
- 断本身没改坏东西。第十八窗口五次都是这样。改坏发生在接着做的时候。
- 记录只说明「发出去了」，不说明「做完了」。第二十一窗口那三个调用，记录里写得清清楚楚，磁盘上却没有。
- 为什么会停，第十八窗口那五次没查清。猜过两样：把一次工具调用的结束当成一轮的结束；网络断了让这一轮提前结束。都没查证，只能标成假设。原因没查清，复查就更不能省。

### 四、行业怎么解决

**一句话：先把要做的记下来，再动手；断了，拿记录和现场对，不凭记忆。**

数据库早就这样做。PostgreSQL 的预写式日志，文档这样讲：「Briefly, WAL's central concept is that changes to data files (where tables and indexes reside) must be written only」「after those changes have been logged, that is, after WAL records describing the changes have been」「flushed to permanent storage.」崩了怎么办：「because we know that in the event of a crash we will be able to recover the database using the log:」「any changes that have not been applied to the data pages can be redone from the WAL records.」

对到这里：改之前先拼好的副本，就是「先记下要改成什么样」；会话记录，就是那份日志。没落的，照着重做。

机器崩过，还要查仓库本身坏没坏。git 有现成的命令 git fsck，文档第一句：「Verifies the connectivity and validity of the objects in the database.」

### 五、考虑过哪几种

### 七、具体怎么用（走一个例子）

第二十一窗口那一次。新会话第一件事，不是接着写。

第一步，看现场：

```
git status --short --branch
git stash list
ls .git/*.lock
git fsck --full; echo "退出码 $?"
git log -6 --stat --format='%h %s'
```

那一次：工作区干净，领先远端 6 条，没有 stash 和 lock，退出码 0。已提交的都在。

第二步，找断点。会话记录在 `~/.claude/projects/<项目>/<会话>.jsonl`，一行一条。每个工具调用有一个编号，它的结果带着同一个编号。挑出没有结果的调用：

```
python3 - 记录文件 <<'EOF'
import json, sys
uses, done = {}, set()
for line in open(sys.argv[1], encoding='utf-8'):
    c = (json.loads(line).get('message') or {}).get('content')
    if not isinstance(c, list):
        continue
    for b in c:
        if b.get('type') == 'tool_use':
            uses[b['id']] = b['name']
        if b.get('type') == 'tool_result':
            done.add(b.get('tool_use_id'))
for i, name in uses.items():
    if i not in done:
        print(name, i)
EOF
```

那一次打出三行：

```
Bash toolu_01JesR8zAeCjSYFTpkZJrjqC
Edit toolu_01Hcim4zvm9jdk3SWzcCjAmS
Bash toolu_01GNXPuyfTdX4wsmg1XutU6Y
```

第三步，到磁盘上核这几个调用落没落。那一次：书章还是 1930 行，没有第八节的标题；git 里没有那次提交；三个悬空提交都是几周前的。三个都没落。

第四步，取回。文字从那次调用的内容里取，不重写。写临时文件那次的内容，加上插入点，要等于 Edit 的新文。两边逐字相等，才信它。

第五步，先报告。写清哪些在、哪些丢了、接下来怎么办。项目主人说记录全没了，和磁盘对不上，先指出来，不顺着说。

第六步，再接着做。重新拼副本，Edit，逐字节比，相同才提交。

### 八、有没有用

**一句话：复查每次都查清了断点，没有一次接错；可是它拦的是接错，不是中断本身。**

第十八窗口第五次，查出待办清单正好差三行，补上就齐。第二十一窗口，两节 55 行一字不差取回，6 次提交先推到了远端。

这一招也不是万能的。第二十一窗口接着做之前，要定读多少，Claude Code 只搜了待办，没搜决策记录，说开课流程没写这种情况。后来写书时才撞见先例：第五窗口的第二个会话，读全了七份必读，只是没重新体检。所以当时选的「不重读七份」，比先例松，它没说。复查查的是文件，查不出当时漏想的事。后面还有一件：轻量接着做之后，Claude Code 到点没读检查单，消息里却写了「卡 4 过」，过了好几轮才自己查出来。查文件验证得了活，验证不了规矩。

局限有四处：
- 停在半路的根因没查清。
- 第 14 张卡靠读。要 Claude Code 自己察觉上一轮断了；WSL 那次，是项目主人说的。
- 副本放在 /tmp，重启就没。这次能取回，靠的是会话记录。
- 会话记录也不是永久的，默认 30 天就删。

### 九、换个项目照着做

1. 每一轮结尾，给人一条完整的消息。
2. 大改动之前，先把改后的样子存一份，落完逐字节比。
3. 改一点，提交一点。提交了的，机器崩了也还在。
4. 断了，先别接着做。看工作区、提交、有没有锁。
5. 机器崩过，跑一次 git fsck。
6. 找发出去但没有结果的调用，到磁盘上核落没落。
7. 要重做的文字，从记录里取，不凭印象重写。
8. 先告诉人：哪些在，哪些丢了，接下来怎么办。
9. 推得勤一点。只在一台机器上的提交，机器坏了就没了。
