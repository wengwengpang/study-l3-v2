# 第 1 课　用户研究

## 一、本章位置

这一章属于第一篇「立项准备」。业务代码仍然不写。它是全书第一次让 AI 角色干活的一章。

**上一章交来什么。** 第 0 课留下一个仓库，里面有规则书 `CLAUDE.md` 的第一层、反模式库 `docs/lessons/anti-patterns.md`，还有第一次提交。

**这一章产出什么。**

- 项目方向：一段话，写进规则书第二层。
- 两个角色文件：`.claude/agents/client.md`（用户研究员），`.claude/agents/persona.md`（AI 扮的目标用户）。
- 角色文件的标准 `docs/AGENT_SPEC.md`：以后建任何角色都照它。
- 研究报告 `docs/design/USER_RESEARCH.md`：真人确认的需求和 AI 假设的需求，分两栏写。
- 目录树文件 `docs/PROJECT_STRUCTURE.md`，反模式库新增的五条。

**下一章拿它做什么。** 第 2 课的 pm 角色读这份研究报告，写需求文档。报告里标着「待验证」的，到了第 2 课只能当假设用，不能当事实用。

**有一件事先说清。** 这一章会看到 AI 扮的用户讲得有鼻子有眼：哪天晚上加班，心里多烦。这些全是编的，没有发生过，这个人也不存在。这一章最重要的本事，就是看着这么像的东西，仍然记得它是编的。

## 二、学完能做到什么

1. 能建一个子代理的角色文件，说出每个字段干什么。
2. 能让两个子代理一问一答，由主对话转话。
3. 能用三个标记审 AI 给的需求，把真人确认的和 AI 假设的分开写。
4. 能看出 AI 的汇报和实际发生的事哪里不一样，知道去哪里核。

## 三、原理

**为什么要有这一步。** 打个比方。盖房子之前，要先问住的人怎么过日子：几口人，谁早起，东西往哪放。不问，房子盖得再结实，住进去也别扭。软件也一样。这一步要回答的是：谁用，他现在怎么过日子，哪里最难受。

**不做会怎样。** 第 2 课的需求只能凭想象写。第 5 课的表、第 10 课的接口，都压在这些想象上。等到发现没人要，返工的是后面所有的东西。

**这一步的难处。** 用户研究本该去找真人聊。可一个学习项目往往找不到真人：本项目的主人对带团队的具体痛点就没有第一手的感觉。这种情况有三种做法：

- 自己访谈自己。最简单，但信号弱，自己问自己问不出意外。
- 让 AI 访谈 AI。形式最像回事，但有个大漏洞，下面讲。
- 还是用 AI 扮用户，但加上纪律：AI 说的一律先标「未验证」，由真人审过才算数。

本项目选第三种，这一章也照它讲。

### 先认几个词

**子代理（subagent）。** 像公司里请来的专家：一个文件写清他是谁、守什么规矩、能碰什么。要用时请他进会议室，事情完了就走，不占着位子。官方的说法是，每个子代理跑在自己的上下文窗口里，有自己的系统提示和工具权限。

**主对话。** 你直接在跟它说话的那个 Claude Code。子代理是它派出去的。

**上下文。** AI 这一次对话手上有的全部材料。第 0 课讲过。

**YAML 头。** 文件最开头，两道 `---` 夹起来的那几行，写着名字、权限这类设置。`YAML` 是一种写设置的格式，这里只用到最简单的「名字: 值」。

**persona。** 一个虚构但具体的目标用户。本项目的叫张伟。

**JTBD。** Jobs To Be Done，一种做用户研究的方法，下面讲。

### 把 prompt 变成文件

没有角色文件的时候，每开一个新会话，都要重新粘一大段：「请扮演有十年经验的研究员，规则如下」。一是费事，二是把上下文占满，三是想给别人用只能传文字。

写成文件以后，放进 `.claude/agents/`，Claude Code 自己会找到它。别人拿到你的仓库，角色跟着一起来。所以重点不是 prompt 写得越详细越好，是把它变成能复用、能分发的文件。

角色的正文不让 AI 凭空写。让它自己写「你是个十年经验的研究员」，它会凭训练时见过的东西编一堆听着合理的设定，就像让演员自己写人物小传，一定会加戏。这是反模式 18 号说的事。本书的角色文件原文在第五节，你照贴。到了自己的项目，可以让 AI 照标准起草，但你看过、同意了才落进文件。

### 合成用户：AI 扮的用户

AI 扮的用户，业界有个名字，叫合成用户（synthetic user）。Nielsen Norman Group 2024 年的文章这样定义：

> A synthetic user is an AI-generated profile that attempts to mimic a user group.

意思是，一个由 AI 生成、试图模仿某类用户的角色。这篇文章列的毛病，这里挑两条：它们「often provide shallow or overly favorable feedback」，给的反馈常常浅，或者好得过头；它们「seem to care about everything」，好像什么都在乎，所以帮不了你判断先做哪个。结论很明确：

> Synthetic users cannot replace the depth and empathy gained from studying and speaking with real people.

合成用户代替不了和真人的接触。文章也说它们还有用处：做前期调研、想出一些假设，但不能拿来做最后的决定。

漏洞在这里。AI 没有见过你的用户，它说的需求只能来自训练数据。于是整条链变成这样：AI 凭空编需求，AI 再把编的整理成研究报告。而且这份报告看起来很专业，有访谈，有画像，有分级。后面的需求文档、数据库全建在它上面，错了都不知道错在哪。

那为什么还用？因为它能很快铺出一张「可能的需求清单」，给真人当靶子。它负责广撒网，你负责定真假。对着空白页硬想，又累又漏。

所以本项目的做法有四条：

1. client 只当研究员，不扮用户。
2. persona 专门发出用户的声音，它说的话默认「未验证」。
3. 项目主人是验证者，不是假用户。留哪条、删哪条，由人定。
4. 报告里，真人确认的和 AI 假设的分开写。

### 为什么拆成两个角色

一个角色又问又答，会自问自答。比如问「你管项目时最头疼什么」，它自己问自己答，答案是它觉得「应该头疼」的，问一句答一句，糊弄过去。

拆成两个，一个专门追问为什么，一个是有具体处境的人，被追问就得给具体回答。一个负责挖，一个负责被挖。这是一个通用的道理：一个角色容易又当裁判又当运动员的地方，就拆开。

### persona 要具体，还不能说大话

「一个项目经理」问不出东西。「张伟，32 岁，一家十来人小公司的技术负责人，手下带 7 个人」才问得出。越具体，被追问时越要给具体的场景。

它还不能说大话。它只能说「我每天上午要花半小时同步进度，烦」，不能说「所有团队都需要自动同步功能」。前者是一个人的处境，后者是把猜测包装成结论。所以 persona 的硬规则里写死了：禁止说「所有人都需要」「市场普遍」这类话。

### 用 JTBD 问

Christensen Institute 这样讲 JTBD：人不是单纯买产品，是把它拉进生活，好在某个处境下取得进展。这个进展就是 job。它要看的是处境，以及功能、社交、情感三面。

问法上有一条要紧：不直接问「你为什么这么选」。它的原话是「Jobs is not asking why someone made their decision」，要找的是故事和当时的处境。下面第四节 client 的第一个问题就是这样：「回想最近一次你们团队要一起完成一件事」。

client 的产出里还有两样。这两样是本项目自己的约定，写在角色文件里：

- **痛点分级。** P0，不解决，这件事就干不下去。P1，能干，但反复吃亏。P2，有了更好，没有也过得去。
- **竞品根因分析。** 不是列竞品功能表，是问对方现在用什么办法解决，包括微信、便利贴这类土办法，哪里还不满意，为什么没换。

### 诚实关卡和假设账本

AI 给的东西不能直接用，要过一道关，由真人审。审的时候只用三个标记：

- ✅ 这是真的，我或我认识的人真这样。
- ❓ 可能有，但我不确定。
- ❌ 不对，这是瞎编的。

这道关最容易走过场。本项目第一次审张伟的时候，六条全打了 ✅，理由是这些内容暂时关系不大。这就是橡皮图章。同样是 ✅，一种是真人的信号，一种只是想快点过去，两者的价值差得很远。后者填进去，记录下来的就不再是真需求，而是 AI 的幻觉加上一个没细看的图章。

后来这六条改成了全部标「待验证」，因为确实没有第一手的感觉。方向照样能定，只是如实记下这些还没验证。

记这些东西的地方叫假设账本。它像法庭的证物袋：每件东西进来先贴标签，谁提供的，核实过没有。没核实的不能当判决依据，但也不扔，先存着。账本就三样：

- **来源。** 谁说的：AI，还是真人。
- **内容。** 具体哪条需求。
- **状态。** 已确认、待验证、已否决。

这一章还没有单独的账本文件，研究报告的两栏就是它这时候的样子：第一栏是已确认，第二栏是待验证。到了第 2 课，需求文档里才单独有一节账本。

### 大方向和具体需求是两回事

项目方向可以先定，本项目靠的是课程的几条硬要求：多用户加权限，有实时或通知，五到八张表，有复杂的前端交互，能部署。可方向定了，不代表张伟那些痛点是真的。这两件事要分开记。

### 为什么两栏物理分开

研究报告是下一课的依据。真需求和 AI 假设混在一起，pm 就会把幻觉当真需求，一路写进需求文档、写进表、写进接口。分开写，是在源头把这条污染链掐断。

### 样品和标准

第一次建完 client 和 persona，文件是有了，可没人写下「角色文件该长什么样」。到了下一课，建 pm 角色时只能照着这两个文件仿，顺手改了权限、人称、落盘方式，三处都不一样。这叫留了样品，没留标准。

所以凡是会反复出现、结构又稳定的东西，第一次做完就抽成一份标准文件，以后照标准做，不照样品仿。`docs/AGENT_SPEC.md` 就是这么来的。反过来，一次性的、每次内容都变的东西，不必立标准。

### 同一件事只记一处

打个比方：同一个电话号码抄在三张便利贴上，改了一张，另外两张还是旧的。文件也一样。一件事写在好几个地方，迟早对不上。所以每件事只定一个正本，别处只写「详见哪里」。本章的规则书第二层就是这样：需求不抄进去，只指向研究报告。这叫单一信息源。

### 这一步的盲区

用户研究只会问出功能上的需求。不管是真人还是 AI，都只会说「我想看任务」「我想派活」，不会说「我想要登录」。就像你跟人说要三间卧室、一个厨房，不会专门说要地基和承重墙。本项目就在这里漏过：需求文档一直写到界面设计，才发现没有登录。第 2 课会讲怎么补这个洞。现在只要记住，研究报告不是全部需求。

## 四、动手

**先说一件事。** 本项目当时并不是这样做的。当时两个角色只建好了，没有真跑：张伟那六条，是 AI 在对话里直接写的草稿。项目文件里已经加了更正，第五节能看到。本节的第 5、6 步是写这本书时补跑的，所以读者能照做，结果也是真实的。怎么跑的，见第十节。

下面的命令都在项目根目录敲。

### 第 0 步　确认起点

**目的。** 确认第 0 课的东西都提交了，这一章的改动才不会和别的混在一起。

```
git status
```

**应该看到。**

```
On branch master
nothing to commit, working tree clean
```

**出了错怎么办。** 如果列出了文件，先照第 0 课把它们提交了。

### 第 1 步　定方向，写进规则书

**目的。** 用户研究要有一个问的范围。这一步定大方向，具体需求不在这里定。

本项目在这四个方向里选了第一个：

- 团队协作类：带小团队，被进度同步、任务分配、谁在干啥这些事烦。
- 学习和知识管理类：笔记资料找不到、记不住、没法协作。
- 内容创作辅助类：写东西、做素材，有协作和版本的烦恼。
- 别的小型协作工具。

你跟着书做，就选第一个，这样后面各章都对得上。

在 VS Code 里打开 `CLAUDE.md`，把下面这段贴到文件末尾，存盘：

```markdown
## 第二层 A：项目方向（Lec 1 定）

项目类型：团队任务协作工具。
依据：满足课程硬底线（多用户+权限、实时/通知、5-8 张表、复杂前端交互、可部署）。

⚠️ 仅"方向"已定。具体需求见 docs/design/USER_RESEARCH.md，
   目前第二栏六条全部"待验证"，无一条真人确认。
   本层后续随第 2-5 课逐步补充已确认的项目事实。
   通用规则不进本文件，见全局 ~/.claude/CLAUDE.md。
```

这段里提到的报告，第 8 步才建。规则书只放项目事实，通用的规矩放全局那份，第 0 课讲过。

验一条：

```
grep -c '第二层 A' CLAUDE.md
```

**应该看到。** `1`。

**出了错怎么办。** 是 `0`，说明没存盘。是 `2`，说明贴了两次。

### 第 2 步　先建目录

**目的。** 给角色文件和设计文档留好地方。

```
mkdir -p .claude/agents docs/design
```

`-p` 的意思是：上一级目录不存在就一起建，已经存在也不报错。

```
ls -d .claude/agents docs/design
```

**应该看到。**

```
.claude/agents
docs/design
```

**出了错怎么办。** 报 `No such file or directory`，就是目录没建上，再跑一次 `mkdir`。记住顺序：先有目录，才能往里写文件。这是第七节 20 号的坑。

### 第 3 步　建标准，建两个角色

**目的。** 先有标准，再照标准建角色。

在 VS Code 里新建下面三个文件，把第五节对应的原文贴进去，存盘：

- `docs/AGENT_SPEC.md`
- `.claude/agents/client.md`
- `.claude/agents/persona.md`

验一条，数两个角色文件各有几个带编号的小节：

```
grep -c '^## [1-5]\. ' .claude/agents/client.md .claude/agents/persona.md
```

**应该看到。** 两行，末尾都是 5。标准要求正文固定五段。

```
.claude/agents/client.md:5
.claude/agents/persona.md:5
```

**出了错怎么办。** 数不对，说明贴漏了，打开文件对着第五节看。

### 第 4 步　重启 Claude Code

**目的。** 让它认识这两个角色。官方写明：Claude Code 会盯着 `.claude/agents/`，文件改了，下一次派单就用新版，不用重启；但在一个新建的 agents 目录里放第一个文件时，要重启才能加载。你刚好是这种情况。

退出 Claude Code，在项目根目录重新敲 `claude`。

### 第 5 步　跑一轮访谈

**目的。** 让 client 问，persona 答，三轮，最后出一份研究结论。这份结论是给你审的靶子，不是结果。

把下面这段贴进 Claude Code：

```text
请做一轮用户研究访谈。项目方向是团队任务协作工具。

做法：
1. 派 client 子代理提问。一次最多 3 个问题。
2. 把问题原样交给 persona 子代理回答。
3. 把回答原样交回 client，让它追问。
4. 最多问答三轮。
5. 第三轮之后，让 client 产出研究结论：用户画像、JTBD、痛点分级、竞品根因分析、给 pm 的输入清单。每条标来源。

规矩：
- 你只转话。不替 client 提问，不替 persona 回答，不改他们的话。
- 每一轮把问题和回答的原文都打出来，第 1 轮也一样。一个字不改，人称也不改。
- 不写任何文件。
- 开始前先读当前目录 .claude/agents/ 下的 client.md、persona.md。发现它们和这个做法有冲突，先指出再继续。

做完第 5 步就停。
```

这些规矩各有用处。「只转话」是怕主对话自己加戏。「不写任何文件」是因为这时候内容还没审。「先读角色文件」和「第 1 轮也一样」这两句是第一次试跑后加的，为什么加，下一步讲。

**应该看到。** 写书时跑的一次，用了约三分半钟。结果里报的花费约 0.6 美元。每次跑出来的内容都不一样，下面是那一次的样子。

client 第一轮问的：

> 2. 回想最近一次你们团队要一起完成一件事，比如一个项目或一次活动。从任务分下来到做完，整个过程是怎么走的？当时任务是怎么分配的，进度是怎么跟的，用了哪些工具或办法，包括微信群、表格、便利贴这类？
