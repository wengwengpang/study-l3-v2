## 二、学完能做到什么

1. 碰到一件接口上要定的事，能先找行业标准：选一份主参考，判它是必须、建议还是可选，没照做的写下理由。
2. 能为一组接口写出全局约定：路径怎么起，凭据放哪，请求收什么格式，成功和出错各回什么。
3. 能讲清两组容易混的退回：「看不见」回 404，「不许做」回 403；请求本身不对回 400，和目标资源的现状冲突回 409。
4. 能给一个接口写齐七样：方法与路径、鉴权级别、请求的校验规则、响应的校验规则、成功码、可能的退回、依据。也能把「本版没有接口的」列全。
5. 能让 AI 分两轮写一节长文档：先核对，拍完再起草；按小节落盘，落完逐字节比对。

## 三、原理

**为什么要有这一课。** 上半章打过比方：接口契约是前端和后端之间递的交接单。上半章定的是这张单子管什么，画好了框。这一章往框里填字。

填的字分两种。一种管所有的单子：抬头怎么写，凭据放哪，出了错怎么退回。这是契约第一节「全局约定」。另一种是每一张单子本身：找谁，带什么，会收到什么。这是第二节「接口清单」。先定前一种，后一种就短了：每个接口只写自己特有的几样，全局约定写过的不再重复。

不定会怎样？17 个接口，每个都得各自决定凭据放哪、出错回什么。17 处各定各的，到第 12 课前后端接起来时，就是 17 处可能对不上。

### 先认几个词

上半章认过接口、请求与响应、方法和路径、请求体、状态码这些词。这一章再补几个，只补本章用得上的。

**另外三种方法。** 上半章讲了 GET（取）和 POST（提交）。这一章还用到三种：PUT，把一个东西整个换掉；PATCH，只改一个东西的一部分；DELETE，删掉一个东西。

**头。** 请求和响应除了正文，开头还带一串「名字: 值」的附注，叫头。比如 `Content-Type: application/json` 说正文是什么格式；`Cache-Control: no-store` 叫中途经手的缓存别存这份响应。

**媒体类型。** 就是 Content-Type 的值，说明正文是哪种格式。本项目的接口只收 `application/json`，也就是 JSON 格式的文字。

**Cookie。** 浏览器替网站保管的一小段数据。网站在响应里让浏览器存下它，浏览器以后每次访问这个网站，都自动带上。

**会话。** 登录以后，后端在数据库里记一条「这个人已登录」，把这条记录的凭据放进 Cookie 交给浏览器。之后每次请求，后端看 Cookie 里的凭据，就认得是谁。本项目用的就是这种做法，第 4 课定的。

**跨站请求伪造。** 一个人登录着本项目，又打开了另一个网站。那个网站悄悄让他的浏览器朝本项目发一条请求，浏览器照常带上 Cookie，后端就以为是他本人要做的。防这件事的手段，下文叫跨站防护。

**查询参数。** 写在路径后面、问号之后的附加条件，比如 `?status=done`。

**幂等。** 同一个请求发一次和发好几次，对服务器的效果一样。比如移出一个成员，移一次和移两次，结果都是他不在项目里了。

**RFC。** 互联网的技术规范文档，每份有个编号，比如 HTTP 的语义写在 RFC 9110。下文说「照 RFC 某某」，指的就是这些文档。

**后端的几道关。** 本项目后端用 NestJS。一条请求进来，依次经过中间件、守卫（Guard）、拦截器、管道（Pipe），最后才到业务代码。上一章讲的 AuthGuard、AuthzGuard 就是守卫；校验规则在管道这一关执行。

**唯一约束。** 数据库给一列定的规矩：这一列里不许有两行的值相同。比如两个账号不能用同一个邮箱。

### 标准怎么用

打个比方。装修房子，电线怎么走有国家规范，照做就是；规范没管的，看行内通行的做法；两样都没有，才自己拿主意。

本项目定接口时照的就是这个顺序：先照行业标准，没有才照主流做法，再没有才自己定。这条方针写在规则书第二层 D；哪个领域照哪一份标准，登记在这一章新建的 `docs/arch/STANDARDS.md`。用法有五条。

- **按层定先后。** 标准分四层，依次是：协议层的正式规范，比如 HTTP 的 RFC；安全基线，比如 OWASP 的速查表；框架自己的约定，比如 NestJS 官方文档；设计规范，比如 Zalando 的接口设计指南。层与层说法冲突时，排在前面的层说了算。四层都没有，才自己定。
- **同一层先选一份主参考。** 接口设计规范有好几家，本项目选 Zalando RESTful API Guidelines 当主参考（API-5）。同一层几家说法不一，列出来，由项目主人拍。
- **每条分三档。** 必须的，照做；建议的，代价小就做；可选的，可以不做，但不把路堵死，记进待办。档次逐条判，写在用到它的那条裁决里。
- **偏离要登记。** 主参考要做、本项目没照做的，理由写进登记表的「偏离登记」，别处只写一个指针。比如会话固定 30 天、不设空闲超时，偏离了 OWASP 的会话管理（API-10）；字段名用 camelCase，偏离了 Zalando（API-22）。
- **说「标准」要拿得出原文。** 说「标准这么规定」，要能指出是哪一份、哪一句，而且当场核过。没核过的，不当标准用。

还有一句要记住：标准管怎么做，不管做多少。项目数量设不设上限、要不要做找回密码，是产品取舍，归项目主人；标准只管决定做了以后怎么做才对。

### 路径与前缀

打个比方。路径像寄信的地址：先写哪个城市，再写哪条街、几号。本项目所有接口的地址，都从同一个「城市」开始，就是前缀 `/api`。

**前缀。** 所有接口挂在 `/api` 下，由后端统一加，只定义一处；前面的 Nginx 原样转发，不剥掉它（API-6）。这样定，是因为一个请求可能走三条路：上线后经 Nginx 转给后端；服务端渲染时，由前端服务直接找后端；本地开发时，由 Next.js 转发给本地的后端。三条路上的路径要长得一样（API-6、API-12、API-13）。浏览器发请求只写相对路径 `/api/...`，不写域名；只有服务端渲染才配后端的内网地址。

**不带版本号。** 接口设计规范几家说法不一，本项目照主参考，路径里先不带版本号。哪天出现第二个调用方，再照当时的主参考加（API-6）。

**写法。** 路径段一律小写，单词之间用连字符；资源名用复数，比如 `/api/projects`（API-51）。

**只写名词，不带动词。** Zalando 第 141 条：「The API describes resources, so the only place where actions should appear is in the HTTP methods.」动作只靠方法表达（API-58）。口语里是动词的接口，换成名词来写：注册是新建一个用户，`POST /api/users`；登录是新建一个会话，`POST /api/sessions`；登出是删掉当前这个会话，`DELETE /api/sessions/self`。NestJS 官方认证一页的例子写 auth 下的 sign-in，那是教程里的例子，不是框架的约定。

**只有一个的东西，用单数。** 有的子资源，一个上级只有一个：项目的负责人、任务的状态、项目的汇总。Zalando 第 134 条要求它们也写成集合：「modeled as a collection with cardinality 1」。同一层的 Google AIP-156 说法相反：「Singleton resources are always singular.」照集合写，改负责人、改状态两个接口的请求体都要多包一层数组，「状态们」还会被读成状态的历史。所以本项目写单数，比如 `/api/projects/{projectId}/owner`，这一条偏离登进了标准登记表（API-57）。

**self。** 「当前用户」「当前这个会话」没有一个现成的编号可写。Zalando 第 143 条是必须档，标题是「MUST identify resources and sub-resources via path segments」，同一条里写着：「Here, it is reasonable to use self as pseudo-identifier path segment.」所以 `GET /api/users/self`、`DELETE /api/sessions/self` 用 self 当编号，不算偏离。

**路径里的编号转不成数字。** 本项目的编号都是整数。路径里写了 `abc` 这类转不成数字的，当作查不到，回「看不见」（架构文档决策 B）。路径里有几种编号，就要定几种去处：项目 id 在 AuthzGuard 那一关退回；任务 id、成员的用户 id 在业务代码里退回。成员的用户 id 是后来才加进路径的，加路径时要回头补上它的去处。

**项目 id 只认路径。** 路径里带项目 id 的写接口，项目一律以路径为准，不从请求体里取。请求体里多带了项目 id，按多余的字段拒绝（架构文档决策 D、API-31）。

### 会话凭据与跨站防护

打个比方。游乐园进门验一次票，在手腕上扣一个手环；之后玩每个项目，工作人员看一眼手环就放行，不再验票。会话就是这个手环：后端在数据库里记下发出去的每一个，浏览器把它存在 Cookie 里，每次请求自动亮出来。

**凭据只放 HttpOnly Cookie。** 会话凭据只放在 Cookie 里，放在请求头里的凭据一律不收（API-8）。Cookie 设了 HttpOnly，页面上的脚本就读不到它。这样选有两个好处：服务端渲染时浏览器会带上 Cookie，第一屏就认得是谁；页面上的脚本偷不走凭据。代价是前面说的跨站请求伪造，要另加防护。

**Cookie 的几个属性。** Secure（本地开发也加）、HttpOnly、SameSite=Lax、不设 Domain、Path 为 `/`、Max-Age 与服务端会话的期限一致（API-8、API-9）。过期以服务端为准。

**30 天，不设空闲超时。** 会话固定 30 天，不续期，也不因为一段时间没动就过期（API-10）。这一条偏离了 OWASP 的会话管理速查表，理由登在标准登记表。将来出现敏感数据、多人共用设备这类情况，再加空闲超时，已记进待办。

**登录时换掉旧会话。** 注册、登录都会新建一个会话。这次请求里要是带着一个还有效的旧会话，同一次请求里先把它删掉。依据是 OWASP 会话管理速查表「Renew the Session ID After Any Privilege Level Change」一节：「the old or previous session ID must be destroyed」（API-8）。

**失败时不动旧会话。** 那一节的标题，说的是权限变化之后。登录时密码错了、注册时邮箱已被使用，权限都没变，所以只在成功时删旧会话，失败时照旧。原文没直接写失败的情形，这一条是从标题推出来的。反过来做，已登录的人在登录页输错一次密码，就被登出了。

**登出。** 删掉服务端的会话，并让浏览器清掉 Cookie。会话本来就已失效时调登出，照样回「未登录」，前端照常跳登录页（API-8）。

**跨站防护。** 用 NestJS 自带的防护，要求 NestJS 12.1 起（API-11）。它先看请求头 Sec-Fetch-Site；没有这个头，再比 Origin 与 Host。GET、HEAD、OPTIONS 三种方法直接放行，所以这三种方法不许改数据；其余方法都要过这道检查，PATCH 也在内。不过的回 403，退回性质叫「跨站被拒」（API-29）。SameSite=Lax 本身也能拦下跨站发来的写请求，但它只算多一层保护，替代不了这道检查（API-9）。

**写请求只从浏览器发。** 服务端渲染只发读请求；写请求一律从浏览器，经前端的请求封装发出。本版不用 Next.js 的 Server Actions（API-48）。

**角色怎么到前端。** 项目列表的每一项、项目详情，都带「我在本项目的角色」（API-34）。前端只拿它决定显示哪些入口，不当授权用；每个受限的接口，都由后端的守卫自己查成员表判定，前端传来的角色一概不信（架构文档决策 Q1）。当前登录的是谁，由单设的「当前用户」接口给（API-34）。

### 请求格式

打个比方。寄快递有统一的面单：寄件人、收件人、物品各写在哪一栏，都是定好的。填错一栏、多写一栏，快递站都会退回来。请求格式就是这张面单的规矩。

**只收 JSON。** 带请求体的接口只收 `application/json`；`application/json; charset=utf-8` 这种带参数的写法也收（API-27、API-51）。Content-Type 不对，回「格式不支持」（415）。

**字段名用 camelCase。** 字段名和查询参数名都用 camelCase，比如 `dueDate`（API-22）。本项目的命名规范在架构文档里早定了：数据库的列用 snake_case，代码和接口全用 camelCase。接口照架构文档走，偏离了主参考 Zalando 第 118、130 条，理由登在标准登记表。

**多出来的字段，一律拒绝。** 请求体里出现校验规则没列的字段，回「参数不合法」（400），出错的外壳里逐项列出多出来的是哪几个（API-31）。Zod 默认会把多余的字段悄悄剔掉，本项目不照这个默认。依据是 OWASP 的批量赋值速查表：请求里多塞一个字段，后端照单收进数据，就是批量赋值。

**没定义的查询参数，也拒绝。** 查询参数同理（API-56）。主参考 Zalando 第 109 条：「Unknown input fields in payload or URL should not be ignored」。

**必填的文字，先去首尾空白。** 必填的文字字段，去掉首尾空白后为空的，当作没填，回「参数不合法」；存进去的，是去掉首尾空白后的值（API-32）。哪些字段必填、最长多少，归校验规则。

**密码例外，原样收。** OWASP 认证速查表写「Allow usage of all characters including unicode and whitespace.」，又写「Do not silently truncate passwords.」用户设的密码里带空格，服务端悄悄去掉，下次照原样输入就登不上。所以密码原样收，不去空白，也不截断（API-32）。

**没传和传 null。** 新建时，可空的字段没传和传 null 是一个意思，都是空（API-54）。更新时照 JSON Merge Patch（RFC 7396）的规则：没传的字段不改，传 null 表示清空（API-33）。null 只对可空的字段有效，比如任务的负责人、截止日期；对不可空的字段传 null，回「参数不合法」。负责人把任务改回未分配，就是把负责人传 null。更新请求仍只收 `application/json`，不用 RFC 7396 登记的那个专门的媒体类型，这一条偏离也登了记（API-33）。

**改一部分用 PATCH，整个换用 PUT。** RFC 9110 第 9.3.4 节：「The PUT method requests that the state of the target resource be created or replaced」。主参考 Zalando 第 148 条也这么分：PATCH 是「to update parts of the resource objects」；「PUT requests are used to update (and sometimes to create) entire resources – single or collection resources.」用 PUT 只传改动的字段，没传的会被当成「换成空」。所以改任务、改状态这类只改一部分的，用 PATCH；转让负责人是把「本项目的负责人」整个换掉，用 PUT（API-50）。

**时间的两种写法。** 接口里的时间分两种。一种是「某一刻」，比如创建时间，一律用世界标准时间，照 RFC 3339 写成 `2019-07-30T06:43:40.252Z` 这样（API-41）。Zalando 第 169 条原话：「APIs MUST use the upper-case T as a separator between date and time」，结尾也用大写 Z，Z 就表示世界标准时间。JavaScript 自带的写法正好一样，MDN 原话：「The timezone is always UTC, as denoted by the suffix Z.」另一种是「某一天」，比如截止日期，写成 `2019-07-30`，不带时刻，也不带时区。

**邮箱怎么比。** `Bob@example.com` 和 `bob@example.com` 是不是同一个邮箱？OWASP 邮箱校验速查表说，@ 后面的域名部分「always case-insensitive」，前面那部分「technically case-sensitive under SMTP, though many providers do not enforce this in practice」。它要求项目自己「Define an explicit comparison policy for the local part」，并且「Preserve the original email address as entered by the user」。本项目定的是：存用户输入的原样，只去掉首尾空白；注册查重、登录、按邮箱邀请成员时，整个地址不分大小写比较（API-55）。

**这条规则由数据库兜住。** 比较规则要落到数据库的唯一约束上。architect 比了四种写法：

- citext 列：换成扩展里「不分大小写的文字」类型。PostgreSQL 官方页写「The citext module provides a case-insensitive character string type」。
- 表达式唯一索引：在 lower(email) 上建唯一索引。官方原话是，它「would prevent creation of rows whose col1 values differ only in case」。
- 不区分大小写的排序规则：官方提醒「their use leads to a performance penalty」，有的模式匹配也用不了。
- 小写影子列：另存一列全小写的邮箱，对它建唯一约束。

选了 citext（ADR-DB-008）。理由有三条：规则落在列的类型上，注册、登录、邀请三处照常按邮箱查，不各自处理大小写；Prisma 的 schema 写得出（@db.Citext）；库还没建，改列类型没有迁移成本。代价是多依赖一个 PostgreSQL 扩展，而且比较规则随数据库的区域设置变，官方原话「citext's case-folding behavior depends on the LC_CTYPE setting of your database」，所以区域设置要在环境设计里定死。影子列没选：数据库只保证小写的那一份不重复，不分大小写要靠程序每次都转对，漏一处就拦不住。排序规则也没选：有性能代价，有的模式匹配用不了，Prisma 那边还要手写 SQL。

PostgreSQL 的 citext 页其实建议考虑改用排序规则：「Consider using nondeterministic collations (see Section 23.2.2.4) instead of this module.」本项目没照这条建议走，理由写进了标准登记表的「偏离登记」，决策记录里只留指针。

### 成功响应

打个比方。快递员把包裹交到手上，不会再套一个信封，上面写「本次投递成功」。成功的响应也是这样，直接给东西。

**不加外包装。** 成功的响应直接回资源本身，不套一层统一的外壳（API-18）。单个资源直接回对象。列表的顶层也回对象，数组放在其中一个字段里，这样以后加分页，响应的形状不用改。前端解析时，容忍多出来的字段（API-31）。

**成功码三个。** 读取、更新成功回 200，带资源；新建成功回 201，带新资源和它的 id；成功但没有内容回 204，比如登出（API-25）。

**改状态回 200，带整个任务。** PATCH 成功后回什么，标准没限死。Zalando 第 148 条：「Successful PATCH requests return 200 or 204 (if the resource was updated — with or without returning the resource)」。RFC 5789 的例子回 204，又写「other success codes could be used as well」。改状态会让「可能卡住」重新计时，这个标记只在后端算，所以改状态回 200，带回整个任务（API-35）。

**注册回 201，但不带 Location。** 新建成功时，标准做法是用 Location 头告诉对方新东西的地址。注册新建了一个用户，所以回 201；可这个用户没有自己的地址，能读到他的只有「当前用户」接口，而那个地址随会话指向不同的人。RFC 9110 第 15.3.2 节允许不带 Location，原话是新资源由 Location「or, if no Location header field is received, by the target URI」标识。不带时，标准把注册接口的地址当作新资源的标识，读起来别扭，这个代价接受了（API-25）。

**转让负责人回 204。** 转让成功后，调用的人自己就成了执行者；按产品规定，执行者看不见负责人是谁。所以转让成功只回 204，不把新负责人带回去。RFC 9110 第 9.3.4 节允许：PUT 成功「MUST send either a 200 (OK) or a 204 (No Content)」。前端收到 204，重新取一次项目信息，按调用者的新角色渲染（API-52）。

**登录回 200，不带会话。** 登录虽然新建了会话，仍回 200，不回 201；响应里带当前用户，和「当前用户」接口同一个形状（API-53）。会话凭据只放在 HttpOnly Cookie 里，响应体里从不出现会话或它的编号：放进响应体，页面上的脚本就读得到，HttpOnly 就白设了。

**一个响应带什么，不只看接口规范怎么说，还要看此刻谁在看、他该看什么。**

**列表不分页，但要知道门槛在哪。** 分页，就是数据太多时一次只给一页。主参考 Zalando 第 159 条是必须档，但它有门槛：「This holds true for all lists that are (potentially) larger than just a few hundred entries.」只管可能超过几百条的列表。本项目的规模是一个没验证过的假设：每个项目几百条任务以内。这正卡在门槛上，所以本版不分页，同时记进待办：假设被推翻，就照第 159、160 条加游标分页，第 160 条要求避开按页码分页（API-40）。不分页时，后端按 id 升序返回，只为每次顺序一致；按截止日期排序、筛选，在前端做。

**标准里的「必须」，常带着适用的门槛。用之前，先看门槛。**

### 退回性质与状态码

打个比方。快递退件，退件单上有一排勾选项：地址不详、收件人拒收、超重。经手的人只勾「为什么退」，不自己编号码；到了出口，由一个窗口照一张表，把勾的项翻成统一的代码。

**各层只说为什么退。** 后端各层出错时，只抛出一种「退回性质」，不直接写状态码。全局异常过滤器在一处把性质翻成状态码，再收成统一的出错形状（API-23）。要改映射，只改这一处。

**八种性质。**

- 未登录，401：凭据缺失或无效；登录时凭据不对（API-14、API-16）。
- 看不见，404：项目不存在或自己不是成员；任务不存在、不属于本项目或不属于自己；路径里的编号转不成数字；路径不存在（API-15、API-21）。
- 不许做，403：看得见，但这个动作不许做，比如执行者调负责人专用的「改任务」（API-21、API-35）。
- 跨站被拒，403：跨站防护没过（API-29）。
- 参数不合法，400：请求本身不合法，或它引用的别的东西不合要求（API-14、API-38）。
- 冲突，409：和目标资源的现状冲突，比如邮箱已被使用、已在项目中、唯一的负责人要移出自己（API-37、API-38）。
- 格式不支持，415：有请求体，但 Content-Type 不是 JSON（API-27）。
- 内部错误，500：过滤器认不出的错（API-14）。

不用 422（API-14）。

**看不见和不许做，为什么分开。** 「看不见」回 404，是不让对方知道这个东西存在：一个不是成员的人来探某个项目，收到的 404 和这个项目真的不存在时一模一样。「不许做」回 403，是对方本来就看得见，只是这个动作不归他。界面上两种都显示「权限不足」（API-4、API-21）。

**400 还是 409，看目标资源。** 请求要新建、修改、删除的那个东西（或它所在的那一组），现状和请求冲突，回 409；请求本身不合法，或它引用的别的东西不合要求，回 400（API-38）。比如注册时邮箱已被使用，冲突的是用户这一组，回 409；创建任务时派给了一个不是本项目成员的人，派给谁是引用的别的东西，回 400。这条线照的是 RFC 9110 对 409 的说法：和目标资源的现状冲突。

**删一个本来就不在的成员，回 404。** 移出成员时，被移出的人本来就不在项目里，回 404（API-37）。Zalando 第 148 条：「Failed DELETE requests will usually generate 404 (if the resource cannot be found)」。前面说过 DELETE 是幂等的：移一次和移两次，结果都是他不在项目里了。可 RFC 9110 第 9.2.2 节的幂等，管的是「the intended effect on the server」，不管每次回什么码。所以第二次移出回 404，并不违反幂等。

**401 要带一个头。** 回 401 时必须带 WWW-Authenticate 头，说明该怎么认证（API-20）。本项目写方案名 `Session`，不带 realm。照 RFC 写 Basic 也合规矩，可浏览器看到 Basic，会自己弹出一个要账号密码的框。`Session` 这个名字没在 IANA 登记过，所以算偏离，理由登了记。

**几种退回同时成立，先拦的先回。** 依次是：跨站检查、AuthGuard、AuthzGuard、Content-Type 检查、管道、业务代码（API-46）。Content-Type 检查特意排在两道守卫之后：一个不是成员的人，不管格式对不对，先收到的都是「看不见」，不让他从 415 里看出项目在不在。

**请求体写坏了，先回 400。** 请求体由框架在守卫之前解析，写坏的 JSON 在这一步就被挡下，回「参数不合法」。所以没登录的人发来坏 JSON，收到的是 400 而不是 401，前端靠 401 跳登录页的逻辑这时不会触发（API-46）。这是从框架的处理顺序推出来的，第 10 课写后端时实测。

**框架自己拦下的退回。** 路径不存在、请求体不是合法 JSON，这些不是本项目的代码抛的。能对上现有性质的就并进去：路径不存在算「看不见」，坏 JSON 算「参数不合法」。对不上的保留标准码，type 用 RFC 9457 登记的通用类型 `about:blank`（API-47）。网关出的错不经后端，带不了本项目的出错形状。

### 错误外壳

打个比方。退件单有固定的格式：哪一栏写代码，哪一栏写说明，哪一栏写这张单子的编号。

**照 RFC 9457。** 所有接口出错，都回 RFC 9457 规定的形状，媒体类型是 `application/problem+json`；框架自己拦下的退回，也由后端收成这个形状（API-17）。外壳表达五样东西：

- type：机读的问题类型，前端照它出中文提示（API-19）。
- title、detail：文字说明，只用来排查和兜底。
- status：状态码。
- instance：这一次出错的编号。
- 扩展部分：要用时加，比如 400 时逐项列出哪里不对。

**type 按性质给，要分提示的才另起。** 同一种退回性质，提示一样，就共用一个 type；同一性质里要分出不同提示的，才另起专门的 type。比如同是 409「冲突」，「邮箱已被使用」要单独提示（API-24）。两个请求同时写，后到的撞上数据库的唯一约束，回的 type 和先查就查到时一样，用户看到同一个提示（API-28）。type 的字面值归校验规则那一层（ProblemType），契约只定性质到状态码的映射。

**出错编号用 UUID 第 4 版。** instance 是全局异常过滤器每次出错时现生成的随机编号，写成 `urn:uuid:` 开头；同一个编号写进服务端日志，查日志时照它找（API-26）。RFC 9562 第 5.4 节：「UUIDv4 is meant for generating UUIDs from truly random or pseudorandom numbers.」第 7 版按时间有序，日志里好排，可它不是纯随机，和「随机编号」的定义对不上，没选。

**不透露多余的东西。** 401 的外壳不指向任何字段；登录失败，不说是邮箱错还是密码错（API-16）；不暴露程序的堆栈（API-17）。注册时邮箱已被使用，照实回「冲突」，因为需求文档要求提示这一句；登录另防有人拿它试探哪些邮箱注册过，两处有意分开。

### 前端怎么读退回

打个比方。前台拿到退件单，看代码那一栏，用顾客听得懂的话转告。

- 中文提示由前端照 type 出；title、detail 只兜底（API-19）。
- 前端不能指望每个出错都是这种外壳：网关出的错，按加载失败处理（API-14）。
- type 是 `about:blank` 的，出通用提示（API-47）。
- 「看不见」「不许做」都显示「权限不足」；前端打错路径，也显示「权限不足」（API-21、API-47）。
- 「跨站被拒」另出提示（API-29）。
- 在登录页收到 401，显示「邮箱或密码不正确」；不在登录页收到 401，跳登录页（API-16）。

### 所有响应共有的头

**一律不缓存。** 所有接口的响应，成功、出错都带 `Cache-Control: no-store`，登录、注册也带；由后端统一加，不靠各接口自己写（API-44）。

**为什么要加。** 常见的令牌做法，把凭据放在 Authorization 请求头里。RFC 9111 第 3.5 节对带这种头的请求有一条默认保护：共享缓存不能拿缓存的响应去应付别人。本项目的会话放在 Cookie 里，RFC 9111 第 7.3 节特意说：「Note that the Set-Cookie response header field does not inhibit caching;」Cookie 没有这条默认保护，只好自己加。OWASP 会话管理速查表也这么要求。同时要知道，RFC 9111 提醒过 no-store「not a reliable or sufficient mechanism for ensuring privacy」：它是多一层保护，不是唯一一层。

**换一种技术方案，原来白送的保护可能就没了，要重新核一遍。**

**框架挡下的也要盖住。** 框架自己挡下的退回，比如路径不存在、坏 JSON、在中间件之前就退回的跨站被拒，可能绕过统一加头的那一层。挂在哪一层，写后端骨架时定，但要把这几种都盖住。网关出的错不经后端，本来就带不了这个头（API-44）。

### 接口清单怎么写

打个比方。前面几块是公司统一的公文格式；这一块是每一类公文的样张。格式里写过的，样张上不再重复。

**每个接口写七样。** 方法与路径、鉴权级别、请求的校验规则、响应的校验规则、成功码、可能的退回、依据。退回只写性质，状态码照第一节的映射表。

**鉴权分四档。**

- 公开：不挂 AuthGuard。只有注册、登录两个接口。
- 只要登录：只挂 AuthGuard。路径里没有项目 id 的接口用这一档，因为 AuthzGuard 要拿路径里的项目 id 查成员表，没有就判不了。
- 本项目成员：两道守卫都挂，负责人、执行者都放行。执行者只能碰分给自己的任务，这一条在业务代码里判。
- 只有负责人：两道守卫都挂。执行者调用，由 AuthzGuard 回「不许做」（API-35、API-42）。

**共有的退回只写一处。** 内部错误、路径不存在、未登录、跨站被拒、格式不支持、参数不合法、并发撞上唯一约束，这几种很多接口都会有，写在接口清单开头一处，各接口不再列。

**名字怎么起。** 请求体照「动作 + 资源 + Request」起：POST 写 Create，PATCH 写 Update，PUT 写 Replace，比如 CreateUserRequest。列表响应照「List + 资源复数 + Response」起，比如 ListProjectsResponse（API-30）。两层标准说法一致。框架层，NestJS 官方的 CRUD 生成器给的是 CreateUserDto、UpdateUserDto。设计规范层，Google AIP-133 写「The request message must match the RPC name, with a `Request` suffix.」；AIP-132 写「The request and response messages must match the RPC name, with `Request` and `Response` suffixes.」，例子是 ListBooksResponse。只照请求那一半起名、列表另写一个 TaskList，就成了两套规则。名字后面写不写 Schema 这类后缀，归共享类型那一节。

**列表项和详情，用同一个形状。** AIP-132 还写：「The response should usually include fully-populated resources unless there is a reason to return a partial response」。所以列表的每一项和详情同一个形状、同一个名字。改状态回来的整个任务，前端可以直接替换列表里那一行（API-30）。同一个资源按调用者的角色给不同形状时，也用一个名字；几种形状在校验规则里怎么写，归共享类型那一节。

**17 个接口，分三个模块。** 按代码放在哪个模块分组：

- auth，四个：注册 `POST /api/users`、登录 `POST /api/sessions`、登出 `DELETE /api/sessions/self`、当前用户 `GET /api/users/self`。
- projects，七个：我所在的项目列表、创建项目、项目详情、成员列表、邀请成员、移出成员、转让负责人。
- tasks，六个：任务列表、任务详情、创建任务、改任务、改状态、项目汇总。

**改任务拆成两个接口。** 字段级的权限，变成路由级：负责人专用的「改任务」，两种角色都能调的「改状态」（API-35）。执行者调「改任务」，回「不许做」；执行者用「改状态」改不分给自己的任务，回「看不见」；往「改状态」里多带别的字段，按多余的字段回「参数不合法」。

**一个词在同一个接口里只指一样东西。** 「负责人」在这个项目里有两个意思：一是项目角色，派活、看全局的那一方；二是一个任务分给了谁。创建任务的鉴权级别写「只有负责人」，指的是项目角色。退回里要说「分给的人不是本项目成员」，如果也写「负责人」，读的人就分不清。需求文档澄清注记 10 定了读法：说任务分给谁，写「任务负责人」。

**能由别的数算出来的，接口里不另给。** 项目主页要显示完成率。汇总接口已经给了四个数：任务总数、已完成、进行中、未开始。完成率就是「已完成」除以「任务总数」，前端一除就有，后端没有别处要用它，所以接口里不另给（API-42）。这段算法也不放进前后端共享的那一层：判断的第一问是「前后端是不是都真的用它」，只有前端用，就不进。任务总数为 0 时，页面本来就有空态，前端不做除法。将来要在后端判断项目风险，再往汇总里加一个字段，只加不改，老的前端不受影响。

**「本版没有接口的」也要列全。** 接口清单最后一小节，列本版没有接口的东西，分三类：没有接口的模块，是 users、authz、notifications；本版不做、所以没有接口的操作，是删任务、删项目、成员自己退出、把成员直接改成执行者，以及用户对自己账号的四样操作；本版延后的功能。列这一节，是为了让写后端、写前端的人不去写、不去调根本不存在的接口，也不把「没做」当成「漏了」补上。

账号的四样操作，是改密码、改邮箱、找回密码、注销账号。需求文档里一句都没提，「不做」的清单里也没写。认证这块的主参考 OWASP Authentication Cheat Sheet 有三节讲这些，开头分别是：「When developing a change password feature, ensure to have:」「It is common for an application to have a mechanism that provides a means for a user to gain access to their account in the event they forget their password.」「User email addresses often change.」三句讲的都是做的话该怎么做，没有写必须提供。本版定为都不做，并写明后果：忘了密码就进不去，也没有管理员能代为重置（需求文档审定决策 D19）。

**文档里的示例，用 example.com。** 示例邮箱原先写成 Bob@x.com。x.com 是一个真实在用的域名，拿它当示例，照着测试就可能把请求发到别人的服务器上。RFC 2606 第 3 节写：「The Internet Assigned Numbers Authority (IANA) also currently has the following second level domain names reserved which can be used as examples.」保留的是 example.com、example.net、example.org。示例邮箱都改成了 example.com 的写法。

### 产品口径回需求文档定

打个比方。交接单上要写「谁能签收」，可谁能签收是公司的规定，不归交接单定。规定先在规章里写好，交接单照着办。

上半章定过三份文件的分工：需求文档管「能不能」，契约管「怎么调」，校验规则管「长什么样」。写契约时碰到的产品规则，回需求文档去定：派 pm 只核对、出选项，拍板归项目主人。真人确认过的故事原文不动，只加澄清注记；pm 推导、经项目主人审定的，可以直接改。这一章回去定了这些审定决策：

- 首版单负责人，成员一律以执行者身份加入；负责人可以转让，原负责人同时变成执行者（D10）。
- 执行者只看得见自己所在的项目和分给自己的任务，看不见成员列表和未认领的任务（D11），也看不见项目负责人是谁（D17）。依据是 OWASP 授权速查表的最小权限。
- 任务三种状态任意互转，谁能改照权限矩阵（D12）。
- 「可能卡住」只看已分配、未完成的任务，从最近一次状态变化和最近一次分配里较晚的那个起算，满 7×24 小时（D13）。
- 负责人可以移出成员，被移出的人立即失去访问，名下任务变成未认领；成员不能自己退出（D14）。
- 只有负责人能改任务的标题与描述（D15）；负责人可以把任务改回未分配（D16）。
- 删任务本版不做（D18）；账号自己的四样操作本版不做（D19）。
- 密码最短 15 位、最长不少于 64 位、不限字符种类（D20，取代 D9）。

密码这一条，原来定的是「至少 8 位，含字母和数字」。认证这块的主参考 OWASP Authentication Cheat Sheet，在「Implement Proper Password Strength Controls」一节写了三样：

- 「If MFA is not enabled passwords shorter than 15 characters are considered to be weak」：没开多因素认证时，少于 15 位就算弱；开了多因素认证，门槛是 8 位。
- 「There should be no requirement for upper or lower case or numbers or special characters.」：不该要求大小写、数字或特殊字符。
- 「"Maximum" password length should be "at least 64 characters" to allow passphrases」：最长至少允许 64 位，好用一整句话当密码。

本项目没有多因素认证，于是改成现在这样。注册接口的契约只点名这条决策，不抄规则本身，规则的正本在需求文档。拦常见的与泄露过的密码、强度提示、哈希算法与具体上限，本版没做，记在待办里。

### 连带的数据改动

写契约时还牵出了几处表结构的改动。改表结构之前，先回 architect 确认写法，再出改动给项目主人看（决策边界 D2）。

- 截止日期说的是某一天，改存纯日期：字段 dueDate，列 due_date，推翻了第 5 课「存时间点、界面只显示到日」的做法（ADR-DB-003 修订）。
- 每个项目至多一个负责人，用部分唯一索引兜底；写法随 Prisma 锁定的版本定（ADR-DB-006）。
- 任务加一列分配时间 assigned_at，可空：「可能卡住」要从最近一次分配起算，没有这一列算不出来。不存分配历史，也不加检查约束（ADR-DB-007）。
- 邮箱列改用 citext，见前面「请求格式」（ADR-DB-008）。

### 第 2 步　定用标准的方针，建标准登记表

**目的。** 第 1 步的推荐不能直接拍：一条推荐对不对，要拿行业标准的原文来比。这一步先定「标准怎么用」，再建一个地方，登记每个领域照哪一份标准。用法本身在第三节「标准怎么用」讲过，这里讲它怎么落下来。

**起头的是项目主人的一句要求。** 原话是：「当然整个项目都首先按行业标准来做，不要做出来也不达标。如果没有相关行业才其它方法或自定标准。」

方向是对的，可直接照做会掉进四个坑：一个领域的标准常常不止一份；全照着做会做多；AI 说一句「标准这么规定」，人很难当场核；查原文慢。所以先加三道护栏，再定层次和档次，第三节那几条用法就是这样来的（问 339 A、343 A、345 A）。已经定了的不专门回头核，往后碰到相关的顺带核，不达标的列出来请项目主人拍（问 344 A）。

**要做的三件。**

1. 每个领域先选一份主参考。选之前把候选几份的原文取来比。接口设计规范这一格，比过 Google、微软、Zalando 三家，选了 Zalando（API-5）。
2. 新建 `docs/arch/STANDARDS.md`。文件头写做法，正文三块：登记表、偏离登记、待登记。先登用得上的几行，往后每碰到一个领域再登。

```
### 1. 适用范围与标准

- 本节对全部接口生效（API-1）。
- 字段名、类型、必填与否、取值范围不在本节。它们归共享 Zod schema（API-1、ARCHITECTURE 第二节取舍 4）。
- 本节点名的 schema 名字就是接缝。05-类型 按名字交货（API-1）。
- 本节提到的标准只写名字。原文出处与核对记录见 docs/arch/STANDARDS.md「登记表」（API-5）。
- 偏离主参考的地方，本节只写指针。理由见 docs/arch/STANDARDS.md「偏离登记」（API-10、API-20、API-22、API-33、API-57）。

### 2. 路径与前缀

- 所有接口挂在 `/api` 前缀下（API-6）。
- 前缀由后端统一加，只定义一处。Nginx 原样转发，不剥前缀（API-6）。
- 路径不带版本号（API-6）。
- 出现第二个调用方时，按当时的主参考加版本（API-6）。
- 路径段一律小写，单词之间用连字符（API-51 第六点）。
- 资源名用复数（API-51 第六点）。
- 只有一个的子资源（如本项目的负责人、任务的状态、项目的汇总）用单数，偏离 Zalando #134，理由见 docs/arch/STANDARDS.md「偏离登记」（API-57 修订）。
- 路径只写名词，不带动词；动作只用 HTTP 方法表达（API-58）。
- 接口都在 NestJS。本版 Next.js 不写 Route Handler（API-7）。
- 将来 Next.js 要写 Route Handler，不得用 `/api` 前缀（API-7）。
- 浏览器发请求用相对路径（`/api/...`），不写域名（API-13）。
- 只有服务端渲染配后端的内网地址（API-13、T15）。
- 本地开发由 Next.js rewrites 把 `/api` 转给本地后端。只在开发环境打开（API-12）。
- 任务类接口的路径嵌套项目 id（T2）。
- 路径参数不做格式校验，和查询参数分开处理（T3）。
- 路径 id 转不成数字，视为查不到，按「看不见」退回（决策 B、API-21）。
- 凡路径带项目 id 的写接口，项目一律以路径为准，不从请求体取（决策 D、API-51 第四点）。
- 请求体里多带了项目 id，按多余字段拒绝，回「参数不合法」，见第 4 小节（API-31、API-51 第四点）。

### 3. 会话凭据与跨站防护

凭据：
- 会话凭据只用 HttpOnly Cookie。放在请求头里的凭据一律不收（API-8）。
- Cookie 属性：Secure（本地也加）、HttpOnly、SameSite=Lax、不设 Domain、Path 为 `/`、Max-Age 与服务端会话期限一致（API-8、API-9）。
- 过期以服务端为准（API-8）。
- 会话固定 30 天。不续期，不设空闲超时（API-10、T4）。
- 这一条偏离 OWASP 会话管理，理由见「偏离登记」（API-10）。
- 纯读请求不写 sessions（T4）。
- 每次注册、登录都新建会话（API-8、API-53）。
- 注册、登录成功时，请求里带着的有效旧会话在同一次请求里先删掉；失败时照旧（API-8 补充，问 625 A）。
- 登出删掉服务端会话，并让浏览器清掉 Cookie（API-8）。
- 会话已经失效时调登出，照样回「未登录」，前端照常跳登录页（API-8 补充）。
- 服务端渲染把浏览器带来的 Cookie 原样转发给后端（API-8、T15）。

跨站请求伪造：
- 防护用 NestJS 自带的，要求 NestJS 12.1 起（API-11）。
- 先看 Sec-Fetch-Site。没有这个头，再比 Origin 与 Host（API-11）。
- GET、HEAD、OPTIONS 放行。所以这三种方法不得改数据（API-11）。
- 其余方法都要过这道检查，含部分更新用的 PATCH（API-11、API-50）。
- 被拒回 403，性质为「跨站被拒」，见本节第 6 小节（API-11、API-29）。
- 这道检查排在中间件与 Guard 之前（API-23）。
- 服务端渲染只发读请求（API-48）。
- 写请求一律从浏览器经 api client 发。本版不用 Next.js Server Actions（API-48）。
- SameSite=Lax 拦跨站的 POST、PUT、PATCH、DELETE（API-9、API-50）。
- SameSite=Lax 只作纵深防护，不替代这道检查（API-9）。
- 本地经 rewrites 转发后，Set-Cookie 与 Sec-Fetch-Site 是否原样，Lec 9 实测（API-12）。

身份与角色：
- 项目内角色由项目列表的每一项与项目详情下发，带「我在本项目的角色」（API-34、ARCHITECTURE 第二节决策 Q1）。
- 执行者拿到的项目信息，照 PRD 审定决策 D11、D17（API-34）。
- 前端拿到的角色只用来渲染入口，不构成授权（决策 Q1）。
- 角色只在本次页面上下文内使用，不做跨页面长缓存（决策 Q1）。
- 每个受限接口由后端 Guard 自己查成员表判定。前端传来的任何角色信息都不信（决策 Q1）。
- 当前用户身份由单设的「当前用户」接口下发，返回当前用户的 id 与邮箱（API-34）。
- 刷新页面与服务端渲染都靠这个接口取身份（API-34）。
- 注册、登录成功的响应带同一个用户形状，见第 5 小节（API-34、API-53）。
- 「当前用户」接口的路径、所属模块与 schema 名，随第二节接口清单定（API-34）。

### 4. 请求格式

媒体类型：
- 有请求体的接口只收 `application/json`（API-27）。
- 比对时忽略媒体类型的参数，`application/json; charset=utf-8` 也收（API-51 第三点）。
- Content-Type 不对，回「格式不支持」（API-27）。
- 这道检查用拦截器做，排在 Guard 之后、Pipe 之前（API-46）。
- 几种退回同时成立时谁先回，见第 6 小节（API-46）。
- 框架会不会在 Guard 之前自己回 415，未核。写后端代码时实测（API-27、API-46）。
- 「格式不支持」只看 Content-Type。请求体不是合法 JSON，回「参数不合法」，见第 6 小节（API-46、API-47）。

命名与校验：
- 字段名与查询参数名用 camelCase（API-22、ARCHITECTURE 第二节「命名规范」）。
- 这一条偏离主参考 Zalando 第 118、130 条，理由见「偏离登记」（API-22）。
- 请求体与查询参数的形状和类型，由后端自写的 Zod 管道按共享 schema 校验（T1、T3）。
- 校验不过，回「参数不合法」（API-14）。

多余字段：
- 请求体出现 schema 没列的字段，一律拒绝，回「参数不合法」（API-31）。
- 外壳用 ValidationProblemDetails，逐项列出多出来的键（API-31）。
- 不照 Zod 的默认把多余字段静默剔除（API-31）。
- 查询参数里出现 schema 没定义的参数，同样拒绝，回「参数不合法」，外壳与列法同上（API-56）。

必填与空白：
- 必填文本字段照下面两条处理。适用哪些字段、最大长度多少，归 schema（API-1、API-32）。
- 去掉首尾空白后为空的，按没填处理，回「参数不合法」（API-32）。
- 存的是去掉首尾空白后的值（API-32）。
- 密码不照上面两条：原样收，不去首尾空白，也不截断（API-32 补充，问 576 A）。
- 去空白在哪一层做，见 BACKLOG 79（ADR-DB-008）。

没传与 null：
- 新建接口里，可空字段没传与传 null 同义，都表示空（API-54）。
- 如新建任务不带负责人，和负责人传 null 一样（API-54）。
- 更新接口照 JSON Merge Patch（RFC 7396）的规则：没传的字段不改，传 null 表示清空（API-33）。
- null 只对可空字段有效，如任务的负责人、截止日期（API-33）。
- 对不可空字段传 null，回「参数不合法」（API-33）。
- 负责人把任务改回未分配，就是把负责人传 null（API-33、PRD 审定决策 D16）。
- 哪些字段可空，归 schema（API-1）。
- 更新请求仍只收 `application/json`，不用 RFC 7396 登记的 `application/merge-patch+json`。偏离理由见「偏离登记」（API-33、API-27）。

方法：
- 部分更新用 PATCH，请求体照上面的更新规则（API-50、API-33）。
- 整个替换一个资源用 PUT（API-50 补充，问 588 A）。

时间格式（请求与响应通用）：
- 时间点一律用 UTC，照 RFC 3339 写（API-41）。
- 日期与时刻之间用大写 T，结尾用大写 Z，如 `2019-07-30T06:43:40.252Z`（API-41）。
- 截止日期是纯日期，写成 `YYYY-MM-DD`，不带时刻与时区（API-41、ADR-DB-003 修订）。
- 本版没有接口收时间点。以后要收，也只收以 Z 结尾的写法（API-41）。

邮箱：
- 邮箱存用户输入的原样，只去掉首尾空白（API-55）。
- 注册查重、登录、按邮箱邀请成员时，整个地址不分大小写比较（API-55）。
- 这条规则由数据库列类型兜住：users.email 用 citext，带唯一约束（API-55、ADR-DB-008）。
- 三个入口照常按邮箱查，不各自处理大小写（ADR-DB-008）。

### 5. 成功响应

形状：
- 成功响应不加统一外包装（API-18）。
- 成功响应的媒体类型是 `application/json`（API-51 第二点）。出错时见第 7 小节。
- 单个资源直接返回对象（API-18）。
- 列表接口顶层也返回对象，数组放在其中一个字段里（API-18）。
- 这个字段叫什么归 schema，由 05-类型 定（API-18）。
- 响应里的时间格式见第 4 小节（API-41）。
- 前端解析响应时，容忍多出来的字段（API-31）。

状态码：
- 读取、更新成功回 200，带资源（API-25）。
- 转让负责人是例外：成功回 204，不带内容（API-52）。
- 转让成功后，前端重新取项目信息，按调用者的新角色渲染（API-52、API-34）。
- 新建成功回 201。响应体带新资源和它的 id（API-25）。
- 新资源有能读的地址时带 Location 头，没有就不带，如注册（API-25 补充，问 590 A）。
- 成功但没有内容回 204，如登出（API-25）。

注册与登录：
- 注册成功回 201，响应体带新建的用户（API-53）。
- 登录成功回 200，响应体带当前用户（API-53）。
- 登录虽然新建会话，仍回 200，不回 201（API-53）。
- 两处的用户形状与「当前用户」接口相同（API-53、API-34）。
- 注册、登录都新建会话。会话凭据只经 HttpOnly Cookie 下发（API-53、API-8）。
- 响应体里从不出现会话或它的 id（API-53）。

列表：
- 列表本版不分页，一次返回全部（API-40）。
- 后端按 id 升序返回，只为每次顺序一致（API-40）。
- 按截止日期排序、筛选在前端做（API-40）。
- 顶层是对象，以后加分页不改响应形状（API-40、API-18）。
- PRD 假设账本的规模被推翻时，加游标分页，见 BACKLOG（API-40）。

### 6. 退回性质与状态码

各层出错只抛退回性质，不直接写状态码（API-23）。
全局异常过滤器在一处把性质翻成状态码，照的就是下表（API-23）。
实现落点见 ARCHITECTURE 第二节「后端分层」第 6 条（API-23）。

| 退回性质 | 状态码 | 什么时候 | 依据 |
|---|---|---|---|
| 未登录 | 401 | 凭据缺失或无效；登录时凭据错 | API-14、API-16 |
| 看不见 | 404 | 项目不存在或不是成员；任务不存在、不属于本项目或不属于自己；路径 id 转不成数字；路径不存在 | API-15、API-21、API-47、T2、决策 B |
| 不许做 | 403 | 看得见，但这个动作不许做，如执行者调负责人专用的「改任务」接口 | API-14、API-21、API-35 |
| 跨站被拒 | 403 | 跨站请求伪造检查不过 | API-11、API-29 |
| 参数不合法 | 400 | 请求本身不合法，或它引用的别的资源不符合要求；如形状或类型不符、多出 schema 没列的字段、必填项去空白后为空、对不可空字段传 null、请求体不是合法 JSON、assignee 不是本项目成员 | API-14、API-31、API-32、API-33、API-38、API-47、T1、T5、决策 E |
| 冲突 | 409 | 与目标资源（或它所在集合）的当前状态冲突；如邮箱已被使用、已在项目中、唯一负责人移出自己；含并发写入撞上唯一约束 | API-14、API-28、API-37、API-38 |
| 格式不支持 | 415 | 有请求体，但 Content-Type 不是 `application/json` | API-27 |
| 内部错误 | 500 | 过滤器认不出的错误 | API-14、API-23 |

- 400 与 409 按目标资源分（API-38）：
  - 请求与它要新建、修改、删除的资源（或该资源所在的集合）的当前状态冲突，回 409「冲突」。
  - 请求本身不合法，或它引用的别的资源不符合要求，回 400「参数不合法」。
- 不用 422（API-14）。
- 框架自己拦下的退回（不是本项目代码抛的），能对上现有性质的就并进去（API-47）：
  - 路径不存在，算「看不见」（404）。
  - 请求体不是合法 JSON，算「参数不合法」（400）。
- 对不上的保留标准码，type 用 `about:blank`，见第 7 小节（API-47、API-14）。
- 两种都由后端收成第 7 小节的外壳（API-17）。
- 网关错误不经后端，不带本项目外壳（API-14）。
- 回 401 必须带 WWW-Authenticate 头，方案名为 `Session`（API-20）。
- challenge 只写方案名，不带 realm（API-51 第五点）。
- 这个方案名没在 IANA 登记，理由见「偏离登记」（API-20）。
- 并发写入撞上唯一约束时，由该表的 Repository 翻成「冲突」（API-28）。
- 注册时邮箱已被使用照回「冲突」：PRD「US-A01 用户注册」要求提示「该邮箱已被使用」；登录另行防枚举（API-16），两处有意分开。

改任务的两个接口（API-35）：
- 字段级权限变成路由级：改任务拆成负责人专用的「改任务」与两种角色都能调的「改状态」。路径随第二节接口清单定。
- 执行者调「改任务」，由 AuthzGuard 按角色回「不许做」（API-35）。
- 执行者用「改状态」改不分给自己的任务，回「看不见」。归属在 Service 里先判（API-35、API-15）。
- 往「改状态」多带别的字段，按多余字段回「参数不合法」，不回「不许做」（API-35、API-31）。

谁先回（API-46）：
- 几种退回同时成立时，先拦的先回。依次是：跨站检查、AuthGuard、AuthzGuard、Content-Type 检查、Pipe、Service。
- 不是成员的请求，不论 Content-Type 对错，都先回「看不见」（API-46、API-21）。
- 请求体由框架在 Guard 之前解析，不在上面的顺序里。不是合法 JSON 回「参数不合法」，项目在不在都回同样的 400（API-46、API-47）。
- 所以没登录时发来不合法的 JSON，先回「参数不合法」（400），不回「未登录」（401）。前端靠 401 跳登录页，这种情况跳不了（API-46 补充，问 592 A）。
- 解析时机写后端代码时实测（API-46）。

### 7. 错误外壳

- 所有接口出错都回 RFC 9457 形状，媒体类型为 `application/problem+json`（API-17）。
- 框架自带的退回，也由后端收成这个形状（API-17）。
- 外壳的 schema 名为 ProblemDetails（API-3、API-17、API-30）。
- 外壳表达五样东西，各给前端的用处如下（API-3、API-17）：
  - type：机读的问题类型。前端按它出中文提示（API-19）。
  - title、detail：文字说明。只作开发排查与兜底（API-19）。
  - status：状态码（API-17）。
  - instance：这一次出错的编号。生成规则见下面（API-26）。
  - 扩展部分：需要时加，如 400 时的逐项问题（API-17）。
- instance 由全局异常过滤器在每次出错时生成：一个随机 UUID，用第 4 版，写成 `urn:uuid:` 开头（API-26、API-23；版本见 API-26 补充，问 594 A）。
- 同一编号写进服务端日志。日志怎么记，留到讲可观测性那一课（API-26）。
- instance 的生成规则归本文件，schema 只定它是字符串（API-51 第一点）。
- 带逐项问题的 400 外壳，schema 名为 ValidationProblemDetails（API-17、API-30）。
- type 的字面值归共享 schema，名为 ProblemType（API-24、API-30）。
- 以上三个名字只定主体。写不写 Schema 后缀，照 05-类型 的命名规则（API-30）。
- 关于 type，本文件只定两件事：「退回性质 → 状态码」的映射，见本节第 6 小节（API-24）；`about:blank` 什么时候用，见下一条（API-47）。
- 框架拦下的退回对不上现有性质时，type 用 RFC 9457 登记的 `about:blank`，title 照该状态码的标准短语（API-47）。
- `about:blank` 这个字面值同样收进 ProblemType（API-24、API-47）。
- 401 的外壳不附任何字段指向（API-17）。
- 登录失败不区分是邮箱错还是密码错（API-16）。
- 不暴露堆栈（API-17）。

### 8. 前端怎么读退回

- 给用户看的中文提示，由前端按 type 出（API-19）。
- 前端不能指望每个出错响应都是 problem JSON（API-19）。
- 收到网关错误，按加载失败处理（API-14）。
- type 为 `about:blank` 的退回，出通用提示（API-47）。
- 「看不见」和「不许做」，界面上都显示「权限不足」（API-4、API-21）。
- 路径不存在也算「看不见」，所以前端打错路径时，界面同样显示「权限不足」（API-47、API-21）。
- 「跨站被拒」有单独的 type，前端另出提示（API-29）。
- 在登录页收到 401，显示「邮箱或密码不正确」（API-16）。
- 不在登录页收到 401，跳登录页（API-16）。
- 提交前的校验提示本来就在前端，不靠后端的 title、detail（API-19）。

### 9. 所有响应共有的头

- 所有接口的响应一律带 `Cache-Control: no-store`，含登录、注册（API-44）。
- 成功与出错都带（API-44）。
- 由后端统一加，不靠各接口自己写（API-44）。
- 挂在哪一层，写后端骨架时定。要盖住在中间件之前就退回的跨站被拒（API-44、API-23）。
- 也要盖住第 6 小节说的框架退回，如路径不存在、请求体不是合法 JSON。网关错误不经后端，不带这个头（API-44 补充，问 596 A）。
- no-store 只作多一层保护，不能单靠它保密（API-44）。

## 二、接口清单

本节列出本版全部 17 个接口，按代码所在的模块分组。每个接口写七样：方法与路径、鉴权级别、请求的 schema、响应的 schema、成功码、可能的退回性质、依据。退回只写性质，状态码照第一节第 6 小节的映射表；要靠专门的 type 才分得开的退回，标「专门的 type」，字面值归 ProblemType，本节不写。没标的，与同一性质的其他退回共用一个 type（API-24 补充，问 611 A、627 A）。

第一节写过的不再重复（API-1）。第 1 到 3 小节是各接口共用的读法，第 4 到 6 小节逐个列接口，第 7 小节列本版没有接口的部分。

### 1. 鉴权级别

- 公开：不挂 AuthGuard。只有注册、登录两个接口（API-8 补充）。
- 只要登录：只挂 AuthGuard。路径里没有项目 id 的接口用这一档。AuthzGuard 要拿路径里的项目 id 查成员表，没有就判不了（API-2）。
- 本项目成员：挂 AuthGuard 与 AuthzGuard，负责人、执行者都放行。执行者只能碰分给自己的任务，这一条由 Service 判，判不过回「看不见」（API-35、API-42）。
- 只有负责人：挂 AuthGuard 与 AuthzGuard。执行者调用，由 AuthzGuard 回「不许做」（API-35、API-42）。

### 2. 各接口共有的退回

下面几种，各接口不再列。几种同时成立时谁先回，见第一节第 6 小节「谁先回」（API-46）。

- 内部错误：全部接口（API-14）。
- 看不见：路径不存在（API-47）。路径带项目 id 的接口，还有三种：项目不存在、调用者不是本项目成员、路径 id 转不成数字（API-15、API-21、决策 B）。
- 未登录：公开接口以外的全部接口（API-14）。
- 跨站被拒：GET 以外的全部接口。专门的 type（API-11、API-29）。
- 格式不支持：带请求体的全部接口（API-27）。
- 参数不合法：带请求体的全部接口。有四种：形状或类型不符；多出 schema 没列的字段，含请求体多带项目 id；必填项去空白后为空；请求体不是合法 JSON（API-14、API-31、API-32、API-47、决策 D）。GET 接口带了 schema 没定义的查询参数，也回这一种。本版 GET 接口都不收查询参数（API-56）。
- 冲突：写接口在并发下撞上数据库唯一约束（API-28）。撞的是注册、邀请成员那两条唯一约束的，回各自那一种专门的 type；撞的是「每个项目至多一个负责人」的（ADR-DB-006），回冲突的默认 type（API-28 补充，问 630 A）。

### 3. schema 名字

- 只定名字主体。写不写后缀，照 05-类型 为全部 schema 定的命名规则（API-1、API-30）。
- 请求体的名字写成「动作 + 资源 + Request」。动作跟着方法走：POST 写 Create，PATCH 写 Update，PUT 写 Replace（API-30 补充，问 626 A）。
- 响应用资源名。列表接口顶层是一个外壳对象，数组放在外壳的哪个字段里，归 schema（API-18）。
- 列表接口响应的外壳写成「List + 资源复数 + Response」，如 ListProjectsResponse（API-30 补充，问 631 A）。
- 列表的每一项与这个资源的详情同一形状，用同一个名字（API-30 补充，问 628 A）。
- 一个资源按调用者角色给不同形状时，仍用一个名字。几种形状在 schema 里怎么写，归 05-类型（API-30 补充，问 629 A）。
```

```
## 二、偏离登记

- 会话期限（API-10）：固定 30 天、无空闲超时，偏离 OWASP 会话管理「should implement an idle or inactivity timeout」与「absolute timeout」。理由：PRD D7 经项目主人确认；空闲超时要求读请求写 sessions，会推翻 T4；补救为登出即删服务端会话、角色改即时生效、Cookie 加 HttpOnly 与 Secure。将来风险变高时加空闲超时，见 BACKLOG。
- 401 认证方案名（API-20）：自定方案名 Session 没在 IANA HTTP Authentication Scheme Registry 登记，RFC 9110 第 11.1 节写的是「ought to be registered」，属建议档。理由：登记表 14 个方案里没有会话 Cookie 类的；登记要走 IETF 评审，本项目不对外提供接口，唯一调用方是自家前端，前端不读这个头（API-6）。核对 2026-10-15。
- 字段命名（API-22）：API 字段名与查询参数名用 camelCase，偏离 Zalando 第 118 条「MUST property names must be snake_case (and never camelCase)」与第 130 条（查询参数同）。理由：同层另一家主流规范微软 Azure 要求「DO use camel case for all JSON field names.」；Zalando 第 118 条自述「No established industry standard exists」；本项目前后端与 Prisma 都用 TypeScript，全链路不做命名转换（ARCHITECTURE 第二节「命名规范」）。核对 2026-10-15。
- 部分更新的媒体类型（API-33）：照 RFC 7396 的规则处理 null 与没传，但请求只收 application/json，不用它登记的 application/merge-patch+json。理由：唯一调用方是自家前端（API-6），换媒体类型要修订 API-27、改前端 api client，收益只是类型名对得上，规则本身照 RFC 7396 走。核对 2026-10-16。
- 只有一个的子资源用单数（API-57 修订）：本项目的负责人、任务的状态、项目的汇总写单数，偏离 Zalando 第 134 条「The special case of a resource singleton must be modeled as a collection with cardinality 1」（必须）。理由：同一层另一家 Google AIP-156（https://google.aip.dev/156，状态 Approved）「Singleton resources are always singular.」；照复数写，两个写接口的请求体要多一层只含一个元素的数组，改状态还要把 PATCH 改成 PUT，「状态们」会被读成状态的历史；唯一调用方是同仓同发的自家前端（API-6），将来放开多负责人时改路径代价小。核对 2026-10-23。
- 邮箱不分大小写用 citext（ADR-DB-008）：没照 PostgreSQL 文档 citext 一页「Consider using nondeterministic collations (see Section 23.2.2.4) instead of this module.」改用不区分大小写的排序规则，属建议档。理由：排序规则有性能代价、部分模式匹配用不了、要手写 SQL；citext 写得进 schema，注册查重、登录、按邮箱邀请成员三个入口照常查（问 572 A）。代价是多依赖一个 PostgreSQL 扩展，比较随数据库的 LC_CTYPE（BACKLOG 80）。核对 2026-10-28。
```

```
## ADR-DB-006 · 每个项目至多一个负责人：部分唯一索引兜底
- 背景：PRD 审定决策 D4、D10 定首版单负责人，负责人经转让交接；D10、D14 不许唯一负责人直接降级或被移出。只靠应用逻辑，并发写入可能写出两个负责人。

## ADR-DB-007 · 任务的分配时间：可空列 assigned_at
- 背景：PRD 审定决策 D13 定「可能卡住」从最近一次状态变化与最近一次分配两者中较晚的那个起算。tasks 只有 status_updated_at，分配时间没处记（ADR-DB-005 修订行交给第 3 组 architect）。
- 决策：tasks 加可空列 assigned_at（Prisma 字段 assignedAt，@db.Timestamptz(6)），不设默认值，不加索引（问 459 A）。只和当前负责人比：创建时带负责人写创建时间，不带为空；换负责人写当前时间；改回未分配（PRD 审定决策 D16）清空；移出成员（D14）在同一事务里把名下任务的负责人与本列一起清空；分给当前负责人不动（问 465 A，与 PRD 澄清注记 12、API-39 同一口径）。改状态、标题、描述、截止日期都不动它。只由后端写，请求体带它按 API-31 拒绝。改前经 architect 确认不挡路。
- 后果：「可能卡住」由后端按本列与 status_updated_at 较晚者算（API-43）。不存分配历史，与 ADR-DB-005「只存当前状态」一致。残留：删用户时外键 SetNull 清了负责人却不清本列，「有负责人才有分配时间」会被打破；本版不设删用户入口，碰不到，不加数据库检查约束（问 464 B，加了会让删用户撞约束，悄悄推翻 ADR-DB-004）。判定先看有没有负责人，不拿本列非空当「已分配」。将来做删用户时一起处理。

## ADR-DB-008 · 邮箱不分大小写的唯一约束：users.email 用 citext
- 背景：API-55 定邮箱存用户输入的原样（去掉首尾空白后），注册查重、登录、按邮箱邀请成员时整个地址不分大小写比较，并要求数据库有不分大小写的唯一约束。users.email 原为 String @unique，区分大小写。Prisma 版本未锁（BACKLOG 74）。库还没建，没有数据要迁。
- 决策：users.email 改用 PostgreSQL 的 citext 类型（Prisma @db.Citext），保留 @unique（问 572 A）。扩展的启用照 ADR-DB-006 的做法随 BACKLOG 74 定：锁的版本支持 datasource 的 extensions 就写进 schema，否则在建 users 表的迁移开头手写 CREATE EXTENSION。查询照常按邮箱查，不用 mode。去掉首尾空白不归本约束管，在哪一层做见 BACKLOG 79。改前经 architect 确认不挡路。
- 后果：大小写规则落在列类型上，三个入口不用各写一遍；撞约束按 API-28 回 409。代价：多依赖一个 PostgreSQL 扩展，换库要改写；比较随数据库的 LC_CTYPE，库的区域设置要在环境设计里定死（BACKLOG 80）。放弃了 PostgreSQL 文档建议考虑的不区分大小写的排序规则（有性能代价、部分模式匹配用不了、要手写 SQL），放弃了 lower(email) 唯一表达式索引（schema 写不出、三个入口查询都要特殊写），也放弃了小写影子列（多一列，数据库不保证两列一致，不算满足 API-55，问 573 甲）。锁版本后的实测见 BACKLOG 74。
- 后续（补课 05-API，问 648 A）：后果里放弃不区分大小写的排序规则这一处，偏离的是 PostgreSQL 文档的建议，登进 docs/arch/STANDARDS.md「偏离登记」，理由以那里为准；登记表同时加「数据库与 ORM」一行。上面原文不改。
```

## 六、Claude Code 知识点

这一章第一次用到四样。每样讲：是什么，原理，怎么用，什么时候不用。子代理怎么派，`/tasks` 和 `Ctrl+O` 怎么看全文，05-ARCH 一章第六节讲过，这里不重复。

### 从记录文件里取子代理的全文

**是什么。** 子代理跑过的每一步，都记在磁盘上的一个文件里。官方子代理页写的位置是 `~/.claude/projects/{project}/{sessionId}/subagents/`，文件名是 `agent-{agentId}.jsonl`。

**原理。** 子代理交回主对话的是摘要，要一字不差的东西，得回记录里取。这个文件一行一条记录，第一条是派单，最后一条带文字的是它的回报。官方写明，主对话压缩不影响这些记录。但它们不是永久的：到了 `cleanupPeriodDays` 这个保留期就删，默认 30 天。它们也不在仓库里，换一台机器就没有。

**怎么用。** 第四节收的派单原文，就是这样取的。下面这段打印派单的第一行，再数回报有多少字符。把「记录文件的路径」换成你的：

```
python3 - 记录文件的路径 <<'EOF'
import json, sys
rows = [json.loads(line) for line in open(sys.argv[1], encoding="utf-8")]
def text(row):
    content = row.get("message", {}).get("content", "")
    if isinstance(content, str):
        return content
    return "".join(b.get("text", "") for b in content if b.get("type") == "text")
said = [r for r in rows if r.get("message", {}).get("role") == "assistant" and text(r).strip()]
print("派单第一行：", text(rows[0]).splitlines()[0])
print("回报字符数：", len(text(said[-1])))
EOF
```

应该看到两行。第 1 步那次派单，跑出来是：

```
派单第一行： 先读你的定义文件 .claude/agents/architect.md，确认身份、职责、边界，再开始干活。
回报字符数： 16267
```

要数它调用了几次工具，按调用的 id 去重。同一次调用，记录里可能存了两遍。要留的东西，当场存进仓库，别等它过期。

**什么时候不用。** 只想看一眼它做了什么，`/tasks` 或 `Ctrl+O` 就够。要进仓库、要进书、要逐字比的，才回记录里取。

### 一轮一件

**是什么。** 派给子代理的一次任务，只要一样交付物。

**原理。** 官方子代理页的最佳实践第一条是「each subagent should excel at one specific task」。这句说的是定义角色，派单是同一个道理。每个子代理都从全新的上下文开始，只看得到派单。一次要太多，它跑得久，中途断了什么也留不下，交回来的东西也不好审。补课 05-ARCH 时有过一次（反模式 38 号）：一次派单同时要核对、结论、取舍和草稿，跑了六分钟没完，中断以后全丢。

**怎么用。** 写派单前先问一句：这一轮交回来的是什么。第 6、7 步和第 9 步的两轮都是这样分的。核对轮只交冲突和待拍的项，不起草。拍完再开起草轮，只交正文。

**什么时候不用。** 一样交付物里分几块，不算几件。第 6 步的核对报告分六块，还是一件。

### 取网页原文

**是什么。** WebFetch 工具。给它一个网址和一段要求，它去取网页。

**原理。** 官方工具参考页写明，多数时候它用另一次模型调用，照要求处理页面。Claude 收到的是处理的结果，不是原始页面，所以官方说它「lossy by design」。它说页面里没提某件事，可能只是要求里没问到。每次最多读 100,000 字符。

**怎么用。** 这一章称「标准」的地方都要原文。做法是在要求里写明逐字引用（verbatim），一句一句要。长页看结果里的提示，带 `offset` 接着读。官方给的另一条路是用 `curl` 取未处理的页面；本项目把 `curl` 放在禁止一档，所以走前一条。

**什么时候不用。** 只要大意、不引原文时，不必一句一句要。本机的地址它也不取：官方写明它拒绝 `localhost` 和不带点的主机名。

### 推理强度与用量

**是什么。** 两样放在一起讲。`/effort` 调推理强度。`/context` 看上下文用了多少。

**原理。** 官方模型配置页写的是：强度决定模型每一步要不要想、想多少，「Each level trades token spend against capability」。强度越高，想得越深，用量越多。官方费用页写的是：用量随上下文增长，每次请求都带上整段对话。所以同一句话，在长会话里比在新会话里用得多。

**怎么用。** `/effort` 不带参数，弹一个滑杆。官方列的档位是 `low`、`medium`、`high`、`xhigh`、`max`，不同模型支持的不一样。滑杆上按回车，或者直接敲 `/effort xhigh`，会存成默认，以后的会话也用。滑杆上按 `s`，只管这一次。`max` 只管当前会话。这一章后面几个窗口，主对话用 Opus、强度 `xhigh`。

`/context` 显示用了多少。这一章写第五节之前，一次看到的是 `531k/1m tokens (53%)`。定下一步写多少时，把先查和后写都算上。这一章估错过一次：只算了要写的原文，漏了要先查 `git diff` 的那部分。

**什么时候不用。** 搬运的活用不着高强度。官方说低档「faster and cheaper for straightforward tasks」。不过一连串小活中间夹着要想的活，来回切并不省事。

## 七、常见的坑

这一章踩过的，挑八件。编号是反模式库里的条号，没写编号的，反模式库里还没有单独立条。出了错的固定动作，上半章第七节讲过，这里不重复。

### 40 号的又一例　同类没列全

**长什么样。** 接口清单起草前，定「只有一个的子资源也写复数集合」，推荐理由是代价只落在一个接口。这里只数到了项目的负责人。核对轮查出，任务的状态和项目的汇总也是只有一个的子资源，理由站不住，只好重拍，改成单数。同一份派单还把 schema 名字划错了地方，鉴权级别也漏了公开那一档。

**怎么防。** 写派单、出推荐、扫传播面之前，先把同类的东西列成全集，再逐个过。鉴权一共几档，只有一个的子资源有哪几个，那一行摘了哪几条。

### 37 号的又一例　出推荐之前没搜旧裁决

**长什么样。** 定截止日期的口径前，只搜了需求文档和 UI 设计，没搜课堂记录和书。定下来才发现，和第 5 课定的截止时间口径相反，而题目里没写会推翻哪一条。

**怎么防。** 出推荐之前，先搜决策记录和旧材料，看有没有拍过相反的口径。要推翻旧的，题目里写明推翻哪一条。

### 核过一句，不等于核过整节

**长什么样。** 需求文档原来写「至少 8 位，含字母和数字」。对 OWASP 时只核了「不该要求字母和数字」那一句，只报了这一处打架。后来把整节取回，又多出一处：没开多因素认证时，少于 15 位算弱。8 位这个数也站不住。

**怎么防。** 拿标准核一条规则，把规则所在的整节取回来读。一句对上了，只说明这一句对上了。

### 子代理给的判据，要拿现有例子套一遍

**长什么样。** architect 给了一条判据，用来分 400 和 409。判据读着很顺，套上「邮箱已被使用」这个现成的例子，结果和现行口径相反。后来改用 RFC 9110 的「目标资源」来划线。

**怎么防。** 子代理给判据，先拿手上已有的例子逐个套一遍。有一个套不上，判据就要改。

### 推荐也要对标准原文核

**长什么样。** 第 1 步 architect 第一轮的推荐，有六处和标准对不上。读着都有道理，对了原文才看出来。

**怎么防。** 推荐里说「标准是这样」，就把原文取回来对，给出处。没核过的标「未核」。子代理给的也一样。

### 46 号的又一例　核对命令自己写错

**长什么样。** 四样。要数的原文以「- 」开头，`grep` 把它当成选项，没数出数。`grep -c` 数到 0 次时退出码是 1，接在 `&&` 后面，后面的命令不跑了。按旧行号切文件去比，行号已经挪了，报不相同。用 `sort -V` 排好交给 `comm`，`comm` 要字典序，结果作废。

**怎么防。** 原文以「- 」开头的，`grep` 加 `-e`。写正则的核对命令，先拿造的样本跑一次，抓得到再用。计数写成命令自己判，数不等就不提交。按标题定位，不按行号。整份改后的文件先拼进副本，落完逐字节比；核对命令写错时，这一道仍拦得住。

### 47 号　搜不到不等于没有

**长什么样。** 想把决策记录排除在搜索之外，用 `grep -v DECISIONS-R1` 按整行内容过滤，别的文件里引了决策记录的行也一起滤掉了。另一次只搜字面的「B 节」，漏了意思上指向它的一句「对应的节」。

**怎么防。** 说「没有」「只有这几处」之前，先想这个意思还有几种写法，逐种搜。排除文件按文件名，不按行内容。手上有一个已知应该命中的，先拿它核：搜不到它，说明搜法漏了。

### 偏离了标准，却没登记

**长什么样。** ADR-DB-008 定邮箱用 citext，放弃了 PostgreSQL 文档建议考虑的不区分大小写的排序规则。决策记录里写了放弃，标准登记表的偏离登记没写，登记表也没有「数据库与 ORM」这一栏。过了好几个窗口才补上。

**怎么防。** 拍板里引了一份标准，当场查登记表登没登。没登的同批补登；偏离了的，同批登进偏离登记。

## 八、小结与速查

- 接口上要定的事，先找标准。按层定先后，每个领域一份主参考，记进标准登记表。标准管怎么做，不管做多少。
- 每条标准分三档：必须、建议、可选。没照做的，理由写进偏离登记。
- 标准里的「必须」，常带着适用的门槛。用之前，先看门槛。
- 路径：前缀 `/api`，小写，连字符，资源名用复数，只写名词不带动词。只有一个的东西用单数，当前用户用 `self`。
- 凭据只放 HttpOnly Cookie，会话固定 30 天，跨站防护用 NestJS 自带的。
- 请求只收 JSON。多出来的字段、没定义的查询参数，一律拒绝。改一部分用 PATCH，整个换用 PUT。
- 成功不加外包装，成功码三个：200、201、204。
- 一个响应带什么，不只看接口规范怎么说，还要看此刻谁在看、他该看什么。
- 各层只说为什么退，状态码由全局异常过滤器在一处翻译。
- 「看不见」回 404，「不许做」回 403。请求本身不对回 400，和目标资源的现状冲突回 409。
- 几种退回同时成立，先拦的先回。
- 出错一律回 RFC 9457 的形状，不透露多余的东西。
- 所有响应一律不缓存。换一种技术方案，原来白送的保护可能就没了，要重新核一遍。
- 接口清单每个接口写七样；共有的退回只写一处；「本版没有接口的」也要列全。
- 产品口径回需求文档定，数据改动回 architect。
- 长文档分两轮：先核对，拍完再起草。拍一条登一条，拍完扫传播面。按小节落，落完逐字节比。
- 子代理的派单和回报，要留的当场存进仓库。记录默认 30 天就删。
- 验证命令先拿造坏的副本试，抓得到才用。

本章用到的命令：

| 命令 | 干什么 |
|---|---|
| `ls 文件 文件` | 核对前提：要用的文件都在 |
| `cmp 文件 副本; echo "退出码 $?"` | 逐字节比。相同时没有输出，退出码 0 |
| `sed -n '/^## 甲/,/^## 乙/p' 文件` | 取两个标题之间的一段，不靠行号 |
| `grep -cE '候选\|待定\|待确认'` | 数还有几行没定。数到 0 次时退出码是 1 |
| `git show 提交号^:路径` | 取一份文件删除之前的版本 |
| `python3 - 记录文件的路径` | 从子代理记录取派单和回报，第六节有全文 |
| `/effort` | 调推理强度 |
| `/context` | 看上下文用了多少 |

## 九、换个项目还用得上的

判断的标准只有一句：换个项目还用得上的，列在这里；只属于本项目的，不列。

- **标准方针与标准登记表。** 按层定先后，一个领域一份主参考，三档，偏离登记。
- **长文档分两轮写。** 核对轮只交冲突和待拍的项，起草轮只交正文。
- **分批拍板。** 拍一条登一条；拍完扫传播面，逐类写「要改」或「不影响」。
- **退回性质与状态码分开。** 各层只说为什么退，一处翻译。
- **「看不见」和「不许做」分开。** 不让对方知道它存在的，回 404；看得见但动作不许做的，回 403。
- **出错的统一外壳。** RFC 9457 的形状，401 带 `WWW-Authenticate`，一律不缓存。
- **接口清单的写法。** 每个接口七样，共有的退回只写一处，「本版没有接口的」也列全。
- **校验规则的起名。** 动作 + 资源 + Request，名字先定死。
- **按小节落，落完逐字节比。** 整份改后的文件先拼进副本，比副本。
- **产物的原文用命令导出，不手打。** 书里写的命令，从正文抠出来再跑一次。
- **验证命令先自测。** 拿造坏的副本试，抓得到才用。
- **子代理的记录当场存进仓库。** 平台默认的保留期一到，取不回。
- **四条核对的习惯。** 同类先列全集；判据拿现有例子套；推荐对标准原文核；核标准取回整节。
- **估用量把先查和后写都算上。**

只属于本项目、不往外带的：API-3 到 API-59 的具体裁决，17 个接口，需求文档审定决策 D10 到 D20，ADR-DB-006 到 ADR-DB-008。
