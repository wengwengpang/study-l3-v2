**核心讲解**

先打个比方。

你公司新来一个产品经理，叫 pm。他刚进门，桌上空空，没有职责说明书，没人告诉他归他管什么、不归他管什么。这种状态下让他干活，他只能瞎猜。

我们现在要做的，就是给他一份职责说明书。这份说明书就是 `.claude/agents/pm.md`。

**那 pm 这个角色，核心是什么？**

一句话：pm 是边界守护者。

普通人以为产品经理的活是"想功能"。错。好产品不是功能堆出来的，是砍出来的。pm 最值钱的动作，是对一堆需求说"这个不做"。没有这个守门人，需求会像野草疯长，最后什么都想做，什么都做不完。

所以 pm 的说明书里，"你不做什么"和"你做什么"一样重要。

**Level 1 对应（网页版你是怎么做 pm 的）**

在 Claude 网页版，你激活 pm 是这样：每次新会话，在 prompt 里写一长段"请你扮演有 10 年经验的 SaaS 产品经理，你的职责是……"。

那时的痛点有三个。
一，每开一个新会话就要重写一遍，重复劳动。

三，团队没法复用，只能互相拷贝 prompt 文本。

升级到现在：角色写进 `.claude/agents/pm.md` 一次，CC 自动加载，主对话保持干净，别人 `git clone` 项目就直接拿到这个角色。上面三个痛点一次全解决。

---

**先讲 PRD 是什么**

一句话:PRD 是产品的"施工图说明",写清楚要造什么、造到什么程度算完。

打个比方。

你要盖房子,不会直接喊工人开砌。你先给一张图纸,图上写明:三室两厅,主卧带飘窗,厨房通燃气。工人照图施工,验收时拿图对一遍,飘窗有没有、燃气通没通,一项项打钩。

PRD 就是这张图。它不写"怎么砌墙"(那是架构和代码的事),它写"要砌成什么样、怎么算砌好了"。

PRD = Product Requirements Document,产品需求文档。它是 pm 这个角色最核心的产出。

---

**再讲用户故事——PRD 的最小积木**

PRD 不是一篇散文,是由一块块"用户故事"拼起来的。

什么是用户故事?一句话:从用户视角描述一个需求,而不是从功能视角。

差别在哪?看一组对比。

功能视角写法:**"系统要有登录功能。"**
用户故事写法:**"作为一个团队成员,我想用邮箱和密码登录,以便进入我参与的项目。"**

后者多了什么?多了三样东西,这正是用户故事的固定公式:

> **作为 <谁>,我想 <做什么>,以便 <得到什么价值>。**

英文原版是 As a... I want... so that...。

为什么非要这个公式?因为它逼你回答"为什么"。

"系统要有登录功能"——为什么要登录?没说。
"以便进入我参与的项目"——价值写出来了。

一旦价值说不清,这个需求很可能就是多余的。这个公式是 pm 砍需求的第一把刀:凡是 so that 后面填不出真价值的,就该怀疑它该不该做。

⭐ **关键:用户故事的价值不在格式,在那个"以便"。它强迫你证明这个需求值得做。**

---

**最后讲验收标准——怎么算"做完了"**

用户故事说了"要什么",但还差一样:怎么算做到了。这就是验收标准。

一句话:验收标准是一组能客观判断"做没做完"的条件。

关键词是**客观**。看反例。

模糊的验收标准:**"登录要好用。"**
什么叫好用?你说好用,测试说不好用,吵架。没法验收。

可测的验收标准:
- 输对邮箱和密码,跳转到项目列表页。
- 密码错误,提示"邮箱或密码错误",停在登录页。
- 邮箱格式不对,提交按钮不可点。

这三条,每一条都能拿来测,结果只有"是"或"否",不会吵架。

业界常用一个格式来写,叫 **Given-When-Then**(给定—当—则):

> **给定** 一个已注册用户,**当** 他输入正确的邮箱密码,**则** 系统跳转到项目列表页。

这个格式好在哪?它把一条验收标准拆成三段:前提、动作、预期结果。写的时候不容易漏掉边界情况。

**证据契约是什么**

一句话:AI 说的每句"事实",都要能指回它从哪看来的,不许凭印象。

打个比方。

法庭上,证人不能说"我记得他当时在场"。法官要问:你怎么知道?你在哪看到的?几点?证人得拿出可核对的来源,否则那叫"传闻",不采信。

证据契约就是让 AI 当一个合格证人。它说"这个函数在 auth 模块定义",你可以要求它写成 `src/auth/login.ts:42`。你照着一翻,要么对,要么错,一翻便知。

**为什么需要它**

因为 AI 最危险的失败不是"不知道",是"不知道但编得像真的"。这就是你库里的反模式 18 号(CC 编造文件路径或 API)和 4 号(出错后编理由)。证据契约是这两个反模式的物理解药——你逼它给出处,它就编不动了,因为出处是可核对的,编的当场穿帮。

**什么时候用、什么时候不用**

这点很关键,不是每次都要证据,滥用会拖慢节奏。

要证据的场景:
AI 声称"现有代码里有 X"、"某文件里写了 Y"、"这个 API 的参数是 Z"。
凡是它声称在引用项目里已存在的东西,都该要出处。

不要证据的场景:
AI 在做创造性产出,比如现在 pm 写用户故事。
这时它是在"造新东西",不是"引用旧东西",没有出处可给。

⭐ **关键区分:证据契约管"引用",不管"创造"。引用旧的要出处,创造新的不需要。**
