- 框架自带的退回，也由后端收成这个形状（API-17）。
- 外壳的 schema 名为 ProblemDetailsSchema（名字待确认）（API-3、API-17）。

  - type：机读的问题类型。前端按它出中文提示（API-19）。
  - title、detail：文字说明。只作开发排查与兜底（API-19）。
  - status：状态码（API-17）。
  - instance：这一次出错的编号。服务端日志记同一个编号，写法见 API-26（API-26）。
  - 扩展部分：需要时加，如 400 时的逐项问题（API-17）。

- 登录失败不区分是邮箱错还是密码错（API-16）。
- 不暴露堆栈（API-17）。

### 8. 前端怎么读退回

- 给用户看的中文提示，由前端按 type 出（API-19）。
- 前端不能指望每个出错响应都是 problem JSON（API-19）。

### 议题 4：会话凭据用什么载体

**① 已定的与留给本课的**
- 鉴权用 DB session，不用 JWT（`TECH_STACK.md:34-36`；`CLAUDE.md:130`）。
- 服务端存的是令牌哈希，按哈希查 sessions（`ARCHITECTURE.md:285`）。客户端拿着的是原始令牌（推导）。
- 会话固定 30 天，不续期，纯读请求不写 sessions（T4，`ARCHITECTURE.md:275`、`:410`）。
- 关掉浏览器再打开，30 天内仍保持登录（`PRD.md:160`）。
- 登出立即失效（`PRD.md:167`）。角色改后即时生效，授权每次由 Guard 查表（`PRD.md:207`；`ARCHITECTURE.md:223`）。
- 注册成功后直接进入已登录状态（`PRD.md:147`），所以注册接口也要发凭据。
- 路由层负责登录态重定向和首屏取数（`ARCHITECTURE.md:198`；`TECH_STACK.md:18`）。
- SSR 取数要手工转发浏览器带来的凭据（T15，`ARCHITECTURE.md:529`、`:567`）。后端不会因为请求来自内网就放宽鉴权（`:530`）。
- 生产环境同域名（T14，`:566`）。生产有 TLS，本地没有（T20，`:572`、`:551`）。
- 会话存储将来可以换成 Redis，只换实现（`TECH_STACK.md:54`）。用什么载体和这件事无关（推导）。
- 留口：
  - 「凭据载体属 API 契约」（`ARCHITECTURE.md:280`）。
  - SSR 转发「待 05-API 定凭据载体」（`:584` 第 7 条、`:593`）。
  - 本地不同源时「会话凭据怎么带」还没定义（`BACKLOG.md:34`；`ARCHITECTURE.md:589`）。

**② 要定的问题**

登录或注册后，令牌放在浏览器的哪里；每次请求经什么通道带到后端，包括 SSR 转发时走什么通道。

**③ 候选**（Cookie 和请求头的行为属文件外知识）

| 候选 | 内容 | 象限 | 一句理由 |
| --- | --- | --- | --- |
| A | HttpOnly Cookie。有效期和服务端的 30 天对齐，固定不刷新。生产带 Secure，SameSite=Lax，Path 覆盖页面路径。SSR 从进来的页面请求里读出 Cookie，再转发给后端 | 右下 甜区 | 浏览器做页面导航时只会自动带 Cookie，不会带自定义请求头。只有它能让 SSR 路由层在首屏就知道登录态（`ARCHITECTURE.md:198`）。另外脚本读不到令牌 |
| B | Authorization 请求头加 Bearer 令牌，前端把令牌存在 localStorage | 左上 排除 | 页面导航不带这个头，SSR 路由层拿不到登录态，和 `ARCHITECTURE.md:198`、`TECH_STACK.md:18` 冲突。令牌能被脚本读到。浏览器的 WebSocket API 不能设自定义头，Lec 13 还得另想办法（`TECH_STACK.md:44-47`） |
| C | 双通道：浏览器走 HttpOnly Cookie；后端同时接受 Bearer 头，给 SSR 转发或将来的非浏览器客户端用 | 右上 权衡 | 所有约束都满足，但第二条通道今天没有消费方（`PRD.md:113`）。AuthGuard 多一条路，就多一处攻击面。SSR 用 Cookie 头转发同样可行，有更轻的 A |

推荐 A。理由：只有它同时满足三件事：SSR 首屏能判断登录态，关掉浏览器重开 30 天内仍保持登录，脚本读不到令牌。

选 A 之后会跟着来几件事（文件外知识，其中两处需实测）：
- 跨站请求伪造（CSRF）的口子打开了。SameSite=Lax 会拦住别的站点发来的改状态请求，前提是所有改状态的接口都不用 GET。这一条要写进全局约定。
- 本地不同源（BACKLOG 23）：
  - Cookie 不按端口隔离。localhost 的不同端口算「同站」，所以带凭据的跨源请求会带上 Lax Cookie。
  - 但跨源 fetch 还需要后端放行凭据、写明允许的来源；或者让本地变成同源（见 ④-3）。
- 本地 http 下的 Secure 属性：主流浏览器把 http://localhost 当安全上下文，允许 Secure Cookie。Safari 以前行为不同，需实测。稳妥做法是按环境配置，符合 T23「配置按环境不同」（`ARCHITECTURE.md:575`）。
- Path：如果 Path 限在 API 前缀下，页面导航就不带 Cookie，SSR 读不到。所以 Path 必须覆盖页面路径。
- 登出时：服务端删掉会话记录，同时在响应里让浏览器清掉 Cookie。

**④ 该主人拍的取舍**
1. CSRF 防护做到什么程度。属 D3（`CLAUDE.md:158`）。
   - 甲：只靠 SameSite=Lax，再加一条「改状态不用 GET」。我推荐这个。理由：单域名、没有子域名（假设，文件里没写子域名），Lax 已经覆盖跨站场景；按 `TECH_STACK.md:4` 不提前堆。

## 三、「先降后升」会不会被唯一索引的检查时机挡住

**结论（推导）：不会挡。** 前提是写成两条独立的 UPDATE，先降后升。
- 第一条执行完，这个项目里没有负责人，索引不管。
- 第二条执行完，正好一个负责人。
- 任何时刻都不会出现两个负责人，所以逐行检查还是语句末检查都无所谓。
- 中间「零负责人」的状态在事务内，读已提交隔离级别下别的事务看不见。

两种写法会撞：
- 先升后降。
- 用一条 UPDATE 同时改两行（比如 `CASE`）。如果数据库是逐行检查，能不能成功取决于先改哪一行。

**延迟检查（全部未核）：**
- 据我记忆，PostgreSQL 非延迟的唯一约束是逐行立即检查，不是 SQL 标准说的语句末检查。
- `CREATE UNIQUE INDEX` 没有 DEFERRABLE 子句。
- 部分索引不能经 `ADD CONSTRAINT ... USING INDEX` 升格为约束，所以部分唯一索引不能延迟。
- 真要延迟，替代是 `EXCLUDE ... WHERE (...) DEFERRABLE`，Prisma 同样表达不了。按上面的结论，本项目用不到。

**含取舍、我没替主人选的细节（问 439 C 的锁）：**

**二，冲突与缺口**
1. 冲突：故事写「无进展」，验收写「无更新」。两词对应不同字段。
2. 缺口：「已完成」的任务要不要排除。PRD 没写。
3. 缺口：未分配任务按 US-02a 第一条验收应标「未认领」，而不是「卡住」。一个任务能不能同时挂两个标记，没写。
4. 缺口：长期未认领的任务一旦被分配，若按 `statusUpdatedAt` 计，因为它仍停在创建时的值，分配当天就会立刻被判「可能卡住」。
5. 缺口：天数的具体值、全局还是按项目、日历日还是工作日。时区和时间格式在 API:94 也还是「待第 3 组定」。

**三，选项**

A. 判定字段用 `statusUpdatedAt`：只有状态变化重置计时。
- 规则：已分配、未完成、距上次状态变化超过 N 天，标「可能卡住」。
- 负责人：改描述、改截止日期不会让任务「假装有进展」。
- 缺点：见缺口 4，旧的未认领任务一分配就立刻被标卡住。
- 牵动表结构：无。

B. 判定字段用 `updatedAt`：任何修改都重置计时。
- 负责人：改一下截止日期或描述，卡住标记就消失，会掩盖真实停滞。
- 不存在缺口 4。
- 牵动表结构：无。

C. A 加「被分配或更换负责人时重新计时」。
- 规则：以「最近一次状态变化」与「最近一次分配」中较晚者为起点。
- 负责人：新分配的任务从分配日起算，更符合直觉。
- 落进 PRD：US-02a 验收（PRD:62）加三条：计时起点、已完成不计、「未认领」与「卡住」互斥。
- 牵动表结构：此处不确定，可能需要新字段，也可能由写入 `statusUpdatedAt` 的口径变宽解决，归 architect。

**四，推荐：C。**
- 理由：A 有缺口 4 这个明显的误报，B 会被无关编辑洗掉信号，C 只补一条最小规则。

  3. 「已分配但从未开始」算不算卡住。我倾向算。

# 报告：tasks 加「分配时间」列的写法确认（问 459 A 落地前核对）

## 〇、适用标准（docs/arch/STANDARDS.md）

- **批量赋值防护**，OWASP Mass Assignment（docs/arch/STANDARDS.md:28，API-31），**必须**。这一列只能由后端写。请求体里带了它，照 API-31 回 400（docs/arch/API_CONTRACT.md:296）。
- **部分更新**，RFC 7396（docs/arch/STANDARDS.md:27，API-33），**必须**。负责人字段没传，表示不改，这一列也不动。传 null 表示改回未分配，这一列一起清空（docs/arch/API_CONTRACT.md:305-306）。
- **日期与时间格式**，RFC 3339（docs/arch/STANDARDS.md:30，API-41），**必须，有条件**。只有这一列出现在接口响应里才适用。API-43 定的是后端算好标记再下发，不下发时间戳（docs/arch/API_CONTRACT.md:351-353）。所以本版大概率用不到。下不下发归 05-类型 定。
- **授权（最小权限）**，OWASP Authorization（docs/arch/STANDARDS.md:26），**必须**。「可能卡住」只给负责人，照 API-43 现有口径，本列不改变它。
- **库表字段命名**：登记表里没有数据库命名标准，写「无」。下面照 schema 现有写法：字段名 camelCase，用 @map 映射成 snake_case 列名。

## 一、字段名、列名、类型、可空

建议放在 prisma/schema.prisma:85 `assigneeUserId` 的下一行，和负责人字段挨着。原文如下，对齐方式照 Task 模型现有列宽：

```
  assignedAt      DateTime?  @map("assigned_at") @db.Timestamptz(6)
```

- 字段名 `assignedAt`，列名 `assigned_at`。
- 类型 `DateTime?`，落库为 timestamptz(6)。依据是 ADR-DB-003「时间点用 Timestamptz(6)」（docs/arch/DECISIONS.md:48）。
- 可空，**不设默认值**。写法和 `readAt` 一样（prisma/schema.prisma:104）。它和 `statusUpdatedAt` 的写法不同：那一列是非空，并带 `@default(now())`（prisma/schema.prisma:87）。原因是未分配的任务没有分配时间。设了默认值，未分配的任务也会带上一个时间。
- 命名是我的推荐，不是已定。候选还有 `assigneeUpdatedAt`，可以和 `statusUpdatedAt` 对称。我选 `assignedAt`，因为它和 D13 的措辞「最近一次分配」对得上，读起来就是一个时间点。
- 不加索引。规模假设是每个项目几百条任务以内（docs/design/PRD.md:123）。判定在后端逐条算（API-43），用不上索引。

## 二、什么时候写，什么时候清

总原则：只和这条任务**当前**的负责人比，和历史无关。负责人变了就写当前时间，变成未分配就清空，没变就不动。理由是 ADR-DB-005 定了「只存当前状态」，不存轨迹（docs/arch/DECISIONS.md:62）。

1. **创建时带负责人**：写入，值是创建时间。
   - 依据：问 459 A 的「分配时写入」。
   - 补充事实：创建时 `statusUpdatedAt` 也是创建时间（prisma/schema.prisma:87），两列取较晚者，结果一样。写入不改变判定结果。写入的好处是守住一条约定：有负责人，这一列就有值；没负责人，就是空。
2. **创建时不带负责人**：保持空。
   - 依据：docs/design/PRD.md:272 允许不分配，任务进入未认领。
3. **更换负责人**（A 换成 B，或从未分配到分给 A）：写入当前时间。
   - 依据：D13「含更换负责人」（docs/design/PRD.md:296）。
4. **改回未分配**（D16）：负责人传 null，这一列一起清空。
   - 依据：问 459 A，以及 D16「按 D13 不再标『可能卡住』」（docs/design/PRD.md:299）。
   - 已经是未分配又传 null：没变化，什么都不动。
5. **移出成员**（D14）：被移出者名下本项目的任务，负责人和这一列一起清空。
   - 依据：docs/design/PRD.md:297。
   - 要和删 membership 那一行放在**同一个事务**里。
   - **注意**：这一步要靠应用代码做，外键不会代劳。ADR-DB-004 的 SetNull 只在删**用户**时触发（docs/arch/DECISIONS.md:56），删 membership 不会触发。tasks 的外键指向 users，不指向 memberships（prisma/schema.prisma:93）。
6. **分给原来那个人**：不写，保持原值。
   - 依据：问 459 A。
   - 读法：我把「原来那个人」读作**当前**负责人。先改回未分配、再分给同一个人，比的是当前的空值，算一次分配，要写入。按历史比要存轨迹，和 ADR-DB-005 相反。这是我的读法，请项目主人看一眼对不对。

下面几种情况都**不动**这一列：
- 改状态：只动 `statusUpdatedAt`。
- 改标题、描述、截止日期：D13 写明不算（docs/design/PRD.md:296）。
- 转让负责人（API-36）：不碰 tasks。
- 更新接口里没传负责人字段（API-33）。

## 四、有没有挡路的事

结论：没有挡路的事。下面三点不挡路，但要知道。

1. **迁移和默认值：不挡路。**
   - 加一列可空、无默认值的列，PostgreSQL 不用回填，按决策边界 D2 属于「可空加列」。迁移照 ARCHITECTURE 第四节，人工触发。
   - ADR-DB-003 修订时写过「库还没建，没有数据要迁」（docs/arch/DECISIONS.md:50）。现在有没有 prisma/migrations、库里有没有数据，本轮没核。
   - 万一已有数据：老的已分配任务这一列为空，判定就退回只看 `statusUpdatedAt`，最多晚标一点，可以接受。
2. **删用户时会留下残留：不挡路。这里有一个要主人拍的取舍。**
   - 事实：删用户时，外键 SetNull 会清空负责人，但不会清空这一列。「有负责人才有分配时间」这条约定会被打破。本版不设删用户入口（docs/arch/DECISIONS.md:44），所以眼下碰不到。
   - 判定写法要防住它：先判有负责人、未完成，再取两列较晚者。不能拿「这一列非空」当「已分配」。顺带一提，PostgreSQL 的 GREATEST 会忽略空值。在 TS 里算要自己处理 null。
   - 取舍（交项目主人）：要不要加一条数据库 CHECK 约束，规定「负责人为空 ⇔ 这一列为空」。加了，SetNull 一触发就会撞上 CHECK，删用户实际变成拒绝，等于悄悄推翻 ADR-DB-004。Prisma schema 也写不了 CHECK，只能在迁移里手写 SQL。**我推荐不加**，把这条残留写进新 ADR 的后果，以后做删用户时一起处理。
3. **和 ADR-DB-006 的锁：不挡路。**
   - 移出成员本来就要拿那把锁（docs/arch/DECISIONS.md:71）。清空这一列在同一个事务里做，不用新加锁。
   - 发现一个旧问题，不是这一列带来的：负责人在两个页面里，一边把任务分给 X，一边移出 X，可能出现任务分给了非成员。按 ADR-DB-006 原文，分配不在「改动成员」的锁范围内。这个问题和本列无关，「锁哪一行写转让接口时定」时可以一起考虑。
4. **和澄清注记 12：对得上。**
   - 注记 12 说状态改回原值不算变化（docs/design/PRD.md:351）。这里分给当前负责人不写，两边口径一致。API-39「转给自己当作成功、什么都不改」也是这个口径（docs/arch/API_CONTRACT.md:336-337）。
   - 实现建议：「比较后再写」最好在一条 UPDATE 里完成，用 `IS DISTINCT FROM` 比较新旧负责人，避免并发时先读后写读到旧值。

## 问 5：去掉首尾空白和本约束的关系

A、B、C 三种约束都只管大小写，不管空白。「 bob@x.com」和「bob@x.com」对它们来说是两个值（C 下是否如此是待确认（假设））。

数据库层做不了去空白：CHECK 只能拒收，不会帮你去掉。可选档的兜底是加一条 CHECK，要求 email 等于去掉空白后的值。但它要手写 SQL，而且 PostgreSQL 的 btrim 和 JS 的 trim 认的空白不一样（未核）。

## 二、接口清单

本节列出本版全部 17 个接口，按代码所在的模块分组。每个接口写七样：方法与路径、鉴权级别、请求的 schema、响应的 schema、成功码、可能的退回性质、依据。退回只写性质，状态码照第一节第 6 小节的映射表；要靠专门的 type 才分得开的退回，标「专门的 type」，字面值归 ProblemType，本节不写（API-24，问 611 A）。没标的，与同一性质的其他退回共用 type（待确认（假设））。

第一节写过的不再重复（API-1）。第 1 到 3 小节是各接口共用的读法，第 4 到 6 小节逐个列接口，第 7 小节列本版没有接口的部分。

### 1. 鉴权级别

- 公开：不挂 AuthGuard。只有注册、登录两个接口（API-8 补充）。
- 只要登录：只挂 AuthGuard。路径里没有项目 id 的接口用这一档。AuthzGuard 要拿路径里的项目 id 查成员表，没有就判不了（API-2）。
- 本项目成员：挂 AuthGuard 与 AuthzGuard，负责人、执行者都放行。执行者只能碰分给自己的任务，这一条由 Service 判，判不过回「看不见」（API-35、API-42）。
- 只有负责人：挂 AuthGuard 与 AuthzGuard。执行者调用，由 AuthzGuard 回「不许做」（API-35、API-42）。

### 2. 各接口共有的退回

下面几种，各接口不再列。几种同时成立时谁先回，见第一节第 6 小节「谁先回」（API-46）。

- 内部错误：全部接口（API-14）。
- 看不见：路径不存在（API-47）。路径带项目 id 的接口，还有三种：项目不存在、调用者不是本项目成员、路径 id 转不成数字（API-15、API-21、决策 B）。
- 未登录：公开接口以外的全部接口（API-14）。
- 跨站被拒：GET 以外的全部接口。专门的 type（API-11、API-29）。
- 格式不支持：带请求体的全部接口（API-27）。
- 参数不合法：带请求体的全部接口。有四种：形状或类型不符；多出 schema 没列的字段，含请求体多带项目 id；必填项去空白后为空；请求体不是合法 JSON（API-14、API-31、API-32、API-47、决策 D）。GET 接口带了 schema 没定义的查询参数，也回这一种。本版 GET 接口都不收查询参数（API-56）。
- 冲突：写接口在并发下撞上数据库唯一约束（API-28）。注册、邀请成员撞上的约束，就是它们各自那一种冲突，回同一个专门的 type（推导）。

### 3. schema 名字

- 只定名字主体。写不写后缀，照 05-类型 为全部 schema 定的命名规则（API-1、API-30）。

- 列表的每一项与这个资源的详情同一形状，用同一个名字（待确认（假设））。
- 一个资源按调用者角色给不同形状时，仍用一个名字。几种形状在 schema 里怎么写，归 05-类型（待确认（假设））。
