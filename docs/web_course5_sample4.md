### 3a · 原理：部署拓扑到底在画什么

先打个比方，这个比方我会撑完整段。

第二节画的是**一间屋子里家具怎么摆**。进门先过玄关，再到客厅，再到厨房。那就是 Guard、Pipe、Controller、Service 的顺序。

第四节画的是**整个小区的平面图**。

小区里有几栋房子。
大门传达室在哪。
外面的人怎么进来，进来之后怎么找到对应的那栋。
房子跟房子之间走哪条内部路。
水电煤（配置）从哪个方向接进来。

对应到技术上，四个词：

**容器**，就是一栋独立的房子。它自带水电和家具，也就是自带运行环境。你换一台服务器，房子原样搬过去还能住。

**Docker Compose**，就是小区的规划图加物业。它一份文件说明：这个小区有几栋房子、每栋叫什么名字、谁能走到谁家门口、谁负责先盖谁负责后盖。

**Nginx**，就是大门传达室。外面所有人只能从这进。传达室看你要找谁，替你带过去。外面的人根本不知道里面有几栋楼、每栋叫什么。

**端口映射**，就是在围墙上开一个对外的窗口。开了，外面的人能直接够到那栋房子，绕过传达室。不开，那栋房子只能从小区内部访问。

**不画这张图会怎样。**
Lec 9 起 Docker，那时候要写 compose 文件。没有拓扑图，就是边写边想「诶数据库要不要开端口」。想一次改一次，改完前面的又对不上。Lec 15 上线时更糟，HTTPS 证书该放哪、前端静态资源谁发，全是现场拍。

**特别提醒一句**：第四节是**图纸，不是生效**。写进文档不代表机器上跑起来了。真跑在 Lec 9。这一点是反模式 35 的教训——「写了」和「生效」是两件事。

## 三、BACKLOG 第 21 条那个真决策

这条你选了本窗口处理。先讲清楚问题在哪。

### 3a · 原理：两道岗，两本名册

接着上一段小区那个比方往下说。

小区大门口有**两道岗**。

第一道岗问的是：你是不是本小区住户。它翻的是住户名册。
第二道岗问的是：你在你要去的那栋楼里是什么身份，是业主还是租客。它翻的是楼栋成员名册。

对应到代码：

第一道岗是 **AuthGuard**，它读 `sessions` 表，确认会话有效，拿到当前用户 id。
第二道岗是 **AuthzGuard**，它读 `project_memberships` 表，确认你在这个项目里是负责人还是执行者。

第三节的 R2-1、R2-2 走的就是这两步，W1-1、W1-2 也是。

**现在问题来了。**

两本名册归属不同。住户名册（`sessions`）归 auth 模块，第一节写死了。楼栋成员名册（`project_memberships`）没人拥有，归 projects 模块写、authz 模块读。

而第二节的 Guard 那一块写了一句：

> 只能调：authz 模块暴露的能力。

这句话把两道岗当成一道岗写了。按字面读，第一道岗也只能翻 authz 的名册。但它要的是住户名册，authz 手里没有。

**所以按现在这个措辞，AuthGuard 读 sessions 找不到合规出口。**

这不是错别字。它牵动的是「一个模块的守卫能不能属于那个模块自己」这个边界口径，定错了，Lec 10 写 backend 时会照着建错目录。

### 3b · 三个选项

**A. 按归属把 Guard 拆成两句写。**
AuthGuard 归 auth 模块，它调 auth 自己暴露的能力去读 sessions。
AuthzGuard 归 authz 模块，它调 authz 暴露的能力去读 project_memberships。
第二节那一句改成两句，各自说清能调谁。

**B. 让 authz 也读 sessions。**
authz 职责扩成「认证与授权的横切判定」，拥有表仍为无，只读表从一张变两张。第二节那句话原封不动就成立了。

**C. 维持一句话，但把它改宽。**
写成「Guard 只能调 auth 与 authz 两个横切模块暴露的能力」。不动模块归属，只把范围说全。

**我推荐 A。**

理由两条。

一，A 不改任何已定归属。`sessions` 还是 auth 的，`project_memberships` 还是 projects 写、authz 读。第一节的归属自检和依赖图一个字不用动。

二，B 会让同一张表出现两个读入口。auth 模块登录登出本来就在读写 sessions，再让 authz 也读，`sessions` 就有两个模块伸手。第一节「一表一主」里「读不算拥有」这条虽然允许跨模块读，但认证这种安全边界上的表，读入口越少越好判。

C 的问题是把两件事糊在一句话里。将来再加一个横切模块，这句话又要改一次。A 是一句变两句，以后加第三道岗就加第三句，结构撑得住。

**A 有一个附带问题我不在这替你定，交给 architect 第一轮去核**：第一节写着 authz 的依赖是「auth（当前会话）、projects（读角色）」。如果 AuthGuard 归了 auth，AuthzGuard 拿当前用户 id 是从请求上下文里取的（第三节决策 A 定的），那 authz 到底还依不依赖 auth 模块，就要重新核一遍。这属于依赖图的事实核对，该由能真打开文件的角色来做，不该我在这推。

打个比方。盖房子之前先让人下去探一遍地基。探完给你一张单子：这里有根老水管、那边土质松、还有两处图纸对不上。你看完单子拍几个板，再让人正式开工。

不探就开工，挖到一半撞上水管，整面墙拆了重来。

**这一轮具体要探三样东西。**

一，你刚拍的五条裁决，跟已经定死的文件有没有打架。
二，文件与文件之间本身有没有打架（这是 D8 管的事，只报不改）。
三，**还有哪些取舍你根本没被问到过。**

第三样最重要。要把一张部署图画完整，需要定的事远不止你拍的那四件。architect 心里清楚还缺什么，但如果不明确要求它列出来，它会自己挑一个看着合理的填进去，写得顺顺当当，你读的时候完全看不出这里原本有个选择。

这是 33 号坑：**把属于主人的取舍包装成理所当然的技术结论。**

### 3b · Level 1 对应

网页版时代你也让 AI 做过类似的核对。做法是把文件内容贴进对话，让它比对。

两个痛点。
一，贴进去的是你手选的片段。你没贴的地方它看不见，冲突就漏在那。
二，它说「TECH_STACK 第 28 行写着三职责」，你没法验。它可能记错，也可能编。

现在升级在哪：architect 有 Read 权限，**它自己去打开文件**，你没选的地方它也看得见。而且它给的出处是 `文件路径:行号`，你能用 `sed` 拿那几行出来当场对。

上一个窗口你抽查了四处，四处全中。**但这一轮还得抽。** 原因很实在：**抽查之前，可信报告和编造报告长得一模一样。** 上次全中只证明上次可信。

### 3c · 这个 prompt 有五块，逐块说

下面先讲每一块为什么在，讲完再给完整的可复制块。**不把说明夹在代码块中间**，那是 28 号坑，你整段复制时说明会被粘进终端。

**第一块 · 侦察边界。**
第一句要求它先读 `.claude/agents/architect.md`。子代理跨会话激活时，角色定义不会自动进它脑子，必须让它自己读一遍（3 号坑）。

然后写死三个文件：ARCHITECTURE.md、TECH_STACK.md、DECISIONS.md。加上它自己的定义文件一共四个，在协议 2 的五个上限之内。

**还要写一句「不得因早前读过而跳过」。** 这是上两轮的老教训。子代理会觉得自己读过了，凭印象答，答出来的东西看着有理但对不上原文。

DECISIONS.md 为什么在名单里：里面是 ADR-001 到 005 的决策记录。如果其中哪条锁过部署相关的东西，T9 收窄 Nginx 职责就可能撞上。不读就不知道。

**第二块 · 背景。**
T8 到 T12 五条裁决，全部要原文写进 prompt。

这是 1 号坑，也是最容易犯的一个：**子代理跑在独立的上下文里，它不在我们这个对话中。** 你刚才在聊天里拍的板，它一个字都不知道。不写进去，它会按自己的判断重新推一遍，推出来的跟你拍的不一样。

每条裁决还要带一句理由。带了理由它才能判断这条跟现有文件冲不冲突，只给结论它只能照抄。

**第三块 · 四件交付。**
核对清单、冲突清单、取舍清单、小节骨架。

冲突清单那里特意写了「只报不改、给双方出处、不给结论」。这是 D8 决策边界的原文要求。为什么要强调「不给结论」：架构类 AI 发现两份文件矛盾时，往往很有把握哪份更新，有把握就不会停下来问，直接挑一边写下去。D8 就是为了堵这个。

取舍清单那里写了「凡属『因为现在不做某事，所以也不预留某结构』这类合并判断，必须拆开写」。这句是 33 号坑的探针，上一轮靠它把 onDelete 那个藏起来的取舍逼了出来。

**第四块 · 不要做。**
不写正文、不改文件、不发明选型、不把推导写成有出处的事实。

最后那条是硬要求。ARCHITECTURE.md 前三节每节末尾都有「出处」段，凡是没有文件依据的都标了「推导，无直接出处」。这个习惯必须延续，否则下一节课的老师会把推导当成已决事实引用。

**第五块 · 停止条件。**
60 到 100 行，不必精确。字数给范围是规则 40，给死数它会为了卡数反复删改，白烧 token（14 号坑）。

还有一句「中途若发现必须先由主人裁决才能继续，立即停下」。这是防它自己猜一个答案继续往下推。

### 组二 · 拓扑骨干（两条，画图靠它们）

#### T14 · Nginx 怎么把请求分给前端和后端

外面来的请求都撞在 Nginx 上。它得知道这一条该送去前端还是后端。三种分法：

```
A 同域名按路径分
   app.com/          → 前端
   app.com/api/...   → 后端

B 子域名分开
   app.com           → 前端
   api.app.com       → 后端

C 全给前端，前端再转
   app.com/*         → 前端 → 后端
```

**我推荐 A。**

理由：一张证书，Cookie 天然同源，不用配跨域。代价是路径前缀要跟 API 契约对齐，05-API 那节把 `/api` 这个前缀定死就行。

C 的问题是所有接口流量都压在前端进程上，多一跳，而且前端挂了接口跟着挂。

**这条推荐有个前提我要说清楚**：我说「Cookie 天然同源」，是假定会话凭据走 Cookie。**但第三节明写了凭据载体属 API 契约，现在还没定。** 如果最后走 Authorization 请求头，B 的跨域成本就低很多，A 的优势没这么大。

这是刚学的 40 号教训：理由要完整，不能只走一种形态就下结论。

#### T15 · 前端服务端取数走哪条路

Next.js 的 SSR 是在服务器上先把页面渲染好。渲染时要拿数据，就得调后端。问题是这个调用走哪条网。

**A. 走容器内网直连**，前端容器直接喊 `http://backend:3000`。
**B. 走公网域名绕回来**，前端容器访问 `https://app.com/api`，再从 Nginx 进去。

**我推荐 A。**

理由：B 有个很现实的坑。容器里要能解析公网域名，还要 VPS 支持从内部访问自己的公网地址再绕回来。很多 VPS 这条路是不通的，通了也是多一次 TLS 加解密。

代价说清楚：A 要前端配两个后端地址（浏览器用公网那个，服务端用内网那个），而且服务端渲染时要手工把浏览器带来的 Cookie 转发给后端，不会自动带。
