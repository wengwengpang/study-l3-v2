# 第 4 课　技术选型

## 一、本章位置

这一章属于第一篇「立项准备」。业务代码仍然不写。前三章定了给谁用、做什么、长什么样，这一章定用什么技术来做。

**上一章交来什么。** 需求文档 `docs/design/PRD.md`，界面设计 `docs/design/UI_DESIGN.md`。界面设计里定的组件方向（Tailwind CSS 加 shadcn/ui），到这里已经是一条约束。规则书第二层 A、B、C。

**这一章产出什么。**

- architect 角色 `.claude/agents/architect.md`。
- 技术选型 `docs/arch/TECH_STACK.md`：选了什么，每项为什么，四个分叉怎么定的，哪里留了扩展点，依据哪些约束。
- 决策记录 `docs/arch/DECISIONS.md`：五条，每条写清当时的情况、定了什么、放弃了什么。
- 规则书第二层 D：AI 每次进项目都要知道的几条结论。
- 待办清单 `docs/BACKLOG.md`：跨章的事记在这里。
- 反模式库第 32 号。

**下一章拿它做什么。** 第 5 课设计数据库，用的就是这里选的 PostgreSQL 和 Prisma。有一张会话表，光看需求推不出来，是这一章选了「把登录状态存在数据库里」才带出来的。后面每一章写代码，都照这份选型。

**这一章最要紧的一件事。** 技术不是挑最流行的。答案是被约束逼出来的。选完还要写下「为什么选它」和「放弃了什么」，不然几个月后，自己都不敢动它。

## 二、学完能做到什么

1. 能用六个问题摸清一个项目的约束，分清哪些文件里有，哪些只有人知道。
2. 能用一把两根轴的尺子比较候选，说清为什么选这个、不选那个。
3. 能分清一个选择是被真实约束逼出来的，还是为了教学放进来的。
4. 能写一条三行的决策记录，后果里写清放弃了什么。
5. 能审 AI 的选型草稿：抽查它的出处，判断它多提的建议收不收，不把它的推荐当成拍板。

## 三、原理

### 先认几个词

这一章要提到十几样技术。你不用会用它们，先知道每样是干什么的。

**写代码用的。**

- **TypeScript。** 一门编程语言。官方的话是「TypeScript is JavaScript with syntax for types.」也就是在 JavaScript 上加了类型。写错了类型，代码还没跑就会报错。
- **React 和 Next.js。** 做网页界面用的。React 管界面怎么拼。Next.js 建在它上面，官方写「Next.js is a React framework for building full-stack web applications.」
- **Tailwind CSS、shadcn/ui。** 管样子和现成的界面部件，第 3 章讲过。
- **Node.js。** 让 JavaScript 能在服务器上跑。官方写「Node.js is an open-source and cross-platform JavaScript runtime environment.」
- **NestJS。** 写后端用的框架，跑在 Node.js 上。官方写「Nest is written in TypeScript and runs on Node.js」。

**框架是什么。** 做菜打比方：语言是食材和刀工，框架是一间配好灶台和流程的厨房。你照它的规矩做，很多重复的事不用自己搭。

**存数据用的。**

- **PostgreSQL。** 数据库。官方写「PostgreSQL is a powerful, open source object-relational database system」。
- **Prisma。** 帮代码读写数据库的工具，这类工具叫 ORM。官方写它是「an open-source next-generation ORM」。有了它，代码里不用手写查询语句，写错了字段名，类型检查就能查出来。
- **Redis。** 把数据放在内存里的存储，常拿来做缓存。官方写「Redis can be used as a database, cache, streaming engine, message broker, and more.」

**管工程的。**

- **Zod。** 检查数据格式对不对。官方写「Zod is a TypeScript-first validation library.」比如注册时密码够不够长。
- **pnpm workspaces。** 一个仓库里放好几个小项目，比如前端、后端、两边共用的代码。官方写「You can create a workspace to unite multiple projects inside a single repository.」这种放法叫 Monorepo。

**上线用的。**

- **Docker。** 把程序连同它需要的环境打成一个包，到哪儿都一样跑。跑起来的那个东西叫容器。
- **Docker Compose。** 「a tool for defining and running multi-container applications.」一份文件写清要起哪几个容器。
- **Nginx。** 站在最外面接请求，再转给后面的程序。官方写它是 HTTP 服务器和反向代理，还能做别的几样事。

**两组待会要比的。**

- **认登录。** 第 0 章讲过两种：JWT 像通行证，自带签名，服务器不查名册；会话（session）像号码牌，服务器每次拿号码去名册上查。
- **让页面知道有新消息。** 三种。轮询：浏览器隔一会儿问一次。SSE：服务器有消息就发过来，只能单向。MDN 写「Unlike WebSockets, server-sent events are unidirectional」。WebSocket：两边随时互发。MDN 写它可以收发消息「without having to poll the server for a reply」。

### 答案是被约束逼出来的

裁衣服要先量尺寸。尺寸没量，布再好也裁不对。

选技术也一样。多少人用，谁来维护，部署到哪，预算多少，这些就是尺寸。量清楚了，答案常常自己浮出来。

**不做会怎样。** 直接问 AI「用什么数据库」，它会给你一个流行答案。答案本身未必错，可是没有依据。过几个月想不起当初为什么这么选，也说不清为什么不选别的。遇到问题，不知道这个选择能不能动。

这件事交给一个角色来做，它叫 architect，架构师。它的招牌不是写代码，是在几条路里选一条，再把为什么写下来，让以后接手的人看得懂。它不替你拍板，只给候选和推荐。

### 六个问题

architect 选型之前，先过六个问题。

| 问题 | 它决定什么 | 本项目当年的答案 |
|---|---|---|
| 1. 规模与并发：多少人用，同时多少人 | 要不要缓存、队列、多台服务器 | 小规模，团队级，5 到 50 人，低并发 |
| 2. 团队与技能：谁写，谁维护，熟悉什么 | 选型要落在维护的人管得住的范围 | 一个人全栈，沿用上一个项目的技术 |
| 3. 数据特征：多大，结构化程度，一致性，实时性 | 用哪类数据库，要不要 Redis、WebSocket | 结构清楚，约束强，验收只要刷新可见 |
| 4. 部署与运维：部署到哪，谁管 | 用容器还是托管平台 | 一台服务器，自己管 |
| 5. 时间与成本：多久交付，预算多少 | 用现成的还是自己做 | 学习节奏，零预算，全用开源 |
| 6. 演进与扩展：一到三年内会怎么变 | 哪里要留口子，别选必换的路 | 随课扩展 |

**这六问是本课程自己定的。** 课程的知识库只给了「6 必问」这个名字，具体内容是当年上课时补的。写书时没有查到哪份标准规定这六问。它们是一份好用的清单，不是行业规范。

**它们的答案从哪来。** 第 3、6 问多半能从需求文档里读出来。第 1、2、4、5 问文件里常常没有，只有人知道。这时候 AI 该问你，不该编。第四节第 4 步写书时跑了一次，它确实没编，全列成了「需要你确认」。

**「已确认」不等于「验证过」。** 规模那一条是项目主人拍的，不是真实用户给的数字。拍了，设计就照它走，这是对的。可它仍然是一个假设。后面的补课里，它会进需求文档的假设账本。

**你没有「上一个项目」怎么办。** 第 2 问的答案，当年是真实情况：项目主人走过一遍别的项目，熟悉这套技术。你跟着本书做，不用熟悉它们，照这组约束走就好，后面每一章都建在这上面。

你自己的项目，这一问要写实情。如果写代码的主要是 AI，你自己不太看得懂代码，下面是本书的判断，不是哪份标准说的：优先选用的人多、资料多、出了错好搜的。少一样组件，就少一样出事时要你扛的东西。有一篇常被引用的文章叫 Choose Boring Technology，作者说每家公司大约只有三个「创新额度」：「Let's say every company gets about three innovation tokens.」它讲的是公司，道理相通：新奇的东西要算成本。

### 一把两根轴的尺子

挑技术像挑工具进工具箱。每件工具问两句：它多趁手，它多沉。

- 横轴是**契合度**：它多大程度满足上面的约束和需求。
- 纵轴是**代价**：学习、维护、运维、长期风险，加起来要付多少。

| | 低契合 | 高契合 |
|---|---|---|
| **高代价** | 左上，排除 | 右上，权衡区。写清为什么仍然值得，或者有没有更轻的 |
| **低代价** | 左下，可有可无。不进第一版，除非教学要用 | 右下，甜区。直接选 |

这叫四象限决策法。两根轴也是本课程自定的。同类的做法行业里有，比如 NN/g 讲过的优先级矩阵，「A 2D-visual that shows the relative importance of a set of items based on two weighted criteria.」它举的例子是用户价值对投入。

**走一遍。** 当年拿数据库示范过。

PostgreSQL。契合度高：上一个项目用过，和 Prisma 配合好，支持带时区的时间和 JSON 这类类型，以后加东西方便。代价中低：项目主人刚入门，有一点学习成本，但不是从零开始。落在甜区。

MySQL。契合度中：够用，可换回去就丢了上一个项目的积累。代价低：项目主人很熟。也在右下，但比 PostgreSQL 靠左。

结论选 PostgreSQL。「更熟 MySQL」这一点是真的，只是学习成本只付一次。

**力气花在哪。** 十三项选型不是每项都要争。约束一摆，大多数直接落进甜区，确认一下就过。真正要拿出来拍的只有几个。把甜区的也摊开讨论，是仪式，不是工程判断。

### 选型没有绝对的好坏

常有人问：为什么不用 Vue，为什么不用 Django？

先纠正一个说法。这个项目一直在用框架。Next.js 是，NestJS 也是。真正的问题是为什么用这几个，不用那几个。

**前端，React 系和 Vue。** 像两把都好用的螺丝刀。问题不在哪把更好，在哪把已经在手上、配件齐不齐。项目主人熟 React。第 3 章定的 shadcn/ui，官方安装页列的都是 React 系的框架，没有 Vue。Vue 那边有别人移植的版本，网站页脚写着「Ported by unovue」，不是同一个项目。选 Vue 也能做，只是要重学，还要换一套部件。

**后端，NestJS 和 Django。** 「Django is a high-level Python web framework」，它成熟、省事。可它是 Python。本项目是一种语言走到底，前端后端都用 TypeScript。这不是顺手，是有意的：一种语言，才能共用同一份校验规则和类型。密码规则写一次，两边都用。换成 Python，就要两边各写一份，慢慢会对不上。

注意这两段没有一句说 Vue 或 Django 不好。全程在拿它们对这组约束。同一个 Django，放到一个 Python 团队、不需要共用类型的项目里，可能正好落在甜区。

**选型没有绝对的好坏，只有配不配这组约束。** 契合度那根轴，吃的就是约束。

### 约束驱动和教学驱动

一个选择放进来，来路有两种：

- **约束驱动。** 被真实约束逼出来的。
- **教学驱动。** 为了练某件事放进来的，不是产品需要。

这个项目有点特殊。它是一门课的实战项目，第 1 章说过课程有硬底线：多用户加权限、实时或通知、五到八张表、复杂的前端交互、能部署。这些要求不是十万用户逼出来的，是为了教这些东西。

**为什么要分清。** 看这个例子。architect 当年读文件时停下来报矛盾：需求文档的验收标准只要「刷新可见」，规则书却把「实时/通知」列成底线。到底要不要实时？

这个矛盾一拆时间线就化开了。这一版照需求做，不做实时，用通知表加轮询，这是约束驱动。第 13 课再把 WebSocket 加进来，这是教学驱动。**实时这个功能，产品不需要，课程需要。** 两条时间线，不是两个打架的需求。

底线的原话也要抠一下。规则书里写的是「实时/通知」，斜杠不清楚。课程规则的原话是「必须有至少一个实时或通知的场景（后面第 13 课要教 WebSocket）」。是「或」。

**后来有一处改了，这里说清楚。** 当年的说法是「一张通知表已经满足了底线的通知那一支」。到第 5 课之后的补课，定了这一版的通知模块只是空壳：表建好，不产生任何通知。所以严格说，表建了不等于场景有了，底线的通知那一支也要到第 13 课才兑现。这一章的文件原文不改，后面会加修订行。这也是一个例子：**当时写下的判断，后来可能要修。修的时候留痕迹，不抹掉。**

看着矛盾的需求，先查来源。常常不是矛盾，是来源没标。这是反模式 32 号。

### 第一版先跑通，扩展留接口

项目主人在选型中途补了一句：现在是第一版，项目随课扩展，后面可能还会加课。这句话变成了贯穿选型的方针：

> 第一版先跑通，扩展留接口。不为「以后可能用」提前堆东西，但每个选择留清楚的扩展点，后面接得上，不用推倒重来。

它有两半，各有道理。前一半常叫 Yagni，You Aren't Gonna Need It，你用不着它。Martin Fowler 专门写过，还划了界限，这个原则不管让软件更容易改的那些功力：「it does not apply to effort to make the software easier to modify.」所以后一半不矛盾：Redis 现在不装，可是把会话的读写封装在一处，以后真要换，只换这一处。

留口子也有分寸。写一个「以后可能用」的字段，和把一段代码写得好改，是两回事。第五节 TECH_STACK 第三节列了六个扩展点。其中「任务表预留外键挂载位」这句后来被读错过，以为任务表上要留字段，后面的补课才写明：外键长在子表一侧，任务表本身什么都不用留。

### 四个真分叉

约束一摆，十三项里四项真有得选。

**一，登录状态怎么存。** 候选三个：JWT；会话存 Redis；会话存 PostgreSQL。

需求里有两条硬验收：登出后立即失效，角色改了立即生效。

JWT 的麻烦在第一条。它的标准 RFC 7519 写的是「a compact, URL-safe means of representing claims to be transferred between two parties」，通篇没有吊销机制。OWASP 的 JWT 速查表写：「However, if you use JWTs for user sessions, you will need a solution for managing session invalidation.」办法是「a deny list of revoked sessions/tokens」，也就是服务器存一份已作废清单，每次去查。可这样一来，JWT 不查名册的好处也没了。

会话存数据库，登出时删一行，立刻作废。数据库本来就有，不用多装东西。所以定的是存 PostgreSQL。

**这里有个主次，要讲清楚。** 项目的文件写的是「两条验收都要求服务端存状态，无状态 JWT 做不干净」。这句话是对的，前提是「无状态」三个字：令牌里写着角色，请求时不查库，角色改了确实生效不了。可如果每次请求都去查一下成员表，JWT 也能让角色立即生效，只是这样就不再是无状态了。本项目角色按项目划分，存在成员表里，本来每次都要查。所以对这个项目，真正分出高下的是**登出立即失效**。写书时让 AI 重跑，它自己把这一点指出来了，第 8 步会看到。

还有一点值得记。上一个项目用的就是 JWT。这次多了即时失效的要求，答案就跟着变。不能因为上次用过就照搬。

**二，Redis 现在装不装。** 登录状态不放它，它在第一版就没活干了。没有缓存压力还装，就是提前堆。定的是不装，留接口。当年还查了课程大纲：没有专门的缓存课。想学它，是「加一节课」的决定，归人定。

**三，实时怎么做。** 候选：不做实时，通知表加轮询；SSE；WebSocket。验收只要刷新可见，主动提醒的那条故事优先级是 P2、已延后。定的是不做实时，WebSocket 留到第 13 课。

**四，校验用什么。** 候选 Zod 和 class-validator。NestJS 官方写「Nest works well with the class-validator library, which provides decorator-based validation.」这条路最常规，可它只能后端用。Zod 一份规则两边共用，贴合「一种语言走到底」。代价是要自己接一层，官方文档「Schema based validation」一节给了示例。定的是 Zod。

### 决策记录

TECH_STACK 记的是选了什么，是结论。决策记录记的是当时为什么这么选、放弃了什么，是理由。

打个比方，它是决策的病历。不只记开了什么药，还记当时什么症状，吃了会怎样，有什么副作用。换个医生接手，看病历就懂为什么这么治，不会乱改。

**不写会怎样。** 半年后你看到「登录用数据库会话」，想不起为什么不用更轻的 JWT，手一痒改了，把「登出立即失效」这条硬验收撞坏。

**它有出处。** 英文叫 Architecture Decision Record，简称 ADR。Michael Nygard 2011 年写的一篇文章提出来，开头就说：「One of the hardest things to track during the life of a project is the motivation behind certain decisions.」他定了五段：标题、背景、决策、状态、后果。后来 AWS、微软的架构指南都收了它。它是主流做法，不是正式标准，专门讲它的网站 adr.github.io 也没有这样称呼。

**本项目用三行。** 叫 ADR-Lite：

- **背景。** 当时面对什么约束或问题。
- **决策。** 定了什么。
- **后果。** 换来什么，放弃了什么。

这正好是 AWS 写的最低要求：「At a minimum, each ADR should define the context of the decision, the decision itself, and the consequences of the decision」。和 Nygard 的五段比，少了「状态」一段，是有意简化。

**后果要写代价。** 只写好处的不叫决策记录，叫自夸。Nygard 的原话是「All consequences should be listed here, not just the "positive" ones.」微软写「Avoid hiding consequences of decisions intentionally or accidentally.」选了 A，就没有 B 的某个好处，写下来，后人才知道这是权衡，不是拍脑袋。

**写哪些，不写哪些。** 微软写「Only include choices that affect the system's structure, key quality attributes, or are difficult to reverse.」甜区里没有纠结的选型不写，写了只会稀释真正重要的那几条。本项目第一批写五条。

**定了以后要改怎么办。** 这里本项目和标准不一样。AWS 写「Changes to an existing ADR requires creating a new ADR」，微软写「If a decision changes, write a new record that supersedes the original and link the two together.」都是新开一条，旧的标「已被取代」。本项目的做法是旧条目原文不动，在它下面加一行修订。好处是读一条就能看全它后来怎么变，代价是现在算数的结论要读到这一条末尾。这个偏离是项目主人定的，理由和代价都登记了。第五节的文件是第一版，所以还没有这种行，后面几章你会看到。

### 结论上墙，理由留档

TECH_STACK 和 DECISIONS 放在 `docs/arch/`，AI 不会每次进项目都读。可「登录用数据库会话」这样的结论，它每次都得知道。不然下一章它可能顺手写个 JWT。

所以把结论钉进规则书第二层 D。只写结论，指向那两份文件，不抄理由。这是第 1 章讲过的单一信息源：理由只在一处维护。

### 方法只有名字，等于没有

当年踩过一个坑。architect 的定义文件里写着「走 6 必问」「用四象限」，可这两样的具体内容，全在当时的 prompt 里。文件里只有名字。

下一个窗口它重新上岗，读到「用四象限」，不知道两根轴是什么。它要么问你，要么自己编一套。

所以补了两件事。一是把内容写进 architect 文件末尾的方法论附录。二是在角色标准 `docs/AGENT_SPEC.md` 加了一条通则：点名的方法，内容必须有持久的落点，要么写在角色文件里，要么指向某个文件。第 1 章第三节那张限制表里「方法」一行，来历就在这里。

### 拍过的事要落进文件

这一条是写书时才查出来的。

当年第 5 步拍了四条约束，也说了「连同 TECH_STACK 一起落」。可落下去的文件里，只有部署那条，规模、团队、预算都没写。那几条只活在当时的对话和 prompt 里。到后面的补课，architect 做约束分析时又提了一次规模，这次是另一个数：每个项目任务几百条、成员十人以内。它手上的文件里，查不到之前拍过什么。

所以本书让你的 TECH_STACK 多一节，把这四条写进去。第五节的文件就是这样的。

规律是一样的：**对话会结束，文件才活得下去。** 拍了板，当场落进文件，第 3 章讲信息分层时说过。

### 第 2 步　派一次子代理，看它真的生效

**目的。** 文件在，不等于它真能干活。这份文件开头写了 `tools: Read` 和 `model: opus`，这一步看这两行是不是真起作用。

这两行只在它被派出去时才算数。所以这一步要真派：

```text

```

**这句话怎么写，有讲究。** 当年的 prompt 第一句是「请以 architect 子代理身份工作。」写书时用同样的话跑了一次，它没有派：主对话自己读了文件，自己答了，答得也很像那么回事。换成「用 architect 子代理做这件事」或者 `@"architect (agent)"`，都真派了。三种叫法各跑一次：

| 叫法 | 主对话 | 子代理的模型 | 子代理的工具调用 |
|---|---|---|---|
| 「请以 architect 子代理身份工作。」 | 自己读，没派 | 无 | 无 |
| 「用 architect 子代理做这件事：」 | 派了 | claude-opus-5-5 | Read、Read |
| `@"architect (agent)"` | 派了 | claude-opus-5-5 | Read、Read |

各跑一次，不等于每次都这样。官方的说法是 @ 提及「guarantees the subagent runs for one task」，点名是「Name the subagent and Claude typically delegates」。要确保，就用 @。

## ADR-001 · 鉴权用 DB session 而非 JWT
- 背景：PRD 要求登出立即失效（PRD.md:167-168）、角色改后即时生效（PRD.md:207），需服务端可控的会话状态；无状态 JWT 在「主动失效」上做不干净。

- 后果：换来即时失效与即时权限变更的可控性；代价是每次请求多一次 DB 往返（比 JWT 纯签名校验重），且会话状态需自己维护清理。放弃了 JWT 的无状态与水平扩展便利。

## ADR-002 · Redis 在 MVP 延后引入
- 背景：鉴权改走 DB session 后（见 ADR-001），Redis 在 MVP 已无明确职责；无缓存压力、无专门教学课节。

- 后果：换来更少的运维组件、更简单的环境，守住「不提前堆」方针；代价是会话查询直压主库 PG，未来真出现缓存/会话压力时需补一次引入改造。放弃了「现在就备好缓存层」的前置便利。

- 背景：PRD 验收只要「刷新可见」（PRD.md:23、42、71），主动推送 US-02b 已 P2 延后（PRD.md:96）；课程硬底线要「实时或通知」（CLAUDE.md:52），通知表已满足「通知」这一支。
- 决策：MVP 做通知表 + 刷新/轮询，不做实时推送；WebSocket 作为教学驱动功能留到 Lec 13，先铺扩展点 #1。这是教学驱动与约束驱动的分离——实时这个功能产品当前不需要（约束驱动），课程后续需要（教学驱动），是两条时间线而非互相打架的需求。

- 背景：需要强一致 + 唯一约束（邮箱唯一 PRD.md:148）、以及 user×project×role 多对多关系建模（PRD.md:173）。
- 决策：选 PostgreSQL 作为主库，配 Prisma 做类型安全 ORM 与 migration。
- 后果：换来更严谨的约束与关系表达、对复杂查询与未来演进更友好；代价是若团队更熟 MySQL 则有一次性上手成本。放弃了 MySQL 的广泛默认部署便利。

## ADR-005 · 数据校验用 Zod 而非 class-validator
- 背景：项目目标是前后端共享一份类型（packages/shared 扩展点 #5）；密码等规则需两端一致校验（PRD.md:149）。
- 决策：用 Zod 写一份 schema 前后端共享复用，而非 NestJS 默认的 class-validator 装饰器。
- 后果：换来「写一次、两端复用」与从 schema 直接推导 TS 类型；代价是偏离 NestJS 默认范式，需自接 Zod 管道（如 ZodValidationPipe），生态示例不如 class-validator 顺手。放弃了 NestJS 官方默认校验链的开箱即用。
```

## 32 号 · 教学驱动需求混进 PRD 没标来源，看着像矛盾
现象：PRD 里「实时」这类需求，不是用户研究推出来的（用户验收只要刷新可见），是课程自上而下为教 WebSocket 塞进来的。两者都写成「需求」却没标来源，下游 architect 选型时撞出来，看着像 PRD 自相矛盾。
根因：E4 架构错。需求来源没标清——「用户研究推导的」和「课程教学塞进的」混在一起，缺一个来源标签。
修复：凡自上而下/为教学塞进 PRD 的需求，显式标「教学驱动」，与「用户验证」「pm 推导」区分。选型时按时间线拆解：本版兑现哪条（约束驱动）、留到哪节课兑现（教学驱动），不是两个打架的需求。
教训：看着矛盾的需求，先查来源，常常不是矛盾，是来源没标。
抽象模式：与 19（AI 编需求当事实）、29（隐性基础需求）、31（新旧措辞不对齐）同族——都是「需求来源没标清」。
```
