## 一、决定一：丙成立吗？

成立。
- 甲违反原则 16（最后要另请独立反方）。子代理只算半独立（原则 13）。
- 乙的粘贴成本是真的。证据 2 也说了，问题出在「两边没有管道」。

但包里漏了这些风险：

**1-1 丙提前用上了原定「项目完成后」才用的模式。**
证据 3 写的是「全 CC：项目完成后」。当初为什么要等？
如果理由是教学上的，比如学生要先学会看、学会判断，再交给 CC，那丙就跳过了这一步。
要看到原文才能下判断（见上面第 1 条）。

**1-2 审查包由被审的一方来写。**
丙里，CC 讲课、执行，然后也由 CC 决定往审查包里放什么。
举例：这份包里的 9 条「依据」都是 CC 挑的。要是有一条对丙不利的原文没被挑进来，我没办法知道。
这个洞比「子代理半独立」更大：审查者是独立的，但它看到的材料不独立。
**补法**：包里的原文一律用命令直接导出（cat、git show），不经过 CC 转述。学生自己再加一栏「我想问的」。

**1-3 要不要送审，也由被审的一方判断。**
CC 的不确定点 2 问「什么算大决定」。问题其实不在怎么定义，而在谁来判断。
让 CC 判断「这事够不够大」，就等于让被审的人决定自己要不要被审。
**补法**：把触发条件写成学生能机械检查的事，不靠判断。例如：
- 本节改了 docs/ 下的规则文件（`git diff --stat docs/` 不为空），送审
- 新增或删除了规则号，送审
- 改了 CLAUDE.md、权限文件或子代理定义，送审
- 每个阶段结束，送审
- 学生说「请反方」，送审

这些条件由学生来查，不由 CC 来判断。

**1-4 互相挑错的次数会少很多。**
证据 5 说明，原方式下老师和 CC 每一轮都在互相挑错。丙里，挑错只发生在阶段末和大决定时。中间讲错的东西，可能一直错到阶段末才被发现。
**补法**：先试行。头两节课每节都送一个短包给网页版复核，稳定了再降到只在阶段末送审。

**1-5 学生容易从「做决策」退成「点同意」。**
乙里粘贴很累，但它逼学生每次都看一眼输出。丙里 CC 讲完就直接做，学生可能只剩按「同意」。
这门课的目的是让学生学会，包里没提这个风险。
**补法**：在讲课标准里写死几个固定的停顿点，停下来让学生做决定或用自己的话复述。具体放在哪，由学生定。

**1-6 丙的一条好处，在乙里也成立。**
「资料管理员在 CC 里才好落地」：乙里 CC 也在，一样能建子代理。所以这条不是丙独有的，别算两次。
「拆目录」那条部分成立：乙里文件拆得越多，网页版老师要粘贴的就越多。

**1-7 丙说的「去掉乱源」，和决定二列的根子对不上。**
决定一说，丙能去掉「两个世界抄来抄去」这个乱源。但决定二列的根子只有两条（不对账、只增不减），没有这一条。
要么根子漏了一条，要么丙的这条好处说大了。请 CC 二选一，写清楚。
另外，换到 CC 并不会自动止住规则增长。这次重构就是在 CC 里做的，还新立了规则 74、75、76、84。

**1-8 开课读全七份文件，会让会话更早被压缩。**
能读全是好处。但每次开课都吃掉一大块上下文，压缩就来得更早，人设漂移（不确定点 1）也就更早。
所以开课必读的内容越少越好。这和决定二的「拆目录」是连着的。

**有没有更好的做法？**
有一件值得先查：「网页版读不了学生电脑上的文件」这个前提，可能已经不成立了。
我这个对话里能看到连文件夹的入口：在 Claude 桌面版 App 里，点输入框旁的「+」，选「Add folder」。如果仓库在 GitHub 上，也可以只读接进来。

如果能接上：
- 审查时我自己读原文，不用 CC 挑，1-2 的洞基本就堵上了。
- 审查包只需写「审什么、为什么」，不用再贴原文。

要注意两点：
- 这只解决「材料不独立」，不解决「同一类模型」。网页版审查者也是 Claude，只是上下文独立。原则 13 的顾虑对它也部分成立。
- 接的时候尽量只读，保持「只审不改」。

所以我的建议是：**丙，加上网页版直接读仓库做审查。** 这是丙的加强版，不是新方案。

## 二、决定二：A 成立吗？

成立。否决 B 和 C 的理由也对。但有下面几处要补：

**2-1 A 的顺序和 BACKLOG 60 不一致。**
BACKLOG 60 定的是先填 HARNESS 一、二节，再分析上课环境。A 是从「定环境」开始的。
我认为 A 的顺序反而更对：HARNESS 第一节写的是「三种模式」，选了丙以后，那段本来就要重写。
所以请把 BACKLOG 60 的顺序也改过来。不然以后有人读到，会照旧顺序去做。

**2-2 「跟一两节课验证」没写怎么算通过。**
没有标准，验证一定会「通过」。建议事先写好，比如：
- 资料管理员至少抓到一个 CC 主会话没发现的真问题，并由学生或网页版确认它是真的
- 两节课的结课体检都真的做了
- 规则总数没涨；如果涨了，要有对应的删并

**2-3 报告出来以后，交给谁？谁来删？**
「只查不改、出报告」之后，缺了后半截。建议写成一个环：
管理员出报告 → 学生选删哪条、并哪条 → CC 执行 → 管理员复查。
删规则是决策，按分工是学生的事。
另外，报告别每次都新建文件，不然资料又多一堆。固定用一个文件、覆盖着写，历史留在 git 里。

**2-4 用加规则来治「只增不减」。**
重构里为了「不对账」，新立了规则 74、75、76、84。这是在用「加」来治「加太多」。
建议：
- 资料管理员的第一次体检，任务就是出一份删并候选清单。
- 以后每份报告都必须有「可删/可并」一栏，没有就写「无」，并说明理由。
- 把规则总数当作体检指标记下来。

**2-5 CC 的不确定点 3：同一类模型，能不能抓到 CC 抓不到的重复？**
**补法**：让管理员多做机械活，少做判断活。
- 机械活：列出所有规则号；找重复的编号；找被引用了但不存在的规则号；找从没被引用过的规则；看同一个关键词出现在几份文件里；每份文件的行数比上次多了多少。
- 这些机械活可以写成一个脚本。脚本不用模型，也就没有模型的盲区。
- 判断活，比如「这两条意思是不是重复」，才交给子代理。

还可以做一次**埋雷测试**：在一个 git 分支里故意放两处重复、一处矛盾，看管理员能不能抓到。抓不到，就说明它不可靠。测完把分支删掉。

**2-6 CC 的不确定点 4：没有 hook，会不会变成「写了没人做」？**
会。结课是最容易被省掉的一步：人累了，或者会话断了。
**补法**：把检查挂在开课上，而不是结课上。开课是一定会发生的。
SESSION_START 第一件事：上节课的体检报告在不在？不在，先补，再上课。
这是一道闸门，不是一句提醒。这样可以撑到第 8 课学 hook，不用为了这件事把第 8 课提前。

**2-7 拆目录放在最后，我同意。**
提醒一点：「一条规则一个文件」就是 80 多个文件，开课要读的、互相引用的都会变多。
拆之前先看体检结果：删并之后还剩多少条规则，再定怎么拆。

**2-8 资料管理员的定义文件，谁来写？**
这个角色是用来查 CC 的。按原则 10，「被约束者不写自己的墙」，所以不该由 CC 自己写。
建议由学生来写。或者 CC 起草、学生改定，再送网页版审一次。

## 三、选丙后要改的清单，漏了什么

包里已经列了：规则 65、SESSION_START J 节第 3 件、LESSON_TEMPLATE 分工行、讲课标准能不能照着讲。

漏了下面这些：

**3-1 HARNESS 第一节的「三种模式」要按丙重写。**
丙不是原来三种里的任何一种。「全 CC：项目完成后」这个时间条件也不再对了。
HANDOFF 里「终局图按第三种设计」这句，也要一起核一遍。

**3-2 讲课标准（TEACHING_STYLE 等）的归属变了。**
以前它约束的是网页版老师，现在约束的是 CC。按原则 10，以后 CC 不能自己改它。要写明：这几份文件归学生改，或者改动必须送审（用 1-3 的触发条件）。
光「确认 CC 能照着讲」还不够。还要改掉只适合网页版的写法，比如要求画图、复杂排版的地方，在终端里显示不出效果。

**3-3 BACKLOG 46 要改。**
46 写的是用 reviewer 子代理「替代」网页版。选丙以后，网页版审查是要保留的。
46 不改，将来有人照着它做，就会把网页版审查删掉。要把「替代」改成「补充」。

**3-4 BACKLOG 61（导出版开课包）要重新评估。**
它主要是为了把资料粘贴给网页版。丙里上课不用粘贴，只剩审查包还需要。
如果网页版能直接读仓库，61 可能整个都不用做了。

**3-5 审查包本身的规则还没写。**
谁来写（见 1-2）、什么时候送（见 1-3）、原文怎么取、审查结论回到 CC 以后记在哪里。这些现在要么散在各处，要么还没有。

**3-6 会话压缩后的规矩。**
CC 的不确定点 1 提到压缩后人设会漂移。建议加一条：一节课开一个会话；会话被压缩以后，先重读讲课标准，再继续讲。

**3-7 找「贴回」写法，别靠记忆列。**
BACKLOG 42 只列了两处，其他地方可能还有。用命令搜一遍，比 CC 凭印象列更可靠：
```
grep -rn "贴回\|粘贴\|网页版\|老师" docs/
```
搜出来的每一处，逐条判断要不要改。

**3-8 留一个回退点。**
切换之前先打一个 git tag。如果试行两节课不行，要回到乙，能一步退回去。

官方 What loads at startup 一节写明：非 fork 的子代理从全新上下文起步，看不到对话历史（这正是 K1 引的那一条）。落到管理员身上：
- **职责 2「和上一份报告比」**：定义文件没说上一份报告在哪。
- **职责 5「上一份报告里学生选了删并的，CC 执行后，核对落没落」**：学生选了什么，发生在主对话里，管理员看不到；仓库里也没规定记在哪。2-3 的那个环（出报告 → 学生选 → CC 执行 → 管理员复查），就断在「学生选」这一步。

建议：定义文件写明，第一件事是读 docs/LIBRARIAN_REPORT.md，作为上一份报告；学生的删并选择，由 CC 照学生原话记到一个固定位置（比如报告文件末尾另开一栏，或 DECISIONS-R1 里固定格式的条目），定义文件指向那里。记在哪里由学生定。

**F72（须处理）「只查不改」目前只靠硬规则 3 一句话。**
给了 Bash，就能写文件。CC 假设「子代理沿用项目权限，非白名单命令会弹窗」，官方页 Permission modes、Run subagents in foreground or background 两节大体支持这个假设，但有三个口子：
- **跟随主对话的模式。** 定义文件没写 permissionMode，子代理就跟主对话的模式走。主对话如果处在 acceptEdits 或 auto 模式，子代理一定跟着，定义文件里即使写了 permissionMode 也会被忽略。而 acceptEdits 模式下，工作目录里常见的文件系统命令会被自动放行。
- **放行会扩散到整个会话。** 交互会话默认开着 fork 模式，Claude 派出的子代理都在后台跑，它的权限弹窗会出现在主会话里。学生如果选了「本会话不再问」，这个放行对整个会话生效，主对话里的 CC 也跟着被放行了。按原则 10，这等于学生给 CC 的墙开了一个本没打算开的口。
- **allow 名单不明。** settings.json 的 allow 名单里放了什么，决定哪些 Bash 命令不弹窗。这份文件包里没有。

兜底办法，按成本从低到高：
1. **每次管理员跑完，跑一次 `git status --porcelain`**，由学生跑，或 CC 当着学生跑。有输出，就说明它写了东西。这是现成做法：DECISIONS-G1 补遗 94、109 都记着「子代理只读，审完 git status 干净」。由学生机械地查，也合原则 16 补的那一层。建议写进开课闸门那一步。
2. **在定义文件的 frontmatter 里加一个 PreToolUse hook**，只放行 `bash scripts/doc-check.sh` 和少数只读命令。官方 Conditional rules with hooks 一节的只读数据库例子就是这个模式，并写明 hook 是提示词之外的后备。但这样一来，定义文件就成了会自动跑代码的配置，按规则 66 和原则 10，应归学生亲手写，不能由 CC 起草。可以留到第 8 课学 hook 时再做（BACKLOG 7、9）。
3. **埋雷测试里专门试一次**：让它 `touch` 一个文件，看弹不弹窗、是谁放行的。

缺材料：请导出 .claude/settings.json（defaultMode 和 allow 名单），我才能判断现在的口子有多大。
