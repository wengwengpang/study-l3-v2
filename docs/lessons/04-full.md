# Lec 4 完整笔记 · architect 激活 + 技术选型决策

## 这节课做了什么
第一次激活 architect 架构师角色，让它做选型前约束分析、四象限选型、ADR 决策记录。产出技术栈与决策档案，并把关键结论钉进项目宪法第二层。

## 学到的能力
1. 建一个重思考子代理（architect，model: opus），并验证它真读了定义、真生效，不是列表里有个名字。
2. 用「6 必问」做选型前约束分析，把拍脑袋改成对着约束选。
3. 用「四象限决策法」给每个选型上秤，留下可追溯的理由。
4. 用「ADR-Lite 三行」记决策，后果诚实写「放弃了什么」。
5. 学会区分「约束驱动」与「教学驱动」两类需求，按时间线拆解看似矛盾的需求。

## 三个核心方法（已沉淀进 architect.md 方法论附录）
6 必问：规模并发 / 团队技能 / 数据特征 / 部署运维 / 时间成本 / 演进扩展。查不到的列「需主人确认」+ 假设默认值，不自己编。
四象限：横轴契合度（吃 6 必问的约束）、纵轴代价。右下甜区直接选，右上权衡区（教学驱动归这），左下可有可无，左上排除。铁律：选型没有绝对好坏，只有配不配这组约束。
ADR-Lite：背景 / 决策 / 后果。后果必须写放弃了什么，否则是自夸不是留档。

## 四个分叉的裁决（Michael 拍板）
1. 鉴权 = DB session（不是 JWT）。因 PRD 要登出立即失效 + 角色即时生效，需服务端可控状态。约束驱动。
2. Redis = MVP 不引入，留可替换接口。鉴权走 DB session 后 Redis 无活干，不提前堆。
3. 实时 = MVP 通知表 + 轮询；WebSocket 留 Lec 13。产品不需要（约束驱动），课程需要（教学驱动），两条时间线。
4. 校验 = Zod。一份 schema 两端共享，贴合共享类型目标。约束驱动。

## 一个关键认知：约束驱动 vs 教学驱动
本项目复杂度是「教学驱动」的，不是「用户量驱动」的。多用户、权限、实时、5-8 表，是为教 harness 套路故意要求的（调节器 I 节）。选型时诚实分两类：被真实约束逼出来的，和为练某套路放进来的。ADR 标清楚，三年后不会误判。

## Level 1 对应
网页版时代：选型靠「我觉得 X 好」，聊完即过、不留档、说不清为何不选 Y。
现在升级：架构师变成可复用子代理；6 必问是固定前置关；四象限是一杆秤；ADR 把理由钉死。选型全程可追溯、可交接。
