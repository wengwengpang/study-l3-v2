# 第 2 课　需求文档

## 一、本章位置

这一章属于第一篇「立项准备」。业务代码仍然不写。上一章问的是用户难受在哪，这一章定产品做什么、不做什么、做到什么程度算完。

**上一章交来什么。** 研究报告 `docs/design/USER_RESEARCH.md`：第一栏（真人确认）是空的，第二栏六条全是「待验证」。还有角色文件的标准 `docs/AGENT_SPEC.md`。

**这一章产出什么。**

- pm 角色 `.claude/agents/pm.md`。
- 需求文档 `docs/design/PRD.md`：每条需求都写明来源。
- 规则书第二层 B：只放骨架，详情指向需求文档。
- 反模式库更新和新增的几条。

**下一章拿它做什么。** 第 3 课的 designer 照需求文档画页面。第 4、5 课的 architect 照它选技术、建表。第 10、11 课照它写代码。到了测试，还要拿验收标准一条条对。

**这一章最要紧的一件事。** 第一次把 AI 假设的需求变成真人确认的需求。这一步只能由人来做。

## 二、学完能做到什么

1. 能分清 pm、designer、architect 各管什么，一条需求来了能判断谁起头定。
2. 能写用户故事和可以测的验收标准。
3. 能让 pm 写草稿，并用认、否、改把它变成自己确认过的需求。
4. 能查出用户没有明说、但系统跑起来离不开的基础需求。
5. 提交之前能看清这次到底带走了哪些文件。

## 三、原理

**为什么要有这一步。** 打个比方。盖房子不会直接喊工人开砌。先有一张图纸，写明三室两厅，主卧带飘窗，厨房通燃气。工人照图施工，验收时拿图对一遍，一项项打钩。需求文档就是这张图。它不写怎么砌墙，那是架构和代码的事。它写要砌成什么样，怎么算砌好了。

**不做会怎样。** 什么都想做，什么都做不完。写到一半才发现少了登录。做完了也没法说算不算做完，只能吵。

### 先认几个词

**PRD。** Product Requirements Document，产品需求文档，本书也叫需求文档。

**用户故事。** 从用户的角度写一条需求，下面讲。

**验收标准。** 能客观判断做没做完的条件，下面讲。

**In Scope 和 Out of Scope。** 这一版做的和这一版明确不做的。

**权限。** 谁能做什么。这里说的角色是产品里的用户角色，比如负责人、执行者，和 Claude Code 的 pm、designer 这种角色不是一回事。前者是系统里的用户分几等，后者是请谁来帮你干活。不要为产品里的角色去建 agent。

### 三个角色，一张总图

还用盖楼打比方：

- 有人先问住户想要什么：调研，上一章的 client。
- 有人把住户的话翻译成建筑要求清单：3 室 2 厅，几个消防出口。这是 **pm**。
- 有人画住户怎么走：进门、玄关、客厅，门朝哪开。这是 **designer**。
- 有人算楼怎么不塌：地基多深，水电怎么走。这是 **architect**。
- 有人真的搬砖砌墙：开发。

画动线的和算承重的，看的是同一份要求清单，管的却是两件事。整条线是这样，每一步的产物是下一步的输入：

| 步骤 | 谁 | 产物 | 在第几课 |
|---|---|---|---|
| 用户研究 | client | `USER_RESEARCH.md` | 第 1 课 |
| 产品需求 | pm | `PRD.md` | 第 2 课 |
| 界面设计 | designer | `UI_DESIGN.md` | 第 3 课 |
| 技术架构 | architect | 选型、表、接口契约 | 第 4、5 课与补课 |
| 后端、前端 | 开发 | 代码 | 第 10、11 课 |
| 联调测试 | 测试 | 能跑的版本 | 第 12 到 14 课 |
| 部署上线 | 运维 | 线上产品 | 第 15 到 17 课 |

本书为了一个角色一个角色学，按顺序排。实际做项目，设计和架构可以并行，边做边对。有一条要守：表结构不要在界面大方向定下来之前锁死。

**一条需求来了，看谁起头。** 比如「密码输错 3 次，锁定账号 5 分钟」。三个角色都沾边：

- pm 定要不要锁，错几次，锁多久。
- designer 定提示长什么样，倒计时怎么显示。
- architect 定错误次数存在哪，5 分钟怎么计时。

起头的只有一个，是 pm。他没定，另外两个根本不知道要做这件事。记住这条线：

- 要不要做，做到什么程度：pm。
- 用户看到什么，怎么操作：designer。
- 系统内部怎么实现：architect。

### pm 是守边界的

很多人以为产品经理的活是想功能。其实好产品不是功能堆出来的，是砍出来的。pm 最值钱的动作，是对一堆需求说「这个不做」。没有人守门，需求会像野草一样长，最后什么都想做，什么都做不完。

所以 pm 的角色文件里，「你不做什么」和「你做什么」一样重要。它只给 Read 权限，也是这个道理：它只能说，不能动手，需求文档必须经人才能落进文件。给了写权限，这道审查就被绕过去了。

### 用户故事：逼你说出为什么

看一组对比：

- 功能的写法：系统要有登录功能。
- 用户故事的写法：作为一个团队成员，我想用邮箱和密码登录，以便进入我参与的项目。

后者多了三样东西，这就是固定的公式：作为谁，我想做什么，以便得到什么价值。Mountain Goat Software 的说法是：

> As a [type of user], I [need/want/am required] to [do something], so that [reason or benefit].

它把用户故事说成「a short description of desired functionality」，一段简短的、对想要的功能的描述。

价值不在格式，在那个「以便」。系统要有登录功能，为什么？没说。一旦「以便」后面填不出真价值，这个需求就该怀疑。这是 pm 砍需求的第一把刀。

### 验收标准：只有是和否

用户故事说了要什么，还差一样：怎么算做到了。关键词是客观。

- 模糊的：登录要好用。你说好用，测试说不好用，吵架。
- 可测的：输对邮箱和密码，进入主界面。密码错误，统一提示「邮箱或密码不正确」。

后面这两条拿来测，结果只有是或否。常用的写法叫 Given-When-Then，中文写成给定、当、则。Cucumber 的文档这样说这三段：

- 「Given steps are used to describe the initial context of the system」：给定，交代开始时的情况。
- 「When steps are used to describe an event, or an action」：当，发生一件事或一个动作。
- 「Then steps are used to describe an expected outcome, or result」：则，应该得到的结果。

拆成三段，写的时候不容易漏掉边界情况。

### 用户故事和假设账本要一起用

只用用户故事：格式很漂亮，可分不清哪条是真用户要的，哪条是 AI 编的。漂亮，但不可信。

只用假设账本：知道哪些没验证，可需求写得乱，下游读不懂。诚实，但不可用。

两个一起：每条用统一公式写，每条标来源。

第 0 课讲过证据契约：AI 说的事实要能指回出处。它管的是引用，不管创造。pm 写用户故事是创造，给不出代码行号，但要给另一种出处：这条需求从哪来。这就是来源标注。

本章的来源有三种，要物理分开：

- **已验证。** 真人确认过。
- **AI 假设。** AI 提的，还没人确认。
- **pm 推导的基础需求。** 不是谁提的，是 pm 从现有需求推出来的，经人审定。下面讲。

### 认、否、改：唯一的升级路径

AI 假设怎么变成已验证？只有一条路，人一条条看，做三个动作之一：

- **认。** 这条我要，来源改成已验证。
- **否。** 这条不要，划掉。
- **改。** 意思要改，改完再认。

这一刻才是账本真正转起来的时候。pm 不能替人认，AI 不能替人认。本项目的人并没有带团队的第一手经验，所以认的时候是在替这个产品拍板要什么，不等于用户真这么想。这一点记在需求文档的「待真实验证的盲区」一节里，不藏着。

**认了一条，可能牵动一大片。** 本项目里，pm 提醒六条全站在负责人一个视角，执行者的需求整个缺失。认了这条补充，产品就从一种视角变成两种，第 5 课的表、第 11 课的前端、第 13 课的权限都跟着变。所以「认」不只是打个钩，要想一下它牵动什么。还有「要不要拆」是另一件事：一条里塞了简单的「能看见」和复杂的「主动提醒」，认了也可以拆开，各排各的优先级。

### 隐性基础需求

用户研究只会问出功能。你请人盖楼，会说要三间卧室、一个厨房、两个卫生间，不会专门说要地基、承重墙和大门。可这些没有，楼立不起来。

软件也一样。用户故事记的是想要的房间，注册、登录、权限、项目这些是承重墙和大门。所有的故事都预设了「已登录用户」，却没有一条说用户怎么登录。

这不是谁的错，是这个方法本身就问不出来。所以要加一道专门的关：pm 写完功能故事，必须再问一遍，这些故事跑起来，底下还需要哪些没人明说的基础件？至少查认证、权限角色、项目容器。

这和「该现在做的推迟了」不一样。那是知道要做，往后拖。这个是压根没意识到要做。

**三条要守的界。**

- **已确认的不能改标。** 已验证的故事里其实已经藏着权限规则，比如「执行者只看分配给自己的任务」。pm 把它们集中成一张权限矩阵，标「pm 推导」的只是集中这个动作，每条写明来自哪条故事。原来的故事一字不动，更不能重新标成 pm 推导。把确认过的降级重标，也违反诚实底线。
- **只写产品要求。** 「刷新不掉线」是产品要求。「用什么技术保持登录」是 architect 的事。
- **不镀金。** 专业不等于什么都堆到现在。不该这一步做的，标给下游。

### 决策点要分档，越界要认得出

pm 写基础需求时，会碰到它拍不了的事：角色按项目分还是全局分？执行者能不能建任务？这些列成决策点，每点带推荐和理由，由人拍。

本项目把九个决策点分了三档，这个分法好用：

- **必须现在定。** 影响地基本身，比如角色范围，第 5 课等着它建表。
- **可以现在定。** 顺手定了省后患，比如登录态多久。
- **建议只记一句。** 越了界或超了范围的。比如「任务入口分几个」是设计题，pm 只定意图，入口结构留给 designer。「要不要做项目删除」是新范围，不是地基，记进不做的清单就好。

### 已验证的故事写错了怎么办

补完权限后发现，一条早先确认过的故事写着「作为团队成员，我想在一个地方看到所有任务」，和权限矩阵「执行者不能看全部任务」对不上。这不是逻辑矛盾，是它写在权限之前，措辞缺了权限这一层。

有三种处理：改原文，不留记录，或者加一段澄清注记。本项目选加注记：已验证的原文一字不动，旁边写清「所有任务」指统一入口的意图，具体谁能看到什么照权限矩阵。不留记录，下次有人读还会糊涂。

没有真实信号的留白，也不要补。比如「执行者跨项目看自己的任务」，确实没人提过。现在补一个，就是 AI 假设当需求。记进盲区，以后有真人再问。

### 规则书第二层只放骨架

需求写好了，规则书要不要也抄一份？不要。同一件事只记一处，详情留在需求文档，规则书只放编号、标题、优先级和一句「详见哪里」。

还有一层道理。打个比方，你要做一套能盖任何房子的施工管理系统，里面该沉淀的是怎么验收、怎么分工。「这栋房子主卧带飘窗」只属于这一个项目，焊进系统里，下次盖厂房全是噪音。可复用的结构放框架，具体内容放项目。

信息还要按寿命分层：只用一次的放交接说明，长期有效的放持久文件。

## 四、动手

**先说一件事。** 本项目当时分了两次：第 2 课只写了九条功能故事，到第 3 课画界面才发现没有登录页，回头单独补了基础需求。本章把这两次合成一次，pm 写完功能故事就查基础需求，读者不用再撞这一下。当年的经过写在第七节。第 2、3 步的 prompt 和结果是写这本书时跑的。

### 第 2 步　让 pm 写草稿

**目的。** 把研究报告第二栏转成用户故事，再查一遍基础需求。这份是草稿，下一步才由人定。

把下面这段贴进 Claude Code：

```text
请你以 pm 角色工作。

第一步，先读你自己的定义文件 .claude/agents/pm.md，读完用一句话复述你是谁、你的边界、你只有什么权限。

第二步，读这一个文件：docs/design/USER_RESEARCH.md。只读这一个文件，不要扫描其他目录。

任务：把 USER_RESEARCH.md 第二栏里的需求，逐条转成用户故事。写完再做一遍隐性基础需求检查。

硬要求：
1. 每条用户故事用固定格式：作为<角色>，我想<动作>，以便<价值>。
2. USER_RESEARCH.md 里这些需求目前全部是「待验证」状态，没有任何一条经过真人确认。所以你产出的每一条用户故事，都必须标注「来源：AI 假设（未验证）」。一条都不能漏标，也不得写成确定语气。
3. 每条用户故事配 2 到 3 条验收标准，用「给定…当…则…」格式，必须可测。
4. 给每条标优先级：P0（核心，没它产品不成立）/ P1（重要）/ P2（锦上添花）。
5. 如果你发现某条需求本身有问题（模糊、自相矛盾、价值说不清），先指出来再转，不要闷头照转。
6. 隐性基础需求检查：这些故事要跑起来，底下还需要哪些没人明说的基础件。至少查认证、权限角色、项目容器这三组。单独列出，每条标「来源：pm 推导的基础需求」，不要混进功能故事。这里说的权限角色是产品里的用户角色，不是 Claude Code 的 agent 角色。
7. 基础件只写产品要求，比如「刷新不掉线」。不提用什么技术实现，不写界面长什么样。

不要做的事：
- 不要落盘，不要尝试写文件。你只把结果打在对话里，我会负责落盘。
- 不要自己补 USER_RESEARCH 里没有的功能需求。如果你觉得缺了什么，在结尾单独列「pm 建议补充（也标 AI 假设）」，不要混进正式列表。

输出结构：
一、用户故事列表（每条：编号 + 故事 + 优先级 + 来源标注 + 验收标准）
二、pm 对需求质量的提醒（如有问题需求）
三、pm 推导的基础需求（每条：编号 + 故事 + 优先级 + 来源标注 + 验收标准）
四、pm 建议补充（如有，单独区，标 AI 假设）
五、待项目主人决策的点（哪些地方你做了取舍、哪些要人拍板，每点给推荐和一句理由）

输出完这五节就停。
```

这段 prompt 有几处是专门防坑的：

- **第一步让它先读定义文件。** 不写这句，它可能照自己想的职责开干。
- **「只读这一个文件」。** 不写死路径，它可能满项目找。这是在给它戴眼罩，只看该看的。
- **把「必须标假设」写死。** 只写「请标来源」，它可能挑几条标，或者标得含糊。
- **「发现问题先指出」。** 不写这句，它会闷头把有问题的需求也照转。
- **「权限角色是产品里的用户角色」。** 不写这句，它可能去建新的 agent。

**应该看到。** 写书时跑的一次，用了一分多钟，结果里报的花费约 0.17 美元，只读了这两个文件。每次跑的内容不一样，下面是那一次的样子。

每条故事都标了来源：

> - 故事：作为团队负责人，我想对任何一个任务一眼看出当前负责人，以便不再问"这个谁在做来着"。

> - 来源：AI 假设（未验证）。对应第二栏第 6 条。

验收标准能测：

> 2. 给定任务未指派，当查看任务，则明确显示"未指派"，不留空白。

它会挑研究报告的毛病，这是最值钱的部分：

> 5. **第 5 条（`docs/design/USER_RESEARCH.md:33`）**：这是背景描述，没有动作，也没有想要的价值。我把它保守地转成 US-05，但它本质是上下文，价值说不清。

> 7. **整体问题**：六条全部来自负责人一个视角，没有成员的声音。同时六条互相印证，都出自同一个 AI 画像，不是独立证据。

基础需求查出来了，第一组就是注册和登录：

> **F-01 注册**

> **F-03 刷新不掉线**

> - 来源：pm 推导的基础需求

最后是留给人拍的点：

> 6. **角色数量：负责人和成员两类够不够**。

完整记录在 `book/notes/lec02-pm-run2.md`。

**出了错怎么办。**

- 故事没标来源，或者写成了确定语气：告诉它硬要求第 2 条没做到，重写。
- 它想写文件：拒绝。它只有 Read 权限，本来也写不了。
- 基础需求里出现了具体技术：告诉它只写产品要求。

### 第 3 步　认、否、改

**目的。** 把 AI 假设变成你确认过的需求。这一步只有你能做。

把故事和 pm 的提醒一条条过，照这个格式回：

```text

US-02 ……
```

先想这几件事：

- pm 提到执行者的视角缺了，要不要补？补了牵动后面哪几课？
- 有的故事塞了两件事，要不要拆？
- 有的条目只是背景，你真正想要的是什么？

本项目的结果：八条（六条加 pm 建议的两条）全认。其中「同时推三四个项目」那条，定的意图是跨项目总览和人力视图。「任务认领可见加卡点预警」拆成两条。一共九条。认了「执行者接收任务」，产品成了负责人和执行者两种视角。

**应该看到。** 每条都有一个明确的动作。

**出了错怎么办。** 全认了又说不出为什么，回头看第 1 课的橡皮图章。这里和第 1 课有点不同：这是在替产品拍板做什么，可以认；但要记下来，这不等于用户验证过。

```markdown
### P0 · 核心(没它产品不成立)

#### US-03 任务统一入口
作为团队成员,我想在一个地方看到所有任务,以便不再需要在微信、口头约定、便利贴之间反复确认。
优先级:P0
来源:已验证(Michael)
验收标准:
- 给定已登录用户,当打开任务列表,则所有任务集中展示在同一页面,无需跳转外部工具。
- 给定用户创建新任务(标题、描述、负责人),当提交后,则任务立即出现在统一列表,其他成员刷新后也能看到。
- 给定任务已创建,当任何成员打开该任务,则标题、状态、负责人完整可查。

#### US-06 责任人清晰可见
作为团队成员,我想在任意任务上立即看到当前负责人,以便责任归属清晰,不需要每次追溯。
优先级:P0
来源:已验证(Michael)
验收标准:
- 给定已分配负责人的任务,当任何成员打开,则负责人姓名首屏可见,无需滚动。
- 给定用户浏览任务列表,当列表加载完成,则每行直接显示负责人,不需点进详情。
- 给定负责人被更换,当更换完成,则详情页与列表的负责人信息同步刷新。

#### US-07 执行者接收与更新任务
作为普通团队成员,我想查看分配给我的任务并更新进度,以便不需要被负责人追问状态。
优先级:P0
来源:已验证(Michael)
验收标准:
- 给定已登录执行者,当打开「我的任务」,则只显示分配给本人的任务。
- 给定执行者打开一个任务,当修改其状态(如未开始→进行中),则状态立即保存并对负责人可见。
- 给定执行者更新了进度,当负责人刷新进度视图,则数据反映该更新。

### P1 · 重要

#### US-01 进度自动汇聚
作为负责人,我想上班时一眼看到全员任务状态,以便不再每天逐个询问进度。
优先级:P1

- 给定团队有 N 名成员,当负责人打开进度视图,则全员状态同屏可见,无需翻页。

#### US-02a 任务认领与状态可见
作为负责人,我想看到哪些任务未认领或长时间无进展,以便及早发现而非到截止日才知道。
优先级:P1
来源:已验证(Michael)
备注:由原 US-02 拆分而来,本条只管「可见性」,主动预警见 US-02b。

### 第一组 · 认证（注册 / 登录 / 登出）

解决的地基问题：现有九条故事全预设「已登录用户」，但没有任何故事定义用户如何登录、身份如何被识别、登录态如何维持。

#### US-A01 用户注册
作为新用户，我想用邮箱创建账号，以便获得访问系统的凭据。
优先级：P0
来源：pm 推导的基础需求
验收标准：
- 给定未注册的邮箱，当填写邮箱和密码并提交，则账号创建成功，用户直接进入已登录状态，无需再次登录。
- 给定已注册的邮箱，当用户尝试注册，则注册被拒绝，提示「该邮箱已被使用」。
- 给定密码不满足最低复杂度（至少 8 位、含字母和数字），当用户提交，则注册被阻止并提示密码规则。

#### US-A02 用户登录
作为已注册用户，我想输入邮箱和密码登录，以便访问我的任务和项目。
优先级：P0
来源：pm 推导的基础需求
验收标准：
- 给定正确的邮箱和密码，当用户提交，则登录成功并进入应用主界面。
- 给定错误的凭据（邮箱错或密码错或账号不存在），当用户提交，则统一提示「邮箱或密码不正确」，不区分哪个字段出错（安全要求，防账号枚举）。
- 给定登录成功，当任意界面需展示当前用户身份，则系统能提供当前登录用户的姓名或邮箱（「我是谁」在整个会话中可读取）。
- 给定用户已登录，当刷新页面，则保持登录状态，无需重新输入凭据。
- 给定用户已登录，当关闭后重新打开，则在 30 天有效期内保持登录状态，无需重新输入凭据。

#### US-A03 用户登出
作为已登录用户，我想主动退出登录，以便离开设备时保护账号安全。
优先级：P0
来源：pm 推导的基础需求
验收标准：
- 给定已登录用户，当点击登出，则登录态立即失效，界面跳转至登录页。
- 给定已登出用户，当尝试访问任何需登录的页面，则被重定向到登录页，原操作不执行。

### 第二组 · 权限角色模型

解决的地基问题：现有故事散落着隐性权限规则，从未集中定义谁能做什么。本组将其显式抽取、集中成权限模型；标「pm 推导」的仅是「集中显式化」这一动作，已验证故事文字不做任何改动。
角色范围：角色按项目划分（项目内角色），同一用户在不同项目可担任不同角色（决策 D1）。

#### US-R01 权限拦截
作为系统用户，我需要在尝试执行超出自己角色的操作时被系统明确拒绝，以便边界由系统保证而非依赖人工自觉。
优先级：P0
来源：pm 推导的基础需求
验收标准：
- 给定执行者，当面对仅负责人可用的功能，则该功能入口在界面层不展示。
- 给定任意用户，当强制触发其角色不被允许的操作，则操作被拒绝并提示「权限不足」，不暴露系统内部错误信息。

#### US-R02 成员角色分配
作为负责人，我想让新成员以执行者身份加入，并能把负责人身份转让给项目内另一名成员，以便系统能按角色控制权限，项目也不会因负责人离开而无人可管。
优先级：P0
来源：pm 推导的基础需求
验收标准：
- 给定负责人添加成员，当提交时，则该成员以执行者身份加入本项目，添加时不提供负责人选项（首版单负责人，决策 D4、D10）。
- 给定成员角色被修改，当修改完成，则新权限立即生效，不等待该成员重新登录。
- 给定项目内负责人，当把负责人身份转让给本项目另一名成员，则该成员成为负责人，原负责人在同一操作内变为执行者（决策 D10）。
- 给定项目只有一名负责人，当尝试把该负责人直接改为执行者，则操作被拒绝，提示需先转让负责人身份（决策 D10）。

### 第三组 · 项目管理

解决的地基问题：项目是任务的容器，现有 PRD 反复提「项目」却从未定义它如何产生、成员如何管理。

#### US-P01 创建项目
作为负责人，我想创建一个新项目，以便有容器来组织一组相关任务。
优先级：P0
来源：pm 推导的基础需求
验收标准：
- 给定已登录用户，当填写项目名称并提交，则项目创建成功，创建者自动成为该项目的负责人成员。
- 给定一个项目，当其创建完成，则它只有一个负责人（首版不设多负责人，决策 D4）。
- 给定项目创建成功，当负责人打开该项目，则可在其中创建任务和管理成员。
- 给定项目名称为空，当提交，则创建失败并提示项目名称为必填。

#### US-P02 邀请成员进入项目
作为负责人，我想把团队成员添加到项目，以便他们参与该项目的任务。
优先级：P0
来源：pm 推导的基础需求
验收标准：
- 给定项目内负责人，当填写被邀请人邮箱并提交，则该成员以执行者身份成功加入项目，获得执行者权限（决策 D10）。
- 给定被成功添加的成员，当其登录并进入该项目，则能按角色权限看到项目内容。
- 给定被邀请的邮箱已是该项目成员，当再次邀请，则提示该成员已在项目中，不重复添加。

#### US-P03 查看项目成员列表
作为负责人，我想查看项目内所有成员及其角色，以便了解谁在参与本项目及其权限。
优先级：P1
来源：pm 推导的基础需求
验收标准：
- 给定项目内负责人，当打开成员列表，则看到所有成员的名称和角色。
- 给定项目目前只有创建者自己，当打开成员列表，则显示列表（含创建者本人），不显示空态。

#### US-P04 移出项目成员
作为负责人，我想把已经离开的成员移出项目，以便该成员不再能看到本项目的任何内容。
优先级：P1
来源：pm 推导的基础需求（补课 05-API 补，决策 D14）
验收标准：
- 给定项目内负责人，当把一名执行者移出项目，则该成员立即失去本项目的全部访问，不等待其重新登录。
- 给定被移出的成员原先分到了本项目的任务，当移出完成，则这些任务变为未认领。
- 给定项目只有一名负责人，当尝试移出该负责人，则操作被拒绝，提示需先转让负责人身份。

### 本组错误 / 边界验收规则

> 仅定产品规则（什么情况发生什么），不定 UI 长相（颜色、弹窗样式由 designer 决定）。

认证组：
- 注册邮箱已存在 → 拒绝，提示「该邮箱已被使用」。
- 注册密码不达标 → 阻止提交，提示密码规则。
- 登录凭据错误或账号不存在 → 统一提示「邮箱或密码不正确」，不区分字段（防枚举）。
- 未登录访问需登录页面 → 重定向到登录页，登录后跳回原目标页，不丢失意图。
- 登出后访问需登录功能 → 重定向到登录页，原操作不执行。

权限组：
- 执行者面对仅负责人功能 → 界面不渲染入口；强制访问则提示权限不足，不暴露数据。
- 角色修改 → 权限立即生效，不等重新登录。
- 尝试把唯一的负责人直接改为执行者 → 拒绝，提示需先转让负责人身份（决策 D10）。
- 项目内暂无其他成员，负责人建任务时「分配给」无人可选 → 允许不分配，任务进入未认领状态（符合 US-02a），系统不报错。

项目管理组：
- 创建项目名称为空 → 阻止提交，提示项目名称必填。
- 邀请的邮箱不存在于系统 → 拒绝，提示「该用户不存在」（内部邀请操作，不构成枚举风险）。
- 被邀请邮箱已是项目成员 → 拒绝重复添加，提示已在项目中。
- 尝试移出唯一的负责人 → 拒绝，提示需先转让负责人身份（决策 D14）。
- 项目成员列表只有创建者 → 显示列表（含创建者本人），不显示空态。

### 审定决策记录（Michael 拍板）
> 编号说明：这里的 D1 起是 PRD 自己的审定决策编号，和 CLAUDE.md 第三层 A 的决策边界 D1-D8 不是一套。别处引用写「PRD 审定决策 Dn」，引用决策边界写「决策边界 Dn」。

- D1 角色范围：项目内角色（同一用户不同项目可不同角色）。
- D2 执行者建任务：否，仅负责人。
- D3 执行者设截止日期：否，仅负责人。
- D4 多负责人：首版单负责人。
- D5 邀请标识：邮箱。
- D6 任务入口：PRD 只定功能意图（负责人可见全部+自己，执行者仅自己），入口结构留给 designer。
- D7 登录态期限：30 天。
- D8 项目删除：首版不做，进 Out of Scope。
- D9 密码规则：至少 8 位，含字母和数字。
- D10 负责人数量（补课 05-API 定）：首版单负责人不变。成员一律以执行者身份加入。负责人可把身份转让给本项目另一名成员，原负责人同时变为执行者。唯一负责人不得直接降为执行者。
- D11 执行者可见范围（补课 05-API 定）：执行者看得见自己所在的项目（名称与自己的角色）和分配给自己的任务。看不见成员列表，看不见未认领任务，不能自取任务。
- D12 任务状态流转（补课 05-API 定）：未开始、进行中、已完成三态之间任意互转。谁能改，仍照权限矩阵「更新任务状态」一行。
- D13 「可能卡住」判定（补课 05-API 定）：只看已分配、未完成的任务；未认领的标「未认领」，不标「可能卡住」。从最近一次状态变化与最近一次分配（含更换负责人）两者中较晚的那个时间起算，满 7×24 小时没有新的状态变化或分配，标「可能卡住」。改标题、描述、截止日期不算。天数全局固定，不按项目设。
- D14 移出成员（补课 05-API 定）：首版做负责人移出成员，成员自行退出项目不做。被移出者立即失去本项目的全部访问，名下本项目的任务变为未认领。唯一负责人不能被移出，要先转让。
- D15 编辑任务内容（补课 05-API 定）：任务的标题与描述只有负责人能改。执行者只能改分给自己的任务的状态。
- D16 改回未分配（补课 05-API 定）：负责人可以把已分配的任务改回未分配，任务变为未认领，按 D13 不再标「可能卡住」。执行者不能把自己从任务上摘下。
- D17 执行者看不见项目负责人（补课 05-API 定）：执行者看得见的项目信息只有名称和自己的角色（D11），不含负责人是谁。
- D18 任务删除（补课 05-API 定）：首版不做，进 Out of Scope。PRD 没有删除任务的用户故事；把边界写明，免得以后当成遗漏补上（问 615 A）。
- D19 账号自己的操作（补课 05-API 定）：改密码、改邮箱、找回密码、注销账号，首版都不做，进 Out of Scope。PRD 没有这几样的用户故事；把边界写明，免得以后当成遗漏补上（问 636 A）。后果：首版用户忘了密码无法找回，也没有管理员能代为重置，同一邮箱不能重新注册；以后再评估，见 BACKLOG 81。
- D20 密码规则（补课 05-API 定）：最短 15 位，最长不少于 64 位；不要求大小写、数字或特殊字符，允许所有字符，含空格与中文等 Unicode。取代 D9「至少 8 位，含字母和数字」，D9 原文不改。依据 OWASP Authentication Cheat Sheet「Implement Proper Password Strength Controls」：没开多因素认证时少于 15 位算弱，本版没有多因素认证；不该有组成规则；最长至少 64 位，好用一句话当密码（问 649 A、650 A）。拦常见与泄露过的密码、强度提示、哈希算法与具体上限，见 BACKLOG 82。
```

```markdown
## 3 号 · 表象成功 ≠ 实质生效
现象:
```

### 反模式库新增

```markdown
## 24 号 · 重要意图只记进桥梁,不进持久层
现象:学生提出"做成通用 harness"这类长期目标,老师第一反应是记进桥梁。桥梁只活一次,长期方针放进去会每课重抄,某课漏抄就丢。
根因:E4 架构错。把"一次性交接信息"和"贯穿全程的方针"放错了层。
修复:判断信息寿命。只用一次的进桥梁,长期生效的进持久文件(COURSE_RULES 等)。
抽象模式:信息要按寿命分层存放,别把长期方针塞进一次性载体。

## 25 号 · 制度只保证"本次执行",不保证"传承延续"
现象:加了规则保证"这一课更新文件",但没机制保证"下一课也知道要更新"。制度可能三五课后断代。
根因:E4 架构错。设计制度时只想了执行,没想自我延续。
修复:凡新增制度,必须确认它能通过"必读 + 自检"自动传到下一课。检查传承链本身有没有漏(规则 61 是这条的解药)。
抽象模式:23 号是"没固化成标准",25 号是"固化了但传承会断"。设计制度要带自传承机制。

## 26 号 · 新增制度没说清与旧制度的衔接
现象:新写规则 60(结课自检),只写了它自己,没说和现有自检(K 节 1-8 + 规则 57 的 9-11)什么关系。下一课老师可能以为"自检 = 规则 60 这两句",把旧自检项丢了。
根因:E4 架构错。新制度孤立成文,没挂靠到现有体系,造成"新的盖过旧的"误读。
修复:凡新增规则/自检/标准,末尾必须写一句"与现有 X 的关系:叠加生效 / 替代 X / 不影响 X"。双向加指针,旧的也指向新的。
抽象模式:25 号管"制度会不会断代",26 号管"新旧制度会不会打架"。新增制度必须显式声明衔接关系。

## 28 号 · 说明文字夹在命令块之间,被连带复制进终端
现象:老师把多段命令用中文说明("第二段,加规则:")隔开,学生整段复制时把说明也粘进终端,说明行报 command not found,还可能截断前一段命令导致它静默失败(本课 LESSON_TEMPLATE 第一次没改成)。
根因:E2 工具错。命令与说明边界不清,混在一个可复制区里。
修复:一条命令自成一个独立代码块,前后不夹说明文字。要解释就写在代码块外的正文里。关键替换命令内置成功/失败打印,别让它静默失败(配合反模式 3)。
抽象模式:可复制区里只放可执行的东西,人读的说明放外面。和 12 号(代码块套代码块)同源:复制边界要干净。

## 29 号 · PRD 漏掉隐性基础需求
现象：pm 顺着用户研究写 PRD，只记了用户明说的功能需求（看任务、派活、更新进度），漏掉了系统跑起来必需却没人明说的基础需求——注册、登录、登出、权限角色、项目容器本身。后续画 UI、建表、写接口时才发现没地基。
根因：E4 架构错。用户研究天然只产出"用户想要的功能"，不会产出"系统的地基"。纯靠用户研究推需求，必漏基础设施。缺一道专门的补全关。
修复：pm 写完功能性用户故事后，必须额外做一遍"隐性基础需求检查"：这些故事跑起来，底下还需要哪些没人明说的基础件（认证/权限/容器/数据持久化入口）？补进 PRD，来源标"pm 推导的基础需求"，与"已验证""假设"区分。

## 30 号 · git add -A 前不看 status，提交信息漏掉实际改动
现象：用 git add -A 一把全加，把之前别的窗口产出、一直没提交的文件（如 designer.md、PRD.md）一起夹带提交，但 commit 信息只写了本轮预期的改动，没提这些夹带文件。提交信息与实际改动范围对不上，日后翻历史会误判。
根因：E2 工具错。add -A 加入全部改动，提交前未先 git status 看清这次到底要带走哪些文件。
修复：commit 前先跑 git status，逐一确认待提交文件都在预期内；若有预期外文件，要么本轮一并在信息里写明，要么先分开处理。提交信息必须如实覆盖所有实际改动。
```

## 六、Claude Code 知识点

### 让主对话照角色办事

**是什么。** 这一章的 pm 不是子代理。prompt 第一句是「请你以 pm 角色工作」，就是让主对话读定义文件，照着做。

**原理。** 和子代理的区别，第 5 课第六节有表。简单说：这样做，它没有隔离的上下文，权限也不是 `tools: Read` 拦着的，靠的是 prompt 里的「不要落盘」。

**怎么用。** 写需求这种一次出一大段、你要接着审的活，放主对话方便，结果直接在对话里。

**什么时候不用。** 要机器拦着不让写文件，或者不想占主对话的上下文，就用第 1 课那样的子代理。

### 怎么算「被识别了」

**是什么。** 早先的做法是敲 `/agents` 看列表里有没有这个角色。

**原理。** 官方现在写明，`/agents` 只打印一条提醒，叫你直接让 Claude 管理或改文件。这个验证手段不能用了。

**怎么用。** `ls` 看文件在，`grep` 看内容对。真要验它能不能被派上，就派一次，第 1 课第 6 步那样看记录。

### 给角色写 prompt

第 2 步的 prompt 可以当模板：先读定义文件，只读哪几个文件，硬要求，不要做的事，输出结构，停在哪。把「不要做的事」写出来，比只写要做的更管用。

## 七、常见的坑

### 3 号　看起来对，不等于真的成了

**一件事。** pm 文件贴出来内容是对的，当时就算过了。可内容对，不代表存到了磁盘，也不代表行尾干净。

**为什么会这样。** 拿「看起来对」当「确实成了」。

**怎么防。** 走完整条链：内容对，文件在，行尾干净。凡是说「完成」，问一句验到实质了吗。

### 29 号　需求文档漏了隐性基础需求

**一件事。** 九条故事写完、确认完，都提交了。到第 3 课画界面才发现，没有登录页。九条全预设「已登录用户」，没有一条说怎么登录。后来专门开了一次补充，定了八条基础需求和九个决策点。

**为什么会这样。** 用户研究只产出用户想要的功能，产不出地基。

**怎么防。** pm 写完功能故事，必做一遍基础需求检查。第 2 步的 prompt 第 6 条就是这个。

### 24 号　重要的东西放错了地方

**一件事。** 一条贯穿全程的长期目标，差点只记在一次性的交接说明里。交接说明只活一次，某次漏抄就丢了。同一类的事：一份界面草案只在对话里，关了机就没了。

**为什么会这样。** 没想这条信息要活多久。

**怎么防。** 产生的时候就定它的寿命和落点。只用一次的放交接说明，长期的放持久文件，产出物当场落盘。

### 25、26 号　新定的规矩传不下去，或者和旧的打架

**一件事。** 加了一条规矩，只保证这次照做，下次没人知道。还有一次，新规矩只写了自己，没说和旧的什么关系，读的人以为旧的作废了。

**为什么会这样。** 定规矩时只想了这一次。

**怎么防。** 新规矩要写进下次一定会读到的地方，末尾写一句和旧规矩的关系：叠加、替代、还是不影响。

### 28 号　说明文字夹在命令中间

**一件事。** 几段命令用中文说明隔开，整段复制时，说明也进了终端，报 `command not found`。

**为什么会这样。** 能复制的区域里混了不能执行的东西。

**怎么防。** 一个代码块只放能执行的内容。解释写在代码块外面。本书都是这样排的。

### 30 号　add 之前不看 status

**一件事。** 用 `git add -A` 一把全加，把别的窗口做的、一直没提交的两个文件也带走了，提交信息却没提。预期 3 个文件，结果是 5 个。

**为什么会这样。** 没看就加了。

**怎么防。** 第 7 步：先看 `git status --short`，再点名加。

### 没看清就回滚

这一条没有编号。

**一件事。** 一次窗口有点乱，想重开，并把 git 回滚到某个提交。先看了 `git log` 和 `git status`，才发现工作区是干净的，要丢的东西其实只在对话里，一行 git 都不用动。真要是直接回滚了，反而可能丢东西。

**为什么会这样。** 把「重开窗口」和「回滚提交」当成一件事。

**怎么防。** 回滚之前先看状态。有两种回滚要分清：撕掉已经提交的档案（改历史，有风险），和擦掉还没提交的草稿。

## 八、小结与速查

- 要不要做、做到什么程度归 pm。用户看到什么归 designer。系统内部怎么实现归 architect。
- pm 最值钱的动作是说「这个不做」。
- 用户故事：作为谁，我想做什么，以便什么。价值在「以便」。
- 验收标准：给定，当，则。结果只有是或否。
- 来源三种：已验证，AI 假设，pm 推导的基础需求。
- 认、否、改是假设升级的唯一路径。认一条要想它牵动什么。
- 写完功能故事，必查基础需求：认证，权限角色，项目容器。
- 已确认的不改标。已验证的原文不动，用澄清注记。
- 决策点分三档，越界的只定意图。
- 规则书只放骨架，详情指向需求文档。
- 提交之前看 status，核 `N files changed`。

本章用到的命令：

| 命令 | 干什么 |
|---|---|
| `ls 目录` | 看目录里有什么 |
| `file 文件` | 看文件的编码和行尾 |
| `grep -c '词' 文件` | 数文件里有几行含这个词 |
| `git status --short` | 简短地看有哪些改动 |
| `git add 文件` | 点名把文件加进这次提交 |
| `git commit -m "信息"` | 提交 |
| `git log --oneline -5` | 看最近 5 次提交 |

## 九、换个项目还用得上的

判断的标准只有一句：换个项目还用得上的，列在这里；只属于本项目的，不列。

- **需求文档的结构。** 定位，故事，做什么，不做什么，账本，盲区。
- **三种来源。** 已验证，AI 假设，推导的基础需求。
- **隐性基础需求检查。** 写完功能故事必查一遍。
- **认、否、改。**
- **决策点三档。** 必须现在定，可以现在定，只记一句。
- **澄清注记。** 已确认的原文不动。
- **给角色写 prompt 的结构。** 第六节那几样。
- **谁起头定。** 规则、长相、实现三条线。
- **规则书放骨架。** 结构通用，内容换项目就换。
- **提交前看 status，点名加。**

只属于本项目、不往外带的：十八条故事的内容，各决策的具体选择。
