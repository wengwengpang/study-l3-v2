## 二、正式裁决

### API-1 · 字段的唯一真相是共享 Zod schema
API_CONTRACT.md 只写接口层与全局约定：接口清单、方法、路径、鉴权级别、
退回性质到状态码的映射、响应外壳、管住全部接口的全局约定。
每个接口点名它用哪个 schema，字段本体（字段名、类型、必填与否）留给 05-类型。

三份文件各管一段：PRD 管「能不能」，契约管「怎么调」，schema 管「长什么样」。
每条信息只有一个家。

依据是架构第二节取舍 4——类型由 z.infer 推导，不手写 DTO。
契约文档若手写字段，等于换个文件继续手写 DTO。

这条一拍，甲-08（时间格式）、甲-09（必填与多余字段）等条目**被拆开**，不是被砍掉：
业务语义那半回 PRD，全局规则那半留本课，字段本体那半走 05-类型。

### API-2 · 创建项目不依赖项目内角色
任何已登录用户均可创建，创建者自动成为负责人。接口只挂 AuthGuard，不挂 AuthzGuard。

根因不是两句话打架，是权限矩阵问了一个不成立的问题。
角色按项目划分，脱离项目不存在角色身份。创建项目时项目还不存在，
用户在其中没有任何角色，AuthzGuard 需要的「路径项目 id」也不存在。
所以「创建项目」那一格不该填「可」或「否」，该标「不适用」。

比方：办健身卡时被问「您是金卡还是银卡会员」——这个问题在那一刻不成立。

更正（复课前，DECISIONS-R1 R1-369、R1-377）：课上说两处来源分量不同，一处「已验证」，一处「pm 推导」。
对过 PRD，这个说法不成立：两处同在「二之二」一节，来源同为 pm 推导，同经项目主人审定。
API-2 的结论不变，凭的是上一段的理由。

项目数量上限本版不设，进 BACKLOG 32。
不设不是技术结论，是产品取舍——「不做」是事实，「不预留」是取舍，取舍归主人（反模式 33）。
本条不贵：限额是 Service 里一条独立规则，不改表结构不改契约骨架。是门锁，不是门框。

### 三、新做法：标准怎么用（问 345 A）

- 按层定先后：协议层正式标准、安全基线、框架约定、设计规范，都没有才自定。
- 冲突：上下层冲突，上层让下层；同层几家不一，列出来由主人拍，拍完记 ADR 或契约。
- 每条标准分三档：必须照做；建议便宜就做；可选不做但不堵死，记待办。
- 标准管怎么做，不管做多少；凡称「标准」须给原文出处，没核过的标「未核」。

本窗口的两个例子：版本号三家打架（Google 放路径、微软用查询参数、Zalando 尽量不做），按主参考不加；OWASP 原话说 SameSite 顶替不了正式防护，所以另加 NestJS 自带防护。

问题

- 已跟踪文件的差异；
- 新建但未跟踪的文件；
- 已暂存但尚未提交的文件；

## 第四包审查

本包补齐了三个此前缺失的脚本原文，以及两份送审包生成脚本。现在可以审查脚本的实际逻辑，不再只能依据前面材料中的说明。

先说明边界：以下是对你贴出的脚本内容进行静态审查，没有在项目环境中实际运行，也没有看到脚本运行时的日志文件、测试数据或完整报告。因此，我会区分代码中可以直接确认的问题和需要实测的问题。

### 一、`scripts/report-check.sh`

1\. 确定问题：没有验证所选记录文件是否确实包含预期的管理员最终答复。

脚本通过 `agentType == 'librarian'` 找到最近修改的 `.meta.json`，然后读取对应 `.jsonl`。但它把日志中最后遇到的 assistant text 赋给 `last`：

```
if d.get('type') == 'assistant' and b.get('type') == 'text':    last = b['text']
```

它没有进一步确认这段文字是不是管理员最终交付的体检报告正文。

这意味着：如果管理员最后一条 assistant 文本不是报告正文，脚本就会拿错误的文本与报告比较。结果可能是误报，而不是准确指出报告与管理员最终返回不一致。

\*\*建议：\*\*明确最终答复的识别条件，至少检查日志末尾的消息结构，并确认被比较的文本确实是管理员最终答复。不能只依靠“最后遇到的 assistant text”。

2\. 待核实：最近的元数据文件不一定对应最新、完整的日志。

```
log = max(metas, key=os.path.getmtime).replace('.meta.json', '.jsonl')
```

这是按元数据文件的修改时间选择记录，而不是按日志文件的修改时间，也没有确认对应 `.jsonl` 存在、完整且可读取。

\*\*建议：\*\*至少检查对应日志文件存在，并在读取失败或记录不完整时明确报错。是否需要改成按日志文件时间选择，应结合 Claude Code 实际记录结构验证。

3\. 已有的防重复设计基本合理，但仍有边界。

脚本按 `tool_use_id` 归拢重复返回，并检查同一次调用的多份返回是否一致；也会在识别到多次 `doc-check.sh` 调用时停止。这些设计与注释中的核对目标一致。

但目前只核对能够从日志中识别出的工具调用和返回。它没有独立证明日志记录完整，也没有证明管理员最终报告确实采用了唯一那次调用的结果。

\*\*建议：\*\*把“日志中识别到唯一一次调用”与“报告采用的就是这次调用”分成两个核对条件，不要把前者当成后者的充分证明。

### 二、`scripts/doc-check.sh`

这份脚本是本包最值得仔细审查的部分。它覆盖编号、引用、文件行数、文件变化和去留标记，整体上有明确的机械检查目标。

但它的检查能力存在边界。

1\. 确定的能力边界：它只能检查已纳入 Git 跟踪的文件。

```
files=$(git ls-files ...)
```

因此，未跟踪的新文件不会进入 `files`。

这与前面已经发现的送审范围问题相关：新增文件可能尚未被 Git 跟踪，却已经成为项目实际交付物。脚本不会自动发现它们。

S6 同样明确只比较已提交的文件变化，注释已经说明了这一点。

\*\*建议：\*\*保留“已跟踪文件”的检查，同时明确另有一项检查未跟踪文件。不能把 S1–S7 的检查结果解释为整个项目文件范围已经完整。

2\. 确定的能力边界：引用计数不等于语义引用核验。

`refs()` 通过正则表达式提取编号，跳过标题行，但没有排除代码块。

因此，代码示例、命令示例中的编号也可能被算成引用。这可能让某个规则看起来已被常驻文件引用，实际却只是示例中出现过编号。

这与原则19、原则18所强调的“核对实际内容”不是一回事。

\*\*建议：\*\*至少明确引用统计包含代码块这一限制。如果项目要求引用必须是有效的正文引用，应当排除代码块，或增加人工复核。

3\. 确定的能力边界：S3 的区间检查并不覆盖所有可能的引用写法。

脚本支持 `45、61`、`18 到 20`、`18-20` 等形式，并对跨度超过10的区间另行列出。

但它依赖固定的文本格式和正则表达式。不同写法、特殊连接符、格式漂移可能导致漏检。

脚本已经对取出0条作了提醒，这一点是合理的；但取出非零条数并不代表所有引用都成功识别。

\*\*建议：\*\*把输出定义为“按约定格式提取到的编号”，不要称为完整的引用审计。高风险引用仍需要原文核对。

4\. 确定的能力边界：S4 不能判断规则是否真正有用或应该删除。

S4 检查的是规则是否在常驻列被引用，并把未引用规则标成删并候选；脚本注释也明确写了“删不删学生判”。

这个权限边界是正确的。

但反过来说，S4 不能证明某条规则没有价值，也不能证明一条被引用的规则仍然有效。它只是引用统计。

\*\*建议：\*\*维持现有定位，不要把 S4 输出升级成自动删并依据。

5\. S6 的限制已经写明，但要避免被误读。

S6 从上次报告的提交开始，只比较已提交变化：

```
git diff --name-status --diff-filter=ADR "$last" HEAD -- docs CLAUDE.md .claude scripts
```

它不会列出未提交变化。这一点与注释相符，不是代码与注释不一致。

但如果用户把 S6 输出当作完整的送审文件变化清单，就会漏掉未提交改动。

\*\*建议：\*\*报告中明确区分已提交变化和未提交变化；不能只依靠 S6。

### 三、两份送审包生成脚本

这里发现一个比前面几个统计边界更直接的问题。



确定问题

&#x20;两份生成脚本的 `run()` 都会吞掉命令失败状态。



两份脚本都使用类似逻辑：

```
run() {
  printf '【命令】\n%s\n【输出开始】\n' "$1"
  bash -c "$1" 2>&1
  printf '\n【输出结束】\n\n'
}
```

`bash -c` 执行失败后，函数仍会继续执行最后的 `printf`。由于没有保存并检查前一条命令的退出码，函数最后通常返回 `printf` 的成功状态。

因此：

- 命令执行失败，生成脚本仍可能继续；
- 命令只输出部分内容，也可能被当成正常输出收录；
- 最终送审包没有可靠的失败标记；
- 审查者无法仅凭包内的【输出开始】和【输出结束】判断命令是否成功。

这与脚本头部强调的“原文一律命令导出”存在重要缺口：原样输出不等于成功、完整的原样输出。

\*\*建议：\*\*每次执行后立即保存 `$?`，把退出码写入输出，并在失败时明确标记。对于关键导出命令，最好让生成脚本在失败后停止，避免产生看似完整的送审包。

另外，`make-review-05api.sh` 和 `make-review-05api-supp.sh` 都使用 `set -u`，但没有启用能阻止失败命令继续执行的机制。仅有 `set -u` 不能解决这个问题。

1. 送审生成脚本没有可靠的退出码机制
严重
位置：第一包末尾，make-review-05api.sh 的 run() 函数。

原文：
run() {
  printf '【命令】\n%s\n【输出开始】\n' "$1"
  bash -c "$1" 2>&1
  printf '\n【输出结束】\n\n'

这里有两个问题：
- 没有保存和打印 bash -c 的退出码。

这与送审包最重要的证据要求冲突：审查者必须知道每条命令是否真正成功。

Claude Code Docs+1

这对 R1-523 有三个具体影响：

Claude Code Docs

因此，如果目标是：
指纹不一致，就不能继续执行受保护的操作。

更合理的设计是：
- SessionStart：读取并报告当前状态。
- PreToolUse：在受保护的工具操作之前检查状态，不符合条件就拒绝。
- SubagentStop：检查子代理交付结果，不符合条件就要求修正。
