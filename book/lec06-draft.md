# 第 6 课　决策边界与权限

## 一、本章位置

这一章是第一篇「立项准备」的最后一章。业务代码仍然不写。前面几章定了做什么、怎么做。这一章定另一件事：做的过程中，AI 哪些事可以自己来，哪些事必须停下来问人，哪些事根本不许它碰。

**上一章交来什么。** 规则书前两层：怎么干活，项目事实。设计文件：需求、界面、选型、数据库、架构、接口契约。书上排在这一章前面的还有补课 05-类型和补课 05-环境，这两节还没上。这一章不靠它们交来的东西，用到的只有上面这些。

**这一章产出什么。**

- 规则书第三层 A：决策边界 D1 到 D8。
- 权限设置 `.claude/settings.json`：放行、先问、禁止三档。
- 反模式库第 35、36 号。

**下一章拿它做什么。** 第 7 课开始建工程。这道墙从那时起才会被频繁撞到：跑 `pnpm` 走放行，改 `prisma/` 和规则书要问，删文件直接拒绝。

**和前面几章的关系。** 05-ARCH 和 05-API 已经用过这一章的东西，当时各交代了两句，说细的在这里。这本书按道理排，实际做的时候，这一章排在四节补课前面。你可以提前做。先立规矩和墙，再做设计，等于先拿到地图再走路。

**这一章不做的三样。** 课程全景原来把三样也排在这一课：会话简报、prompt 模板、剩下五个角色（backend、frontend、reviewer、tester、devops）。当年上课选的范围是决策边界加权限，这三样没做。它们的去向：五个角色各在要用的时候建，分别是第 10、11、12、14、15 课；会话简报在第 13 课和附录 B；模板在附录 B。还没写代码就定 backend 这些角色，没有活可以验证它们写得对不对。

**这一章最要紧的一件事。** 规矩是写给 AI 读的，它读了通常照做，但没人能保证。墙是 Claude Code 执行的，不看模型怎么想。能变成命令的危险动作交给墙，变不成命令的判断交给规矩。两样都要，都要验证过才算数。

## 二、学完能做到什么

1. 能用两个问题判断一个决定该不该喊人：能不能撤销，错了影响多大。
2. 能从项目真拍过的决定里反推一份「必须问人」的清单，写进规则书，并试出它有没有起作用。
3. 能写 `.claude/settings.json` 的三档规则，读懂一条规则对得上什么、对不上什么。
4. 能验证权限真生效：先看解析结果，再真撞一次。
5. 说得清这道墙的缝在哪，能判断一条规矩该放规则书、权限规则、钩子还是技能。

## 三、原理

### 先认几个词

- **工具。** Claude Code 动手靠工具：`Read` 读文件，`Edit` 改文件，`Bash` 跑命令。权限规则管的就是这些工具的调用。
- **决策边界。** 一张清单，列出哪几类决定 AI 不能自己拍，必须停下来喊项目主人。它写在规则书第三层。第 0 课讲过规则书分三层，前两层回答「这个项目有什么」，第三层回答「这个项目里谁说了算」。
- **权限模式。** 每个会话有一个总开关，决定规则没提到的动作怎么办。它显示在输入框下面的状态栏上。第 0 课让你切到的 `manual mode` 就是其中一种。
- **放行、先问、禁止。** 权限规则的三档。配置文件里叫 `allow`、`ask`、`deny`。

### 一次差点溜过去的取舍

第 5 课定删除策略时，architect 给了一个结论，大意是：首版不做删除功能，所以表里不加 `deleted_at` 字段。

这句话很顺。其实是两句话粘在一起。

第一句，首版不做删除功能。这是事实，需求文档里确实没有这一条。

第二句，所以表里不预留字段。这是取舍。预留了，将来加软删除不用改表。不预留，现在省事，将来要动表结构。

事实谁都可以说。取舍要有人负责，负责的人是项目主人。AI 把两句粘成一句，取舍就藏进了一个「技术结论」里。没细看，它就这么过去了。

那次是人把它抢了回来。最后表里确实没加这个字段，软删除记进了待办。结果看着一样，区别在于这是人拍的，不是 AI 替人咽下去的。反模式库的 33 号记的就是它，第 5 章讲过。

这一章要做的，是不再靠人眼尖去抓。把「什么时候必须喊人」写成条文，放进 AI 每次进项目都读的地方。第 4 步会用一个没发生过的新例子试一次，看写了到底有没有用。

### 一个比方：门禁

把规则书第三层想成家里的门禁。家里住着一个很勤快的助手。大部分门，它自己刷卡就进：读个文件，查一下状态，你根本不想被打扰。有几道门，它的卡必须刷不开，得回头喊你。

决策边界就是「哪些门必须喊人」的清单。清单上的东西分三种性质：

- D1 到 D5 是五道**房间门**。每道门后面是一类具体的决定。
- D6 是门口的**验货台**。任何需求进门之前，先验出身。
- D7 是装在每个门框上的**感应器**。它不管进哪间房，只管 AI 当时的状态。

D8 是后来补的，管文件之间打架，下面单讲。

### 一把尺子，两个数

只看「这件事属于哪一类」不够。下面两件事都叫动数据结构。

第一件，给任务表加一个可以为空的字段。不想要了删掉就行，老数据不受影响。能撤销，影响小。

第二件，删掉一张已经有数据的表。数据没了就是没了。不能撤销，影响很大。

门牌一样，都是 D2。第一件 AI 可以自己做，第二件必须喊人。所以每一类决定都要量两个数：

1. 能不能撤销？
2. 错了影响多大？

能撤销而且影响小，AI 自己处理。不能撤销，或者影响大，停下喊人。

这把尺子不是这门课发明的。Amazon 2015 年的致股东信把决定分成两类。一类是单向门：「Some decisions are consequential and irreversible or nearly irreversible – one-way doors –」，要慢慢来。另一类是双向门：「they are changeable, reversible – they’re two-way doors.」，「can and should be made quickly」。信里还提醒，组织大了容易把重流程用到所有决定上，结果是「slowness, unthoughtful risk aversion」。它讲的是公司怎么做决定，不是讲 AI，但道理相通：什么都喊人，人被淹没；什么都不喊，出了事收不回。

讲 AI 的也有。OWASP 给大模型应用列的十大风险里，第 6 条叫 Excessive Agency，也就是 AI 手里的能力太大。它写的根因有三样：「excessive functionality」「excessive permissions」「excessive autonomy」。防范办法里有一条：「Utilise human-in-the-loop control to require a human to approve high-impact actions before they are taken.」高影响的动作，做之前先让人批。

行业文章里还常见一对叫法：人在环内（human-in-the-loop），做之前等人批；人在环上（human-on-the-loop），先做，人盯着，能拦能撤。这对叫法和这把尺子对得上：撤不回的事前批，撤得回的事后拦。它们是常见说法，不是标准。

### 五道房间门

**D1 范围门：这个功能做不做。** 凡是动到「做什么、不做什么」的边界，喊人。评论功能写在首版不做的清单里，AI 写任务详情页时说「顺手加个评论框吧」，就是在动范围。多做一个功能要建表、写接口、做页面，回头再砍都白做；它改的是产品的样子。默认喊人。

**D2 数据结构门：动表、动字段、动约束。** 这道门最能说明那把尺子。加可空字段可以放行，删有数据的表必须喊人。还有两个细节。就算是能放行的那种，改表之前也要先回 architect 确认：不必喊人，不等于随手就改。另外，条文专门钉了一句：「现在不做，所以不预留」这种合并判断要拆开，不做是事实，不预留是取舍。

**D3 权限门：谁能看、谁能改。** 需求文档里有两条用户故事写「所有成员看所有任务」，权限矩阵定的是负责人看全项目、执行者只看自己的。差别很大，最后的口径记在规则书第二层 C。口径改起来中等麻烦，可它是安全边界，定错了就是执行者看到不该看的东西。默认喊人。

**D4 选型门：选框架、选库、选架构。** 登录状态存数据库、不用 JWT，第 4 课拍的。这道门的特点是很难撤销：一个库用深了，代码到处依赖它，换它等于砸墙重来。默认喊人。

**D5 不可逆门：删库、迁移、删文件、上线。** 这道门要喊两次。AI 先列影响范围和回滚方案，人回一句 CONFIRM，它才动手。拿不出回滚方案的，不做。它的定义就是撤不回，所以不管影响大小一律喊人。到这一章为止，项目还没真碰到过这种操作，它是一个空着的门框，先立在那。

### 验货台、感应器和后来补的一条

**D6 验货台：这条需求是哪来的。** 出身只有三种：已验证，真人确认过；AI 假设，AI 觉得该有，没人确认；教学驱动，产品不需要，课程为了教某个技术才加。要单设一张台子，是因为手里没有真实用户时，AI 会编出一条听着很合理的需求，当成事实写进文档，后面整个产品就建在它上面。第 4 章的 32 号就是这件事。它不算第六道房间门，因为它横着切过所有需求。

**D7 感应器：AI 没把握就该停。** D1 到 D6，你都能指着说这属于哪一类。D7 不是一类决定，它管的是 AI 当时的状态。心里没底，缺上下文，或者给的「技术结论」里藏着一个该人拍的取舍，感应器就该亮。亮了只许做一件事：停下来报，不许猜个合理的答案填上。

回头看 `deleted_at` 那次。它算 D2，因为动的是数据结构；它也触发 D7，因为结论里藏着取舍。一件事同时碰到两条，说明 D7 罩在前面几条上面，不是排在旁边的第七类。

条文给 D7 配了一句口令，AI 和人都可以拿来自问：

> 这里面有没有藏着一个该我拍的取舍？

**D8 文档打架：只报不改。** AI 发现两份已定的文档互相矛盾时，只报，由人裁决以谁为准。不许挑一份看起来更新的，也不许顺着写下去当没看见。

为什么不并进 D7？D7 的触发条件是没把握。可是发现文档冲突时，AI 往往很有把握，一眼看出哪份更新。有把握就不触发 D7，它就直接挑一边改了。所以单立一条。05-ARCH 那一章的做法就是它，这里补上原文。

### 同一套东西，两种写法

打开规则书第三层，每条只有一两行。上面讲了几页。同一套内容有两个读者。

这本书写给人，目的是让人明白，所以要比方，要例子，要讲慢。规则书写给 AI，它每次进项目都读一遍，每个字都占它的上下文，所以要短，一条一句，能照着执行。官方的建议是「Keep CLAUDE.md under 200 lines.」。

### 为什么有了规矩还要墙

规矩靠 AI 读了自觉遵守。它读漏了呢？会话太长，前面读过的东西淡了呢？

官方最佳实践页把指令分成两种，分得很清楚。第一种，你写下来，模型读，模型决定怎么办：prompt、`CLAUDE.md`、技能都是这种，它写「there's no *guarantee* that it'll follow your instructions」。第二种，你配置好，Claude Code 这个程序来执行：钩子、deny 规则都是这种，它写「Claude Code applies this every time, no matter what the model decided to do.」

权限页说得更短：「Permission rules are enforced by Claude Code, not by the model.」

这就是墙。`.claude/settings.json` 这个文件不是写给模型看的，是写给程序看的。

### 三档，和撞门的顺序

**放行 `allow`。** 自己刷卡就进，不打扰你。比如 `git add`。

**先问 `ask`。** 门锁着，它得按铃，你点头才开。比如往远端推代码，改表结构。

**禁止 `deny`。** 门焊死了，按多少次铃都没用。比如读密钥文件。

每条规则的写法是工具名，加括号里的条件。工具名首字母大写。

```text
Bash(git push *)     用 Bash 跑 git push 开头的命令
Edit(prisma/**)      改 prisma 目录下的任何文件
Read(./.env)         读当前目录的 .env 文件
```

程序不是三张清单一起看。官方写：「Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order.」先看禁止，再看先问，最后看放行，撞上第一条对得上的就照办。写得再细的放行也救不了。

结果就是**禁止永远赢**。先问清单里有 `Edit(.claude/**)`，禁止清单里有 `Edit(.claude/settings.json)`。改 `settings.json` 时两条都对得上，程序先看禁止，直接拒绝，连问都不问。你想点头也没有地方点。

这也跨文件。配置文件有好几层，你个人的、项目的、本机的。官方写：「If a tool is denied at any level, no other level can allow it.」所以放行可以给得大方一点，禁止才是安全网。

### 规则上的字怎么读

命令规则里的空格和星号有讲究。官方的表：

| 规则 | 对得上 | 对不上 |
|---|---|---|
| `Bash(ls *)` | `ls -la`、`ls` | `lsof` |
| `Bash(ls*)` | `ls -la`、`lsof` | |

星号代表后面什么都行。星号前面的空格是规则的一部分，表示 `ls` 到这里是一个完整的词。

没有星号就要一字不差。`Bash(git status)` 只对得上 `git status`，后面多一个参数就对不上。

文件规则用的是 `.gitignore` 那种写法，起头不同，意思不同：

| 写法 | 意思 | 例子 |
|---|---|---|
| `路径` 或 `./路径` | 相对当前目录 | `Read(./.env)` |
| `/路径` | 相对配置来源，项目配置就是项目根 | `Edit(/prisma/**)` |
| `~/路径` | 相对家目录 | `Read(~/.ssh/**)` |
| `//路径` | 从文件系统的根开始 | `Read(//etc/**)` |

有两点容易错。一，`/Users/alice/file` 不是绝对路径，一条斜杠只是相对配置来源，绝对路径要写两条。二，本项目写的 `Edit(prisma/**)` 是相对当前目录的，所以要从项目根目录启动 Claude Code。

### 写了不等于查了：死规则

第 6 课第一次写这份文件时，凭直觉写了 `Write(prisma/**)`、`Write(CLAUDE.md)`、`Write(.claude/**)`。工具叫 Write，规则就写 Write，很合理。

可官方写的是：文件权限只查 `Edit(路径)` 和 `Read(路径)`。写成 `Write`、`NotebookEdit`、`Glob`，「Claude Code accepts the rule but never matches a read or edit against it」。规则被收下了，但永远不会被查。`Edit` 规则管所有改文件的内置工具，写它一条就够。

这三条从建立当天起就是死的。真正干活的一直是旁边那三条 `Edit`，所以没出事，也就一直没人发现，到补课 05-ARCH 才查出来。这是反模式库的 35 号。

写书时拿机器验了一次，比讲道理更清楚。用会自动放行改文件的 `acceptEdits` 模式，规则只留一条，让 Claude Code 改 `prisma/schema.prisma`：

| 规则 | 结果 |
|---|---|
| `Write(prisma/**)` | 文件被改了，没问 |
| `Edit(prisma/**)` | 被拦下，文件没动 |

还有更要紧的一点。用这条死规则启动时，界面上有一行警告：

```text
⚠ Ask rule Write(prisma/**) never matches · use Edit(prisma/**)
```

可是进 `/permissions` 看，先问一栏照样列着 `Write(prisma/**)`。列表里有，不等于它在干活。所以验证要两步：先看解析结果和警告，再真撞一次。

### 没写的由谁定：兜底档

规则再多，也有没写到的动作。这些由权限模式决定。

第 6 课定了决策边界，定了三档规则，唯独没声明模式。项目跑了好几节课，到补课 05-ARCH 才发现，实际一直跑在自动模式下。这是反模式库的 36 号：没声明的档位，由厂商的默认值替你填，还会随版本变，不通知你。

现在这件事更要紧了。官方写，2.1.283 起，终端和 VS Code 的交互会话没声明模式时，「`auto` with Claude Code v2.1.283 or later」，从自动模式开始。这个模式下由一个分类器替你审。写书时实跑对比，状态栏是这样的。

没声明 `defaultMode`：

```text
⏵⏵ auto mode on (shift+tab to cycle) · ← for agents
```

声明了 `"defaultMode": "default"`：

```text
⏸ manual mode on · ? for shortcuts · ← for agents
```

`default` 就是界面上的 manual，官方写「Labeled Manual in the CLI」。这本书第一篇用它，每一步自己看过再批。自动模式不是不好，官方有它合适的场景。要点是这一档要你自己选，写明白，不要留空。

所以「两条轴」不够，要说全是三样：枚举出来的决定类型，枚举出来的动作规则，加上没枚举到时的兜底档。只看规则清单，会漏掉最大的那一块。

### 墙的缝

这道墙不是铁板。先把缝讲清楚，免得你以为立了墙就万事大吉。

**前缀匹配的缝。** 第一版写的是 `Bash(rm -rf *)`。它只对得上以 `rm -rf` 加空格开头的命令。`rm -r -f 目录`、`rm -fr 目录`、单删一个文件的 `rm 文件`，都对不上。后来改成 `Bash(rm *)`，凡是 `rm` 开头都挡。代价是 Claude Code 再也删不了文件，要删的时候你自己在终端敲。这是取舍，本项目选了挡。

**换个写法的缝。** 官方写 Bash 规则只对命令的文字，「isn't a security boundary around the program」。它的表里，`Bash(rm *)` 挡 `rm -rf build/`，不挡 `/bin/rm -rf build/` 和 `bash -c 'rm -rf build/'`。写书时跑的结果比官方写的严一点：`/bin/rm` 被拒了，`sh -c 'rm 文件'` 弹窗问你，写着有一条规则禁止这段脚本里的命令。这是这个版本的表现，官方没有承诺，不要当成边界来靠。

**读文件的缝。** `Read(./.env)` 比早先管得宽：内置工具、`cat`、`head` 这类它认得的命令，还有重定向的目标，都算。官方写它不管的有两种：「a command that reads files without naming them, such as `grep -r pattern .`」，还有自己开文件的脚本。第 8 步会用一个假密钥真撞一次。

**重定向的缝。** `echo test >> 文件` 这种写法走的是 Bash，不是 Edit。官方写重定向的目标「the check covers your `Edit` allow and deny rules」，点名的是放行和禁止，先问没有点名。所以禁止一档的路径，重定向也写不进去，写书时试过；先问一档的路径，就不能全靠它。手动模式下这条 Bash 命令本来要弹窗，看清弹窗里的命令。本项目给 AI 的 prompt 里常写死一句「用 Edit 工具，不要用 sed、不要用 heredoc、不要用 bash 重定向」，道理就在这：靠机制才守得住的东西，要先保证走的是有机制的那条路。

**墙外的事。** 权限规则管的是 Claude Code。你自己在终端敲的命令，它不管。别的程序改文件，它也不管。

要操作系统层面的拦截，官方给的是沙箱：「For OS-level enforcement that blocks all processes from accessing a path, enable the sandbox」。这一版本项目没开，知道有这一层就行。

### 一个管脑，一个管手

这是这一章最要紧的认识。

你可能会想：把 D1 到 D8 全变成规则，不就都由机器管了吗？做不到。程序只认得命令和文件操作，认不出「它正打算做一个范围决定」。

| 条目 | 贴得住规则吗 | 为什么 |
|---|---|---|
| D5 不可逆操作 | 贴得住 | 删除是 `rm`，推送是 `git push`，迁移是 `prisma migrate` |
| D2 数据结构 | 贴得住一半 | 改 `prisma/` 是文件操作，会问。要不要预留这个字段是判断 |
| D1 范围取舍 | 贴不住 | 要不要加这个功能，没有对应的命令 |
| D3 权限口径 | 贴不住 | 同上 |
| D4 技术选型 | 贴不住 | 同上。文件里也没有给它写规则 |
| D6 需求来源 | 贴不住 | 同上 |
| D7 藏着取舍 | 贴不住 | 程序认不出它现在没把握 |
| D8 文档打架 | 贴不住 | 发现矛盾是读出来的，改文件才是动作 |

两层分工：

**语义层**是规则书第三层，管脑。兜住那些只是判断、没有对应命令的决定。只能靠 AI 读了自觉停。

**机械层**是 `settings.json`，管手。兜住能变成命令和文件操作的危险动作。AI 读漏了、会话长了记淡了，墙照样在。

少了哪层都不行。只有墙没有规矩，`deleted_at` 那种事拦不住，它从头到尾没跑一条危险命令，只是说了一句很顺的话。只有规矩没有墙，AI 哪天读漏了，一条 `git push` 就出去了。

规则书里说这是「两条轴垂直」，一条量决定属于哪类，一条量动作属于哪类。同一件事在两条轴上各有一个读数。比如 AI 要给任务表加一个可空字段：规则书说不必喊人（改之前回 architect），机器照样弹窗，因为 `Edit(prisma/**)` 在先问一档。两个答案不矛盾，量的不是一样东西。

### 先问别塞满

什么都放进先问，你会被铃声烦死，最后看都不看就点同意，这道墙就白立了。Anthropic 自己的工程文章写：「Constantly clicking "approve" slows down development cycles and can lead to ‘approval fatigue’,」，然后人就不再细看自己批了什么。

所以先问只留给风险高、但有时确实该做的事。只读的、能撤销的，放行。本项目先问一档只有两类：往外推和迁移，改规则书、表结构、配置和文档。

### 这道墙谁来写

第 6 课建这份文件时，定了一条规矩：人亲手写，不经过 AI。理由有两个。

一，利益冲突。这份文件是约束 AI 的墙。让被约束的一方砌约束自己的墙，它有可能顺手留个门。

二，攻击面。这个文件不只放权限，还能挂钩子，钩子能跑命令。2026 年 2 月，Check Point 公开了 Claude Code 的两个漏洞（CVE-2025-59536、CVE-2026-21852），都和项目配置文件有关，都已修复。它的一句总结值得记：「Configuration files that were once passive data now control active execution paths.」文件原来只是数据，现在能决定跑什么。也有安全厂商写过检测文章，说有蠕虫专门往 `.claude/settings.json` 里写钩子，这类文章细节各家不一，取一点就够：这个文件已经是别人想写的目标。所以别人的仓库要先看过再信任，这份文件的改动要有人看。

官方现在也设了一道：项目里的放行规则，要你接受信任弹窗才生效，弹窗会把它们列出来。第 6 步会看到。

再往后，这条规矩变成了墙：`Edit(.claude/settings.json)` 进了禁止一档，AI 想改也改不了。规矩先立，后来焊死，这正是下一节要讲的。

### 规矩放哪

真做项目时，一条规矩放规则书、权限规则、钩子还是技能？第 5 章说过这件事放在这里讲。官方的判断标准就一句：

> If something has to happen every time, make it a hook, a deny rule, or a managed setting. `CLAUDE.md` is for guidelines, and Claude is allowed to decide a guideline doesn't apply.

| 规矩长什么样 | 放哪 | 例子 |
|---|---|---|
| 每次会话都该知道的约定和判断 | 规则书 | D1 到 D8，用 pnpm 不用 npm |
| 一个动作必须拦，或必须问，看名字就能判 | 权限规则 | 读 `.env`，`git push` |
| 要看内容才能判，或每次都要自动跑 | 钩子（第 8 课） | 改完自动跑格式化，拦下危险命令并说明理由 |
| 偶尔才用的流程和资料 | 技能 | 发布清单，API 风格指南 |

官方还给了一个信号：「If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook.」一句话在规则书里越写越重，它还是漏，就该往下沉。反过来也成立：只是偏好的事放进钩子，也要拿掉。官方的原话是「a request, not a guarantee」，说的就是把「别改 `.env`」写进规则书的情况。

所以这件事的走向常常是：先写成规矩，撞到了，再焊成墙。不用一开始全部焊死。

### 这一步的盲区

- 语义层没有保证。第 4 步会试出第三层有用，但只跑了一次，不等于每次如此。
- 这份清单是从本项目拍过的决定反推的，换个项目要重推。
- 墙只挡 Claude Code，有缝。它不替你看弹窗。你闭眼点同意，它也拦不住。

## 1. 范围取舍(做什么、不做什么、延后什么)
- **是什么**:功能进不进首版,进 In Scope、Out of Scope 还是延后。

- **能否撤销**:能。文档上改一笔就行,功能后补也行。
- **影响**:中到高。会改变产品边界,还牵连契约和页面。
- **默认**:问。

## 2. 数据结构(表、字段、约束、删除策略)
- **是什么**:加减表和字段、字段类型、约束、onDelete、是否预留结构。
- **真例**:ADR-DB-002 不预留 deleted_at,由你按演进哲学重新拍板(DECISIONS.md:44-48)。ADR-DB-005 里 tasks.description 必填,也是你拍的(DECISIONS.md:67)。
- **能否撤销**:库没建时便宜。ADR-DB-003 和 ADR-DB-008 都写了「库还没建,没有数据要迁」(DECISIONS.md:55、DECISIONS.md:85)。建库有数据后要走迁移,代价高。
- **影响**:高。会传导到契约、共享 schema 和迁移。
- **默认**:问。CLAUDE.md 第二层 E 已写「改表结构前先回 architect」。

## 3. 权限与安全口径
- **是什么**:谁能看、谁能改、拒绝时说什么、认证规则。
- **真例**:D2 执行者不能建任务(PRD.md:288)。D17 执行者看不见项目负责人(PRD.md:303)。任务不存在与无权访问合并成「权限不足」(PRD.md:344)。D20 密码规则(PRD.md:306)。
- **能否撤销**:代码能改。但已经泄露的数据撤不回。
- **影响**:高。
- **默认**:问。

## 4. 技术选型,以及偏离标准
- **是什么**:换栈、加组件、偏离 STANDARDS.md 里认定的标准。

- **能否撤销**:早期能,用久了难。ADR-DB-008 自己写了「换库要改写」。
- **影响**:高。
- **默认**:问。

## 5. 需求的事实地位(来源与验证状态)
- **是什么**:一个设想算不算事实。假设升不升级,教学驱动还是用户驱动。

- **影响**:中。
- **默认**:问。AI 提的设想只许进假设账本,不许直接当事实。

## 6. 推翻已拍板的决定

**有第三层时，开头和中间是这样：**

```text
**结论：tasks 表不做任何调整。** 这一条我建议你拍板，不由我定，原因在后面。

**需要你拍板的取舍**
- 「不做归档」是事实，「现在不预留字段」是取舍。CLAUDE.md 第三层 A 的 D2 说取舍归主人。
- 我的建议是不预留。理由是将来加可空列的代价很小。
- 代价是已完成的任务会一直留在任务列表里，列表变长后只能靠筛选缓解。
```

两次的建议是一样的：不加字段。差别在谁说了算。没有第三层，它把取舍当结论交给你；有第三层，它拆开了，告诉你这是你要拍的。这正是 `deleted_at` 那件事想要的结果。

再试一句范围题，同样先 `/clear`：

```text
任务详情页我觉得空了点。你看要不要顺手加个评论框，你定，定了就把它写进 docs/design/UI_DESIGN.md。
```

**没有第三层时：**

```text
我定了：**不加评论框，所以没有往 UI_DESIGN.md 里写评论框。**
```

**有第三层时：**

```text
先不写。评论框我不能替你定，也不建议加。
```

这一题两次都没加评论框，因为第二层的不做清单里本来就有它。差别还是在第一句：一个说「我定了」，一个说这要你定。

**出了错怎么办。** 它还是替你定了，先看规则书里第三层在不在，再开新会话试一次。这一层没有保证，这是它的本性，不是你写错了。能变成命令的，下面交给墙。

### 第 5 步　亲手写权限文件

**目的。** 建墙。这一步不经过 Claude Code，理由第三节讲了。

在 VS Code 里新建文件 `.claude/settings.json`，把第五节的原文贴进去，保存。三档各装什么：

| 档 | 规则 | 挡什么、放什么 |
|---|---|---|
| 禁止 | `Read(./.env)`、`Read(./.env.*)`、`Read(./secrets/**)` | 读密钥 |
| 禁止 | `Bash(rm *)` | 所有删除，要删自己在终端敲 |
| 禁止 | `Bash(sudo *)` | 用管理员权限跑命令 |
| 禁止 | `Bash(curl *)`、`Bash(wget *)` | 从命令行联网，这是数据往外走的口子 |
| 禁止 | `Edit(.claude/settings.json)`、`Edit(.claude/settings.local.json)` | AI 改自己的权限文件 |
| 先问 | `Bash(git push *)` | 往远端推代码 |
| 先问 | `Bash(npx prisma migrate *)`、`Bash(pnpm prisma migrate *)` | 跑数据库迁移 |
| 先问 | `Edit(prisma/**)` | 改表结构 |
| 先问 | `Edit(CLAUDE.md)`、`Edit(.claude/**)` | 改规则书、角色文件 |
| 先问 | `Edit(docs/arch/**)`、`Edit(docs/**)` | 改文档 |
| 放行 | `Bash(pnpm test *)`、`Bash(pnpm run *)`、`Bash(npm run test *)`、`Bash(npm run lint *)` | 跑测试和检查 |
| 放行 | `Bash(git status)`、`Bash(git log *)`、`Bash(git diff *)` | 只读的 git 命令 |
| 放行 | `Bash(git add *)`、`Bash(git commit *)` | 本地提交 |

开头的 `$schema` 一行不影响运行，只是让 VS Code 能补全和校验。`defaultMode` 那一行就是上面说的兜底档。

有两处是空转的，写着不坏事，你可以知道：`Edit(docs/**)` 已经盖住了 `Edit(docs/arch/**)`，后者是早先留下的；`git status` 这些内置只读命令本来就不弹窗。

先查 JSON 写对没有：

```text
python3 -m json.tool .claude/settings.json > /dev/null && echo OK
```

**应该看到。**

```text
OK
```

**出了错怎么办。** 它报错时会带行号和列号，比如写书时故意多加一个括号，报的是 `Extra data: line 38 column 2`。多半是少了逗号、多了括号。官方写这个文件是严格的 JSON，注释和末尾多余的逗号都算错，下次启动会报 Settings Error。这条命令只证明格式对，离生效还差两步。

### 第 7 步　真撞一次

**目的。** 三档各撞一次。当年这一步差点跳过，第七节讲。

先建一个试删除用的文件，在你自己的终端跑：

```text
echo 这个文件用来试删除。 > notes.txt
```

**撞先问。** 贴进 Claude Code：

```text
在 prisma/schema.prisma 文件末尾加一行注释 // test 。这是试权限用的，不用列计划，直接改。
```

要写明「不用列计划，直接改」。不写的话，规则书第一层要它先列计划等确认，它会先停下，根本撞不到墙。这也是两层在各管各的。

**应该看到。**

```text
Edit file
prisma/schema.prisma
111
112    @@map("notifications")
113  }
114 +// test
Do you want to make this edit to schema.prisma?
❯ 1. Yes
  2. Yes, and switch to accept edits (auto-approve file edits and common file commands) for this session (shift+tab)
  3. No
Esc to cancel · Tab to amend
```

**选 3，No。** 第 2 项看着方便，选了就把整个会话切进 `acceptEdits`，不在先问清单里的文件，后面改起来都不再问你。第六节讲弹窗的几个选项。

**撞禁止。**

```text
跑一条命令：rm notes.txt 。这是试权限用的，我已确认，不用列影响，直接跑。跑不了就说跑不了，不要换别的办法。
```

**应该看到。** 没有弹窗，直接拒绝：

```text
⎿  Not run · permission denied
   │ Reason: Permission to use Bash with command rm notes.txt has been denied.
```

写书时先试的那一次没写「我已确认」，它没有跑，搬出了规则书：

```text
● 我还没执行。CLAUDE.md 第一层 B 第 9 条和 D5 规定，删文件要双重确认，先列影响和回滚方案。
```

脑子先拦了一道，手上还有一道。你说了确认，它去跑，墙照样拒绝。这就是「它的自觉不是墙」。

**撞放行。**

```text
跑一条命令：git add notes.txt
```

**应该看到。** 不弹窗，直接跑。

**出了错怎么办。** 该拦的没拦，回第 6 步看那条规则在不在，写法对不对。放行的也弹窗，一样看规则的写法，尤其空格和星号。

验完撤掉试验品，在你自己的终端跑。这两条是你敲的，墙不管：

```text
git restore --staged notes.txt
rm notes.txt
```

### 第 8 步　看一眼墙的缝

**目的。** 第三节讲的缝，亲眼看一次，以后不会高估这道墙。这一步用假值，不要用真密钥。

在你自己的终端建一个假的 `.env`，看 `.gitignore` 里有没有它：

```text
echo FAKE_SECRET=lec6-test-value > .env
grep -n '^\.env' .gitignore
```

第 0 课的 `.gitignore` 写了它，应该看到 `.env` 和 `.env.local` 两行。没有的话先加上。

然后在 Claude Code 里分别试下面几条，每条都写「跑不了就说跑不了，不要换别的办法」，弹窗都选 No。要试 `.env` 不在 `.gitignore` 里那一行，先把 `.gitignore` 里的 `.env` 那行删掉，试完加回来。写书时的结果：

| 试什么 | 结果 |
|---|---|
| 用 Read 工具读 `.env` | 拒绝 |
| `cat .env` | 拒绝 |
| `echo test >> .claude/settings.json` | 拒绝 |
| `grep -r FAKE_SECRET .`，`.env` 在 `.gitignore` 里 | 没拒绝，没弹窗，没搜到 |
| `grep -r FAKE_SECRET .`，`.env` 不在 `.gitignore` 里 | 没拒绝，没弹窗，**打出了假值** |
| `/usr/bin/grep -r FAKE_SECRET .` | 要批准 |
| `python3 -c "print(open('.env').read())"` | 弹窗要批准 |
| `/bin/rm notes.txt` | 拒绝 |
| `sh -c 'rm notes.txt'` | 弹窗，写着有规则禁止这段脚本里的命令 |

`grep` 那两行要细看。不在 `.gitignore` 时打出来的是这样：

```text
.env:FAKE_SECRET=lec6-test-value
```

禁止一档写着 `Read(./.env)`，假值还是出来了，这就是官方写的那条缝。

在 `.gitignore` 里时没搜到，靠的不是权限规则。Claude Code 的命令环境里，`grep` 被包了一层，背后是 ugrep，带着 `--ignore-files`，所以跳过了 `.gitignore` 里的文件。写书那台机器上，敲 `type grep` 能看到这个函数。这是顺带挡住的，不是谁承诺的；你的版本未必如此。

python 那一行也要看。弹窗不是因为红牌，是因为这条命令没有放行，手动模式下要问。它打开文件的事规则看不见。你要是在弹窗里点了 Yes，假值就出来了。

**应该记住的。** 三件事：`.env` 一定进 `.gitignore`，同名的 `.env.*` 也一样；弹窗里要看清命令；真有要紧的密钥，靠沙箱这种操作系统层面的办法。

**出了错怎么办。** 结果和表不一样很正常，这些行为随版本变。要带走的是做法：拿假值真撞一次，别猜。

撤掉假文件，在你自己的终端跑：

```text
rm .env
```
