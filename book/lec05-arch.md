## 二、学完能做到什么

1. 能把一个系统按业务切成模块，给每张表定一个唯一的主人，画出不成环的依赖图。
2. 能说出后端一个请求依次经过哪几层，每一层管什么、不管什么；能判断一项权限检查该放在哪一层。
3. 能拿一条真实的请求，在纸上把设计走一遍，找出走不通的地方。
4. 能画出部署拓扑：几个容器，谁对外，谁只在内网，配置从哪来。
5. 能用两轮的方式让 AI 做架构：先核对、列取舍，你拍板，再写正文；每一节定稿就当场回头改上游。

## 三、原理

**为什么要有这一课。** 打个比方。第 5 课的数据库设计是仓库里的货架：东西放在哪一格。这一章的架构是整个厂区的平面图：有几个车间，车间里怎么分工，货从哪个门进、经过谁、从哪个门出。下一章的接口契约，是车间之间递的交接单。平面图没画，就不知道有几个车间，也就不知道要开几种交接单。所以先架构，后接口。

不画会怎样？写到第 10 课的后端，每个人按自己的理解建目录、放代码。同一件事有人放在这个模块，有人放在那个模块；一项权限检查有人写在门口，有人写在里面。等到发现，已经有一堆代码压在上面。

### 先认几个词

**模块。** 系统里按业务分出来的一块，像公司里的一个部门。本项目分六个：用户、登录、权限判定、项目、任务、通知。

**依赖。** 一个模块的代码要调另一个模块的功能，就叫它依赖那个模块。像一个部门办事要打电话找另一个部门。

**NestJS。** 本项目后端用的框架。它把一个请求的处理分成固定的几层，下面「分层」一小节讲。

**层。** 一个模块内部按职责分的几段：谁接请求，谁做业务判断，谁碰数据库。

**请求上下文。** 一个请求在后端各层之间传递时，随身带着的一个「小本子」。前面一层查到的东西，比如「当前是谁登录」，写在上面，后面一层直接看，不用再查。

**容器。** 一个打包好的、自带运行环境的小隔间，一个服务跑在一个容器里。用的工具叫 Docker。

**Docker Compose。** 一份文件写清有哪几个容器、它们怎么连，一条命令把它们一起拉起来。

**Nginx。** 一个放在最外面的服务，所有从浏览器来的请求先到它这里，由它转给里面的服务。这种做法叫反向代理。

**TLS。** 网址前面 `https` 的那个加密。在哪一层解开这层加密，叫 TLS 终止。

**SSR。** 服务端渲染。页面先在服务器上拼好再发给浏览器，第一屏出来得快。Next.js 支持它，前提是有一个一直在跑的服务进程。

**端口。** 一台机器上区分不同服务的门牌号。一个服务对外开了端口，外面就能直接连到它。

**数据卷。** 给容器挂的一块存储。容器删了重建，数据卷里的东西还在。

### 第一块：模块划分

**模块就是部门。** 打个比方。一家二十人的公司，不分部门，谁都能改所有东西。想改一条退款规则，不知道散在多少人手里。分了部门，客服遇到退款，就去找财务。分模块真正解决的不是「整齐」，是改一处时，波及的范围可控。

**按业务切，不按技术切。** 有一种分法是按技术：所有接请求的代码放一个目录，所有业务逻辑放一个目录，所有碰数据库的放一个目录。这样改一个功能，要在三个目录之间来回跳。本项目按业务切：和任务有关的放在任务模块里，和项目有关的放在项目模块里。这是这一块最要紧的一句话。

**拥有一张表 = 唯一能写它的。** 每张表有且只有一个主人。只有主人能写这张表；别的模块想改，得调主人提供的方法。为什么？两个模块都能写同一张表，规则就散在两处，改一处忘一处。没人管的表也不行。

**读不算拥有。** 别的模块可以读这张表，归属不变。

**依赖单向，不成环。** 打个比方：三个部门互相等对方先办完，谁都动不了。代码里两个模块互相依赖，框架会报循环引用，只能用别扭的办法绕开。所以依赖只许单向。

**本项目的六个模块。**

| 模块 | 管什么 | 拥有的表 |
|---|---|---|
| users | 用户账号 | users |
| auth | 注册、登录、登出，会话是否有效 | sessions |
| authz | 判定「谁在哪个项目是什么角色」，放行或拒绝 | 无，只读成员表 |
| projects | 项目，以及成员和角色 | projects、project_memberships |
| tasks | 任务的创建、分配、状态、截止、汇总 | tasks |
| notifications | 站内通知 | notifications |

六张表都有主，没有一张表有两个主人。

**几个值得讲的决定。**

- **用户和登录拆成两个模块。** 打个比方：人事部管员工档案，门禁室管刷卡进门。拆开，才守得住「一表一主」：登录模块不直接写用户表，注册时调用户模块建账号。邀请成员时按邮箱找人，直接问用户模块，不用绕登录模块。
- **权限判定单独成一个模块，而且不拥有表。** 它是横切的：几乎每个业务模块的请求都要过它，它不属于任何一个业务。权限是安全边界，口径必须集中在一处。代价是：成员表由项目模块写、由权限模块读，分在两处。
- **通知模块本版是个空壳。** 表已经建了，可本版没有任何功能往里写。架构图上还是要列它，不然那张表就成了没人管的孤儿。打个比方：地图上可以标「此处将建」。
- **项目的进度汇总并进任务模块。** 汇总的数据全来自任务表，单开一个模块只是多一层转手。

**这一块拍的几条本版范围。**

- **用户表不加姓名字段，界面一律显示邮箱。** 判断用的是一把尺子：将来补，贵不贵？第 5 课的软删除，将来补要做数据迁移，很贵，所以要认真拍。加一个可空的姓名列，将来补只是加一列，很便宜，所以现在可以不加。同样的形状，因为将来补的成本不同，结论也不同。
- **跨项目总览（US-05）本版延后。**
- **US-04 的第三条验收延后。** 它要用项目的截止日期。可需求里没有任何一条故事允许谁去设置、修改项目的截止日期。加一列没人能填的字段，比没有更糟。所以这不是「加不加字段」的数据结构问题，是「做不做这个功能」的范围问题，归 D1。

**依赖图只记业务依赖。** 依赖图要回答的是「业务数据往哪个方向流」。所以只记一种关系：一个模块的代码，调了另一个模块的 Service。权限检查是挂在请求入口上的，不算依赖。打个比方：一个部门办事要打电话找另一个部门，这是依赖；公司统一在每个门口派了保安，不算哪个部门依赖保安。但保安自己要去人事部查花名册，这就算保安依赖人事部。

按这个口径，本项目的依赖图是：

```
auth → users
projects → users
authz → projects
tasks → projects、users
notifications → tasks、users
```

users 不依赖任何模块，是地基。authz 只依赖 projects：它要读成员表判角色。它不依赖 auth：当前是谁登录，是 auth 那一道检查查完后写进请求上下文，authz 从上下文里取。两道检查之间没有代码调用，中间隔着这个小本子。看不见，不等于没关系，所以文档里要写一句说明。

### 第二块：分层

**横着切和竖着切。** 模块划分是横着切：公司有几个部门。分层是竖着切：每个部门里，谁接活，谁干活，谁碰仓库。

**打个比方：一家餐厅。** 服务员接单，不下厨；厨师做菜，不接客；仓库管理员管食材，不懂菜谱；菜单前台后厨各一份，内容一样。对到后端：接请求的是 Controller，做业务判断的是 Service，碰数据库的是 Repository，前后端共用的那份菜单是共享层。

**不分层会怎样。** 三个后果。改不动：一段代码里又接请求又判业务又写库，改一处牵一片。测不了：业务判断和数据库缠在一起，想单独测业务逻辑，得先准备一个数据库。重复：同一条规则在好几个接口里各写一遍。

**一个请求依次经过谁。** NestJS 处理一个请求，顺序是固定的：

```
Guard → Pipe → Controller → Service → Repository → Prisma
```

打个比方：保安在前台之前。被保安拦下的人，根本见不到前台。被 Guard 拒绝的请求，Controller 一行都不会执行。这个顺序要记牢：以为能先在 Controller 里做点准备、再让 Guard 判断，是行不通的。

| 层 | 负责 | 不做 |
|---|---|---|
| Guard | 门口的两道检查：会话有效吗（AuthGuard，属 auth）；是不是这个项目的成员、什么角色（AuthzGuard，属 authz） | 读任务这类业务记录，判断记录归谁，解析请求体 |
| Pipe | 检查请求体和查询参数的形状、类型 | 业务规则，权限判断 |
| Controller | 取参数，调本模块的 Service，返回结果 | 业务判断，碰数据库 |
| Service | 业务规则；判断「这条记录归不归当前用户」 | 解析请求，直接写数据库查询 |
| Repository | 这张表唯一的读写出口 | 任何业务和权限判断 |

跨模块只走对方的 Service，不许直接伸手进对方的 Repository。

**Repository 是约定，不是墙。** 每个模块都写 Repository，给「一表一主」一个具体的文件落点。可它挡不住人：别的模块技术上仍然能直接连数据库绕过它。要变成墙，得靠机器检查代码里谁引用了谁，那是第 8 课的事。第 0 课讲过「环境有两种硬度」，这是又一个例子。

**共享层放什么。** 前后端共用的东西放在一个共享包里。可这个包很容易越塞越多，必须划死。

- 允许进：校验规则（Zod schema），从校验规则推出来的类型，三个枚举，没有输入输出的纯常量和纯函数。
- 不许进：连数据库的代码，读环境变量或做输入输出的代码，只属于前端或只属于后端的框架代码，数据库表的类型，以及权限判定的唯一实现。

一个新东西该不该进，问四句，全过才进：前后端是不是都真的用它？它有没有运行时依赖？它变的时候前后端是不是必须一起变？它是不是安全边界的执行点？

第四问是后来补的。权限规则能通过前三问：两边都用，不做输入输出，要一起变。可「共享一份规则」和「共享一个执行点」是两件事。规则可以共享，让前端照着显示按钮；但后端必须自己独立执行判定，前端那份只管显示。

**校验在三处执行，各拦各的。** 前端提交前拦一次，给用户即时反馈，也只有前端能「阻止提交」。后端的 Pipe 拦一次，这是唯一可信的一道：绕过界面直接打接口，只有它拦得住。Service 里再拦业务规则，比如状态能不能这样变。只在前端拦，直接打接口就穿了；只在后端拦，用户每打错一个字都要来回一趟。

**两级权限的界线。** 这是这一块最值钱的一句话：

> 只凭会话和路径就能判的，归 Guard；要读请求体或业务记录才能判的，归 Service。

Guard 手上只有三样：会话凭据，网址路径里的参数，成员表。拿这三样判得了的，比如「他是不是这个项目的成员」，在门口判。判不了的，比如「这条任务是不是派给他的」，得先把任务取出来才知道，就留给 Service。

一开始的界线不是这样写的，是「不查库就能判的归 Guard」。后来发现站不住：两道 Guard 本来就在查库，一个查会话表，一个查成员表。照那个说法，这两个 Guard 都不该存在。分界真正看的不是查不查库，是判断需要哪些输入。

旧说法还附了一条理由：「Guard 里做输入输出会让请求变慢」。这条理由也是假的，删掉了。留下的真理由是：在 Guard 里取业务记录，同一条记录会被 Guard 和 Service 各查一遍。

**一个例子：执行者想改一条不是派给他的任务。**

1. AuthGuard：会话有效吗？无效就退回「未登录」。跳到登录页是前端收到这个回应以后做的事，不是 Guard 做的。
2. AuthzGuard：他是这个项目的成员吗？不是就退回「权限不足」。他是执行者，放行，因为执行者本来就能改自己任务的状态。
3. Pipe：请求体的形状对吗？
4. Controller：调 TasksService。
5. TasksService：取出任务，先比对任务所属的项目，和网址里的项目是不是同一个。不是就拒绝。
6. TasksService：再比对任务的负责人是不是他。不是就拒绝。

拦在第 5、6 步的 Service。Guard 拦不住：它既不知道那条任务属于哪个项目，也不知道派给了谁。

**「没权限」和「不存在」给同一个回应。** 执行者只能看自己的任务；对他来说，看别人的任务和看一条不存在的任务，结果应该一样，不然他能借此打探别人有哪些任务。这和需求里「登录失败统一提示」是同一个思路。但不是铁律：需求里邀请一个不存在的邮箱，是分开提示的，因为那是负责人在项目内部的操作，不构成打探的风险。看场景选。

**前端也分层。** 四层：路由层管页面和登录跳转、首屏取数；数据访问层是唯一发请求的地方；视图组件层管显示和交互；最底下是无业务的基础组件。第 3 课定的「三态」，加载、空、出错，落在视图组件这一层。

**前端从哪知道「我是什么角色」。** 进入项目时，后端在回应里一并给出当前角色。三条硬约束，缺一不可：

1. 前端拿到的角色只用来决定显示哪些按钮，不构成授权。
2. 每个受限的接口，由后端的 Guard 自己去查成员表判定，不信前端传来的任何角色信息。
3. 角色只在这一次页面里用，不跨页面长期缓存；角色确认之前，负责人专属的入口先不显示。

第 3 条的来由：需求要求角色改了立刻生效，不用重新登录。拿一份旧的缓存去显示入口，正好违反这一条。

一句话：后端管拒绝，前端管呈现。

**名字的三层。** 数据库里的列名用小写加下划线，比如 `assignee_user_id`；代码里和接口里一律用小写开头、后面每个词首字母大写，比如 `assigneeUserId`。两套名字的边界就在第 5 课 schema 里的 `@map` 上：下划线的写法被关在数据库里，出不来。这样前端写 `userId`、后端写 `user_id` 这类对不上的错，在本项目里结构上就不会发生。

**类型从校验规则推出来，不手写。** 手写一份类型，等于同一件事有两份真相，改一处忘一处。

### 第三块：数据流，在纸上走一遍

**为什么非得走一遍。** 打个比方。第一、二节合起来是一栋办公楼的平面图：哪个部门在几楼，每个部门里工位怎么排。平面图上画得通的门，真推开可能是一堵墙。第三节就是请一位客人真的走进这栋楼办一件事，看他在哪里被卡住。

本项目走第一趟就撞上一堵墙。第二节规定 Guard 只看会话、路径和成员表，不读任务记录。可执行者查看一条任务的详情时，请求里只有任务的编号。Guard 要判断「他是不是这个项目的成员」，项目的编号从哪来？它藏在任务表里，而 Guard 不许读任务表。这个洞在平面图上看不出来，一走就撞上。不走，就要拖到第 10 课写后端时才炸。

**走几条路才够。** 判据不是每个接口都走一遍，是每一种检查点都覆盖到。打个比方：体检不用把每个器官切开看，覆盖每一类检查就够了。本项目的检查点只有六种：

1. 会话还有效吗？
2. 是不是这个项目的人？
3. 角色够不够？
4. 请求体的形状对不对？
5. 这条记录是不是你的？
6. 这个改动合不合业务规则？

两条路就把六种都踩到了。读路径 R2：执行者查看一条任务的详情，踩到「记录是不是你的」，因为那条任务是不是派给他的，只有先把记录取出来才知道。写路径 W1：负责人建一个任务并派给执行者，踩到「角色够不够」「请求体对不对」和跨模块调用。第二十个接口，只是把前面某几种检查点再走一遍。

**这不是测试。** 它是在纸上走一遍，验的是设计。真发请求、看回应，是第 14 课测试的事。

**每一步写五样。** 经过哪一层；做什么校验；做什么权限判断；不通过时从哪一步退回，退回的是什么性质的结果；读或写哪张表。退回的结果只写性质，比如「未登录」「权限不足」「参数不合法」，不写具体的状态码和网址。那些归下一章的接口契约。同一件事写在两处，将来改一处忘一处。

**R2 读路径：四道拦截。**

| 步 | 层 | 做什么 | 不通过时 |
|---|---|---|---|
| 1 | AuthGuard | 拿会话凭据查会话表，要求存在且没过期，得到当前是谁 | 未登录 |
| 2 | AuthzGuard | 拿「当前用户 + 网址里的项目」查成员表，有记录就放行，角色写进请求上下文 | 权限不足 |
| 3 | Pipe | 这条路没有请求体；查询参数暂按不设处理（这是假设，以下一章的接口契约为准），什么都不检查 | 无 |
| 4 | Controller | 取参数，调 Service | 无 |
| 5 | Service | 按任务编号取出任务 | 查不到：权限不足 |
| 6 | Service | 任务所属的项目，和网址里的项目是不是同一个 | 权限不足 |
| 7 | Service | 他是执行者的话，任务是不是派给他的；没派给任何人也算不是 | 权限不足 |
| 8 | Service | 准备负责人的显示信息，一律显示邮箱 | 无 |
| 9 | Controller | 返回任务详情 | 无 |

四道拦截一句话各一：你登录了吗，你是这个项目的人吗，这条任务真是这个项目的吗，这条任务是你的吗。全程只读，不写任何表。

**第 6 步最要紧：一个越权的漏洞。** 前面那堵墙的解法，是把项目编号也放进网址里，比如「项目 A 下面的任务 7」。Guard 拿网址里的项目 A 去查成员表。这是常见的写法，可它不是白给的。

设想一个人是项目 A 的成员，不是项目 B 的成员。他构造一个请求：网址写项目 A，任务编号却填项目 B 里的一条任务。Guard 一看：他是项目 A 的成员，放行。如果 Service 直接按任务编号取出那条任务返回，他就读到了项目 B 的数据。这叫越权读取。

所以第 6 步是必付的代价：Service 取到任务以后，必须比对任务的项目和网址里的项目，不相等就拒绝。

**W1 写路径：三道拦截，加一条硬规矩。**

| 步 | 层 | 做什么 | 不通过时 |
|---|---|---|---|
| 1 | AuthGuard | 同 R2 第 1 步 | 未登录 |
| 2 | AuthzGuard | 查成员表，并要求角色是负责人 | 权限不足 |
| 3 | Pipe | 检查请求体：标题、描述是文本，负责人是整数或空，截止时间是时间或空 | 参数不合法 |
| 4 | Controller | 取参数，调 Service | 无 |
| 5 | Service | 负责人不为空时，问项目模块：他是不是这个项目的成员？可以派给负责人自己 | 参数不合法 |
| 6 | Service | 写入任务，项目编号只从网址里取 | 内部错误 |
| 7 | Controller | 返回新任务 | 无 |

**第 6 步的硬规矩：鉴权用哪个编号判，写入就必须用哪个编号。** 建任务时还没有旧记录可比，R2 那道比对用不上。假如允许从请求体里取项目编号写入：网址写项目 A（他是负责人，Guard 放行），请求体里写项目 B，任务就被建进了他无权的项目 B。所以新任务的项目编号只从网址取，不从请求体取。它和 R2 的第 6 步是同一个防御的两面。

**第 5 步为什么问项目模块。** 判断负责人是不是本项目成员，要读成员表，而成员表的主人是项目模块。跨模块只走对方的 Service，不许直接摸对方的表。这是第一节「一表一主」在真实流程里的第一次兑现。

为什么不只检查「这个用户存在」？那样会造出「看起来有人负责、实际那人根本不在项目里」的任务。没人知道它，它就静悄悄地烂在那里。先问一句「这里出错会怎么烂」，再决定要不要多做一道检查。

第 5 步不通过时退回「参数不合法」，而不是「权限不足」。区别在于会不会泄露信息：项目成员名单本来就是负责人能看的，告诉他「这人不是成员」不算泄露。

**几个走查时拍下的决定。**

- **服务端用自己写的校验管道。** NestJS 自带的那个校验管道，认的是另一套校验库；本项目选的是 Zod，两边天生不认识。自己写一个，十几二十行。引第三方库，默认的报错格式未必合需求的要求。
- **网址里的编号不单独做格式检查。** 乱写的编号和不存在的编号，结果一样：查不到，权限不足。但有一个坑：一串根本不是数字的字符，直接交给数据库查询，会抛出内部错误，而不是「查不到」。所以查库前先把它转成数字，转不动就当查不到。这是一次容错，不是格式检查。
- **会话固定 30 天，不续期。** 打个比方：健身卡办了 30 天，是到期作废，还是每来一次就往后顺延？续期的话，每个只读的请求都要顺手写一次会话表，一个「看看」的动作悄悄变成了一次写。本项目选固定 30 天。会话表里已经有过期时间这一列，将来要改成续期也来得及。

**选型一变，要拍的板也变。** 如果第 4 课选的是 JWT，「续不续期」根本不是个问题：JWT 是无状态的，想让它提前失效，得另建一张黑名单。正因为本项目把会话存在数据库里（为了登出立即失效、角色改了立即生效），「续不续期」才成了一个需要主人拍板的选项。

**理由比决策传得更远。** 走查时还发现一件事：第二节有一条决定是对的，可写在它旁边的理由站不住。决定只管这一处；理由会被将来的人拿去推别的地方。所以理由错了也要改，不能因为「反正结论对」就放过。

还有一次，一个推荐的理由被推翻了：当时以为「格式不对的编号自然会查不到」，只想了「格式合法但不存在」这一种情况，没想到「根本不是数字」这一种。结论后来还是对的，补了上面那条容错。教训：给一个行为下结论之前，先列出输入有几种形态，逐种走一遍。

### 第四块：部署拓扑

**进程里面和进程外面。** 第二节讲的是后端程序内部的层，第三节从请求进了后端程序讲起。第四节画的是进程外面：有几个容器，谁跟谁通，浏览器发出的请求在进后端程序之前，先撞上谁。

**打个比方：一个小区。** 第二节是一间屋子里家具怎么摆，第四节是整个小区的平面图。

- 容器是小区里一栋一栋独立的房子，各自带着自己的水电。
- Docker Compose 是小区的规划图加物业：哪几栋房子，怎么连，一声令下一起开门。
- Nginx 是大门的传达室：外人只能先到这里，由它领到该去的那栋。
- 端口映射是在围墙上开一扇对外的窗：开了，外人就能绕过传达室，直接敲那栋房子的门。

**图纸不等于生效。** 这一节只画图。真把容器搭起来跑通，是第 9 课的事。写了，不等于它真按写的那样在运行。

**不画会怎样。** 第 9 课写 Compose 文件时只能边写边想；第 15 课上线时，证书放哪、前端的静态文件谁发，全是现场拍板。

**生产环境长这样。**

```
[浏览器]
   │ 只开 80、443
   ▼
[nginx]  反向代理 + 解开 https 的加密
   ├─ 根路径 ──→ [frontend]  Next.js 服务进程
   │                 │ 服务端渲染取数：容器内网直连，不绕回 nginx
   │                 ▼
   └─ 接口前缀 ─→ [backend]  NestJS
                     │
                     ▼
                [postgres] ── 挂数据卷
```

除了 nginx 的 80 和 443，哪个容器都不对外开端口。

**拍下的几件事，和各自的理由。**

- **四个容器，前端单独一个。** 第 4 课选 Next.js 的理由之一是服务端渲染让首屏快。服务端渲染需要一个一直在跑的服务进程，所以前端得单独起一个容器。要是不起，就等于改了第 4 课的选型，那不是这一节该拍的。
- **Nginx 只做两件事：转发请求、解开加密。** 第 4 课原本还让它发静态文件。现在静态文件由前端的服务进程自己发。本项目这点量，让 Nginx 多管一件事带来的牵扯不值得。这一条推翻了技术选型里的一句话，所以要当场回头改那一行。
- **同一个域名，按路径分流。** 根路径给前端，接口前缀给后端。一张证书；浏览器看来是同一个网站，不用配跨域。这个推荐有个前提：登录凭据放在 Cookie 里，同一个网站的 Cookie 浏览器会自动带上。凭据最后怎么带、前缀写成什么字符串，都归下一章的接口契约。
- **服务端渲染取数，走容器内网。** 前端的服务端代码直接连后端，不绕回 Nginx，也不走公网。绕公网要多走一圈，多一次加密解密。代价有两个：前端要配两个后端地址，浏览器用公网的，服务端用内网的；浏览器带来的登录凭据，不会自动跟着服务端的这次请求走，要手工转发。
- **数据库端口：开发时开，生产时不开。** 开发时要从自己的电脑上直接连数据库跑迁移；生产时把数据库端口对公网开着，是真实的攻击面。
- **只画一套生产拓扑，加一张「本地与生产的差异」清单。** 画两套，同一张图画两遍，改一处忘一处。本地日常只有数据库进容器，前后端直接在电脑上跑；另留一份完整的四容器配置，上线前在本地跑一次。
- **数据库迁移由人手动触发，不随容器启动自动跑。** 迁移改的是真数据，做了就难回头，属于 D5，要喊主人并双重确认。藏进容器启动里，就绕过了这道闸。
- **画出数据卷，备份留到灾备那一课。** 不挂数据卷，数据库容器一重建，数据就没了。可数据卷只防重建，不防误删，也不防磁盘坏。第 5 课 ADR-DB-002 写着「恢复误删要靠备份」，可备份方案还没定。这件事要在文档里明写出来：本版上线后如果误删，没有已定的恢复手段。
- **「环境一致」怎么读。** 技术选型里写着 Docker 让「环境一致」。这句话指的是镜像和运行环境一致，配置按环境不同。不然「数据库端口开发开、生产不开」就和它打架了。一个含糊的词，将来会被人拿去推别的结论。
- **将来的组件不画在图上。** 缓存、实时推送、定时任务，只在图外用文字注明「将来从哪接入，不是本版已定的选型」。画上去，下一个读的人会以为已经定了。

### 架构是螺旋，不是流水线

四节不是写完一节就封死一节。第三节走查时，发现第一、二节有好几处写得不对；第四节画拓扑时，又发现第一节的依赖图和第二节的一句话要改。下游暴露上游的洞，是它的正常功能，不是事故。

**毛病出在回写的时机。** 发现了，就当场回头改上游，再往下走。不要攒。这一课的实际经过是攒了：发现一处记一处，到最后攒成二十几处，单独花了一整个窗口去还，文件里一度同时存在三个版本的口径。第七节会讲这件事。

**改上游时的几个手法。**

- **显式的空和沉默的空。** 一节里没有待定项，就写「无」。整节删掉，读的人分不清是真没有，还是没人想过。
- **过时的记录，删还是盖章。** 一条待办做完了：如果它除了「该做某事」，还告诉了后人别的东西，比如当时发现了什么问题，就留着，在上面加一行「已于何时完成」；如果没有，就删。
- **单一信息源。** 不是说一件事只准记一处，是说同一件事只有一个权威的定义，别处都指向它。

### 让 AI 做架构的几个道理

**一轮只出一件交付物。** 一个任务里塞了四件事，跑了六分钟没完，一中断，四件全丢。药方是按交付物拆轮：一轮一件事，每轮都有一个可以落地的中间结果。

**先核对，再起草。** 打个比方：盖房子之前，先下去探一遍地基；探完了再砌墙。第一轮只让 AI 做三件事：把你的决定和已有文件对一遍，找出文件和文件之间的矛盾，列出你还没被问到的取舍。一个字的正文都不写。第二轮才照你拍过的板写正文。

**拆两轮，买到的是选择权。** 部署拓扑这一节看起来很轻，第一轮核对下来，冒出来九项该主人拍、却从没被问过的取舍。一轮写完的话，这九项 AI 会各自挑一个看着合理的答案，直接写进正文。产出短，不等于决策少。

**判断留给人，展开交给它。** 第二轮的 AI 不再做决定，只把你拍过的板展开成正文。就算这一轮中断，丢的只是正文，判断不丢。

**每一节定稿，就扫一遍传播面。** 拍下一个决定，要打开每一份可能受影响的文件，逐份写「要改」或「不影响」。不能靠回忆推断，必须真打开看。立一条新的口径时，还要回头扫一遍自己文件里已经写下的东西：新口径的传播面，包括它自己的过去。

## 四、动手

这一节照推荐的做法走：四节，每节先让 architect 出一轮，你拍板，再落进文件，然后当场回头改上游。数据流和部署拓扑这两节，每节跑两轮。一共十步，第 0 步到第 9 步。每步四样：目的，要发的 prompt 或要敲的命令，应该看到什么，出了错怎么办。

**这一章的 architect 是真正的子代理。** 第 5 课是让主对话读 architect 的定义文件、照着办。这一章换成把活交给 architect 子代理，原因有三。一，每一轮都要读好几份长文件，子代理在自己的上下文里读，不占主对话的地方。二，这几轮只要它交结论，用不着来回问答。三，子代理的只读是机器拦着的：它的定义文件里只给了读文件的工具，写不了文件。两种做法的区别，第 5 课第六节讲过。

**子代理的完整输出，靠机制取，不靠嘱咐。** 子代理跑完，交回主对话的只是一份摘要。prompt 里写「把它的完整输出原样展示给我」，管不住这件事。要看全文，敲 `/tasks`，选中那个子代理，按回车，打开它的记录；或者按 `Ctrl+O`，打开对话记录查看器，看每一步的细节。官方文档对这两样的说法见第六节。

**判断它卡没卡住，看数字动不动。** 子代理跑的时候，界面上有计时和用量的数字。数字还在涨，就是活的；不看已经跑了多久。

**模式。** 状态栏保持 `manual mode on`，每一步都先问。子代理只读，不受影响；后面回头改上游时，主对话每改一处都会先停下来给你看改前改后，这正是要的。

### 第 1 步　模块划分：让 architect 出方案

**目的。** 只做模块划分：有几个模块，各管什么，每张表归谁，谁依赖谁。不做分层，不做数据流。

整段发给主对话：

```

读 .claude/agents/architect.md，按里面的定义激活自己，然后开始下面的任务。

任务：产出【系统架构的第一块：模块划分】。只做模块划分。不做分层，不做数据流，不做部署拓扑，不设计 API。

prisma/schema.prisma
docs/arch/TECH_STACK.md
如果你认为还需要别的文件才能下判断，不要自己去找。在输出里写明「需要哪个文件、为什么需要」，然后停下。

输出四个部分，按顺序：

第一部分 · 澄清问题
```

```
## 二、分层架构

### 后端分层（NestJS，以 tasks 模块走通）

层序按 NestJS 请求生命周期排，即请求实际经过的顺序：
Guard → Pipe → Controller → Service → Repository → Prisma
守卫在 Controller 之前执行。被 Guard 拒绝的请求，Controller 方法根本不会被调用。

#### 1. Guard（AuthGuard → AuthzGuard）
AuthGuard 属 auth 模块，负责会话有效性，只能调 auth 模块暴露的能力读 sessions，并把当前用户 id 放入请求上下文。
AuthzGuard 属 authz 模块，负责项目内角色级放行判定，只能调 authz 模块暴露的能力读 project_memberships（经 ProjectsService，表仍归 projects），并把角色放入请求上下文（第三节决策 A）。
两个 Guard 都不做：读 tasks 等业务记录、判记录归属、解析请求体。

#### 2. Pipe（项目自写 Zod 管道 + 共享 Zod schema）
负责：请求体与查询参数的形状与类型校验。这是服务端唯一可信的形状校验点。
不经过管道：路径参数。路径参数不做格式校验，非法值落入鉴权失败（第三节 T3）；查库前转数字的容错见第三节决策 B。
不做：业务规则、权限判断。

#### 3. Controller（TasksController）
负责：取参、调本模块 Service、返回 DTO。
不做：业务判断、碰 Prisma、判数据归属。
只能调：本模块 Service。

#### 4. Service（TasksService）
负责：业务规则（状态流转、未认领判定、项目内汇总）；数据级权限判定（这条记录归不归当前用户）。
不做：解析 HTTP、直接写 Prisma 查询、伸手进别的模块的 Repository。
只能调：本模块 Repository；别的模块的 Service（如 ProjectsService 校验 assignee 是本项目成员，第三节 T5）。

#### 5. Repository（TasksRepository）
负责：tasks 表的唯一读写出口，对应第一节「一表一主」。
不做：任何业务规则、任何权限判断。
只能调：Prisma。

依赖方向单向不回头。跨模块只走对方 Service，不许直接调对方 Repository。此处指层间调用方向；模块之间的依赖图及其口径见第一节「依赖方向」。

决策 Q3：Repository 层每个模块都写，不按模块复杂度区分。
理由：一，给「一表一主」一个文件级落点，Lec 8 加 lint 限制跨模块 import 时有具体路径可约束；二，Service 抽离后可脱离数据库单独测试；三，「只在复杂模块写」没有判据，会退化成随意。
代价：users / auth / notifications 三个 Repository 会很薄，基本是转发。
注意：Repository 是语义层约定，不是机械层的墙。别的模块技术上仍可直接注入 Prisma 绕过它。要变成墙需靠 lint 限制 import（Lec 8）。

### 共享层边界（packages/shared）

允许进：
- Zod schema —— 前后端共享一份，写一次两端复用（TECH_STACK.md:15）。
- 由 z.infer 从 Zod schema 推导出的请求/响应类型（TECH_STACK.md:57）。
- 枚举 MemberRole / TaskStatus / NotificationType —— 两端都要渲染和判断。
- 无 IO 的纯常量与纯函数（如状态展示顺序）。

明确不许进：
- Prisma Client / PrismaService —— 会把数据库驱动打进前端 bundle，并把表结构泄露到浏览器。
- 读 env 或做 IO 的代码 —— 前端没有那些环境变量，运行时直接失败。
- React 组件 / NestJS 装饰器 —— 单侧框架依赖，另一侧装不上。
- Prisma 生成的 model 类型 —— 表结构一变前端跟着碎，会拖住 EMC 演进。
- 唯一的授权判定实现 —— 见判据第 4 问。

判据（四问全过才进）：
1. 前后端是不是都真的用它？只有一端用 → 不进。
2. 它有没有运行时依赖（IO / env / 单侧框架）？有 → 不进。
3. 它变的时候，前后端是不是必须同时变？是 → 该进；否则各自维护更省事。
4. 它是不是安全边界的执行点？是 → 规则本身可以共享作为单一信息源，但后端必须独立实现强制，前端那份仅供呈现。绝不允许共享层成为唯一执行点。
第 4 问的由来：权限矩阵能通过前三问（两端都用、无 IO、必须同时变），但「共享规则」与「共享执行」是两件事。前三问只问技术上能不能共用，不问共用后安全边界会不会被削弱。

### 校验与权限的落点

Zod 执行三处，各拦不同的东西：
1. 前端提交前 —— 拦格式错，给即时反馈。UI_DESIGN 要求「阻止提交」，阻止只能发生在前端。
2. 服务端 Zod 管道（项目自写，实现 PipeTransform 调共享 schema，不用内置 ValidationPipe，第三节 T1）—— 拦请求体与查询参数的形状与类型错。这是唯一可信的一道。
3. Service 内业务不变量 —— 如状态流转的合法性。
为什么不能只在一处：只在前端，绕过界面直接打接口就穿了（US-R01 要求强制触发被拒）；只在后端，用户每个错字都要一次往返，且做不到「阻止提交」。

两级权限的界线（决策 Q2，按第三节 T6 回写）：
- 角色级 → Guard。只凭「会话凭据 + 路径项目 id」就能判。AuthGuard 读 sessions，AuthzGuard 读 project_memberships。
- 数据级 → Service。要读请求体内容才能判的（如 assignee 是否本项目成员），或者要先取到业务记录才能判的（如 tasks.projectId、tasks.assigneeUserId），都归 Service。
- 界线一句话：只凭会话和路径就能判的归 Guard；要读请求体或业务记录才能判的归 Service。
- 界线不按「查不查库」划：两个 Guard 本来就读表。不在 Guard 里取业务记录的理由：同一条记录会被 Guard 和 Service 各查一遍。

例子 · 执行者尝试修改不属于自己的任务：
1. AuthGuard：会话有效吗？无效 → 退回「未登录」。跳转登录页是前端收到该响应后的行为，不由 Guard 执行。
2. AuthzGuard：他是本项目成员吗？不是 → 权限不足。是执行者 → 放行，因为执行者本来就能更新自己任务的状态。
3. Zod 管道：请求体形状合法吗？
4. Controller：调 TasksService。
5. TasksService：取任务，先比对记录的 projectId 与路径项目 id（第三节 T2）。不等 → 权限不足。
6. TasksService：再比对 assigneeUserId 与当前用户 id（第三节 R2-7）。不等 → 权限不足。
拦在第 5、6 步 Service。Guard 拦不住，它既不知道那条任务属于哪个项目，也不知道 assignee 是谁。

决策（取舍 5，属 D3 权限与安全口径）：
「无权限」与「不存在」合并为同一响应，不区分。
理由：对执行者而言两者语义等价（他只能看自己的任务）；Service 少一次分支；与 PRD 登录失败统一提示同思路。
注意：PRD 对邀请邮箱不存在是分开提示的（内部操作不构成枚举风险）。故本项目两种做法按场景选，不是一条铁律。
落点：本条须回填 PRD 的错误 / 边界规则（规则 64 B 类裁决）。

### 前端分层（Next.js App Router）

1. 路由层（Server Component / layout / page）
负责：路由、登录态重定向、首屏取数、loading.tsx 挂骨架。
不做：业务规则、交互状态。

2. 数据访问层（api client）
负责：唯一发 HTTP 的地方，出入参走 packages/shared 的 Zod schema。
不做：渲染、判权限。

3. 视图组件层（Client Component）
负责：渲染、交互、按角色条件渲染入口。
不做：直接 fetch、直接碰后端。

4. UI 基础层（shadcn/ui + Tailwind）
负责：无业务语义的原子组件。
不做：任何业务判断。

三态落点：
- 骨架屏：路由层用 loading.tsx / Suspense 承载，骨架本体是视图组件。
- 空态：视图组件层，必须按角色分支 —— 负责人给行动引导，执行者只说明（UI_DESIGN.md:139-140）。
- 错误态 / 权限态：视图组件层的局部错误块，不崩成空白页；权限态只显示「权限不足」，不带被访问数据。
- 单实体界面（任务详情）无空态，缺数据按错误态或权限态处理。
- 前端三态是呈现，不是安全边界。真正的拒绝在后端 Guard 与 Service。

决策 Q1：前端角色来源 —— 进入项目时后端在项目上下文里一并返回角色。
三条硬约束，缺一不可：
1. 前端缓存的角色仅用于渲染入口，不构成授权。
2. 每个受限接口的授权由后端 Guard 独立查 project_memberships 判定，不信任前端传来的任何角色信息。
3. 角色随每次进入项目时的后端响应取得，仅在本次页面上下文内使用，不做跨页面长缓存；角色未确认前，角色专属入口不渲染（UI_DESIGN.md:138 加载态要求）。
第 3 条的由来：US-R02（P0）要求角色改后立即生效、不等重新登录。拿陈旧缓存渲染入口会与该验收冲突。
未覆盖：角色变更后主动通知前端刷新，属 Lec 13，已进 BACKLOG。

### 命名规范（三层，边界在 Prisma 的 @map 上）

- 数据库列名：snake_case（如 assignee_user_id、created_at）。仅存在于 Postgres 内部。
- Prisma 字段名与 TypeScript：camelCase（如 assigneeUserId、createdAt）。写代码用这一套。
- API 请求与响应字段：camelCase。与 Prisma 和共享层一致，全链路不做命名转换。
依据：prisma/schema.prisma 全表使用 @map / @@map，snake_case 被封闭在数据库层。
后果：字段名不一致（前端 userId / 后端 user_id）这类联调错误在本项目结构上不会发生。协议 9 一致性报告在字段名这一层由 schema 写法保证。

### 共享类型推导方式（取舍 4）
决策：类型由 z.infer 从 Zod schema 推导，不手写 DTO。
理由：手写等于两份真相（schema 一份、类型一份），改一处忘一处，违反单一信息源。
代价：z.infer 的类型报错信息可读性差，必要时给关键类型起别名缓解。
落点：本条是 05-类型（共享类型）那节的直接依据。同时也是 API_CONTRACT 的依据——契约文档只写接口层与全局约定，不写字段本体（API-1）。

### 走查公共约定

- 层序：Guard → Pipe → Controller → Service → Repository → Prisma（本文第二节）。
- 被 Guard 拒绝时后面各层都不执行。Pipe 拒绝后 Controller 不执行（文件外知识）。
- 「无权限」与「不存在」返回同一响应（本文第二节取舍 5、PRD.md:311）。
- 路径参数不做格式校验，非法值落入鉴权失败（T3）。查询参数走 Zod 管道。
- 非法路径 id 的容错（决策 B）：Guard 查库前先把路径 id 转为数字，转不动即视为查不到，按「权限不足」退回。这是容错，不是格式校验，不改变 T3。
- 会话固定 30 天，不续期，纯读请求不写 sessions（T4、PRD.md:160、PRD.md:271）。
- 角色传递（决策 A）：AuthzGuard 查到的项目内角色放入请求上下文，供 Service 取用。Service 不再重复查询 project_memberships。此约定是 Guard 与 Service 之间的显性契约，实现时须有具体落点。

### R2 读路径：执行者查看一条任务的详情

输入：路径里的项目 id 与任务 id，加请求携带的会话凭据（凭据载体属 API 契约）。无请求体。

#### R2-1 AuthGuard 确认会话

- 校验：无

#### R2-2 AuthzGuard 确认项目成员身份

#### R2-3 Zod 管道
- 层：Pipe（T1 项目自写管道）
- 校验：无。无请求体。本路径不设查询参数（假设，以 API 契约为准）。路径 id 不经过管道（T3）。
- 鉴权：无
- 退回：无
- 表：无

- 校验：无
- 鉴权：无。将路径项目 id、任务 id、当前用户 id 与请求上下文中的角色传给 TasksService。
- 退回：无

- 校验：无
- 鉴权：无。返回任务详情 DTO，类型由共享 Zod schema 推导（本文第二节）。

- 校验：无
- 鉴权：同 R2-1。本路径写 tasks，但同样不写 sessions（T4）。

- 鉴权：无。角色已在 W1-2 判过。

- 层：Service → Repository → Prisma

容器职责清单

1. nginx
   - 负责：对外唯一入口。终止 TLS，按路径前缀把请求转给 frontend 或 backend（T9、T14）。
   - 不做：不托管静态资源（T9），不做鉴权判定，不连数据库（后两条为推导）。
2. frontend
   - 负责：运行 Next.js 服务进程，承担 SSR 和服务端重定向，静态资源也由它发出（T8、T9）。
   - 不做：不连数据库（本文:149），不做权威授权判定（本文:213、:218）。
3. backend
   - 负责：运行 NestJS 全部业务模块和两个 Guard（本文第一、二节）。它是唯一连数据库的服务（推导）。
   - 不做：不终止 TLS，不直接对公网暴露端口（T16），启动时不自动执行数据库迁移（T21）。
4. postgres
   - 负责：持久化六张表，数据落在数据卷（T22）。
   - 不做：生产环境不向宿主机暴露端口（T10）。

网络与端口

- 对外暴露：只有 nginx 的 80 和 443（T16）。80 端口承载什么行为属 Lec 9 配置，本节不定。
- 只在容器内网：frontend、backend、postgres 的端口（T10、T16）。
- 内网里的访问方向（推导，依据本文第二节分层）：
  - nginx 访问 frontend。
  - nginx 访问 backend。
  - frontend 访问 backend（仅 SSR 取数，T15）。
  - backend 访问 postgres。
  - frontend 不访问 postgres。
- TLS 在 nginx 终止。nginx 到 frontend、backend 这一段在容器内网里走，不再加密（推导，TLS 终止的直接含义）。

请求路径

路径一：浏览器访问
1. 浏览器用 HTTPS 访问公网域名，到宿主机 443，进入 nginx。
2. nginx 终止 TLS。
3. nginx 看路径前缀分流（T14）。
   - 根路径转给 frontend。
   - API 前缀转给 backend。
4. 页面和静态资源由 frontend 返回（T9）。页面渲染要取数时，走路径二。
5. API 请求进入 NestJS，从 AuthGuard 开始，后续见第三节。
6. 响应原路返回，由 nginx 加密后发回浏览器。
- 浏览器侧用的是公网后端地址（T15）。

路径二：服务端渲染取数
1. 浏览器请求页面，经路径一第 1-3 步到达 frontend。
2. frontend 服务端代码用内网后端地址直连 backend。不回 nginx，不走公网（T15）。
3. 浏览器带来的会话凭据，不会自动跟着这次服务端请求走。frontend 必须手工转发（T15）。凭据载体属 API 契约（本文:275）。
4. backend 对这次请求的处理和浏览器直连完全一样：从 AuthGuard 开始，不因为请求来自内网就放宽鉴权（本文:218）。
5. 已知代价：前端要配两套后端地址，浏览器用公网地址，服务端用内网地址（T15）。变量名见 ENV_DESIGN（T18）。

数据持久化

- postgres 的数据目录挂数据卷，容器重建数据不丢（T22）。
- TLS 证书放在宿主机，挂载进 nginx 容器（T20）。签发与续期留 Lec 15。理由：引入签发组件属 D4 技术选型。
- frontend、backend 不挂数据卷。会话存在 PostgreSQL（TECH_STACK.md:34-36），这两个服务不在本地落状态（推导）。
- 数据库迁移是人工触发的独立步骤，不随容器启动自动执行（T21）。
  - 理由：迁移不可逆，CLAUDE.md 第三层 D5 要求喊主人并双重确认。藏进容器启动就绕过了 D5。
- 备份方案本节不定，进 BACKLOG，留 Lec 15 灾备（T22）。
- 显式记录（T22）： DECISIONS.md:41 ADR-DB-002 的后果写的是"恢复误删需靠备份或迁移"。备份方案未定前，这条恢复路径暂无落地方案。
  - 数据卷只防容器重建，不防误删，也不防宿主机磁盘损坏（推导）。
  - 本版上线后如果发生误删，没有已定的恢复手段。

1. 前后端在哪跑：生产在容器里。本地日常在宿主机上直接跑，只有数据库进容器（T17）。
```

```
## 37 号 · 在没打开的文件上下具体结论，标「举例」也不豁免
现象：补课 05-ARCH 下半场开场，老师在未读七文件与 ARCHITECTURE.md 时先出了大纲与举例路径，四处与原文不符：反模式 34 的定义、两级权限的落点、会话方案是否已定、规则 54 的结课顺序。其中三处标了「举例」，仍然是错的。
根因：E3 逻辑错。把「标注了不确定」当成可以继续往下推导的许可。
修复：必读文件读完之前，只讲课程层的地图（进度、顺序、分工），不出任何项目具体内容，举例也算。药方并入规则 60 开课闸，不另开规则编号。
教训：标注「这是举例」不改变它进入学生脑子的方式，学生会照着它建立画面。
抽象模式：反模式 35 附带教训的复发——标注猜测不等于可以在猜测上盖楼。与反模式 1 同族，1 号是不喂 AI，37 号是老师自己不读。

## 38 号 · 一轮子代理任务堆太满，没有中间交付，一停全丢
现象：05-ARCH 下半场第一次起草第三节，一个 prompt 同时要核对报告、五点冲突结论、取舍清单、150 行草稿。architect 跑 opus 六分钟未完，学生中断，全部丢失，连它已经核出来的冲突也没留下。
根因：E4 架构错。任务粒度设计里没有中间落点，四件事捆在一次输出里。
修复：子代理任务按交付物拆轮，一轮一件事。先跑短的核对/冲突轮，审完拍完取舍，再跑长的起草轮。判据同规则 33 适用范围：丢了要重跑角色的，就该有落点。
附带：判断子代理是否卡死，看计时与 token 数是否仍在增长，不看已跑时长。数字在动就是活的。
抽象模式：与补丁 1 token 预算、补丁 2 diff<100 行同族，搬到子代理这一层。

## 39 号 · 靠机制才拿得到的东西，写进 prompt 嘱咐是拿不到的
现象：prompt 里写「把子代理的完整输出原样展示给我」。但子代理跑在隔离的子上下文里，机制上天然只向主对话返回摘要，一句嘱咐管不住。取全文要靠 /tasks 打开它的记录，或 Ctrl+O 展开消息历史。
根因：E2 工具错。把机制层的限制当成可以用自然语言绕过的约定。
修复：凡输出完整性、权限、模式这类由机制决定的事，必须配一个验证动作或提取动作，不靠 prompt 里一句话。审查清单里写「原样展示：是/否」，也要写清「否的时候怎么取」。
抽象模式：与 35 号（写了引擎不查）、36 号（没写由默认值填）同属机械层实质状态问题。

### 22 号补案例（假阴性方向）
按编号 grep 查「某决策解决了没有」会漏。本课用 grep "决策 7" 扫 docs/，只命中 ARCHITECTURE.md:87 的待定条目，据此判断未解决。实际 TECH_STACK.md 扩展点 4 已修订，但修订记录里没有出现「决策 7」四个字。

## 40 号 · 只验了一种输入形态就给出适用于全部形态的结论
现象：05-ARCH 下半场，老师推荐「路径 id 不做格式校验，非法值自然落入鉴权失败」，理由是查不到就退回权限不足。该推理只在「格式合法但值不存在」时成立。格式非法时，字符串转整数会让 Prisma 抛异常，走的是内部错误那条路，与推荐想要的行为不一致。由 architect 走查第三节时抓出，随后加决策 B（Guard 查库前先转数字，转不动视为查不到）兜住。
根因：E3 逻辑错。只走了一种输入形态，就下了覆盖全部形态的结论。
修复：给某个行为下结论前，先列出这个输入有几种形态，逐种走一遍再下结论。「格式对但值错」与「格式压根不对」常常走不同的路，必须分开验。
教训：决策可以是对的，理由却是不完整的。理由比决策传得更远——决策只管这一处，理由会被下游拿去推别的地方。
抽象模式：与本节 C3（「Guard 里做 IO 会让管道变重」这条理由，实际两个 Guard 本就在读表）同一形状，均为「结论成立但论据不成立」。与 33 号（取舍藏进顺畅论证）、37 号（在未核实前提上盖楼）同族。

## 41 号 · 用产出的体量估工作量，没数它依赖多少未决项
现象：补课 05-ARCH 第三个窗口，老师照桥梁「第四节是四节里最短的一节」判断本节较轻，排了 4-5 段。实际 architect 第一轮核对就报出 4 处冲突、9 项未暴露取舍，待拍数量超过前三节任何一节，最终走了 7 段，且回写量从预估 9 处涨到 24 处，需另开窗口执行。
根因：E3 逻辑错。用预计产出长度估工作量，不数它依赖多少还没定的东西。正文确实只有约 130 行，但每一笔都压在一个未定的取舍上。
修复：估一节的重量，先数它依赖多少未决项，不看正文预计多长。桥梁里写「本节较轻」这类预判必须注明依据，不许光下结论。下游老师读到无依据的轻重预判，按未知处理，跑完第一轮核对再排段数。
教训：产出短不等于决策少。
抽象模式：与 38 号（一轮子代理任务堆太满）同族，都是任务量估错。38 是高估一轮能装下多少，41 是低估一节要拍多少。

## 42 号 · 交接包由两方拼成，没做覆盖核对就宣告可执行
现象：05-ARCH 第三窗口产出 PENDING-REWRITES.md，前半执行清单由老师写，后半回写文本由 architect 产。
      两半各自都无错，但从未对起来核。实际 24 项清单里有 10 项只有「要改」没有「改成什么」，
      另有 3 段文本已被后续裁决盖掉却仍留在包里，且清单与文本的计数粒度不同（逻辑处 vs 编辑动作），
      数字本身对不齐。下一窗口开课核对时才发现，桥梁里「回写是纯执行」的判断不成立。
根因：E4 架构错。交接物由两方拼成时，接缝处没有任何人负责核。
      老师检查了「产物有没有落点」（规则 61），没检查「落点里的东西全不全」。
修复：交出待执行文件前，逐条核对清单每一项有没有对应的成文内容，
      逐条标「有定稿文本」或「缺文本待补」，两者都要显式写出。
      清单与内容的计数粒度必须统一，并在文件里写明按哪种粒度计数。
      落成规则 70 追加段。
教训：文本多不等于决策全做完了。41 号说「产出短不等于决策少」，本条是它的镜像面。
抽象模式：与 41 号（用体量估工作量）同族但不同环节。41 是估算问题，42 是交付问题。
          与 3 号（表象成功≠实质生效）同源：文件在、内容多，都是表象，可执行才是实质。

### 42 号补案例（断言交接物状态时不核文件）
现象：05-ARCH 第三窗口桥梁第 4 节写「17 条裁决（T8-T24），全部写进第四节『本节裁决汇总』」。
      实际第四节正文在第 5 段就落盘，T24 是第 6 段才拍的，汇总只记到 T23。写桥梁的人凭印象补了「全部」二字。
      下一窗口老师读原文时数出汇总只到 T23，与桥梁的断言不符。
根因：E3 逻辑错。断言一个交接物的状态时不打开文件核。
修复：凡在交接物里写「全部」「已完成」「共 N 条」这类断言，必须当场打开被断言的文件数一遍。
      数不过来就不写总括词，改写「见某文件某小节」。
教训：与本条主案例同源——都是「检查了有没有，没检查全不全」。
      主案例发生在产出方（清单与文本没对起来），本案例发生在描述方（状态与文件没对起来）。
延伸（05-ARCH 第四窗口三次复发）：老师写验收预期时预设了数字（「grep 应剩两行」「应为 2」），
      实际每次都多出几处，且多出的都是该留的。根因同上——下断言前不数。
      特有陷阱：只数了「原有的命中」，没算上本轮新写的内容自己含了被查关键词
      （如新增的口径定义含「authz → projects」、新增的状态行含「尚未回写」）。
      修法：验收预期一律写成「逐行判，以下几种不得残留」，不写「应剩 N 行」；
      非写数字不可时，先跑一次清点再写。写完新文本自问一句：这段话含不含被查的关键词。
```

## 六、Claude Code 知识点

这一章第一次用到四样。每样讲：是什么，原理，怎么用，什么时候不用。

### 把活交给子代理，并取回它的全文

**是什么。** 让主对话把一项任务交给某个子代理去做。第 5 课第六节讲过子代理和「主对话照角色文件办事」的区别，这一章第一次真正用它。

**原理。** 官方子代理页的说法：每个子代理从一个全新的、隔离的上下文开始，看不到你和主对话之前聊过什么；主对话写一段任务说明交给它；它做完，只把一份摘要交回主对话，中间过程留在它自己那里。

**怎么用。** 在 prompt 开头说「请用 architect 子代理执行下面的任务」，由主对话判断交不交给它；想确保一定是它，在 prompt 里写 `@agent-architect`。要看它的全文，有两个办法：

- 敲 `/tasks`。官方说它用来查看正在跑的后台命令和子代理；子代理页写明，在里面选中子代理按回车，就能打开它的记录。
- 按 `Ctrl+O`。官方说它打开或关闭对话记录查看器，能看到每次工具调用的细节，还有每条回复用的是哪个模型。

**什么时候不用子代理。** 要它弹出选择菜单让你拍板时不用：官方写明子代理里去掉了那个工具。要来回问答、一步步商量时也不用。

### Edit 工具：精确替换

**是什么。** Claude Code 改已有文件的工具。

**原理。** 官方工具参考页的说法：它做的是精确的字符串替换，给一段原文、一段新文，把前者换成后者，不用正则，也不做模糊匹配。原文必须一字不差地出现在文件里，差一个空格或缩进就对不上；原文还必须只出现一次，出现多次时，要么带上更多上下文把它定到唯一一处，要么明确说全部替换。

**怎么用。** 第四节第 5 步那样：一处一个 prompt，写清原文和新文，写清在哪一小节，对不上就停下报告。在每一步都先问的模式下，它改之前会停下来给你看改前改后。

**什么时候不用。** 往文件末尾贴一整节新内容，用编辑器贴更直接。

### 会话没了，怎么接上

**是什么。** 关掉终端、重启编辑器，Claude Code 的会话就断了。

**原理。** 断的是会话，不是文件。已经存进文件的东西都还在；只活在对话里的东西，要回到那次对话里才找得到。这一课上有一次重启了 VS Code，对话里刚出来的一份子代理输出不见了，好在已经贴到了别处。这件事之后，定下「每一段定稿就落盘」：出事的时候，最多丢当前这一段。

**怎么用。** 官方 CLI 参考页的说法：`claude -c`（全写 `--continue`）接着当前目录里最近的一次对话；`claude -r`（全写 `--resume`）按会话的编号或名字恢复，不带参数时弹出一个列表让你选。会话里也可以敲 `/resume`。

**什么时候不用接着聊。** 换了一件不相干的事，就开新会话，第 0 课第六节讲过。

### 改完以后，用 grep 照一遍

**是什么。** `grep -n "词" 文件` 列出含这个词的每一行和它的行号；`grep -c` 只数行数。

**原理。** 它只认字，不认意思。「不用 ValidationPipe」和「用 ValidationPipe」它一样会捞出来。

**怎么用。** 第四节第 8 步那样：捞出来的每一行，自己判该不该在。

**什么时候不用。** 不要拿它的行数直接当「过了没过」的结论。

## 七、常见的坑

这一章撞上的坑，都记进了反模式库，原文在第五节。每条讲：一件事，为什么会这样，怎么防。

### 37 号　在没打开的文件上下结论

**一件事。** 这一课里同一个形状的错出了三次，都是在一份没打开的文件上推出一个具体结论。一次是开场时，还没读必读的文件，就先给了大纲和几个「举例」，四处和原文对不上，其中三处标了「举例」，照样是错的。一次是推断界面的页面数要从 10 减到 9，打开界面设计一看，那一页还承载着登出的唯一入口，不能删，页面数仍是 10。还有一次，拍板以后扫传播面，漏扫了界面设计，是 architect 抓出来的。

**为什么会这样。** 标了「不确定」「举例」，就觉得可以接着往下推。可读的人会照着它在脑子里建立画面。

**怎么防。** 必读的文件读完之前，不讲任何项目具体内容，举例也算。扫传播面，必须真的打开文件。

### 38 号　一轮任务堆太满

**一件事。** 一条 prompt 同时要四样：核对报告、冲突结论、取舍清单、一百五十行草稿。architect 跑了六分钟没完，一中断，全丢，连已经核出来的冲突也没留下。

**为什么会这样。** 任务里没有中间落点，四件事捆在一次输出里。

**怎么防。** 按交付物拆轮，一轮一件。先跑短的核对轮，拍完再跑长的起草轮。

### 39 号　靠机制才拿得到的东西，嘱咐拿不到

**一件事。** prompt 里写「把子代理的完整输出原样展示给我」，交回来的还是摘要。

**为什么会这样。** 子代理只交回摘要，这是机制决定的，一句话改不了。

**怎么防。** 凡是机制决定的事，配一个动作去取、去验：全文用 `/tasks` 或 `Ctrl+O` 取。

### 40 号　只验了一种输入就下了全部的结论

**一件事。** 「网址里的编号不做格式检查，非法的自然查不到」。这只对「格式对、但不存在」成立。一串根本不是数字的字符，会让数据库查询抛内部错误。

**为什么会这样。** 只想了一种输入形态。

**怎么防。** 下结论前，先列出输入有几种形态，逐种走一遍。

### 41 号　拿产出的长短估工作量

**一件事。** 部署拓扑被预判为「四节里最短的一节」，排了四五段。第一轮核对就报出四处冲突、九项取舍，待拍的数量超过前三节任何一节。最后走了七段，回写从预计的九处涨到二十四处。

**为什么会这样。** 正文确实只有一百多行，可每一笔都压在一个还没定的取舍上。

**怎么防。** 估一节的重量，先数它依赖多少还没定的东西，不看正文会有多长。产出短，不等于决策少。

### 42 号　交接包两半拼成，接缝没人核

**一件事。** 这是「当场回写，不攒」的反面教材。课上把回写攒到了最后，攒成二十四处，写成一个待执行的文件交给下一个窗口。这个文件前半是执行清单，后半是 architect 给的回写文本，两半各自没错，却从没对起来核过：十处只写了「要改」，没写「改成什么」；三段文本已经被后来的决定盖掉了，还留在包里；清单和文本数数的方法不一样，一个按逻辑处数，一个按编辑动作数，数字对不齐。下一个窗口开工核对时才发现，又专门花一整个窗口去补、去还。

同一条下还记着两件同类的事。交接说明里写「全部写进了汇总」，打开文件一数，最后一条没进。验收时预告「应该剩两行」，三次都数错，每次多出来的都是该留的，或者是自己刚写的新文字里也含这个词。

**为什么会这样。** 交接物由两方拼成，接缝处没人负责核。检查了「有没有」，没检查「全不全」。

**怎么防。** 最根本的是不攒：每一节定稿就当场回写，第四节第 5、7 步就是这么做的。真要交接，交出之前逐条核：每一项有没有成文的内容，计数按哪种口径，被后来的决定盖掉的标作废。写「全部」「共几条」之前，打开文件数一遍。验收的预期写「不得残留什么」，不写「应剩几行」。

## 八、小结与速查

- 先架构后接口：平面图没画，不知道要开几种交接单。
- 模块按业务切；一张表一个主人，读不算拥有；依赖单向无环。
- 依赖图只记「一个模块的代码调了另一个模块的 Service」，门口的检查不算。
- 一个请求依次经过 Guard、Pipe、Controller、Service、Repository。被 Guard 拦下的，后面一行都不执行。
- 两级权限：只凭会话和路径就能判的归 Guard，要读请求体或业务记录才能判的归 Service。
- 后端管拒绝，前端管呈现。
- 在纸上走两条真实的请求，覆盖每一种检查点。
- 网址里带了项目编号，不等于那条任务真属于这个项目：取出来要比对。鉴权用哪个编号，写入就用哪个。
- 理由比决策传得远：结论对、理由错，理由也要改。
- 部署：四个容器，只开 Nginx 的 80 和 443；服务端渲染走内网；迁移由人手动触发。
- 让 AI 做架构：一轮一件交付物，先核对再起草，判断留给人。
- 每一节定稿，就扫传播面，当场回写上游，不攒。
- 改已有文件，一处一改一验；改完用 grep 照一遍，逐行判。
- 子代理的全文用 `/tasks` 或 `Ctrl+O` 取，不靠嘱咐。

## 九、换个项目还用得上的

判断的标准只有一句：换个项目还用得上的，列在这里；只属于本项目的，不列。

- **模块划分的四条原则。** 按业务切；一表一主；读不算拥有；依赖单向无环。
- **依赖图的口径。** 只记业务依赖，横切件不计入，但横切件自己调别人照记。
- **共享层判据四问。** 尤其第四问：共享规则可以，共享唯一的执行点不行。
- **两级权限的界线。** 按判断需要的输入分，不按查不查库分。
- **纸上走查。** 覆盖每种检查点，每步写五样，退回只写性质。
- **跨项目编号越权的防法。** 取出记录比对归属；鉴权用哪个编号，写入就用哪个。
- **部署拓扑的写法。** 一套主拓扑加差异清单；将来的组件只注接入点；迁移不随启动自动跑。
- **两轮法。** 先核对、列没问过的取舍，再起草正文。
- **一处一改一验，加结果验收。** 预期写「不得残留什么」。
- **螺旋式回写。** 下游发现上游的洞，当场改，不攒。

只属于本项目、不往外带的：六个模块各是什么，T1 到 T27 各条的具体选择，四个容器的具体分工。
