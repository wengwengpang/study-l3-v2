## 核心讲解

### 3a · 原理：为什么要单独跑一轮「只核对、不动笔」

打个比方。

你请装修师傅来做柜子。有两种开场方式。

第一种：「来，先把柜子打出来。」师傅边打边发现墙不平、插座位置没定、门朝哪开也没说。于是打一半停下来问你，你答一个，他再打一段，再停下来问。一天下来柜子没成型，你也被问烦了。

第二种：「先别动手。你把整面墙看一遍，把所有没定的事一次列给我。」师傅列出八条：插座位置、门开向、层板间距……你一次性拍完，他再动手，一口气打完。

**第二种之所以快，不是因为师傅手快，是因为把「发现问题」和「解决问题」分开了。**

这一轮就是第一种做法里被跳过的那一步。

为什么非得单独跑？因为上个补课窗口在这里栽过。`anti-patterns.md` 41 号记着：老师照桥梁一句「本节最短」就排了 4-5 段，结果 architect 第一轮核对报出 4 处冲突、9 项没暴露的取舍，最后走了 7 段，回写量从 9 处涨到 24 处，还得另开窗口执行。

教训那条写得很直白：**产出短不等于决策少。**

所以我不预判段数。跑完这一轮，看它报出多少条，再排。

### 3b · 操作：这一轮怎么设计

四件事，每件都对着一个坑。

**第一件，写死文件清单，并且命令它重读。**

子代理跑在独立上下文里。你不点名，它就自己找；你点名了但没说「本轮重读」，它可能拿早前的印象顶上。所以 prompt 里两句都要有。

**第二件，把已知的东西直接喂给它，不让它去查。**

`BACKLOG` 里有六条和 API 契约相关的待办，我已经读过了，内容就在我脑子里。**这种时候再让它去读一遍 BACKLOG，纯属浪费。**

这对应 `anti-patterns.md` 8 号——「prompt 害得 AI 多查文件」，答案已经在对话里了就别让它查。

**第三件，控制读取范围。**

这一轮它要真读的是五个文件。这是有讲究的：协议 2「有预算的侦察」规定，读代码前先声明读哪几个，最多五个，读完即停。我卡在五个，不多给。

（它还要读一个 `architect.md`，那是它自己的定义文件，不算侦察，算照镜子。）

**第四件，规定输出长什么样，并且给停止条件。**

不规定格式，它会给你一篇散文，你没法逐条审。不给停止条件，它可能「反复优化直到满意」，那是个没有终点的指令（规则 43）。

### 3c · 输出格式拆开看

我让它把结果分成甲乙两类。这个分法不是装饰，两类的性质完全不同。

**甲类**：文档里已经明文写着「待定」「假设」「以 API 契约为准」的口子。

比如第三节 R2-3 那行写着「本路径不设查询参数（假设，以 API 契约为准）」。**「假设」两个字就是上一窗口留给你的钩子**，它知道自己没定，明说了。

甲类这种，架构文档自己认账，风险低。

**乙类**：文档没标，但不定就没法写契约的口子。

乙类才是真风险。它没人标，所以谁都不会去找它。等你写契约写到一半撞上去，才发现地基缺一块。

这两类要分开列，是因为**你审的时候用的判据不一样**。甲类你只需要拍板选哪个做法。乙类你还得先判一句：它说的这个洞，是真洞吗，还是它想多了。

每条我要求六行，其中两行专门防坑。

**「出处：文件路径:行号」**——这是协议 3 证据契约。AI 会凭印象描述代码，说得头头是道其实记错了。有出处你才能当场核。

**「候选做法：至少两个，各写一句代价」**——这是防 `anti-patterns.md` 33 号。AI 做权衡时喜欢给一个「自洽且合理」的单一结论，把该你拍的取舍藏进顺畅的论证里。逼它给两个，取舍就被顶到台面上了。

### 3d · 联动：这一轮的产物会被谁用

这条清单不是一次性的草稿纸，它有三个下游。

**一，决定本课段数。**条目多、牵动面广，就多排几段。

**二，决定回写清单。**清单里「牵动谁」那一行，会直接变成结课时要回写的地方。比如决策 C 一旦选了 Prisma 关联查询，第一节依赖图里 `tasks → users` 那条边就得按 T13 口径重新判定。

**三，兜住漏网的。**本课定不了的，进 `BACKLOG`；本课能定的，当场定。这对应 `anti-patterns.md` 9 号——**该现在做的现在做，别因为一部分没准备好就把整件事打包推迟。**

# 三、第 2 段 · 乙-08：谁说了算

## 我们在哪

- 05-API 第 2 段。上一步跑完 architect 核对，拿到 21 项待决。
- 这一步拍第 0 组里的元决策：**API 契约文档和共享 Zod schema，字段的真相归谁。**

**纵向承接**：这一段站在架构文档第二节「取舍 4」之上——那条已经定了类型由 `z.infer` 从 Zod schema 推导，不手写 DTO。本段产物决定 `API_CONTRACT.md` 这份文件里到底写什么，也就决定本课后面还要拍多少条。

## 3a · 原理

先打个比方。

你盖一栋楼，手上有三张图。

**建筑图**画的是房间在哪、墙多厚、门朝哪开。**电路图**画的是线怎么走、插座在哪。**水管图**画的是管子怎么排。

三张图，不是一张。因为一张图上画满三套东西，谁都看不清。

关键在于它们怎么互相引用。

电路图上要不要把墙的尺寸也标一遍？**不标。**电路图上只画线和插座，需要知道墙在哪，翻建筑图。

如果电路图上也把墙宽抄了一份，会发生什么？**墙一改，建筑图改了，电路图上那个数字还是旧的。**两张图打架，施工队不知道该信谁。

**「单一信息源」这条原则，常被误读成「所有东西写在一个文件里」。它真正的意思是：每一条信息只有一个家。**

一个家，不是一个房子。三张图可以各有各的管辖范围，只要每条信息只在一张图上说了算。

不做会怎样：你在契约文档里写「标题是必填字符串」，又在 Zod schema 里写 `z.string().min(1)`。后来发现标题要限制长度，你改了 schema，忘了改文档。下一课的人打开文档照着写代码，写出来的和实际跑的不一样。

## 3b · 操作：三张图怎么分

这个项目已经有三个候选的「图」。

**PRD** —— 业务规则。谁能做什么，状态怎么流转，卡住的阈值是多少天。

**API_CONTRACT.md** —— 接口层。有哪些接口、什么方法、什么路径、挂哪个 Guard、可能退回什么、响应包不包一层。

**共享 Zod schema** —— 字段本体。每个字段叫什么名、什么类型、必填还是可空、取值范围。

分界线用一句话说：

**PRD 管「能不能」，契约管「怎么调」，schema 管「长什么样」。**

## 3c · 拿一条真议题走一遍

光说分界线太抽象。拿 **甲-08 截止日期**这条来拆，你就看明白了。

architect 把它列成一条议题。实际上它是三条，各有各的家。

**第一块：用户只选了个日期，没选时刻，那这个截止是当天零点还是当天结束？**

这是业务语义。同一个「10 月 3 号截止」，零点的意思是 10 月 2 号就得交，当天结束的意思是 10 月 3 号一整天都算。**用户的理解只有一种，这是产品要拍的。**

→ 家在 **PRD**。

**第二块：本项目所有接口的时间字段，一律用什么格式在网络上传？**

带时区偏移的完整时间戳，还是纯日期字符串。**这条一旦定了，管住所有接口的所有时间字段**，不是只管截止日期。

→ 家在 **契约**，写在「全局约定」那一节。

**第三块：`dueAt` 这个字段叫什么名、允不允许为空。**

→ 家在 **schema**。

**看出来了吗。**一条议题拆成三块之后，本课只需要拍第二块。第一块是产品决定，第三块推到 05-类型 那节。

这就是我刚才更正的那句话的准确版本：**不是砍掉，是拆开。**

再快速过两条：

**甲-09 多余字段怎么处理。**请求体多带了字段，是悄悄扔掉还是直接拒绝。这条同样是**管住所有接口**的统一规则。→ 契约的全局约定。

**甲-09 描述必不必填。**这是产品要不要强制用户写描述。→ PRD。落实成 `z.string().min(1)` 还是 `z.string().optional()`。→ schema。

## 3d · 联动

这条为什么不能拖到写正文时再顺手定。

**第一，它和已经拍过的东西直接相关。**架构文档第二节的「取舍 4」已经定了：类型由 `z.infer` 从 schema 推导，不手写 DTO，理由是手写等于两份真相。**如果现在让契约文档写全字段，那就是把手写 DTO 换了个文件继续手写。**跟取舍 4 直接打架。

**第二，这条产物被至少三节课用。**05-类型 要照契约点名的 schema 名字去产出；Lec 10 后端照契约写路由和 Guard；Lec 11 前端照契约封装请求；Lec 12 联调时 reviewer 要出一致性报告，**拿什么对？拿的就是这份契约。**

**第三，你可能会问：干脆一份文件写全，不是更省事吗。**

短期是省事。代价在第 12 课。那节课要做的事是「检查前后端、类型、契约是不是一致」。如果契约文档和 schema 各写一份字段，**一致性报告第一件事就是比对这两份文档谁对**——你等于给自己造了一个本来不必存在的比对工作。

## Level 1 对应

网页版时代，你让 AI 写接口文档，它给你一份 markdown 表格，字段名类型必填全在里面。然后你让它写代码，它又把类型写了一遍。

那时的痛点是：**没人规定谁说了算。**两份不一致，你得自己肉眼比，比完还不知道该改哪边。

现在升级的地方：**先定权威，再动笔。**定完之后，不一致这件事在结构上就不会发生了——因为只有一份。

# 二、第 3 段 · 第 1 组产品口径：先拍冲突 1

## 我们在哪

- 05-API 第 3 段。上一步落盘了 API-1，宪法和架构文档的注记也补完了。
- 这一步进第 1 组，五条产品口径里的第一条：**谁能创建项目。**

**纵向承接**：这一条站在 PRD 的权限矩阵和审定决策 D1 之上。它的产物落回 PRD，同时决定契约里「创建项目」这个接口挂哪个 Guard。

## 3a · 原理：为什么这条非拍不可

先说清楚它卡住了什么。

契约要给每个接口标鉴权级别，也就是「这个接口前面挂哪些 Guard」。

架构文档第二节定了两个 Guard 的分工：

- **AuthGuard** 问一句：你登录了吗。
- **AuthzGuard** 问一句：你在这个项目里是什么角色，够不够格。

**AuthzGuard 有个硬前提：路径里得有项目 id。**它要拿「当前用户 id + 路径项目 id」去查成员表，才知道你是负责人还是执行者。

现在问题来了。

**创建项目这个接口，路径里没有项目 id。**因为项目还不存在，id 还没生成。

所以 AuthzGuard 在这个接口上**根本转不动**。它要查的那张表里，没有一行和「一个还不存在的项目」有关。

不拍这条会怎样：写契约时到「创建项目」那一行，鉴权级别那一栏填不出来。硬填一个，就是在猜。

## 3b · 矛盾的真正样子

上一段我说过一句「权限矩阵多了一行它管不着的东西」。展开讲。

**PRD 有四行相关文字，我核过原文：**

`:173` 定了一条基础口径——角色按项目划分，同一个人在不同项目可以是不同角色。

**这句话的含义比看上去重。它的意思是：脱离项目，你不是任何角色。**

你在 A 项目是负责人，在 B 项目是执行者，那在「所有项目之外」呢？你什么都不是。**「负责人」不是一个贴在人身上的标签，是一个人和一个项目之间的关系。**

`:189` 权限矩阵有一行：「创建项目 | 可 | 否」。

`:261` 跟着写：执行者尝试创建项目，界面不展示入口，强制访问提示权限不足。

`:218` 完全绕开角色：已登录用户填名称提交，创建成功，创建者自动成为负责人。

**所以矛盾不在 `:189` 和 `:218` 谁对谁错。**

矛盾在于 `:189` 那一行**问了一个问不出答案的问题**。

打个比方。

你要办一张健身卡。前台问：「您是本店金卡会员还是银卡会员？」

你说：「我还没办卡。」

**这个问题在这一刻不成立。**金卡银卡是办完卡之后才有的身份，不能拿来判断你能不能办卡。

权限矩阵那一行就是这个前台。它拿「项目内角色」去判「还没有项目时的动作」。

再看 `:261`，它跟着往下推了一步，推出「执行者强制访问要提示权限不足」。**这一步推得更远，但地基是同一个不成立的问题。**

而 `:218` 没问这个问题。它只问「登录了吗」，登录了就能建。**它是对的，只是没人发现它和矩阵那行打架。**

## 3c · 这是什么级别的决策

按宪法第三层，这条**同时中了两个**。

**D1 范围取舍**——「创建项目要不要设门槛」是功能范围的问题。

**D3 权限与安全口径**——「谁能创建」是权限边界。宪法写着这一类必须喊主人，理由是它是安全边界，错了影响大。

**还有 D8 文档口径冲突**。宪法对 D8 的要求是：CC 发现两份已决文档或同一文档新旧措辞打架时，**只报不改，给出双方出处和冲突点，不给结论，由主人裁决**。

architect 这次做得对。它报了冲突，给了四个行号，明说了冲突点在哪，**没有自己挑一边圆过去。**上一课立 D8 的时候，靠的还是 prompt 里写「发现冲突先指出」那一句；这次是宪法兜住的。

## 3d · 联动：这一条会牵动谁

**第一，契约里「创建项目」接口的鉴权级别。**这是直接产物。

**第二，PRD 的权限矩阵和错误边界。**拍完要回填，`:189` 和 `:261` 两处都要动。

**第三，前端的入口渲染。**架构文档第二节的决策 Q1 定了：前端缓存的角色只用于渲染入口，不构成授权。如果创建项目跟角色无关，**那「创建项目」这个入口就不该按角色隐藏**——UI_DESIGN 里跟这个有关的描述要跟着核。

**第四，乙-02 那条（负责人数量）。**它和这条是同一个主题的两半：一个管「怎么成为负责人」，一个管「能有几个负责人」。

## Level 1 对应

网页版时代，你让 AI 写权限设计，它给你一张漂亮的权限矩阵，行是动作，列是角色，每格填「可」或「否」。

**那时的痛点是：矩阵这个形状本身会骗人。**它长得整整齐齐，让人觉得每一格都该填满。于是「创建项目」这种跟角色无关的动作，也被塞进去填了一格。

矩阵不会告诉你「这一格不该存在」。**它只有可和否两个选项，没有「此题不成立」这个选项。**
