# 第 6 课　决策边界与权限

## 一、本章位置

这一章是第一篇「立项准备」的最后一章。业务代码仍然不写。前面几章定了做什么、怎么做。这一章定另一件事：做的过程中，AI 哪些事可以自己来，哪些事必须停下来问人，哪些事根本不许它碰。

**上一章交来什么。** 规则书前两层：怎么干活，项目事实。设计文件：需求、界面、选型、数据库、架构、接口契约。书上排在这一章前面的还有补课 05-类型和补课 05-环境，这两节还没上。这一章不靠它们交来的东西，用到的只有上面这些。

**这一章产出什么。**

- 规则书第三层 A：决策边界 D1 到 D8。
- 权限设置 `.claude/settings.json`：放行、先问、禁止三档。
- 反模式库第 35、36 号。

**下一章拿它做什么。** 第 7 课开始建工程。这道墙从那时起才会被频繁撞到：跑 `pnpm` 走放行，改 `prisma/` 和规则书要问，删文件直接拒绝。

**和前面几章的关系。** 05-ARCH 和 05-API 已经用过这一章的东西，当时各交代了两句，说细的在这里。这本书按道理排，实际做的时候，这一章排在四节补课前面。你可以提前做。先立规矩和墙，再做设计，等于先拿到地图再走路。

**这一章不做的三样。** 课程全景原来把三样也排在这一课：会话简报、prompt 模板、剩下五个角色（backend、frontend、reviewer、tester、devops）。当年上课选的范围是决策边界加权限，这三样没做。它们的去向：五个角色各在要用的时候建，分别是第 10、11、12、14、15 课；会话简报在第 13 课和附录 B；模板在附录 B。还没写代码就定 backend 这些角色，没有活可以验证它们写得对不对。

**这一章最要紧的一件事。** 规矩是写给 AI 读的，它读了通常照做，但没人能保证。墙是 Claude Code 执行的，不看模型怎么想。能变成命令的危险动作交给墙，变不成命令的判断交给规矩。两样都要，都要验证过才算数。

## 二、学完能做到什么

1. 能用两个问题判断一个决定该不该喊人：能不能撤销，错了影响多大。
2. 能从项目真拍过的决定里反推一份「必须问人」的清单，写进规则书，并试出它有没有起作用。
3. 能写 `.claude/settings.json` 的三档规则，读懂一条规则对得上什么、对不上什么。
4. 能验证权限真生效：先看解析结果，再真撞一次。
5. 说得清这道墙的缝在哪，能判断一条规矩该放规则书、权限规则、钩子还是技能。

## 三、原理

### 先认几个词

- **工具。** Claude Code 动手靠工具：`Read` 读文件，`Edit` 改文件，`Bash` 跑命令。权限规则管的就是这些工具的调用。
- **决策边界。** 一张清单，列出哪几类决定 AI 不能自己拍，必须停下来喊项目主人。它写在规则书第三层。第 0 课讲过规则书分三层，前两层回答「这个项目有什么」，第三层回答「这个项目里谁说了算」。
- **权限模式。** 每个会话有一个总开关，决定规则没提到的动作怎么办。它显示在输入框下面的状态栏上。第 0 课让你切到的 `manual mode` 就是其中一种。
- **放行、先问、禁止。** 权限规则的三档。配置文件里叫 `allow`、`ask`、`deny`。

### 一次差点溜过去的取舍

第 5 课定删除策略时，architect 给了一个结论，大意是：首版不做删除功能，所以表里不加 `deleted_at` 字段。

这句话很顺。其实是两句话粘在一起。

第一句，首版不做删除功能。这是事实，需求文档里确实没有这一条。

第二句，所以表里不预留字段。这是取舍。预留了，将来加软删除不用改表。不预留，现在省事，将来要动表结构。

事实谁都可以说。取舍要有人负责，负责的人是项目主人。AI 把两句粘成一句，取舍就藏进了一个「技术结论」里。没细看，它就这么过去了。

那次是人把它抢了回来。最后表里确实没加这个字段，软删除记进了待办。结果看着一样，区别在于这是人拍的，不是 AI 替人咽下去的。反模式库的 33 号记的就是它，第 5 章讲过。

这一章要做的，是不再靠人眼尖去抓。把「什么时候必须喊人」写成条文，放进 AI 每次进项目都读的地方。第 4 步会用一个没发生过的新例子试一次，看写了到底有没有用。

### 一个比方：门禁

把规则书第三层想成家里的门禁。家里住着一个很勤快的助手。大部分门，它自己刷卡就进：读个文件，查一下状态，你根本不想被打扰。有几道门，它的卡必须刷不开，得回头喊你。

决策边界就是「哪些门必须喊人」的清单。清单上的东西分三种性质：

- D1 到 D5 是五道**房间门**。每道门后面是一类具体的决定。
- D6 是门口的**验货台**。任何需求进门之前，先验出身。
- D7 是装在每个门框上的**感应器**。它不管进哪间房，只管 AI 当时的状态。

D8 是后来补的，管文件之间打架，下面单讲。

### 一把尺子，两个数

只看「这件事属于哪一类」不够。下面两件事都叫动数据结构。

第一件，给任务表加一个可以为空的字段。不想要了删掉就行，老数据不受影响。能撤销，影响小。

第二件，删掉一张已经有数据的表。数据没了就是没了。不能撤销，影响很大。

门牌一样，都是 D2。第一件 AI 可以自己做，第二件必须喊人。所以每一类决定都要量两个数：

1. 能不能撤销？
2. 错了影响多大？

能撤销而且影响小，AI 自己处理。不能撤销，或者影响大，停下喊人。

这把尺子不是这门课发明的。Amazon 2015 年的致股东信把决定分成两类。一类是单向门：「Some decisions are consequential and irreversible or nearly irreversible – one-way doors –」，要慢慢来。另一类是双向门：「they are changeable, reversible – they’re two-way doors.」，「can and should be made quickly」。信里还提醒，组织大了容易把重流程用到所有决定上，结果是「slowness, unthoughtful risk aversion」。它讲的是公司怎么做决定，不是讲 AI，但道理相通：什么都喊人，人被淹没；什么都不喊，出了事收不回。

讲 AI 的也有。OWASP 给大模型应用列的十大风险里，第 6 条叫 Excessive Agency，也就是 AI 手里的能力太大。它写的根因有三样：「excessive functionality」「excessive permissions」「excessive autonomy」。防范办法里有一条：「Utilise human-in-the-loop control to require a human to approve high-impact actions before they are taken.」高影响的动作，做之前先让人批。

行业文章里还常见一对叫法：人在环内（human-in-the-loop），做之前等人批；人在环上（human-on-the-loop），先做，人盯着，能拦能撤。这对叫法和这把尺子对得上：撤不回的事前批，撤得回的事后拦。它们是常见说法，不是标准。

### 五道房间门

**D1 范围门：这个功能做不做。** 凡是动到「做什么、不做什么」的边界，喊人。评论功能写在首版不做的清单里，AI 写任务详情页时说「顺手加个评论框吧」，就是在动范围。多做一个功能要建表、写接口、做页面，回头再砍都白做；它改的是产品的样子。默认喊人。

**D2 数据结构门：动表、动字段、动约束。** 这道门最能说明那把尺子。加可空字段可以放行，删有数据的表必须喊人。还有两个细节。就算是能放行的那种，改表之前也要先回 architect 确认：不必喊人，不等于随手就改。另外，条文专门钉了一句：「现在不做，所以不预留」这种合并判断要拆开，不做是事实，不预留是取舍。

**D3 权限门：谁能看、谁能改。** 需求文档里有两条用户故事写「所有成员看所有任务」，权限矩阵定的是负责人看全项目、执行者只看自己的。差别很大，最后的口径记在规则书第二层 C。口径改起来中等麻烦，可它是安全边界，定错了就是执行者看到不该看的东西。默认喊人。

**D4 选型门：选框架、选库、选架构。** 登录状态存数据库、不用 JWT，第 4 课拍的。这道门的特点是很难撤销：一个库用深了，代码到处依赖它，换它等于砸墙重来。默认喊人。

**D5 不可逆门：删库、迁移、删文件、上线。** 这道门要喊两次。AI 先列影响范围和回滚方案，人回一句 CONFIRM，它才动手。拿不出回滚方案的，不做。它的定义就是撤不回，所以不管影响大小一律喊人。到这一章为止，项目还没真碰到过这种操作，它是一个空着的门框，先立在那。

### 验货台、感应器和后来补的一条

**D6 验货台：这条需求是哪来的。** 出身只有三种：已验证，真人确认过；AI 假设，AI 觉得该有，没人确认；教学驱动，产品不需要，课程为了教某个技术才加。要单设一张台子，是因为手里没有真实用户时，AI 会编出一条听着很合理的需求，当成事实写进文档，后面整个产品就建在它上面。第 4 章的 32 号就是这件事。它不算第六道房间门，因为它横着切过所有需求。

**D7 感应器：AI 没把握就该停。** D1 到 D6，你都能指着说这属于哪一类。D7 不是一类决定，它管的是 AI 当时的状态。心里没底，缺上下文，或者给的「技术结论」里藏着一个该人拍的取舍，感应器就该亮。亮了只许做一件事：停下来报，不许猜个合理的答案填上。

回头看 `deleted_at` 那次。它算 D2，因为动的是数据结构；它也触发 D7，因为结论里藏着取舍。一件事同时碰到两条，说明 D7 罩在前面几条上面，不是排在旁边的第七类。

条文给 D7 配了一句口令，AI 和人都可以拿来自问：

> 这里面有没有藏着一个该我拍的取舍？

**D8 文档打架：只报不改。** AI 发现两份已定的文档互相矛盾时，只报，由人裁决以谁为准。不许挑一份看起来更新的，也不许顺着写下去当没看见。

为什么不并进 D7？D7 的触发条件是没把握。可是发现文档冲突时，AI 往往很有把握，一眼看出哪份更新。有把握就不触发 D7，它就直接挑一边改了。所以单立一条。05-ARCH 那一章的做法就是它，这里补上原文。

### 同一套东西，两种写法

打开规则书第三层，每条只有一两行。上面讲了几页。同一套内容有两个读者。

这本书写给人，目的是让人明白，所以要比方，要例子，要讲慢。规则书写给 AI，它每次进项目都读一遍，每个字都占它的上下文，所以要短，一条一句，能照着执行。官方的建议是「Keep CLAUDE.md under 200 lines.」。

### 为什么有了规矩还要墙

规矩靠 AI 读了自觉遵守。它读漏了呢？会话太长，前面读过的东西淡了呢？

官方最佳实践页把指令分成两种，分得很清楚。第一种，你写下来，模型读，模型决定怎么办：prompt、`CLAUDE.md`、技能都是这种，它写「there's no *guarantee* that it'll follow your instructions」。第二种，你配置好，Claude Code 这个程序来执行：钩子、deny 规则都是这种，它写「Claude Code applies this every time, no matter what the model decided to do.」

权限页说得更短：「Permission rules are enforced by Claude Code, not by the model.」

这就是墙。`.claude/settings.json` 这个文件不是写给模型看的，是写给程序看的。

### 三档，和撞门的顺序

**放行 `allow`。** 自己刷卡就进，不打扰你。比如 `git add`。

**先问 `ask`。** 门锁着，它得按铃，你点头才开。比如往远端推代码，改表结构。

**禁止 `deny`。** 门焊死了，按多少次铃都没用。比如读密钥文件。

每条规则的写法是工具名，加括号里的条件。工具名首字母大写。

```text
Bash(git push *)     用 Bash 跑 git push 开头的命令
Edit(prisma/**)      改 prisma 目录下的任何文件
Read(./.env)         读当前目录的 .env 文件
```

程序不是三张清单一起看。官方写：「Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order.」先看禁止，再看先问，最后看放行，撞上第一条对得上的就照办。写得再细的放行也救不了。

结果就是**禁止永远赢**。先问清单里有 `Edit(.claude/**)`，禁止清单里有 `Edit(.claude/settings.json)`。改 `settings.json` 时两条都对得上，程序先看禁止，直接拒绝，连问都不问。你想点头也没有地方点。

这也跨文件。配置文件有好几层，你个人的、项目的、本机的。官方写：「If a tool is denied at any level, no other level can allow it.」所以放行可以给得大方一点，禁止才是安全网。

### 规则上的字怎么读

命令规则里的空格和星号有讲究。官方的表：

| 规则 | 对得上 | 对不上 |
|---|---|---|
| `Bash(ls *)` | `ls -la`、`ls` | `lsof` |
| `Bash(ls*)` | `ls -la`、`lsof` | |

星号代表后面什么都行。星号前面的空格是规则的一部分，表示 `ls` 到这里是一个完整的词。

没有星号就要一字不差。`Bash(git status)` 只对得上 `git status`，后面多一个参数就对不上。

文件规则用的是 `.gitignore` 那种写法，起头不同，意思不同：

| 写法 | 意思 | 例子 |
|---|---|---|
| `路径` 或 `./路径` | 相对当前目录 | `Read(./.env)` |
| `/路径` | 相对配置来源，项目配置就是项目根 | `Edit(/prisma/**)` |
| `~/路径` | 相对家目录 | `Read(~/.ssh/**)` |
| `//路径` | 从文件系统的根开始 | `Read(//etc/**)` |

有两点容易错。一，`/Users/alice/file` 不是绝对路径，一条斜杠只是相对配置来源，绝对路径要写两条。二，本项目写的 `Edit(prisma/**)` 是相对当前目录的，所以要从项目根目录启动 Claude Code。
