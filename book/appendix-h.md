# 附录 H　问题与解法

这一份收课上提出的课程做法类问题，一个问题写一个案例。你遇到同样的问题时，翻到对应的案例，照着做。

每个案例十一节，顺序固定：问题是什么，症状与实据，为什么会这样，行业怎么解决，考虑过哪几种，最后怎么做的，具体怎么用，有没有用，换个项目照着做，还没解决的，出处。

这个结构借自两样现成的做法。一样是事后复盘。Google 的 SRE 一书这样定义它：「A postmortem is a written record of an incident, its impact, the actions taken to mitigate or resolve it,」「the root cause(s), and the follow-up actions to prevent the incident from recurring.」出了什么事、影响多大、怎么处置、根因是什么、后续还要做什么，十一节里都有。另一样是文档写作框架 Diátaxis 里的「操作指南」：「How-to guides are about goals, projects and problems, not about tools.」它按读者要解决的问题排，不按知识的分类排。两句原文都在 2026-10-19 取回核过。

接口、数据库这类知识，写在各章正文里，不在这里。

## 案例一　开课读得太多，中途会漂

### 一、问题是什么

2026-10-17，补课 05-API 第七窗口开课。项目主人提出：

> 我们现在新窗口开篇前加上必读的7个文件和自检要读的内容太多，导致你跑偏或忘记……你认真查下目前行业或有什么专业方法可以解决这问题？或者有没有印象图加深你印象，或关系图来组织？

这里的「你」指 Claude Code。每开一个新窗口，它先读三份开课资料和七个必读文件，再逐条过一遍开课自检，然后才开始上课。规矩都写在文件里，也都读过了，做到一半还是会忘。

### 二、症状与实据

先看要读多少。第七窗口开课时数过：开课读的文件共 2666 行，自动记忆另有 509 行。课程规则 81 条，反模式 46 条，开课自检编到第 20 项。规则文件的 547 个非空行里，有 127 行以「背景」「关系」「判定」这类词开头，讲的是来历和关系，不是要做的动作。反模式库 279 个非空行里，这类行有 96 行。

再看漏了什么。上一个窗口（第六窗口）收尾回顾时，记下了这些错：
- 报进度凭印象，漏了契约的一整节（见案例二）。
- 课程规则 77 要求拍板时当场判定的事，两次被推到了结课。
- 开课没有先带着重温上一个窗口。
- 数错的数七处。其中五处被提交前的计数闸门拦下，没有落进文件；两处是事后自查出来的。
- 用量过半以后，错误明显变多。

前三种，规矩明明写着，到时候没想起来，都在「只靠读」那一层。拦下来的五处，靠的都是命令。

第八窗口开课时又量了一次读量，用 wc -m 数字符，合计约 16.5 万字符。七个必读文件约占 45%。最大的单份不是必读文件，是 Claude Code 自动记忆里的一份会话流水账，约占 17.5%。照 Read 工具给那一份报的 token 数折算，整个开课约 14 万 token；这是折算，实数要看 /context。

### 三、为什么会这样

**一句话：开头读一遍，撑不住一个长会话。读进来的规矩会被越来越长的对话挤到中间，到用的时候想不起来。**

打个比方。早上把一整本员工手册读完，下午遇到一件事，手册里明明写了怎么办，却想不起来。不是没读，是读得太早、读得太多，中间又塞进了一整天的事。

Claude Code 官方的最佳实践页，把这件事放在全页最前面：「Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills.」又说：「When the context window is getting full, Claude may start "forgetting" earlier instructions or making more mistakes.」

几篇研究说的是同一件事：
- Liu 等人的《Lost in the Middle》发现，相关信息放在长输入的开头或结尾时，表现最好：「performance is often highest when relevant information occurs at the beginning or end of the input context」。开课读的规矩，会随着对话变长被挤到中间。这篇测的是从长文里找答案，搬到「守规矩」上，是推断。
- Chroma 的《Context Rot》（2025）：「model performance consistently degrades with increasing input length」。输入越长，表现越差。
- IFScale（2025）一次给出最多 500 条指令：「even the best frontier models only achieve 68% accuracy at the max density of 500 instructions.」要守的规矩越多，守得越差。

Anthropic 讲上下文管理的文章（2025-09-29）把它归成一句：上下文「must be treated as a finite resource with diminishing marginal returns」，越多越不值钱。

还有一层：规矩只增不减。每踩一个坑，就多一条规则或一条反模式，很少有删的时候。于是读量一窗比一窗大。

### 四、行业怎么解决

**一句话：不靠记性。规矩按时刻分成短检查单，到了那一刻再看；能交给机器的，交给机器。**

飞行员不会在起飞前把整本手册背下来。检查单按时刻分开：启动前一张，起飞前一张，降落前一张。美国联邦航空条例第 121.315 条要求：「The procedures must be designed so that a flight crewmember will not need to rely upon his memory for items to be checked.」

Anthropic 那篇文章推荐的也是这个方向，叫「just in time」：「agents built with the “just in time” approach maintain lightweight identifiers」。手边只留轻量的索引，用到的时候再取细节。

安全工程里有个瑞士奶酪模型。James Reason 2000 年在《英国医学杂志》上写，每一层防护都「more like slices of Swiss cheese, having many holes」。安全不靠哪一片没有洞，靠叠几片，让洞对不齐。他还说：「We cannot change the human condition, but we can change the conditions under which humans work」。改不了人会忘，能改的是让人不必记。

Claude Code 官方也把两类东西分开：写在 CLAUDE.md 里的话是建议，钩子是确定会执行的。最佳实践页原话：「Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens.」钩子指南页说，钩子让「certain actions always happen rather than relying on the LLM to choose to run them」。记忆页还给了篇幅上限：「target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence.」

### 五、考虑过哪几种

**印象图、关系图。** 项目主人提过用图来加深印象。对 Claude Code 不管用：官方记忆页写明「Each Claude Code session begins with a fresh context window.」每个窗口从空白开始，图留不下「印象」，起作用的只有这一刻读进来的字。对人有用：所以检查单末尾附了一张关系图，GitHub 上能直接显示，给项目主人看各个时刻的先后。

**现在就把开课资料全面重组。** 没选。整节课结课时出开课那一套的精简方案，早就定了（问 325 A）；中途大改，等于推翻它。

**并进结课时的精简方案再做。** 没选。离结课还有几个窗口，这期间照样会漂。

**选的：先试点一份时刻检查单（问 501 A）。** 开课照旧读七个必读文件，规则一条不改。另建一份短文件，按时刻排卡，到点先读那一张。先试一个窗口，收尾回顾时看错数；后来延长到两个窗口（问 510 A）。

试点里又定了几处：
- 自动记忆里原有一份「发前自查」，本身就是按时刻记的清单。新文件建了，两份并存迟早打架。定的是把它搬进检查单，成为第 12 张卡，自动记忆里只留一行指针（问 503 A）。没选两份并存，也没选只扩自动记忆那一份。
- 每一条标出靠什么守住（问 505 A）。没选不标。
- 钩子先不加（问 511 A）。没选第八窗口开头就加一个「每条消息自动附一行提醒」的钩子。理由：权限与钩子的配置要项目主人亲手写（课程规则 66），课程原把钩子排在第 8 课，试点的数据也还不够。
- 项目主人同时要一份能回溯的记录，像书前面的目录。定的是用脚本从决策记录的标题行现场打印目录，不另存一份（问 502 A）。没选生成一份目录文件，也没选手写目录：两种都要另存，迟早和正文对不上。

### 六、最后怎么做的

**方向，四样：** 能删的删；剩下的到点再读；读也不保险的，交给命令、交给钩子；关键处由人把关。

**先收拢已有的。** 这个办法一提出，项目主人就问：是不是项目里本来就有，只是没留意。一搜，确实大半本来就有，只是散在各处：
- 自动记忆里的发前自查，按「什么时刻做」记。
- 每一步开头三行锚点，第三行写「这一步我最可能犯什么错」。
- 框架规格 docs/HARNESS.md 的原则 17，早已认出长会话这个问题。
- 待办清单第 7 条，早排了第 8 课用钩子在压缩后提醒重读。
- 每条课程规则末尾的「进自检」判定行，早写了它在哪一刻起作用。

新的只有一样：把这些散着的时刻收成一份按时刻排的索引，每张卡指回正本。教训也落了地：**提新办法之前，先在自己项目里搜已有的做法。** 这一条补进了 HARNESS 原则 1。

**检查单 docs/CHECKPOINTS.md。** 十三张卡，从「开课」到「整节课结课」，中间依次是：派子代理前、报告回来、出推荐前、拍板之后、改已有文件前、提交前、删文件前、报进度时、定新做法时、窗口收尾、发每条消息前。每张 1 到 9 条，共 69 条。每条只写要做的动作和正本在哪，不抄正文；正本改了，卡上只改指针。

两种用法，每张卡的标题后写明用哪种：
- 先读再做：动手前读完这一张。
- 做完对一遍：做完逐条核，在消息末尾写出来。

每条标了靠什么守住：
- 【命令】有现成命令判对错，但要记得跑。17 条。
- 【读】只能靠读卡照做。48 条。
- 【你】由项目主人把关。4 条。

由钩子守的，0 条。洞在哪，一眼看得见。

**决策记录目录 scripts/decision-index.sh。** 从决策记录的标题行现场打印「编号 | 日期 | 提交号 | 标题」，日期与提交号取自 git blame。行业里也这么做：管架构决策记录的工具 adr-tools，源码里就有生成目录与关系图的命令。Keep a Changelog 则提醒：「Using commit log diffs as changelogs is a bad idea: they're full of noise.」直接拿 git log 当目录，太吵。

**框架规格。** HARNESS 原则 17 补了一层：到点读卡，交给机器，关键处由人把关。

### 七、具体怎么用（走一个例子）

第八窗口开课，要改交付物清单文件头的一句话，把「本窗口目标」换成第八窗口的。这是「改已有文件前」那一刻，先读第 6 张卡，照着做。

第 1、2 条：原文用命令导出，不手打；改前数原文，恰好 1 次才动手。

```
sed -n '8p' docs/lessons/05-api-wbs.md
grep -cxF "$(sed -n '8p' docs/lessons/05-api-wbs.md)" docs/lessons/05-api-wbs.md
```

应该看到：第一条打出那一行原文，第二条打出 1。是 0，说明原文抄错了；大于 1，说明不止一处，替换会改错地方。原文要是以「- 」开头，grep 会把它当成选项，要在 -cxF 后面加 -e。

第 6 条：预期数先算，不估。新句先存进临时文件，用 wc -l 数，是 1 行；一行换一行，文件应仍是 125 行。

第 5、7 条：改的是 docs/ 下的文件，事先说会弹一次确认窗。只用 Edit 改，改的字和同意的对照一字不差。

接着是「提交前」那一刻，读第 7 张卡：先看 git status，只提交这一份文件；再数次数，和预期比。

```
git status --short
wc -l < docs/lessons/05-api-wbs.md
```

应该看到：git status 只列出这一份文件；行数 125。再用上面那样的 grep -cxF 数新句、旧句，应是 1 次、0 次。几个数都对上才提交；有一个不等，就停下，不提交。

最后是「发每条消息前」那一刻：消息末尾写一行「发前自查」，写这条消息碰到了哪几张卡、各项过没过。

### 八、有没有用

**一句话：拦得住的是命令那一层；只靠读的那一层，照样会漏。整体有没有用，还没有能比的数据。**

错数：第七窗口收尾回顾记下 3 处错。第六窗口那份清单（见第二节）口径不一样，数错的数单算了七处，不能直接拿来比。何况第七窗口同时把推理强度（effort）从 high 换成了 xhigh，两样一起换，分不清是谁起的作用。

两个实例，正好一层一个：
- 漏的。第七窗口收尾时拍了一条裁决，改掉了更早一条裁决的一半。检查单第 5 张卡第 7 条要求：改了一条裁决，回扫指着它的卡。这一条标的是【读】，当时没扫，于是有一张卡还指着旧口径。到第八窗口开课对账时，才查出来。
- 拦下的。第八窗口数原文次数时，原文以「- 」开头，grep 把它当成了选项，报「invalid option」，没有给出数。加 -e 重数，得 1。命令那一层，错了会出声。

机器能查多少：第八窗口跑了一次只读的体检脚本 scripts/doc-check.sh。检查单里它认得的编号有 75 处（规则、反模式、原则、决策记录），引了不存在编号的 0 处。它查不了三样：「问 N」这类问题编号、交付物清单的编号、卡与卡之间的互指。编号还在、意思已经过时的，它也查不出，上面那个「漏的」就是这一种。

token：不省，还略多。检查单约占开课读量的 3%，每条消息末尾还多一行自查。它想换的是少返工，这一点还没有数据证明。量读量时，倒是查出了真正能省的一块：那份自动记忆流水账，定在第八窗口收尾精简（问 520 A）。

### 九、换个项目照着做

1. 先量。开课要读几份、多少字，规矩有多少条。找出最大的那一份。
2. 能删的先删。流水账、讲来历的长段，不放在每次必读的地方。
3. 先在自己项目里搜。已有的、按时刻起作用的提醒，先收拢。
4. 列出一件长事里会停下来的时刻：开工、派人、收结果、出建议、拍板后、改文件前、提交前、删东西前、报进度、定新做法、收尾、每条消息发出前、整件事结束。
5. 每个时刻一张卡，不超过九条。只写动作和正本在哪，不抄正文。
6. 每条标靠什么守住：命令、读、人。
7. 到点先读那一张；做完逐条对一遍，写出来。
8. 标「读」的，挑能写成命令的改成命令；能交给钩子的，交给钩子。
9. 记录的目录从正文现场生成，不另存一份。
10. 先试点，回顾时看错数，再定留不留。

### 十、还没解决的

截至 2026-10-19：
- 检查单还在试点，第八窗口收尾回顾时定留不留。
- 钩子一条都还没有；要不要提前加，同一次回顾定。
- 卡与卡之间有没有重复、正本改了卡上跟没跟上，没有机器查。
- 开课仍然读全七个必读文件；能不能少读，整节课结课时定（问 325 A、521 A）。
- 那份自动记忆流水账，第八窗口收尾精简。

## 案例二　答进度时漏了一整块

### 一、问题是什么

2026-10-17，补课 05-API 第六窗口。项目主人问：

> 本节课还有多少内容没做/做到哪

Claude Code 答了全图，说接口契约「分三块」：第零节、第一节、第二节。项目主人回了一句：

> 第三节呢

契约其实有四节。第三节「本节裁决汇总」，登记着这节课所有拍板的结论，当时已经登到 API-53。漏掉的，恰恰是最要紧的那一节。项目主人接着说：

> 上回的……这么重要的主要内容怎么能忘记？想办法解决，参考行业怎么做专业做法怎么做，是否需要待办清单等。

### 二、症状与实据

契约文件有四个二级标题：零、一、二、三。答进度时没有打开文件一节一节数，是凭对话里的印象说的。

漏掉的那一节有个特点：它是一路随拍随登的。每拍板一条，就顺手登一条，它从来不在「还没做」的那一堆里。于是在印象里，它不算一项要交的东西。

同一个窗口里，同一个形状还出现了两次：
- 课程规则 77 要求拍板时当场判定进不进框架。这个窗口定了一种新做法，判定两次被推到了结课。
- 开课流程本来就要求列「本课产物清单」。开课时只随手列了几样，没有拆成全集。

还有一样连带的。课上说「放到结课再做」的事，记在每个窗口的交接文件（桥梁）里，到这时攒了 35 条。桥梁一窗一份，每次重抄；哪一次漏抄一条，那一条就丢了。

### 三、为什么会这样

**一句话：凭印象报进度，印象里只装得下「还没做」的那几样。一直在顺手做的那一样，从印象里掉了。**

打个比方。搬家时有人问「还剩几箱」，你凭印象说「三箱」，车上其实是四箱。少的那一箱，恰好是你一直顺手在装、从来没当成「待办」的那一箱。

再往下拆，是三个缺口：
- 没有一张盖住全部产物的清单。没有全集，就只能凭印象。
- 规矩按字眼触发。课程规则 77 只在出现「拍板」「入库」这类字眼时才被想起来；这次定的是一种做法，不是一条项目裁决，没触发。
- 说推的事放在了一次性的载体里。这是反模式 24 号（重要的东西只记进一次性载体）的形状。

规矩读过还会忘，更一般的原因见案例一第三节。

### 四、行业怎么解决

**一句话：先列一张盖住全部工作的清单，每项写清做到什么样算完，再用机器核这张清单有没有漏。**

项目管理里有一种做法，叫工作分解结构（WBS），把一件大事要交的东西一层一层拆到最小。它最要紧的一条规矩叫「100% 规则」。项目管理协会（PMI）的《Practice Standard for Work Breakdown Structures》第二版这样写，经维基百科「Work breakdown structure」条目转引：「The 100% rule states that the WBS includes 100% of the work defined by the project scope」。表必须盖住全部工作，一项不少。

表上每一项，要事先写清做到什么样才算完。Scrum 指南管这个叫「完成的定义」：「The Definition of Done is a formal description of the state of the Increment」。

长期的待办和这一轮的待办，要分开放。Scrum 指南说，产品待办是「an emergent, ordered list of what is needed to improve the product」；这一轮的待办是「a highly visible, real-time picture of the work that the Developers plan to accomplish during the Sprint」。

说了「以后再做」的事，管理上叫行动项。维基百科的定义是「an action item is a documented event, task, activity, or action that needs to take place」，每一项要有负责人和计划完成的时间。Scrum 每一轮结束时开回顾会，指南原话：「The most impactful improvements are addressed as soon as possible.」「They may even be added to the Sprint Backlog for the next Sprint.」改进项要进下一轮的待办，和正事一起排。

Scrum 整套做法的根，是三根支柱：「transparency, inspection, and adaptation」，看得见、常检查、随时调。每一轮开头先定一个目标，指南叫它「the single objective for the Sprint」。

最后一层，交给机器。Claude Code 官方最佳实践页说：「Claude stops when the work looks done. Without a check it can run, "looks done" is the only signal available」。给它一个能跑的检查，「做完了」才有硬标准。

### 五、考虑过哪几种

**清单放哪。** 三种（问 489）：
- 放进桥梁的状态表。没选：桥梁一窗一份，放进去还是一次性载体。
- 只靠每条消息末尾的自查。没选：缺的不是提醒，是一份按产物拆到底、每项写清完成标准的清单。
- 本节课单建一份交付物清单文件，报进度从它导出。选了这一种。

长期待办清单（BACKLOG）也考虑过，不合适：它装的是跨课、这节课不做的事，不装这节课要交的全部东西。

**什么时候推到整个项目。** 三种（问 490）：只改框架规格；全都等结课；这个窗口就落三处（课程规则、开课自检、框架规格）。选了最后一种。等结课，正好重犯「推到结课就忘」的错。

**说推的事放哪。** 三种（问 492）：留在桥梁；只另建一张表；搬进交付物清单新开的一节，说推就当场登。选了最后一种。

**从 Scrum 再借什么。** 三种（问 494）：不采纳；全登成待议；每个窗口开头写一句本窗口目标，收尾做一次回顾，现在就进清单。选了最后一种。产品目标（「describes a future state of the product」）本项目早有，导读和框架规格第一节写着最终要做成什么。窗口末检视、待办定期梳理两样，登进清单，结课时再定。

**要不要加进开课自检。** 项目主人提出，把这件事加进每个窗口开头的自检。加了：开课自检第 19 项问「交付物清单建了吗」，第 20 项问「定下新做法时，会当场过三问吗」（用到整个项目吗、进框架吗、进教科书吗）。同时说明：开课提醒一次挡不住这一类，这个窗口开课时读过课程规则 77，照样推到了结课。要和每条消息的自查、能跑的命令一起，三样才稳。
