## 二、正式裁决

### API-1 · 字段的唯一真相是共享 Zod schema
API_CONTRACT.md 只写接口层与全局约定：接口清单、方法、路径、鉴权级别、
退回性质到状态码的映射、响应外壳、管住全部接口的全局约定。
每个接口点名它用哪个 schema，字段本体（字段名、类型、必填与否）留给 05-类型。

三份文件各管一段：PRD 管「能不能」，契约管「怎么调」，schema 管「长什么样」。
每条信息只有一个家。

依据是架构第二节取舍 4——类型由 z.infer 推导，不手写 DTO。
契约文档若手写字段，等于换个文件继续手写 DTO。

这条一拍，甲-08（时间格式）、甲-09（必填与多余字段）等条目**被拆开**，不是被砍掉：
业务语义那半回 PRD，全局规则那半留本课，字段本体那半走 05-类型。

### API-2 · 创建项目不依赖项目内角色
任何已登录用户均可创建，创建者自动成为负责人。接口只挂 AuthGuard，不挂 AuthzGuard。

根因不是两句话打架，是权限矩阵问了一个不成立的问题。
角色按项目划分，脱离项目不存在角色身份。创建项目时项目还不存在，
用户在其中没有任何角色，AuthzGuard 需要的「路径项目 id」也不存在。
所以「创建项目」那一格不该填「可」或「否」，该标「不适用」。

比方：办健身卡时被问「您是金卡还是银卡会员」——这个问题在那一刻不成立。

更正（复课前，DECISIONS-R1 R1-369、R1-377）：课上说两处来源分量不同，一处「已验证」，一处「pm 推导」。
对过 PRD，这个说法不成立：两处同在「二之二」一节，来源同为 pm 推导，同经项目主人审定。
API-2 的结论不变，凭的是上一段的理由。

项目数量上限本版不设，进 BACKLOG 32。
不设不是技术结论，是产品取舍——「不做」是事实，「不预留」是取舍，取舍归主人（反模式 33）。
本条不贵：限额是 Service 里一条独立规则，不改表结构不改契约骨架。是门锁，不是门框。

### 三、新做法：标准怎么用（问 345 A）

- 按层定先后：协议层正式标准、安全基线、框架约定、设计规范，都没有才自定。
- 冲突：上下层冲突，上层让下层；同层几家不一，列出来由主人拍，拍完记 ADR 或契约。
- 每条标准分三档：必须照做；建议便宜就做；可选不做但不堵死，记待办。
- 标准管怎么做，不管做多少；凡称「标准」须给原文出处，没核过的标「未核」。

本窗口的两个例子：版本号三家打架（Google 放路径、微软用查询参数、Zalando 尽量不做），按主参考不加；OWASP 原话说 SameSite 顶替不了正式防护，所以另加 NestJS 自带防护。
