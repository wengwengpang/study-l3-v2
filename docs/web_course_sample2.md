## 3 · 核心讲解

**3a 原理（打比方）**

四象限就是一把**两个维度的尺子**。
横着量「这东西值不值」（收益），竖着量「这东西贵不贵」（代价）。

痛点：没有统一尺子，几个选项摆一起说不清为啥选这个不选那个，也没法跟人解释。
现在升级：四象限是固定的量法，每个选型都过同一把尺，裁决可比、可追溯、能写进 ADR。

两根轴：

- **横轴 · 收益**：这技术给项目带来多少价值，它解决的问题有多重要。
- **纵轴 · 代价**：引入成本 + 学习成本 + 长期维护和演进负担 + 风险。

四个格子 + 裁决：

1. **高收益 · 低代价 → 直接采用**。不用纠结。
2. **高收益 · 高代价 → 权衡引入**。常见做法：分阶段引入，或接受代价但配缓解措施。
3. **低收益 · 低代价 → 可选**。锦上添花，可缓。
4. **低收益 · 高代价 → 拒绝**。

加一条本项目特化的判读（结合你刚才的补充）：

> 对「教学驱动」的组件（如 Redis、WebSocket，不是当前 MVP 负载逼出来的），收益按**教学价值**算。

## 段 3 · 四象限决策法实战 → 产出 TECH_STACK.md

## 1 · 段落定位

## 2 · 这段为什么这么做

约束摸清了，现在要把「选什么」一条条定下来，并且**每条都留下「为什么」**。
不留理由的选型，等于没选型——三年后没人知道当初为啥这么定。

## 3 · 核心讲解

**3a 原理（打比方）**

挑技术像挑工具进工具箱。
每件工具问两个问题：**它多趁手**（解决我的问题吗），**它多沉**（学习、维护、运维要付多少代价）。
趁手又轻 → 直接装进箱。
趁手但很沉 → 得想清楚值不值。
不趁手又沉 → 扔掉。

**Level 1 对应**

网页版时代你选型是「我觉得 X 挺好」就定了。
痛点：没有一杆秤，选完说不清为啥不选 Y，也没法跟人解释。
现在升级：四象限就是那杆秤。每个选择落在哪个格子、为什么留下，全部可追溯。

**3b 操作**

让 architect 把关键候选逐个过四象限，标清「约束驱动还是教学驱动」，产出 TECH_STACK.md 草稿。
能引用 PRD/UI 的标出处（证据契约）。真有分叉的，给你 A/B/C 拍板。

**3c 四象限到底长什么样（⚠️ 下面整块是我补的老师文本，不是 KNOWLEDGE_BASE 原文——它只给了「四象限决策法」这个名字）**

> 你审过觉得合理就用。

两根轴：

- 横轴 = **契合度**：这方案多大程度满足项目约束和需求。左边低，右边高。
- 纵轴 = **代价**：引入它要付的成本——学习、维护、运维、长期风险。下边低，上边高。

四个格子，对应四种处理：

- **右下（高契合 + 低代价）= 甜区，直接选。**
- **右上（高契合 + 高代价）= 权衡区。** 要写清为什么仍然值得这个代价，或有没有更轻的替代。教学需要的东西也归这里。
- **左下（低契合 + 低代价）= 可有可无。** 除非教学要用，否则不进 MVP。
- **左上（低契合 + 高代价）= 排除。**

**我先用「数据库」给你走一遍这把秤**（这样你看清方法，architect 再去套其余的）：

候选 PostgreSQL 16：

- 契合度：高。TaskFlow 沿用、Prisma 配合好、支持 JSON/数组类型和带时区时间，对「以后加课扩展」友好。
- 代价：中低。你 PG 是入门，有一点学习成本。但 TaskFlow 已经用过一轮，不是从零。
- 落点：右下偏右，**甜区**，直接选。

候选 MySQL 8：

- 契合度：中。够用，但类型丰富度和扩展性不如 PG，而且切回 MySQL 等于丢掉 TaskFlow 的继承。
- 代价：低。你 MySQL 熟练。
- 落点：右下，但比 PG 靠左（契合度低一截）。

结论：**选 PG**。继承 + 扩展友好 + Prisma 适配，压过「你更熟 MySQL」这一点。学习成本是一次性的，而且你已入门。

看，这就是四象限——不是凭喜好，是把两个维度摆上秤。

**3d 联动（规则 16，这步串起好几个旧概念）**

四象限不是孤立的。
它的「契合度」一轴，吃的就是上一段 **6 必问** 摸出来的约束。
它每条引用 PRD/UI 标出处，是 **协议 3 证据契约**。
没定的分叉标假设给你拍，是 **协议 4 假设账本**。
约束 → 权衡 → 留档，一条链下来，这正是 architect 这个角色的完整工作法。

## 前端：React 系 vs Vue

Django 是好框架，成熟、省事，单看代价很低。
但它有一个对这门课**致命**的问题：它是 Python。

比方：我们整条栈是「**一种语言走到底**」（TypeScript 前后端通吃）。这不是顺手，是刻意。

为什么刻意？一种语言，才能让前后端**共享同一份东西**：

- 同一份 Zod 校验 schema（密码规则写一次，两端都用）。
- 同一份类型 / DTO（packages/shared）。

换 Django，后端变 Python，边界上就有了两种语言。Zod schema 不能共享了，类型也不能共享了。你得在前端 TS、后端 Python **各写一份**校验和类型，两边还会慢慢对不上。

而「共享类型」正是你这门课要沉淀的核心 harness 资产（强化里的 SHARED_TYPES）。

四象限落点：Django 自己代价低，但对**我们的约束**契合低（打破了 TS-everywhere）→ 落排除区。不是 Django 弱，是它不配我们这组约束。

这就是上一段教的四象限——**契合度那根轴，吃的就是约束**。

**选型没有绝对的好坏，只有「配不配这组约束」。** 这句话你记住，比记住任何一个具体选型都值钱。

## 2 · 这段为什么这么做

TECH_STACK 记的是「选了什么」。
ADR 记的是「**当时为什么这么选、放弃了什么**」。
前者是结论，后者是理由链。理由链丢了，三年后没人敢动这些决策。

## 3 · 核心讲解

**3a 原理（打比方）**

ADR 像**决策的病历**。
不只记「开了什么药」（决策），还记「当时什么症状」（背景）、「吃了会怎样、有什么副作用」（后果）。
换个医生接手，看病历就懂为什么这么治，不会乱改。

不写 ADR 会怎样：半年后你看到「鉴权用 DB session」，想不起为啥不用更轻的 JWT，可能手一痒改成 JWT，把「登出立即失效」这条硬需求撞坏。

**Level 1 对应**

网页版时代你做决策是聊完就过，不留档。
痛点：三个月后自己都想不起为啥这么定；别人质疑你也答不上。
现在升级：ADR-Lite 用三行把背景/决策/后果钉死，可追溯、可交接。

**3b 操作**

让 architect 把**有真权衡**的决策写成 ADR-Lite。甜区无脑选的（TypeScript、Docker 这种没纠结的）不写——给它们写 ADR 是浪费，还稀释了真正重要决策的份量。

**3c ADR-Lite 三行格式（补丁 7，KNOWLEDGE_BASE 有依据，非我编）**

字面就三行：

### 四象限决策法（硬规则 3 · 多候选权衡）

- 右下（高契合+低代价）= 甜区，直接选。
