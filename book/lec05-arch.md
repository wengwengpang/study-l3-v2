## 二、学完能做到什么

1. 能把一个系统按业务切成模块，给每张表定一个唯一的主人，画出不成环的依赖图。
2. 能说出后端一个请求依次经过哪几层，每一层管什么、不管什么；能判断一项权限检查该放在哪一层。
3. 能拿一条真实的请求，在纸上把设计走一遍，找出走不通的地方。
4. 能画出部署拓扑：几个容器，谁对外，谁只在内网，配置从哪来。
5. 能用两轮的方式让 AI 做架构：先核对、列取舍，你拍板，再写正文；每一节定稿就当场回头改上游。

## 三、原理

**为什么要有这一课。** 打个比方。第 5 课的数据库设计是仓库里的货架：东西放在哪一格。这一章的架构是整个厂区的平面图：有几个车间，车间里怎么分工，货从哪个门进、经过谁、从哪个门出。下一章的接口契约，是车间之间递的交接单。平面图没画，就不知道有几个车间，也就不知道要开几种交接单。所以先架构，后接口。

不画会怎样？写到第 10 课的后端，每个人按自己的理解建目录、放代码。同一件事有人放在这个模块，有人放在那个模块；一项权限检查有人写在门口，有人写在里面。等到发现，已经有一堆代码压在上面。

### 先认几个词

**模块。** 系统里按业务分出来的一块，像公司里的一个部门。本项目分六个：用户、登录、权限判定、项目、任务、通知。

**依赖。** 一个模块的代码要调另一个模块的功能，就叫它依赖那个模块。像一个部门办事要打电话找另一个部门。

**NestJS。** 本项目后端用的框架。它把一个请求的处理分成固定的几层，下面「分层」一小节讲。

**层。** 一个模块内部按职责分的几段：谁接请求，谁做业务判断，谁碰数据库。

**请求上下文。** 一个请求在后端各层之间传递时，随身带着的一个「小本子」。前面一层查到的东西，比如「当前是谁登录」，写在上面，后面一层直接看，不用再查。

**容器。** 一个打包好的、自带运行环境的小隔间，一个服务跑在一个容器里。用的工具叫 Docker。

**Docker Compose。** 一份文件写清有哪几个容器、它们怎么连，一条命令把它们一起拉起来。

**Nginx。** 一个放在最外面的服务，所有从浏览器来的请求先到它这里，由它转给里面的服务。这种做法叫反向代理。

**TLS。** 网址前面 `https` 的那个加密。在哪一层解开这层加密，叫 TLS 终止。

**SSR。** 服务端渲染。页面先在服务器上拼好再发给浏览器，第一屏出来得快。Next.js 支持它，前提是有一个一直在跑的服务进程。

**端口。** 一台机器上区分不同服务的门牌号。一个服务对外开了端口，外面就能直接连到它。

**数据卷。** 给容器挂的一块存储。容器删了重建，数据卷里的东西还在。

### 第一块：模块划分

**模块就是部门。** 打个比方。一家二十人的公司，不分部门，谁都能改所有东西。想改一条退款规则，不知道散在多少人手里。分了部门，客服遇到退款，就去找财务。分模块真正解决的不是「整齐」，是改一处时，波及的范围可控。

**按业务切，不按技术切。** 有一种分法是按技术：所有接请求的代码放一个目录，所有业务逻辑放一个目录，所有碰数据库的放一个目录。这样改一个功能，要在三个目录之间来回跳。本项目按业务切：和任务有关的放在任务模块里，和项目有关的放在项目模块里。这是这一块最要紧的一句话。

**拥有一张表 = 唯一能写它的。** 每张表有且只有一个主人。只有主人能写这张表；别的模块想改，得调主人提供的方法。为什么？两个模块都能写同一张表，规则就散在两处，改一处忘一处。没人管的表也不行。

**读不算拥有。** 别的模块可以读这张表，归属不变。

**依赖单向，不成环。** 打个比方：三个部门互相等对方先办完，谁都动不了。代码里两个模块互相依赖，框架会报循环引用，只能用别扭的办法绕开。所以依赖只许单向。

**本项目的六个模块。**

| 模块 | 管什么 | 拥有的表 |
|---|---|---|
| users | 用户账号 | users |
| auth | 注册、登录、登出，会话是否有效 | sessions |
| authz | 判定「谁在哪个项目是什么角色」，放行或拒绝 | 无，只读成员表 |
| projects | 项目，以及成员和角色 | projects、project_memberships |
| tasks | 任务的创建、分配、状态、截止、汇总 | tasks |
| notifications | 站内通知 | notifications |

六张表都有主，没有一张表有两个主人。

**几个值得讲的决定。**

- **用户和登录拆成两个模块。** 打个比方：人事部管员工档案，门禁室管刷卡进门。拆开，才守得住「一表一主」：登录模块不直接写用户表，注册时调用户模块建账号。邀请成员时按邮箱找人，直接问用户模块，不用绕登录模块。
- **权限判定单独成一个模块，而且不拥有表。** 它是横切的：几乎每个业务模块的请求都要过它，它不属于任何一个业务。权限是安全边界，口径必须集中在一处。代价是：成员表由项目模块写、由权限模块读，分在两处。
- **通知模块本版是个空壳。** 表已经建了，可本版没有任何功能往里写。架构图上还是要列它，不然那张表就成了没人管的孤儿。打个比方：地图上可以标「此处将建」。
- **项目的进度汇总并进任务模块。** 汇总的数据全来自任务表，单开一个模块只是多一层转手。

**这一块拍的几条本版范围。**

- **用户表不加姓名字段，界面一律显示邮箱。** 判断用的是一把尺子：将来补，贵不贵？第 5 课的软删除，将来补要做数据迁移，很贵，所以要认真拍。加一个可空的姓名列，将来补只是加一列，很便宜，所以现在可以不加。同样的形状，因为将来补的成本不同，结论也不同。
- **跨项目总览（US-05）本版延后。**
- **US-04 的第三条验收延后。** 它要用项目的截止日期。可需求里没有任何一条故事允许谁去设置、修改项目的截止日期。加一列没人能填的字段，比没有更糟。所以这不是「加不加字段」的数据结构问题，是「做不做这个功能」的范围问题，归 D1。

**依赖图只记业务依赖。** 依赖图要回答的是「业务数据往哪个方向流」。所以只记一种关系：一个模块的代码，调了另一个模块的 Service。权限检查是挂在请求入口上的，不算依赖。打个比方：一个部门办事要打电话找另一个部门，这是依赖；公司统一在每个门口派了保安，不算哪个部门依赖保安。但保安自己要去人事部查花名册，这就算保安依赖人事部。

按这个口径，本项目的依赖图是：

```
auth → users
projects → users
authz → projects
tasks → projects、users
notifications → tasks、users
```

users 不依赖任何模块，是地基。authz 只依赖 projects：它要读成员表判角色。它不依赖 auth：当前是谁登录，是 auth 那一道检查查完后写进请求上下文，authz 从上下文里取。两道检查之间没有代码调用，中间隔着这个小本子。看不见，不等于没关系，所以文档里要写一句说明。

### 第二块：分层

**横着切和竖着切。** 模块划分是横着切：公司有几个部门。分层是竖着切：每个部门里，谁接活，谁干活，谁碰仓库。

**打个比方：一家餐厅。** 服务员接单，不下厨；厨师做菜，不接客；仓库管理员管食材，不懂菜谱；菜单前台后厨各一份，内容一样。对到后端：接请求的是 Controller，做业务判断的是 Service，碰数据库的是 Repository，前后端共用的那份菜单是共享层。

**不分层会怎样。** 三个后果。改不动：一段代码里又接请求又判业务又写库，改一处牵一片。测不了：业务判断和数据库缠在一起，想单独测业务逻辑，得先准备一个数据库。重复：同一条规则在好几个接口里各写一遍。

**一个请求依次经过谁。** NestJS 处理一个请求，顺序是固定的：

```
Guard → Pipe → Controller → Service → Repository → Prisma
```

打个比方：保安在前台之前。被保安拦下的人，根本见不到前台。被 Guard 拒绝的请求，Controller 一行都不会执行。这个顺序要记牢：以为能先在 Controller 里做点准备、再让 Guard 判断，是行不通的。

| 层 | 负责 | 不做 |
|---|---|---|
| Guard | 门口的两道检查：会话有效吗（AuthGuard，属 auth）；是不是这个项目的成员、什么角色（AuthzGuard，属 authz） | 读任务这类业务记录，判断记录归谁，解析请求体 |
| Pipe | 检查请求体和查询参数的形状、类型 | 业务规则，权限判断 |
| Controller | 取参数，调本模块的 Service，返回结果 | 业务判断，碰数据库 |
| Service | 业务规则；判断「这条记录归不归当前用户」 | 解析请求，直接写数据库查询 |
| Repository | 这张表唯一的读写出口 | 任何业务和权限判断 |

跨模块只走对方的 Service，不许直接伸手进对方的 Repository。

**Repository 是约定，不是墙。** 每个模块都写 Repository，给「一表一主」一个具体的文件落点。可它挡不住人：别的模块技术上仍然能直接连数据库绕过它。要变成墙，得靠机器检查代码里谁引用了谁，那是第 8 课的事。第 0 课讲过「环境有两种硬度」，这是又一个例子。

**共享层放什么。** 前后端共用的东西放在一个共享包里。可这个包很容易越塞越多，必须划死。

- 允许进：校验规则（Zod schema），从校验规则推出来的类型，三个枚举，没有输入输出的纯常量和纯函数。
- 不许进：连数据库的代码，读环境变量或做输入输出的代码，只属于前端或只属于后端的框架代码，数据库表的类型，以及权限判定的唯一实现。

一个新东西该不该进，问四句，全过才进：前后端是不是都真的用它？它有没有运行时依赖？它变的时候前后端是不是必须一起变？它是不是安全边界的执行点？

第四问是后来补的。权限规则能通过前三问：两边都用，不做输入输出，要一起变。可「共享一份规则」和「共享一个执行点」是两件事。规则可以共享，让前端照着显示按钮；但后端必须自己独立执行判定，前端那份只管显示。

**校验在三处执行，各拦各的。** 前端提交前拦一次，给用户即时反馈，也只有前端能「阻止提交」。后端的 Pipe 拦一次，这是唯一可信的一道：绕过界面直接打接口，只有它拦得住。Service 里再拦业务规则，比如状态能不能这样变。只在前端拦，直接打接口就穿了；只在后端拦，用户每打错一个字都要来回一趟。

**两级权限的界线。** 这是这一块最值钱的一句话：

> 只凭会话和路径就能判的，归 Guard；要读请求体或业务记录才能判的，归 Service。

Guard 手上只有三样：会话凭据，网址路径里的参数，成员表。拿这三样判得了的，比如「他是不是这个项目的成员」，在门口判。判不了的，比如「这条任务是不是派给他的」，得先把任务取出来才知道，就留给 Service。

一开始的界线不是这样写的，是「不查库就能判的归 Guard」。后来发现站不住：两道 Guard 本来就在查库，一个查会话表，一个查成员表。照那个说法，这两个 Guard 都不该存在。分界真正看的不是查不查库，是判断需要哪些输入。

旧说法还附了一条理由：「Guard 里做输入输出会让请求变慢」。这条理由也是假的，删掉了。留下的真理由是：在 Guard 里取业务记录，同一条记录会被 Guard 和 Service 各查一遍。

**一个例子：执行者想改一条不是派给他的任务。**

1. AuthGuard：会话有效吗？无效就退回「未登录」。跳到登录页是前端收到这个回应以后做的事，不是 Guard 做的。
2. AuthzGuard：他是这个项目的成员吗？不是就退回「权限不足」。他是执行者，放行，因为执行者本来就能改自己任务的状态。
3. Pipe：请求体的形状对吗？
4. Controller：调 TasksService。
5. TasksService：取出任务，先比对任务所属的项目，和网址里的项目是不是同一个。不是就拒绝。
6. TasksService：再比对任务的负责人是不是他。不是就拒绝。

拦在第 5、6 步的 Service。Guard 拦不住：它既不知道那条任务属于哪个项目，也不知道派给了谁。

**「没权限」和「不存在」给同一个回应。** 执行者只能看自己的任务；对他来说，看别人的任务和看一条不存在的任务，结果应该一样，不然他能借此打探别人有哪些任务。这和需求里「登录失败统一提示」是同一个思路。但不是铁律：需求里邀请一个不存在的邮箱，是分开提示的，因为那是负责人在项目内部的操作，不构成打探的风险。看场景选。

**前端也分层。** 四层：路由层管页面和登录跳转、首屏取数；数据访问层是唯一发请求的地方；视图组件层管显示和交互；最底下是无业务的基础组件。第 3 课定的「三态」，加载、空、出错，落在视图组件这一层。

**前端从哪知道「我是什么角色」。** 进入项目时，后端在回应里一并给出当前角色。三条硬约束，缺一不可：

1. 前端拿到的角色只用来决定显示哪些按钮，不构成授权。
2. 每个受限的接口，由后端的 Guard 自己去查成员表判定，不信前端传来的任何角色信息。
3. 角色只在这一次页面里用，不跨页面长期缓存；角色确认之前，负责人专属的入口先不显示。

第 3 条的来由：需求要求角色改了立刻生效，不用重新登录。拿一份旧的缓存去显示入口，正好违反这一条。

一句话：后端管拒绝，前端管呈现。

**名字的三层。** 数据库里的列名用小写加下划线，比如 `assignee_user_id`；代码里和接口里一律用小写开头、后面每个词首字母大写，比如 `assigneeUserId`。两套名字的边界就在第 5 课 schema 里的 `@map` 上：下划线的写法被关在数据库里，出不来。这样前端写 `userId`、后端写 `user_id` 这类对不上的错，在本项目里结构上就不会发生。

**类型从校验规则推出来，不手写。** 手写一份类型，等于同一件事有两份真相，改一处忘一处。

### 第三块：数据流，在纸上走一遍

**为什么非得走一遍。** 打个比方。第一、二节合起来是一栋办公楼的平面图：哪个部门在几楼，每个部门里工位怎么排。平面图上画得通的门，真推开可能是一堵墙。第三节就是请一位客人真的走进这栋楼办一件事，看他在哪里被卡住。

本项目走第一趟就撞上一堵墙。第二节规定 Guard 只看会话、路径和成员表，不读任务记录。可执行者查看一条任务的详情时，请求里只有任务的编号。Guard 要判断「他是不是这个项目的成员」，项目的编号从哪来？它藏在任务表里，而 Guard 不许读任务表。这个洞在平面图上看不出来，一走就撞上。不走，就要拖到第 10 课写后端时才炸。

**走几条路才够。** 判据不是每个接口都走一遍，是每一种检查点都覆盖到。打个比方：体检不用把每个器官切开看，覆盖每一类检查就够了。本项目的检查点只有六种：

1. 会话还有效吗？
2. 是不是这个项目的人？
3. 角色够不够？
4. 请求体的形状对不对？
5. 这条记录是不是你的？
6. 这个改动合不合业务规则？

两条路就把六种都踩到了。读路径 R2：执行者查看一条任务的详情，踩到「记录是不是你的」，因为那条任务是不是派给他的，只有先把记录取出来才知道。写路径 W1：负责人建一个任务并派给执行者，踩到「角色够不够」「请求体对不对」和跨模块调用。第二十个接口，只是把前面某几种检查点再走一遍。

**这不是测试。** 它是在纸上走一遍，验的是设计。真发请求、看回应，是第 14 课测试的事。

**每一步写五样。** 经过哪一层；做什么校验；做什么权限判断；不通过时从哪一步退回，退回的是什么性质的结果；读或写哪张表。退回的结果只写性质，比如「未登录」「权限不足」「参数不合法」，不写具体的状态码和网址。那些归下一章的接口契约。同一件事写在两处，将来改一处忘一处。

**R2 读路径：四道拦截。**

| 步 | 层 | 做什么 | 不通过时 |
|---|---|---|---|
| 1 | AuthGuard | 拿会话凭据查会话表，要求存在且没过期，得到当前是谁 | 未登录 |
| 2 | AuthzGuard | 拿「当前用户 + 网址里的项目」查成员表，有记录就放行，角色写进请求上下文 | 权限不足 |
| 3 | Pipe | 这条路没有请求体；查询参数暂按不设处理（这是假设，以下一章的接口契约为准），什么都不检查 | 无 |
| 4 | Controller | 取参数，调 Service | 无 |
| 5 | Service | 按任务编号取出任务 | 查不到：权限不足 |
| 6 | Service | 任务所属的项目，和网址里的项目是不是同一个 | 权限不足 |
| 7 | Service | 他是执行者的话，任务是不是派给他的；没派给任何人也算不是 | 权限不足 |
| 8 | Service | 准备负责人的显示信息，一律显示邮箱 | 无 |
| 9 | Controller | 返回任务详情 | 无 |

四道拦截一句话各一：你登录了吗，你是这个项目的人吗，这条任务真是这个项目的吗，这条任务是你的吗。全程只读，不写任何表。

**第 6 步最要紧：一个越权的漏洞。** 前面那堵墙的解法，是把项目编号也放进网址里，比如「项目 A 下面的任务 7」。Guard 拿网址里的项目 A 去查成员表。这是常见的写法，可它不是白给的。

设想一个人是项目 A 的成员，不是项目 B 的成员。他构造一个请求：网址写项目 A，任务编号却填项目 B 里的一条任务。Guard 一看：他是项目 A 的成员，放行。如果 Service 直接按任务编号取出那条任务返回，他就读到了项目 B 的数据。这叫越权读取。

所以第 6 步是必付的代价：Service 取到任务以后，必须比对任务的项目和网址里的项目，不相等就拒绝。

**W1 写路径：三道拦截，加一条硬规矩。**

| 步 | 层 | 做什么 | 不通过时 |
|---|---|---|---|
| 1 | AuthGuard | 同 R2 第 1 步 | 未登录 |
| 2 | AuthzGuard | 查成员表，并要求角色是负责人 | 权限不足 |
| 3 | Pipe | 检查请求体：标题、描述是文本，负责人是整数或空，截止时间是时间或空 | 参数不合法 |
| 4 | Controller | 取参数，调 Service | 无 |
| 5 | Service | 负责人不为空时，问项目模块：他是不是这个项目的成员？可以派给负责人自己 | 参数不合法 |
| 6 | Service | 写入任务，项目编号只从网址里取 | 内部错误 |
| 7 | Controller | 返回新任务 | 无 |

**第 6 步的硬规矩：鉴权用哪个编号判，写入就必须用哪个编号。** 建任务时还没有旧记录可比，R2 那道比对用不上。假如允许从请求体里取项目编号写入：网址写项目 A（他是负责人，Guard 放行），请求体里写项目 B，任务就被建进了他无权的项目 B。所以新任务的项目编号只从网址取，不从请求体取。它和 R2 的第 6 步是同一个防御的两面。

**第 5 步为什么问项目模块。** 判断负责人是不是本项目成员，要读成员表，而成员表的主人是项目模块。跨模块只走对方的 Service，不许直接摸对方的表。这是第一节「一表一主」在真实流程里的第一次兑现。

为什么不只检查「这个用户存在」？那样会造出「看起来有人负责、实际那人根本不在项目里」的任务。没人知道它，它就静悄悄地烂在那里。先问一句「这里出错会怎么烂」，再决定要不要多做一道检查。

第 5 步不通过时退回「参数不合法」，而不是「权限不足」。区别在于会不会泄露信息：项目成员名单本来就是负责人能看的，告诉他「这人不是成员」不算泄露。

**几个走查时拍下的决定。**

- **服务端用自己写的校验管道。** NestJS 自带的那个校验管道，认的是另一套校验库；本项目选的是 Zod，两边天生不认识。自己写一个，十几二十行。引第三方库，默认的报错格式未必合需求的要求。
- **网址里的编号不单独做格式检查。** 乱写的编号和不存在的编号，结果一样：查不到，权限不足。但有一个坑：一串根本不是数字的字符，直接交给数据库查询，会抛出内部错误，而不是「查不到」。所以查库前先把它转成数字，转不动就当查不到。这是一次容错，不是格式检查。
- **会话固定 30 天，不续期。** 打个比方：健身卡办了 30 天，是到期作废，还是每来一次就往后顺延？续期的话，每个只读的请求都要顺手写一次会话表，一个「看看」的动作悄悄变成了一次写。本项目选固定 30 天。会话表里已经有过期时间这一列，将来要改成续期也来得及。

**选型一变，要拍的板也变。** 如果第 4 课选的是 JWT，「续不续期」根本不是个问题：JWT 是无状态的，想让它提前失效，得另建一张黑名单。正因为本项目把会话存在数据库里（为了登出立即失效、角色改了立即生效），「续不续期」才成了一个需要主人拍板的选项。

**理由比决策传得更远。** 走查时还发现一件事：第二节有一条决定是对的，可写在它旁边的理由站不住。决定只管这一处；理由会被将来的人拿去推别的地方。所以理由错了也要改，不能因为「反正结论对」就放过。

还有一次，一个推荐的理由被推翻了：当时以为「格式不对的编号自然会查不到」，只想了「格式合法但不存在」这一种情况，没想到「根本不是数字」这一种。结论后来还是对的，补了上面那条容错。教训：给一个行为下结论之前，先列出输入有几种形态，逐种走一遍。

### 第四块：部署拓扑

**进程里面和进程外面。** 第二节讲的是后端程序内部的层，第三节从请求进了后端程序讲起。第四节画的是进程外面：有几个容器，谁跟谁通，浏览器发出的请求在进后端程序之前，先撞上谁。

**打个比方：一个小区。** 第二节是一间屋子里家具怎么摆，第四节是整个小区的平面图。

- 容器是小区里一栋一栋独立的房子，各自带着自己的水电。
- Docker Compose 是小区的规划图加物业：哪几栋房子，怎么连，一声令下一起开门。
- Nginx 是大门的传达室：外人只能先到这里，由它领到该去的那栋。
- 端口映射是在围墙上开一扇对外的窗：开了，外人就能绕过传达室，直接敲那栋房子的门。

**图纸不等于生效。** 这一节只画图。真把容器搭起来跑通，是第 9 课的事。写了，不等于它真按写的那样在运行。

**不画会怎样。** 第 9 课写 Compose 文件时只能边写边想；第 15 课上线时，证书放哪、前端的静态文件谁发，全是现场拍板。

**生产环境长这样。**

```
[浏览器]
   │ 只开 80、443
   ▼
[nginx]  反向代理 + 解开 https 的加密
   ├─ 根路径 ──→ [frontend]  Next.js 服务进程
   │                 │ 服务端渲染取数：容器内网直连，不绕回 nginx
   │                 ▼
   └─ 接口前缀 ─→ [backend]  NestJS
                     │
                     ▼
                [postgres] ── 挂数据卷
```

除了 nginx 的 80 和 443，哪个容器都不对外开端口。

**拍下的几件事，和各自的理由。**

- **四个容器，前端单独一个。** 第 4 课选 Next.js 的理由之一是服务端渲染让首屏快。服务端渲染需要一个一直在跑的服务进程，所以前端得单独起一个容器。要是不起，就等于改了第 4 课的选型，那不是这一节该拍的。
- **Nginx 只做两件事：转发请求、解开加密。** 第 4 课原本还让它发静态文件。现在静态文件由前端的服务进程自己发。本项目这点量，让 Nginx 多管一件事带来的牵扯不值得。这一条推翻了技术选型里的一句话，所以要当场回头改那一行。
- **同一个域名，按路径分流。** 根路径给前端，接口前缀给后端。一张证书；浏览器看来是同一个网站，不用配跨域。这个推荐有个前提：登录凭据放在 Cookie 里，同一个网站的 Cookie 浏览器会自动带上。凭据最后怎么带、前缀写成什么字符串，都归下一章的接口契约。
- **服务端渲染取数，走容器内网。** 前端的服务端代码直接连后端，不绕回 Nginx，也不走公网。绕公网要多走一圈，多一次加密解密。代价有两个：前端要配两个后端地址，浏览器用公网的，服务端用内网的；浏览器带来的登录凭据，不会自动跟着服务端的这次请求走，要手工转发。
- **数据库端口：开发时开，生产时不开。** 开发时要从自己的电脑上直接连数据库跑迁移；生产时把数据库端口对公网开着，是真实的攻击面。
- **只画一套生产拓扑，加一张「本地与生产的差异」清单。** 画两套，同一张图画两遍，改一处忘一处。本地日常只有数据库进容器，前后端直接在电脑上跑；另留一份完整的四容器配置，上线前在本地跑一次。
- **数据库迁移由人手动触发，不随容器启动自动跑。** 迁移改的是真数据，做了就难回头，属于 D5，要喊主人并双重确认。藏进容器启动里，就绕过了这道闸。
- **画出数据卷，备份留到灾备那一课。** 不挂数据卷，数据库容器一重建，数据就没了。可数据卷只防重建，不防误删，也不防磁盘坏。第 5 课 ADR-DB-002 写着「恢复误删要靠备份」，可备份方案还没定。这件事要在文档里明写出来：本版上线后如果误删，没有已定的恢复手段。
- **「环境一致」怎么读。** 技术选型里写着 Docker 让「环境一致」。这句话指的是镜像和运行环境一致，配置按环境不同。不然「数据库端口开发开、生产不开」就和它打架了。一个含糊的词，将来会被人拿去推别的结论。
- **将来的组件不画在图上。** 缓存、实时推送、定时任务，只在图外用文字注明「将来从哪接入，不是本版已定的选型」。画上去，下一个读的人会以为已经定了。

### 架构是螺旋，不是流水线

四节不是写完一节就封死一节。第三节走查时，发现第一、二节有好几处写得不对；第四节画拓扑时，又发现第一节的依赖图和第二节的一句话要改。下游暴露上游的洞，是它的正常功能，不是事故。

**毛病出在回写的时机。** 发现了，就当场回头改上游，再往下走。不要攒。这一课的实际经过是攒了：发现一处记一处，到最后攒成二十几处，单独花了一整个窗口去还，文件里一度同时存在三个版本的口径。第七节会讲这件事。

**改上游时的几个手法。**

- **显式的空和沉默的空。** 一节里没有待定项，就写「无」。整节删掉，读的人分不清是真没有，还是没人想过。
- **过时的记录，删还是盖章。** 一条待办做完了：如果它除了「该做某事」，还告诉了后人别的东西，比如当时发现了什么问题，就留着，在上面加一行「已于何时完成」；如果没有，就删。
- **单一信息源。** 不是说一件事只准记一处，是说同一件事只有一个权威的定义，别处都指向它。

### 让 AI 做架构的几个道理

**一轮只出一件交付物。** 一个任务里塞了四件事，跑了六分钟没完，一中断，四件全丢。药方是按交付物拆轮：一轮一件事，每轮都有一个可以落地的中间结果。

**先核对，再起草。** 打个比方：盖房子之前，先下去探一遍地基；探完了再砌墙。第一轮只让 AI 做三件事：把你的决定和已有文件对一遍，找出文件和文件之间的矛盾，列出你还没被问到的取舍。一个字的正文都不写。第二轮才照你拍过的板写正文。

**拆两轮，买到的是选择权。** 部署拓扑这一节看起来很轻，第一轮核对下来，冒出来九项该主人拍、却从没被问过的取舍。一轮写完的话，这九项 AI 会各自挑一个看着合理的答案，直接写进正文。产出短，不等于决策少。

**判断留给人，展开交给它。** 第二轮的 AI 不再做决定，只把你拍过的板展开成正文。就算这一轮中断，丢的只是正文，判断不丢。

**每一节定稿，就扫一遍传播面。** 拍下一个决定，要打开每一份可能受影响的文件，逐份写「要改」或「不影响」。不能靠回忆推断，必须真打开看。立一条新的口径时，还要回头扫一遍自己文件里已经写下的东西：新口径的传播面，包括它自己的过去。

## 四、动手

这一节照推荐的做法走：四节，每节先让 architect 出一轮，你拍板，再落进文件，然后当场回头改上游。数据流和部署拓扑这两节，每节跑两轮。一共十步，第 0 步到第 9 步。每步四样：目的，要发的 prompt 或要敲的命令，应该看到什么，出了错怎么办。

**这一章的 architect 是真正的子代理。** 第 5 课是让主对话读 architect 的定义文件、照着办。这一章换成把活交给 architect 子代理，原因有三。一，每一轮都要读好几份长文件，子代理在自己的上下文里读，不占主对话的地方。二，这几轮只要它交结论，用不着来回问答。三，子代理的只读是机器拦着的：它的定义文件里只给了读文件的工具，写不了文件。两种做法的区别，第 5 课第六节讲过。

**子代理的完整输出，靠机制取，不靠嘱咐。** 子代理跑完，交回主对话的只是一份摘要。prompt 里写「把它的完整输出原样展示给我」，管不住这件事。要看全文，敲 `/tasks`，选中那个子代理，按回车，打开它的记录；或者按 `Ctrl+O`，打开对话记录查看器，看每一步的细节。官方文档对这两样的说法见第六节。

**判断它卡没卡住，看数字动不动。** 子代理跑的时候，界面上有计时和用量的数字。数字还在涨，就是活的；不看已经跑了多久。

**模式。** 状态栏保持 `manual mode on`，每一步都先问。子代理只读，不受影响；后面回头改上游时，主对话每改一处都会先停下来给你看改前改后，这正是要的。

### 第 1 步　模块划分：让 architect 出方案

**目的。** 只做模块划分：有几个模块，各管什么，每张表归谁，谁依赖谁。不做分层，不做数据流。

整段发给主对话：

```

读 .claude/agents/architect.md，按里面的定义激活自己，然后开始下面的任务。

任务：产出【系统架构的第一块：模块划分】。只做模块划分。不做分层，不做数据流，不做部署拓扑，不设计 API。

prisma/schema.prisma
docs/arch/TECH_STACK.md
如果你认为还需要别的文件才能下判断，不要自己去找。在输出里写明「需要哪个文件、为什么需要」，然后停下。

输出四个部分，按顺序：

第一部分 · 澄清问题

**审。** 重点看三处：分流有没有把前缀字符串写死；证书那一条有没有顺手定下签发方式；迁移有没有写成随容器启动自动跑。出现「可选方案」「视情况而定」这类措辞，就要警惕它在把已拍的板重新打开。

### 第 8 步　结果验收：用 grep 照一遍，逐行判

**目的。** 每一处改动你都看过改前改后，那是过程验收。全部改完以后，再从整体上照一遍，看有没有漏改的、改坏的。两者不能互相代替。

```
grep -c "^## " docs/arch/ARCHITECTURE.md
grep -n "ValidationPipe" docs/arch/ARCHITECTURE.md
grep -n "管道变重" docs/arch/ARCHITECTURE.md
grep -n "^tasks →" docs/arch/ARCHITECTURE.md
grep -n "静态" docs/arch/TECH_STACK.md
```

**应该看到。** 下面是本项目的真实输出，长行截短了：

```

407:- T1 服务端校验用项目自写 Zod 管道（实现 PipeTransform 调共
428:2. 第二节仍写 ValidationPipe，与 T1 不符，待回写。

79:tasks → projects、users

**怎么判。** grep 是探照灯，不是开关。「有命中」不等于「没改干净」，要逐行问一句：这一行该在这吗？

- `ValidationPipe` 三行：第 170、407 行写的是「不用它」，否定的写法要留着，「用什么」和「不用什么」是两条信息。第 428 行在第三节「本节暴露的问题」里，那一节开头已经盖了章，写明这些是演进记录，不是待办。三行都该留。
- `管道变重` 一行：同样在演进记录里，该留。第二节里已经没有这条假理由了。
- `tasks →` 两行：第 69 行在「归属自检」里，意思是 tasks 模块拥有 tasks 表，不是依赖。用了同一个箭头，意思不同。第 79 行是依赖图，里面已经没有 authz，对了。
- `静态` 一行：写的是「不托管静态资源」，对了。

**验收的预期，写「不得残留什么」，不写「应剩几行」。** 课上有三次，事先预告了一个行数，结果数错了：要么漏数了文件里本来就有的否定写法，要么没算上自己刚写的新文字里也含这个词。错误的验收标准比没有标准更危险，它会指挥人去改坏正确的东西。

**出了错怎么办。** 某一行判下来确实是漏改的旧措辞，回到第 5 步的写法补一处。
