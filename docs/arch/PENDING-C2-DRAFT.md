## 一、接口清单骨架

一共 17 个接口。notifications 模块本版没有接口（API-45，docs/arch/API_CONTRACT.md:484）。authz 是横切模块，也没有接口（docs/arch/ARCHITECTURE.md:32-39）。表里写「候选」的路径都还没定，后面括号写着去第四块哪一条。

**鉴权四档**
- 公开：不挂 AuthGuard。
- 只要登录：只挂 AuthGuard。
- 本项目成员：AuthGuard 加 AuthzGuard，两种角色都放行。
- 只有负责人：AuthGuard 加 AuthzGuard，执行者回「不许做」。

**每行都不再重复写的退回**
- 所有接口都可能回「内部错误」。路径不存在算「看不见」（docs/arch/API_CONTRACT.md:207-209）。
- 所有非 GET 都可能回「跨站被拒」（:75-77）。
- 带请求体的都可能回「格式不支持」和「参数不合法」（:101、:111-117）。
- 所有 GET 碰到多出来的查询参数，回「参数不合法」（:117）。
- 除了两个公开接口，都可能回「未登录」。
- 路径带项目 id 的，不是成员或 id 转不成数字时回「看不见」（:55）。

**路径用到的标准**

以下三条都已登记在 docs/arch/STANDARDS.md:33。
- Zalando #129，路径小写、单词用连字符。必须（API-51 第六点）。
- Zalando #134，资源名用复数，只有一个的写成集合。必须（API-57）。
- Zalando #141，路径不带动词。必须（API-58）。

### 第一组：起草第二节前必须先拍（12 条）

**第 1 条　注册的路径**
- A：POST /api/users。注册新建的资源就是用户（API-53）。接口代码放 auth。甜区。
- B：POST /api/accounts。用 PRD 的词「创建账号」（PRD.md:144），但同一个东西就有了两个名字。可有可无。
- C：POST /api/register。路径带动词，违反 #141 必须档，还要推翻 API-58。排除。

**第 2 条　登录的路径**

- B：路径同 A，但把 API-53 改成回 201，照 RFC 9110 第 15.3.2 节的字面读法。权衡区。
- C：POST /api/login。同第 1 条 C，排除。
- 推荐 A。理由：名词资源；API-53 已拍过「会话交不到调用方手里，所以回 200」，第二节这一行写明出处就行。

**第 3 条　登出的路径**
- A：DELETE /api/sessions/self。会话编号从 Cookie 里来，用 self 当伪编号。甜区。
- B：DELETE /api/sessions/{sessionId}。要把会话 id 交给前端，和 :177「响应体里从不出现会话或它的 id」相悖。排除。
- C：POST /api/logout。违反 #141，排除。
- 推荐 A。理由：和第 2 条同一个资源，不暴露会话 id。
- 标准：#143 的 self 例外，2026-10-23 已核（STANDARDS.md:33）。但 #143 本身是哪一档，这六份文件里没写，待确认（假设：必须档，self 是条内允许的例外）。

**第 4 条　当前用户的路径与所属模块**（API-34 留的）
- 路径：
  - A：GET /api/users/self。照 #143 的 self 例外。甜区。
  - B：GET /api/sessions/self。和登出同一个地址，但返回的是用户，名实不符。可有可无。

- 模块：选 A 时，放 auth 还是 users。
- 推荐：路径 A，模块放 auth。理由：注册已经必须放 auth，这样 /api/users 下的路由都在同一个模块里；auth→users 这条依赖本来就有（ARCHITECTURE.md:76），不加新的依赖；users 保持只做数据地基（ARCHITECTURE.md:82）。

**第 5 条　改状态的路径**（API-35 留的）
- A：PUT /api/projects/{projectId}/tasks/{taskId}/statuses。照 API-57 写成恰好一个元素的集合，请求体用一元素数组。要把 API-50 里「改状态用 PATCH」一句改成 PUT。名字容易被读成「状态历史」。权衡区。
- B：PATCH .../tasks/{taskId}/status，单数。读着自然，API-50 不用动。但偏离 #134 必须档，要登偏离，还要在第一节加一句例外（API_CONTRACT.md:536）。权衡区。
- C：POST .../tasks/{taskId}/status-changes。把「一次状态变化」当成新建的资源，不偏离标准。但这个资源没有表、读不回来，要像登录那样回 200，也要改 API-50。权衡区。
- 三种方案成功后回什么还不一样：可能回子资源本身、回整个任务，或者回 204 让前端重取。这个跟方案走，选了方案再定。
- 推荐 A。理由：照刚拍的 API-57 和 #134 必须档走，不添偏离；和转让负责人是同一种写法。
- 标准：#134 必须；RFC 9110 第 9.3.4 节必须（STANDARDS.md:18）；#148 必须。C 依据的 Zalando #138 只在 STANDARDS.md:17 主参考那一行下面，没单独登记，档次未核。

- 推荐：和第 5 条取同一口径，第 5 条取 A，这里就取 A。理由：同一条规则在两处写法一致。

**第 7 条　页 5「成员任务状态区」（US-01）由哪个接口供数**
