# REFACTOR-HANDBOOK · 资料重构手册

> 用途：一套给失忆 AI 读的说明书写乱了，要停下来修时，照这份走。
> 来源：study-l3-v2 项目的开课资料重构（2026-09）。文中「补遗 N」指该项目 docs/DECISIONS-G1.md 里的记录，复制到别的项目后只作来历，不用去找。
> 跨项目用：学生亲手复制到 ~/.claude/templates/。CC 不写那里。

## 零、用词
- CC：Claude Code，在项目里读写文件的 AI。
- 人：做决定的一方（本项目里是学生）。所有改动都由人拍板。
- 正本：某样内容唯一算数的那一份。别处只写「见正本某节」，这叫指针。
- 第二个家：一段内容删之前，它在别处还有没有一份。
- 传播面：改一处之后，别的文件里指着它、要跟着改的地方。
- 宪法：项目根目录的 CLAUDE.md，AI 每次会话自动读的规则。
- 桥梁：上一个会话留给下一个会话的交接说明。
- BACKLOG：跨会话的待办清单文件。
- HARNESS：记「框架原则」的文件，原则 N 的编号只在那份文件里有意义。中枢：将来带人从零建项目的 AI 框架，HARNESS 的读者。
- 网页版：浏览器里的 Claude 对话，读不了项目文件，只能贴。
- 子代理：CC 另起的一个 AI，上下文独立，没看过当前对话，只拿送去的材料干活。
- 反方：专门挑错的独立审查者，不是写的人，也不是和写的人同类的子代理。
- old_string：Edit 工具里「要被替换的原文」那个参数。

## 一、什么时候该停下来修
出现下面任一种，就停下修，不接着用：
- 同一件事写在好几处，改一处漏别处。
- 有句子指向已经作废的东西，读的人只能现编。
- 新会话照旧资料做了一个早已作废的步骤。
理由：每个新会话都读这套说明书，不修，每次都被带歪一点。

## 二、四段流程
- 第一段 · 准备：立工作约定，拍关键裁决，把待办清单更新到最新。做基线提交。
- 第二段 · 修入口：新会话第一个读的文件（读哪些文件、开场做什么）先修对。入口错，后面每步都歪。
- 第三段 · 搬家和删除：内容搬回该在的正本；没用的整节删。
- 第四段 · 收尾：索引定稿，改名后全量扫，跑验证命令，按立项时定的去留处理重构文件（删前扫谁还指着它）。
每段再分组（G0、G1……）。每组开工前做四件：讲这组干什么；列条目让人确认；报要读哪些文件、够不够余量；把每条依据对着现在的文件回核。
每组结束开审查。子代理审只算半独立：和写的人同类模型，盲区可能相同。全部做完，再请一个独立的反方审一遍。

## 三、四份重构文件
立项时就建，立项时就写好去留。会被当出处引用的文件不算临时，要长期留。
- 工作约定：怎么互动、每步节奏、在哪停下。人亲手写。重构结束删。
- 待办清单：每条写状态、依据、判断依据；另有依赖表、执行分组、验证命令。重构结束删；若已被当出处引用，改判长期，只查不追加。
- 终局图：改完长什么样，哪块搬去哪。执行分组落进待办清单后，它只作来源记录。重构结束删。
- 决策记录：每拍一次板记一条补遗。按组拆成多份，别一份记到底。长期留：项目的规则文件和框架原则会拿补遗号当出处；重构结束后只查不追加。
常驻文件尽量不引用要删的文件。非引不可，写明「某文件删除时本句一并删」。
几份内容冲突时，先看这一条落进待办清单没有：
- 已落的，以待办清单为准，另两份只是来源记录。
- 没落的，才按决策记录 > 终局图 > 待办清单。
- 怎么算落了：待办清单对应条目写了「已做」或提交号。

## 四、每一条改动的节奏
1. 我们在哪：第几段、第几组、第几条，还剩几条。
2. 这步干什么：一两句大白话。
3. 为什么改：先打比方，再讲毛病，给出处（文件 + 节 + 原话）。
4. 不改会怎样：举一个具体场景。
5. 新旧对照：原文、改后、影响谁。
6. 停下问同不同意，给「你可以回」。
7. 同意后只用 Edit 定点改。改完用 grep -c 数次数，按预期判：替换是新文 1、旧文 0；搬家第一步复制后旧文仍是 1；纯插入只数新文。
8. 提交，信息带组号和条号，只 add 这一条的文件。
9. 自问：有没有只在对话里的裁决、核查结果、新发现？有就当场落盘。
一处改动一个对照，不合并，不打包问「这一组同意吗」。改的内容必须和同意的对照一字不差；想改措辞，重新出对照。
「你可以回」：每条消息末尾列 2 到 4 句人照抄就能回的话，每句写选了会怎样。另加一项，写此刻能不能安全离开：git status 干净、没有只在对话里的裁决和发现，才算能；不能就写还差什么。
人随时可说的口令：「看不懂」换说法、多举例；「太长了」缩短；「我迷路了」重做开场报告；「重读约定」重读工作约定，从每一条改动的节奏重来；「今天到这」按收尾清单结束会话。
「讲一下整体」讲这次重构为什么做、分几段、到哪了；「这步为什么要做」讲这一步和整体的关系；「我卡住了」安慰不施压，问清卡在哪一步。
审查结果回来：逐条说认不认、为什么；认的走对照改，不认的讲理由。
笼统的「全按你推荐」只放行授权时写进文件的清单条目。清单外的，哪怕改得对，也停下问。清单内遇到 A/B/C 选择、删整节、两份文档打架、改宪法、删文件、验证数不对，也仍然停下问。

## 五、几条硬做法
- 不用脚本改文件，不整份重写。插入时 old_string 带上插入点后面的原文，重跑会失败，不会插第二份。
- 搬家拆两步：先复制，核新家只出现一次，人确认后再删旧家。
- 删前核第二个家；改前扫传播面，逐类写「要改」或「不影响」。
- 写编号前先在正本里查到它。
- 改名用 git mv；合并和改名放同一批，指针只改一次。
- 验证要数次数，不只判存不存在。

什么时候送审（停下出审查包）：出裁决而 A/B/C 没有明显赢家；删整节前核第二个家；两份资料打架要选一边；人连续两次纠正同一类错；人说「不对，但说不清」；自己信心不足。
照已拍裁决搬文本、改指针这类机械活不送审。例外：判进不进框架原则时，判「新开」「并入」的要送审，判「否」的不送；风险是误判「否」没人复核。
同一组的复核点合成一个审查包。

会话管理：
- 上下文用到七八成主动说，结束本次会话，下次新开。
- 自动压缩后，第一件事重读工作约定。
- 开场先查 git status 与 git log，先报半截的活。提交对不上条目时标「待确认」，不猜。

开工安全底座：
- 首次会话实测权限：让 CC 在受保护的正本文件和笔记目录里各改一个字，都必须弹窗，人答 No。不对不开工。
- 工作约定只管互动方式，不覆盖宪法、权限设置和安全规则。
- 每组开工前做基线提交。

## 六、模板
开场报告（每次会话第一件事，自己查 git，不问人）：
```
我们在哪：第几段、第几组；上次做完（提交号）；半截的（没有写「无」）；这次要做
还剩多少：这一段还剩哪几条；后面还有几段
```
补遗（决策记录的一条）：
```
--- 补遗 N · 一句话标题 ---
一，原话：「……」。
二，结论与理由；否决项的理由。
三，执行归属与顺序。
进 HARNESS：新开（原则 N）/ 并入（原则 N）/ 否（换名不成立 | 无出处 | 已覆盖，原则 N | 不是框架层），选其一
```
审查包（每个审查点带三样：改了什么、依据原文、出处）：
```
你是独立审查者，只审不改，挑错为主。
背景 / 要审的 / 依据（出处 + 原文）/ 结论 / 自己不确定的地方
请回答：成不成立？哪里错了？漏了什么？
```
收尾清单（每项写「有（是什么）」或「无」）：没落盘的裁决；没落盘的核查结果；半截的活；新发现的问题；git status 干净吗。

## 七、本场教训
1. 文件立项时就分清临时还是长期。会被当出处引用的文件不是临时文件。决策记录被常驻文件当出处引了几十处，收尾时删不掉，只好专门再定（补遗 130、142）。
   进 HARNESS：并入（原则 11）。
2. 决策记录按组拆。一份记到两千多行（补遗 130 第五点）。
   进 HARNESS：否（不是框架层）。按组拆是本课程文件怎么切的做法，不是中枢的原则（DECISIONS-R1 R1-93 第四点）。
3. 审查者起步就建。前半程每组把审查包整段贴去网页版审，中途才改成子代理，各组审查欠账留到了最后（补遗 56）。子代理和写的人同类模型，只算半独立，最后另请反方。
   前一半（半独立）是审查者一侧的边界，后一半（起步就建、最后请反方）是对策。补遗 56 当时判「否」，判的是那次换审查方式；本条判的是审查者何时建、要多独立。
   进 HARNESS：并入（原则 13）
   进 HARNESS：新开（原则 16）
4. 待记事项拍板时就定落点。「待记 BACKLOG」攒到二十多条，专开一轮清（补遗 127）。
   进 HARNESS：否（已覆盖，原则 5）。只盖住会丢那半：「待记」攒着没落，是原则 5「待办从写下到执行之间会丢」那一关；「拍板时就定落点」这个时机属规则 64，进不进随第三节问题 1 复核（DECISIONS-R1 R1-94 第二点、R1-115 F92）。
5. 验证命令也会过期。命令写死了文件路径，改名后得换（所指对象变了）；写在裁决之前的命令，裁决后命中反成预期（依据变了）（补遗 132、138）。
   进 HARNESS：否（已覆盖，原则 5、11）。
6. 桥梁另列步骤就会过期。入口文件合并两节后，桥梁里抄的步骤指向了已不存在的节（补遗 138）。
   进 HARNESS：否（已覆盖，原则 1）。
