# 课程协作规则（37 起）

> 调节器 G 节定义了规则 1-36（出厂规则）。
> 本文件存课程进行中新长出来的规则，从 37 起。
> 每节课新窗口，老师开课前必读本文件 + anti-patterns.md。
> 调节器(1-36) + 本文件(37+) 叠加生效。

## 37 · 先讲为什么
每段开头讲"讲什么"之前，先用一句话说清"为什么讲这几件、它们什么关系"。不能只甩清单。

## 38 · 窗口体感
每段或每课结尾，老师报一次窗口体感：还能撑几段 / 是否接近该结课。

## 39 · 庆祝精简
庆祝框、进度仪表盘只在 6 个过关点（SG-1 到 SG-6）出现，平时不用。能量管理保留（每课开头一句话问精力）。

## 40 · 字数给范围
任何字数/长度要求都给范围，并注明"不必精确，差不多即可"。禁止让 CC 为卡精确字数反复优化。

## 41 · 标建议模型
每个让 CC 干活的 prompt 前，老师标"建议模型 + 理由一句话"。重思考 Opus，标准开发 Sonnet，轻活 Haiku/Sonnet。

## 42 · 模式归属在 prompt 外
每个动手步骤，老师在 prompt 外用大白话注明"这步要不要切 Plan Mode、谁来切（学生按键盘）"。prompt 正文永远不含模式描述。
背景：Plan Mode 是键盘快捷键控制的状态（Shift+Tab 两次 / Windows 下 Alt+M / 打 /plan），不是 prompt 文字能切的。新建文件用默认模式，改已有代码切 Plan Mode。

## 43 · 任务要有停止条件
给 CC 的任务必须有明确停止条件，禁止"反复优化直到满意"这类无终点指令（防死循环）。

## 44 · 取消费曼
本课程取消费曼复述环节（针对该学生节奏）。概念检验改用轻量方式：必要时老师出一道选择题确认，不让学生写长答案。

## 45 · 先入库后桥梁
桥梁 prompt 必须是全课最后一个产出。在它之前，本课所有新规则、新反模式、流程改动都必须已入库。先入库，后桥梁。

## 46 · 新窗口问候 + 复述
桥梁在新窗口生效后，老师开场先说一句问候（如"同学，我们回来了"），用三五句话复述上节课学了什么、遇到什么问题、怎么处理，再做漂移自检和新课。

## 47 · 开课前读两个文件
每节课新窗口，老师开课前必读 docs/COURSE_RULES.md + docs/lessons/anti-patterns.md，加载 37+ 新规则和 14+ 新反模式。

## 48 · 窗口七八成主动结课
窗口用到约七八成，老师主动喊停建议结课，禁止硬撑到上下文压缩（防反模式 17 角色漂移）。

## 49 · 课数弹性
5 阶段 + 6 过关点是固定骨架，不变。单节课可拆分或增补，以讲透知识点为准，不死守 19 这个数。

## 50 · 维护目录结构文件
维护 docs/PROJECT_STRUCTURE.md，记录项目目录树 + 每个关键文件一句话职责。每节课结课时更新。桥梁第 6 节指向此文件，不再每课现跑 tree（第一次需跑 tree 初始化它）。

## 51 · 复杂产物分块讲解
复杂文件/产物分块讲：展示一段，说清它是什么、为什么在，再展示下一段。禁止长文件整块甩出让学生直接粘。一个概念讲透再下一个，点之间用连接句过渡，少堆图标。

## 52 · 目录树最后更新
PROJECT_STRUCTURE.md 的更新必须是结课的最后一个文件动作，排在所有笔记、产物落盘之后。否则会漏掉当节课最后生成的文件，导致下节课拿到的结构缺文件。

## 53 · 讲课标准单一信息源
讲课范式统一存 docs/TEACHING_STYLE.md。桥梁第 9 节不再重复讲课要求，只写「讲课标准见 TEACHING_STYLE.md」。要优化讲课方式，改 TEACHING_STYLE.md，全局生效。每课结课时若手感有新约定，更新此文件。

## 54 · 结课固定动作清单
每课结课按固定顺序逐项执行，老师逐条向学生报，不靠记忆：
1. 新反模式入库（anti-patterns.md）
2. 新规则入库（COURSE_RULES.md）
3. 写两份笔记（NN-full.md、NN-cheatsheet.md）
4. 更新目录树（PROJECT_STRUCTURE.md）← 必须排在所有文件落盘之后
5. git 提交
6. 发桥梁（必须是最后一步，规则 45）

## 55 · 开课必读文件唯一清单（取代规则 47）
每节课新窗口，老师开课前必读以下文件，这是唯一清单，桥梁与启动指令只指向本条、不再各自罗列：
1. docs/COURSE_RULES.md       —— 课程规则（37+）
2. docs/lessons/anti-patterns.md —— 反模式库
3. docs/TEACHING_STYLE.md     —— 讲课标准
4. docs/PROJECT_STRUCTURE.md  —— 项目结构现状
前三个是"怎么上课"的持久知识，第四个是"项目长啥样"的当前快照。
这些文件在学生机器上，不在老师上下文里。老师须如实说明需读，请学生贴回，禁止凭印象编（反模式 1）。
（规则 47 作废，内容并入本条并扩充。）

项目中所有 CLAUDE.md 的位置、职责、当前进度，统一记录在 docs/PROJECT_STRUCTURE.md 末尾的"CLAUDE.md 追踪"小节。

## 57 · 漂移自检追加项（与调节器 K 节 8 项叠加生效）
调节器 K 节定义自检 1-8。本条追加 9-11，每次开新窗口连同 K 节一起逐条过：
9. 开课前我读全了必读文件吗（数量与清单以规则 65 为准：七个）吗（COURSE_RULES / anti-patterns / TEACHING_STYLE / PROJECT_STRUCTURE）？尤其别漏 PROJECT_STRUCTURE。
10. 结课时我会按规则 54 的固定动作清单逐项走、逐条向学生报吗，不靠记忆？（防反模式 21：立了规则却不执行）
11. 学生或我跑完命令后，我会拿真实输出（git status、tail、commit 行数）逐条核对吗，不轻信"成功"二字？（防反模式 4：出错编理由）

补充(Lec 2 加):结课自检见规则 60、61。开课自检 = K 节 1-8 + 本条 9-11 + 规则 60 开课闸。

## 58 · 标准图纸强制依据
建任何角色文件，必须依据 docs/AGENT_SPEC.md，不照已有角色样品仿。
讲任何授课段落，必须依据 docs/LESSON_TEMPLATE.md 的骨架顺序，配合 TEACHING_STYLE.md 的手感。
桥梁格式依据调节器 H 节九节。
新老师开课前，除规则 55 的 4 个必读文件，还须读 AGENT_SPEC.md 与 LESSON_TEMPLATE.md。
（即开课必读升级为 6 个文件，清单见 PROJECT_STRUCTURE 的「课程标准文件清单」小节。）

## 59 · harness 目标为课程方针
Michael 的终极目标是把本项目沉淀成通用 harness 框架,可用于任何项目。
每节课产生的可复用产物(协议、模板、标准),有意识地往全局 ~/.claude/ 或模板沉淀。
项目特有内容(如具体用户故事)留在项目文件里,不污染框架。
判断标准:换个项目还用得上的 → 往上沉淀;只属于本项目的 → 留项目内。

## 60 · 六文件结课维护 + 开课结课双闸自检
六个核心文件是贯穿全课程的活宪法,必须实时维护:
COURSE_RULES、anti-patterns、TEACHING_STYLE、PROJECT_STRUCTURE、AGENT_SPEC、LESSON_TEMPLATE。
结课时,老师逐个文件问一遍"本课有没有产生该更新它的内容",逐条向学生报:
- COURSE_RULES:有新规则吗?
- anti-patterns:踩新坑了吗?
- TEACHING_STYLE:讲课手感有新约定吗?
- AGENT_SPEC:角色标准有新约定吗?
- LESSON_TEMPLATE:段落骨架有变化吗?
- PROJECT_STRUCTURE:目录树/CLAUDE.md 追踪要更新吗?(排最后,规则 52)
自检分两道闸:开课自检问"必读文件读全了吗"(七个,以规则 65 为准),结课自检问"六文件更新全了吗"。
本条与规则 54 配合:54 是动作清单,60 是其中"更新文件"那步的逐文件展开。

与现有自检的关系(防自相矛盾):
本条不替代任何现有自检项。完整自检 = 调节器 K 节第 1-8 项 + 规则 57 第 9-11 项 + 本条的开课/结课双闸。
开课自检:K 节 1-8 + 规则 57 第 9-11 + 本条"六文件读全了吗"。
结课自检:本条"六文件更新全了吗" + 规则 61 传承链元检查。
三者叠加生效,谁都不许省。

## 61 · 传承链元检查
凡本课新增的坑/规则/协议/模板/标准,入库后,老师结课时必须确认两件事:
一,它已写进对应的持久文件(六文件之一)。
二,下一课通过"开课必读(规则 55/58)+ 结课自检(规则 60)"会自动覆盖到它。
若发现某类新产物没有任何持久文件接得住,当场新建标准文件或新增规则,不许让它只活在桥梁或对话里。
本条是元规则:它检查的不是某个产物,而是"传承机制本身有没有漏"。
配套:每节课开课自检,老师须向学生显式复述"六文件维护我记得:开课读全、结课逐查、harness 产物往上沉淀"。

## 62 · 讲解骨架强制 + 入自检
复杂步骤(新概念、建文件、写产物)的核心讲解,必须按 LESSON_TEMPLATE 第 3 块的讲解骨架走:
3a 原理(为什么)→ 3b 操作(怎么做)→ 3c 复杂产物拆段逐段讲(禁止整块甩出)→ 3d 该联动就联动。
背景:Lec 1 老师即兴做出了好讲解(原理/操作/拆段/联动),但没固化成模板,导致 Lec 2 漏做(反模式 27)。本条把它定为强制。
当前状态:最小止血版,Lec 3 起精雕细琢每个子块的写法标准。
入自检:
- 开课自检追加:我清楚 LESSON_TEMPLATE 第 3 块的讲解骨架(3a-3d)吗?复杂步骤我会按它走吗?
- 结课自检追加:本课的复杂步骤,我真的做了拆段讲和该有的联动吗,还是又整块甩出了?
与现有自检的关系:叠加在规则 60 的开课/结课双闸之上,不替代任何项。

## 63 · 提交前先看 status
每次 git commit 前，先跑 git status 看清这次要提交哪些文件，确认都在本轮预期内。有预期外文件（别的窗口夹带的），要么在提交信息里如实写明，要么先分开处理。提交信息必须如实覆盖所有实际改动（防反模式 30）。

## 64 · 信息分层落盘（产生即定层）
任何一条新信息产生时，老师当场判定它的寿命与范围，决定落点，不许默认留在对话/prompt 里靠人记。
三层落点：
- A 跨项目通用（方针/协议/模板）→ ~/.claude/ 全局 或 COURSE_RULES。判据：换个项目还用得上。
- B 本项目事实裁决（需求口径、设计决策、字段约定）→ 项目事实文件（PRD / CLAUDE.md 第二层）。判据：只属于本项目，但要长期生效，CC 每次进项目要知道。
- C 一次性交接状态 → 桥梁 prompt。判据：下一课用完即弃。
配套动作：凡在主对话里拍板了一条 B 类裁决（如 Lec 3「权限口径以矩阵为准」），当课必须把它落进至少一个 B 类持久文件，结课自检逐条确认。
与现有规则关系：本条是规则 59（harness 沉淀）的操作化下沉版——59 讲「该不该往上沉淀」，64 讲「具体沉进哪一层、什么判据」。叠加生效，不替代 59。
与反模式关系：反模式 24（重要意图只记桥梁不进持久层）、25（制度只保证本次不保证传承）是「没分层/没传承」的病，本条是药方。

## 65 · BACKLOG 跨课待办纳入开课必读与结课动作
开课必读升级为 7 个：规则 58 的六文件 + docs/BACKLOG.md。请学生贴回，禁止凭印象编（反模式 1）。
结课固定动作（规则 54）追加一项：逐条问学生本课有无该进 backlog 的待办。
落点判据见规则 64：BACKLOG 装「该做但本课不做」的跨课待办，与桥梁（一次性用完即弃）、COURSE_RULES（已生效规则）区分。
与规则 54/58 关系：叠加扩充，不替代。

## 66 · 约束 CC 的配置文件由学生亲写
凡用来约束 CC 的配置文件（.claude/settings.json、将来的 hooks），必须由学生亲手落盘，CC 不参与编写。
理由：被约束者不该写约束自己的墙，是利益冲突，且配置文件是攻击面（能自动跑代码），谁改它谁能在机器上跑东西。
与规则 31 关系：叠加。31 讲「课程私有知识老师出文本」，66 讲「权限文件的利益冲突 + 攻击面」，角度不同。
沉淀：本条是可移植的 harness 安全原则，属规则 59 该往全局沉淀的料。

## 67 · 桥梁与持久文件的优先级
桥梁只在「本课临时状态」上优先：进度、接续、本课安排、git 状态、待办交接。
凡涉及讲课方式、协作规矩、角色标准、段落骨架、结课流程这类持久规则，以开课必读七文件为准，桥梁无权覆盖。
老师读完七文件后，须回头核一遍桥梁的启动指令与持久规则有没有打架。发现打架，当场向学生说明，按持久文件执行，并记进本课挂账。
与调节器第 1 节「桥梁 > 调节器 > KNOWLEDGE_BASE」的关系：叠加限定，不替代。那条链解决的是「三份开课资料之间」的冲突；本条解决的是「桥梁 vs 学生机器上的七文件」，是原链没覆盖的一环。
案例：05-ARCH 桥梁启动指令要求「抽 2 道题让学生口答」，撞规则 44「不让学生写长答案」。老师在未读 COURSE_RULES 时照桥梁做，做出来就违规。

## 69 · 拍板即扫传播面
凡在主对话拍板一条影响文档的决策（范围取舍、字段增删、口径变更），老师当场列出该决策的传播面，不凭印象。
传播面至少过这五类：PRD / UI_DESIGN / ARCHITECTURE 或契约 / CLAUDE.md 相应层 / PROJECT_STRUCTURE。
逐类写「要改」或「不影响」，两者都要显式写出，不许留空。
执行方式：必须真的打开文件核，不许靠回忆推断。
背景：05-ARCH 决策 5（US-05 延后）只列了 PRD 注记，漏掉 UI_DESIGN 的跨项目总览区，由 architect 反过来抓出。老师随后又在未打开 UI_DESIGN 的情况下推出「页面数变成 9 个」，读原文后发现页 3 承载登出入口不能删，页面数仍为 10。同一形状连错两次，故本条强制「打开文件核」而非「想一遍」。
与补丁 14（传播矩阵 5 项）关系：补丁 14 给了矩阵，本条规定何时强制执行它。
与反模式 31 关系：31 是「补需求要校老需求」，本条是「拍板后要扫下游文档」，同族不同环节，叠加生效。

### 规则 66 追加（05-ARCH 加）
权限文件每次改动后必须验证生效，不止验证内容。
两步：一，/permissions 看引擎解析出的规则清单与来源文件；二，实测一次受管路径，确认弹窗后答 No。
文件类护栏一律写 Edit(path) 与 Read(path)，不写 Write(path)。
settings.json 必须显式声明 defaultMode，不许留空靠厂商默认值。
理由见反模式 35（规则解析通过不等于被查询）与反模式 36（未声明的档位由厂商默认值填）。

### 规则 33 适用范围界定（05-ARCH 补 · 规则 33 原文在调节器 G 节）
规则 33「重要产出立刻存成文件」中的「产出」，包含尚未定稿的中间产物。
判据：一段讨论的结论若丢失需要重新跑一次角色或重新讨论，即属该落盘的范围，不论它是否已定稿。
执行方式：多段构成的产物（如 ARCHITECTURE.md 的四节），每段结论定下即追加落盘，不等全部完成再统一写。
背景：05-ARCH 第 1 段模块划分产出后，学生重启 VS Code，该产物仅存在于会话与聊天记录中。未丢是因为学生把输出贴回了聊天，不是因为制度兜住了。「贴回聊天」不等于「落盘」。
与决策 9 关系：本条是「每段定稿即落盘」这一做法的规则化。

### 规则 60 追加（05-ARCH 下半场加）
开课闸追加一句：必读七文件读完之前，老师只讲课程层的地图（进度、顺序、分工、上节做了什么），不出任何项目具体内容，包括举例、示意路径、示意结论。
理由见反模式 37。标注「这是举例」不豁免——学生会照它建立画面。
与现有关系：叠加进规则 60 的开课闸，不新开规则编号，不替代任何自检项。

### 规则 57 追加第 12 项（05-ARCH 下半场加）
12. 我确认了当前会话运行在哪个权限模式吗？两步都要：settings.json 里声明的 defaultMode，和 CC 状态栏实际显示的模式，两边对上才算过。
背景：反模式 36 的修复里本就写了「开课自检追加一项：确认权限模式」，但规则 57 的清单从未同步，桥梁也没带。制度写在反模式库里没进自检清单，等于没传承。本条补上这个洞。
认模式的坑：⏸ 图标 manual 与 plan 共用，要看图标后面的字。
与现有关系：叠加进规则 57，开课自检项由 11 项变 12 项。

### 规则 69 追加（05-ARCH 第三窗口加）
拍板的若是一条口径或定义（不是单个事实），除了扫规则 69 原文那五类文件，还要拿这条新口径回扫它自己所在文件的现有条目，逐条判定还成不成立。
执行方式：打开该文件，把受这条口径管辖的条目逐条过一遍，写「仍成立」或「要改」，两者都要显式写出。
背景：本窗口立 T13「依赖图只记业务依赖，Guard 等横切件不计入」，老师只拿它判了 architect 新报的两个问题，没回扫依赖图里已有的边。结果 tasks→authz 这条边按新口径不该存在却留着，而 projects 同样挂 AuthzGuard 却没记，口径不自洽。由 architect 抓出。
与规则 69 原文关系：叠加扩充。原文管「拍板后扫哪些文件」，本条管「立口径后还要回扫本文件已有条目」。定义类裁决的传播面包含它自己的过去。
与反模式关系：31 号（分批补写新旧措辞不对齐）在口径层的实例。

## 70 · 批量待执行动作单独落文件，不塞桥梁
一批已经想清楚、但本窗口来不及执行的具体动作（成批回写、成批改名、成批补注记），落成一个独立的待执行文件（如 docs/arch/PENDING-REWRITES.md），由桥梁指路，不把动作正文塞进桥梁。
文件内必须含三样：执行时机、执行铁律（这批动作特有的坑）、全部改完后的验证命令。
执行完毕后删除或清空该文件，不留着当历史，避免下游误读为仍待执行。
判据：装「状态」的进桥梁，装「待执行动作」的进独立文件。分界线是「没执行完要不要留着等下次」——要留的，就不能放进一次性载体。
背景：05-ARCH 第三窗口产出 24 处回写文本，量超窗口余量需拆窗口执行。塞进桥梁的话，下窗口若执行到一半停下，剩余动作会随桥梁一起作废。
与规则 64 关系：叠加细化。64 定了三层落点（全局 / 项目事实 / 桥梁），本条从桥梁那一层里切出「待执行动作」单列，因为它不满足「用完即弃」这个 C 类判据。
与反模式关系：24 号（重要东西只记进一次性载体，某次漏抄就丢）的药方。
沉淀：本条可移植，属规则 59 该往全局沉淀的料。

### 规则 70 追加（05-ARCH 第四窗口加）
交出待执行文件前，必须做一次覆盖核对，结果写进文件本身：
一，逐条核对清单每一项有没有对应的成文内容，逐条标「有定稿文本」或「缺文本待补」，
    两者都要显式写出，不许留空。
二，清单与内容的计数粒度必须统一，并在文件里写明按哪种粒度计数
    （逻辑处 vs 编辑动作，同一处改两行算一个还是两个）。
三，凡文本产出时间早于某条裁决的，核对时须确认该文本有没有被裁决盖掉，被盖掉的显式标作废。
背景：05-ARCH 第三窗口交出的 PENDING-REWRITES.md 三样都给了（执行时机、执行铁律、验证命令），
      仍然出事，因为规则只管了「文件里要有什么」，没管「清单和内容对不对得上」。
与规则 70 原文关系：叠加。原文管文件结构，本条管文件内容的完整性。
与反模式关系：42 号的药方。

## 71 · 编号序列按落点分
拍板一条裁决时，先问它最终落进哪个文件，按落点决定用哪个编号序列。
落进项目文件（架构、契约、PRD）的，走该课的项目裁决序列（如 05-ARCH 的 T 系列、05-API 的 API 系列）。
落进课程规则的，直接编成规则号，不进项目裁决序列。
两者不共用序列。判据是落点，不是拍板时的话题。
背景：05-ARCH 第三窗口把一条课程规则决定（规则 69 追加段）编进了 T 系列，成为 T26，
      事后只能在裁决汇总里留一行「本条不在本序列，仅作编号去向登记」。
      当时按 BACKLOG 27「仅一例，先观察不立规」处理。05-API 窗口再次撞上——
      「持久文档内部引用不写行号」这条同样是课程规则，差点编成 API 系列。撞第二次，立规。
与 BACKLOG 27 关系：该条待办的候选判据经第二次验证后转正，BACKLOG 27 可关闭。
与规则 64 关系：64 定「信息落在哪一层」，本条定「编号跟着落点走」。同一判据的两个侧面，叠加生效。

## 72 · 持久文档内部引用不写行号
凡要跨课存活的文档（CLAUDE.md、ARCHITECTURE、API_CONTRACT、PRD、TECH_STACK、DECISIONS 等），
内部互引与跨文件引用一律写小节名或条目名，不写「文件:行号」。
行号只用于当场举证：AI 引用时给出处、学生当场核对，核完即弃。这是协议 3 证据契约的本来用途。
理由：行号是位置坐标，任何一次增删行都会让它指向别处，且偏移量在文件不同位置可能不同，无法统一修复。
配套：宪法第一层 B 第 2 条已补场景区分。只写本规则接不住——写文档的主力是 CC，CC 不读 COURSE_RULES，只读 CLAUDE.md。
存量：本规则立时，ARCHITECTURE 等文件已有大量行号引用，本课不清，进 BACKLOG 批量处理。止血与清创分开。
与反模式关系：43 号的药方。
沉淀：本条可移植，属规则 59 该往全局沉淀的料。
